# 先纠正一个前提：CF Worker 不该出现在直播链路的「数据面」

你卡住的地方，本质是一个架构认知问题：**直播系统里，「接入」和「分发」是两类完全不同性质的负载，必须物理分离。**

Worker 是 request/response 模型 + 短生命周期：

- 不能 `listen` 任意 TCP 端口 → **RTMP 推不进来**
- 没有 UDP socket → **SRT / WebRTC 接不住**
- 有 CPU 时间与请求生命周期限制 → 扛不住几小时的长连接
- 无本地持久盘、无状态 → 不能做转发/录制/切片

所以 Worker 的正确位置是**控制面**（开播鉴权、发 stream key、查状态、写 Durable Object）和**分发面的门卫**（签名 URL、playlist 改写、token 校验、geo 调度），而不是媒体面。

> 如果你确实想让 Cloudflare 边缘接 RTMP/SRT，只有两条路：**Cloudflare Stream**（托管，原生 RTMPS/SRT ingest）或 **Spectrum**（L4 Anycast TCP/UDP 转发，企业版，只是把连接转回你源站，不解决转码分发）。

# 一、大厂的通用心智模型：五段式

YouTube / Twitch 的高可用低延迟，不是靠某个黑科技，而是把链路切成五段，**每段单独做冗余、单独伸缩**：

```text
[ 主播 OBS ]
    │  RTMP(S) / SRT / WHIP
    ▼
① Ingest 接入层      ← 有状态、长连接、就近接入、主备双推
    │  (内网高带宽专线 / 私有骨干)
    ▼
② Transcode 转码层   ← GPU 集群、ABR 自适应码率阶梯、分片并行
    │
    ▼
③ Packager 打包层    ← CMAF 切片 + HLS/DASH/LL-HLS/LL-DASH 清单
    │  (写入对象存储 = Origin)
    ▼
④ Origin 源站        ← R2 / S3 / 自研，只承受回源，不承受观众
    │
    ▼
⑤ CDN Edge 分发层    ← 无状态、可缓存、Anycast/GeoDNS、多 CDN
    │  HTTP(S) / HTTP3
    ▼
[ 观众播放器 ]
```

**核心洞见**：第 ③ 步之后，直播流被「**HTTP 化**」了——它变成了一堆可以缓存的静态分片文件。这一步是 YouTube/Twitch 能扛住百万并发而不需要百万条连接的原因。**把直播伪装成点播，是规模化的唯一答案。**

# 二、Ingest：全球接入怎么做

## 协议怎么选

| 协议 | 传输 | 延迟 | 抗丢包 | 场景 |
|---|---|---|---|---|
| RTMP / RTMPS | TCP | 2–8s | 差（TCP 队头阻塞） | OBS 生态兼容性最好，仍然主流 |
| **SRT** | UDP | 0.5–2s | **很强**（ARQ + FEC） | 跨境/弱网推流首选 |
| RIST | UDP | 0.5–2s | 强 | 广电级 |
| **WHIP** (WebRTC) | UDP | <0.5s | 强 | 浏览器直接开播，无需装 OBS |

你源站在海外、主播在国内，**跨境链路丢包是最大杀手**。这种拓扑下 SRT 相比 RTMP 的体验差距是数量级的——这是你最该先做的一步优化。

## 就近接入

大厂的做法：

1. **GeoDNS / Anycast** 把主播解析到最近/最优的接入 PoP（Twitch 的 ingest 列表、YouTube 的全球接入点）
2. **客户端测速选点**：OBS 里 Twitch 的「Auto」就是客户端 RTT 探测选优，比纯 DNS 更可靠
3. **主备双推**：`ingest-a.example.com` + `ingest-b.example.com`，主链路断了自动切。Cloudflare Stream 的做法是：只要推流软件自动重连，Stream 就继续接收——所以**你的客户端必须实现指数退避自动重连**，这是可用性最低成本的一招

# 三、Transcode + Packager

- **ABR 阶梯**：1080p60 / 720p / 480p / 360p，让弱网用户降档而不是卡死
- **CMAF + chunked encoding**：这是低延迟的物理基础。传统 HLS 要等一个完整 6s 分片编码完才开始发；chunked CMAF 是**边编边发**，把分片内部的 chunk 逐个推出去，延迟直接砍掉一个分片时长
- **Per-title encoding**：根据画面复杂度（VMAF）动态决定码率，静态画面（PPT、聊天）能省 50%+ 带宽
- **降本**：转码是整个链路最贵的一环。低峰期/小主播直接 **passthrough**（不转码），只给热门流上 ABR 阶梯——这是 Twitch 的经典策略

---

# 四、分发层：延迟谱系与成本模型（这是决策核心）

| 方案 | 端到端延迟 | 百万并发是否可行 | 成本模型 |
|---|---|---|---|
| HLS（经典 6s 分片） | 15–30s | ✅ | 边缘缓存，**≈ O(1)** |
| **LL-HLS / LL-DASH** | **2–5s** | ✅ | 边缘缓存，**≈ O(1)** |
| WebRTC / WHEP (SFU) | 0.2–1s | ❌ 很贵 | **逐连接转发，O(N)** |
| MOQ (Media over QUIC) | <1s | 理论可行（IETF 在推） | 尚未成熟 |

成本差异是架构的分水岭：

$$\text{CDN 回源流量} \approx B \times (1-\rho),\quad \rho \to 1 \ (\text{命中率})$$

$$\text{SFU 出口流量} \approx B \times N_{\text{viewers}}$$

$B$ 是码率，$\rho$ 是缓存命中率。CDN 路线下，10 万观众和 100 个观众对源站的压力**几乎一样**（都是回源一次）；SFU 路线下，观众数直接乘以带宽成本。

**所以大平台的策略必然是分层的：**

- **一对多大规模广播** → LL-HLS/LL-DASH + CDN。Twitch 的「低延迟模式」（2–3s）和 YouTube 的 ultra-low-latency 都是这条路，**不是纯 WebRTC**
- **小规模强互动**（连麦、连麦 PK、拍卖、课堂） → WebRTC SFU

# 五、高可用：每一段都单独冗余

| 层 | 冗余手段 |
|---|---|
| Ingest | 多 PoP、主备 URL、客户端自动重连、多运营商 BGP |
| Transcode | K8s 集群 + 分区调度，worker 挂了重排任务；**优雅降级**：转码资源不足就 passthrough |
| Packager | 无状态，可水平扩；写多个 Origin 副本 |
| Origin | 对象存储天然多副本；Origin Shield 收敛回源 |
| CDN | 多 CDN 智能调度、Anycast、边缘故障自动摘除 |

**QoE 监控三指标**（比服务器指标重要得多）：首帧时间 TTFF、卡顿率 rebuffer ratio、端到端延迟。

# 六、落到你的平台：三条路线

| 路线 | 构成 | 延迟 | 运维成本 | 适合 |
|---|---|---|---|---|
| **A. 全托管 Stream** | Cloudflare Stream Live：RTMPS/SRT 推入 → 自动转码 ABR → HLS/DASH 全球分发；需要亚秒级用 WebRTC（WHIP 推 / WHEP 看） | HLS 数秒 / WebRTC <500ms | 极低 | 快速上线、不想运维 |
| **B. 自建 RTMP/SRT + LL-HLS** | 海外 VPS 跑 SRS / OvenMediaEngine / MediaMTX → FFmpeg 转码 → LL-HLS 分片写 **R2** → CF CDN 分发；Worker 做鉴权/清单改写 | 2–5s | 中 | 想控成本和数据 |
| **C. WebRTC SFU** | LiveKit / MediaMTX / Cloudflare Realtime SFU | <1s | 中高 | 互动场景 |

Cloudflare 侧的现状（我查了官方文档）：

- **Stream Live**：支持 **RTMPS 或 SRT** 推入，自动 ABR 转码，HLS/DASH 播放，自动录制；计费 \$5/1000 分钟存储 + \$1/1000 分钟分发
- **Stream WebRTC**：支持 **WHIP/WHEP**，延迟 <500ms，\$1/1000 分钟分发，正在 GA。**但有硬限制**：WHIP 输入的流**不能用 HLS/DASH 播放、不能录制、不支持 simulcast**——所以「低延迟 + 大规模回放」不能只靠它一个产品
- **Cloudflare Realtime**：RealtimeKit（会议）、Realtime SFU（自定义 WebRTC）、**TURN（Anycast，无需自建区域 TURN）**

## 推荐给你的混合架构

```text
主播 OBS ──SRT/RTMPS──▶ 海外 VPS (SRS/MediaMTX, 主备两台)
                            │
                            ├─▶ ① LL-HLS 切片 → R2 (Origin) → CF CDN → 海量观众
                            │      (3s 延迟, 成本 O(1))
                            │
                            └─▶ ② WHIP 中继 → CF Stream WebRTC / Realtime SFU
                                   (亚秒延迟, 给付费/互动用户)

CF Worker 负责：
  · 开播鉴权 + 签 stream key
  · 播放签名 URL（防盗链）
  · playlist 改写、geo 调度、Durable Object 存频道状态
```

**降级策略**：观众数超过阈值 → 自动把 WebRTC 用户导流到 LL-HLS，避免 SFU 带宽爆炸。

<details>
<summary><b>实操坑位清单</b>（点开，这几个会直接让你踩坑）</summary>

1. **LL-HLS 的 blocking playlist reload 和 CDN 缓存的矛盾**。LL-HLS 要求播放器对 `.m3u8` 做长轮询（服务器 hold 住请求直到有新分片）。而 CDN 默认只会把文件缓存下来直接返回，长轮询会失效。解法：用 **Worker 自己实现 playlist 的长轮询**，并在清单上设置 `Cache-Control: no-cache` + 短 TTL，而 `.ts`/`.m4s`/`.mp4` 分片设长 TTL（`immutable`）。
2. **别缓存错东西**。清单文件（`.m3u8`/`.mpd`）必须短缓存或绕过缓存；媒体分片必须长缓存。搞反了就是「观众看到 3 分钟前的内容」或者「回源被打爆」。
3. **WebRTC 那一堆限制**要先想清楚再选：Stream WebRTC 目前 WHIP 的流不能同时出 HLS、不能录制、不能 simulcast。如果你的产品既要低延迟又要回放，就得自己搭 WHIP→RTMP relay。
4. **Range 请求**：部分播放器会对分片发 `Range`。确认 CDN 对 `.m4s` 的 Range 缓存行为符合预期，否则缓存命中率会崩。
5. **防盗链**：签名 URL 的 TTL 不能大于分片时长太多，否则链接会被分享。直播场景用短 TTL + 绑定 IP/UA 的组合。
6. **跨境回源**：你的源站在海外，如果回源没走 Origin Shield，国内节点每次穿透国际带宽会又慢又贵。务必开 Origin Shield 收敛回源。
7. **计费陷阱**：Cloudflare Stream 的 WebRTC 是**按分发分钟**计费的，一对多广播下这个数字 = 观众数 × 时长，和 CDN 的「几乎免费」不是一个量级。上量前先算清楚。

</details>

**一句话总结**：YouTube/Twitch 的秘密不是「延迟低」，而是把直播切成了**可缓存的 HTTP 分片**，从而让分发成本与观众数解耦；低延迟只是在这个基础上用 chunked CMAF 和更小的分片去逼近。**亚秒级（WebRTC）和大规模（CDN）在成本模型上是互斥的**，所以正确的做法永远是分层——而不是指望一个协议全搞定。

# 一、架构评审：判断基本正确，但有 6 个会咬人的地方

你把平面切成「控制面 = Worker / 应用面 = WebSocket / 上行面 = RTMP+SRT / 分发面 = CDN」，这个划分是对的。真正的问题都在**平面的边界契约**上。

## 1. WebSocket 不碰媒体 —— 这条必须写进架构原则

HTTP/WS 跑在 TCP 上，有队头阻塞。一旦有人图省事把音视频帧走 WS（"反正都是实时"），弱网下延迟会雪崩式放大：一个丢包卡住整条流。正确分工：

- **WS 传**：SDP/ICE 交换、房间状态、连麦指令、弹幕、礼物、点赞、在线人数、控制事件
- **WS 绝不传**：音视频帧、屏幕共享数据

如果后续要上 WebRTC，媒体走 **DTLS-SRTP/UDP**，WS 只做信令。这条边界划不清，后面一定会重构。

## 2. 控制面与应用面必须有统一凭证

最容易出的 bug 是「状态分裂」：推流成功了，但房间不知道该流已上线；或者暂停了，CDN 还在发。解法是**单一事实来源**：

```text
控制面签发 JWT { room_id, input_id, role, exp, perms } 
  → ingest 用它验推流权限
  → WS 用它验证订阅权限
  → CDN 签名 URL 用它派生（同一 room_id）
```

所有平面共享同一份 session 状态（Durable Object 或 Redis），由控制面驱动状态机：`idle → live → egress → ended`。

## 3. Ingest 是「粘性」的，不能当无状态服务扩缩容

这是直播接入和普通 HTTP 服务最根本的运维差异：

- 主播推流期间**不能迁移服务器**（除非实现 session takeover / 无缝接管）
- 所以扩容必须发生在**连接建立之前** → 需要**预留长尾容量**，而不是按 CPU 弹性伸缩
- 配套要求：主播断线重连后，OBS 重连必须挂回**同一个 room**，而不是新建一个流

**容量公式**：接入机需要的并发槽位 = 峰值同时在线主播数 × 冗余系数（建议 ≥ 1.5）

$$\text{Slots}_{\text{required}} = N_{\text{peak}} \times 1.5$$

## 4. SRT 不等于一定更快 —— 跨境 UDP 的现实

理论上 SRT（UDP + ARQ + FEC）远胜 RTMP（TCP）。但**跨境 UDP 经常被 QoS 限速甚至干扰**，这是国内→海外链路的老问题。所以：

> "支持 SRT" ≠ "SRT 一定更优"。必须**实测**，并且客户端做**协议自动选择**：开局先探测 RTT/丢包，再决定走 RTMPS 还是 SRT。

建议在控制面下发一张 ingest 候选表（协议 + 端点 + 历史质量分），客户端按分数选优 —— 这就是 Twitch "Auto" 的做法。

## 5. 双协议栈的抽象要提前做

RTMP 只能靠 URL 里的 stream key 鉴权，SRT 用 `streamid`。如果不抽象，权限、限流、统计、主备切换逻辑要写两遍。

**抽象出 `Input` 实体**：`input_id` 是唯一身份，协议只是接入方式。这样之后加 WHIP 或 WebTransport 时，下游一行不用改。

## 6. Ingest 必须多机主备，且播前完成调度

单台源站 = 单点。至少 2 台（最好跨可用区/机房），控制面在开播前就决定好主备端点并写进凭证。

# 二、CDN 分发策略：按平面隔离，按资源类型定 TTL

## 核心原则：域名隔离

四种平面的缓存规则、限流策略、WAF 规则**完全不同**。混在一个域名下迟早出事故（尤其是缓存投毒和签名 URL 污染 cache key）。

| 平面 | 域名 | 内容 | 缓存 | 关键约束 |
|---|---|---|---|---|
| 控制面 | `api.` | 鉴权、签发、CRUD、回调 | `no-store` | Worker + DO/KV/D1 |
| 应用面 | `ws.` | 信令、弹幕、礼物 | 非 HTTP，不适用 | DO + Hibernation，按房间分片 |
| 上行面 | `ingest.` | RTMP(S)/SRT/WHIP | 不适用 | 有状态长连接，独立于 CDN |
| 分发面 | `media.` | 清单 + 分片 | 见下表 | 走 CDN 全量缓存 |

## 缓存参数（可直接抄）

```http
# 直播清单 —— 短 TTL，必须能快速更新
Cache-Control: public, max-age=1, s-maxage=1, stale-while-revalidate=2

# VOD 清单 —— 永不变化
Cache-Control: public, max-age=31536000, immutable

# 媒体分片（.m4s / .mp4 / .ts / init.mp4）—— 路径天然唯一，可永久缓存
Cache-Control: public, max-age=31536000, immutable
Accept-Ranges: bytes

# 鉴权 / API
Cache-Control: no-store
```

## ⚠️ 最大的坑：Cache Key 归一化

**如果你的签名 token 参与了 cache key，缓存命中率会直接归零。**

每个观众的 `?token=...&exp=...` 都不同 → CDN 认为每个请求都是新资源 → 全部回源 → 你的 R2 出口等于观众数 × 码率，CDN 形同虚设。

$$\rho \to 0 \quad\Longrightarrow\quad \text{回源流量} \approx B \times N_{\text{viewers}}$$

（$\rho$ 是缓存命中率，$B$ 是码率）

**解法**：在 CF **Cache Rules → Cache Key** 里剔除签名参数（`token`、`exp`、`sig`、`hdnts`），只保留路径 + 真正影响内容的参数（如 `?v=`）。**这一步是整套 CDN 方案里性价比最高的一个配置。**

## 其他要点

- **分层缓存**：Edge → Tiered Cache / Origin Shield → R2。没有 shield，每个边缘 PoP 都会独立回源一次
- **LL-HLS 的 blocking playlist reload 与 CDN 天然冲突**（CDN 不会替你 hold 请求）。用 Worker 在边缘实现长轮询 + ETag 复用
- **一份分片，两个清单**：CMAF 的核心价值 —— 同一份 `.m4s` 同时被 HLS 和 DASH 清单引用，存储和缓存成本减半
- **多 CDN**：规模上来后用 Worker 做决策返回不同 CNAME，按成本/质量实时切换

# 三、HEVC / AV1 改造清单（按环节）

这是个大工程，但**改造点是可枚举的**。

| 环节 | 现状 | 改造点 | 工作量 |
|---|---|---|---|
| **上行** | RTMP / SRT | RTMP 原生不支持 HEVC/AV1，需 **Enhanced RTMP (E-RTMP)**；SRT 是 codec-agnostic，最简单 | 中 |
| **容器** | 可能还在用 MPEG-TS | **必须迁到 CMAF/fMP4** | 🔴 大 |
| **打包** | 单 codec 清单 | 多 codec 变体 + `CODECS` 属性 + DASH codec switching | 中 |
| **播放器** | 直接播 | 能力探测 + 降级链 | 小 |
| **转码** | 全转码 | **Transmux 优先，Transcode 兜底** | 中 |

## 1. 上行：OBS 29.1+ 支持 Enhanced RTMP 带 HEVC/AV1

- **SRT**：最省事。SRT 承载 MPEG-TS，codec 是透明的，SRS/MediaMTX 只要解析出 HEVC/AV1 描述符即可
- **RTMP**：需要 `Enhanced RTMP` 扩展（OBS 29.1+ 提供），老编码器/老服务端不认
- **WHIP**：目前主流是 H.264/VP8/VP9，AV1 要看具体 SFU 实现

> **策略**：不要试图用 HEVC/AV1 替换 H.264，而是**保留 H.264 作为兼容底座，HEVC/AV1 作为附加轨**，播放器按能力选。

## 2. 容器：MPEG-TS → CMAF/fMP4（最大的改造点）

这是绕不过去的。原因：

- **Apple 的 HLS 规范强制要求 HEVC 使用 fMP4**，并要求 codec tag 写成 `hvc1`（不是 `hev1`）
- MPEG-TS 里塞 HEVC 的兼容性极差，各播放器行为不一致
- CMAF 是 AV1/HEVC/H.264 三者统一的容器，一份分片喂所有协议

> 参考：Cloudflare Stream 在 **2026-04-13** 已经把按需 HLS 清单从 `.ts` 切到了 `.mp4`(fMP4) 分片。整个行业都在做这个迁移。

**巧思**：一份 CMAF 分片 → 同时生成 HLS 清单和 DASH 清单 → 播放器自己挑。存储/缓存成本减半，这是 CMAF 的全部意义。

## 3. 打包：多 codec 清单怎么写

```m3u8
#EXTM3U
#EXT-X-VERSION:7

# H.264 兼容档
#EXT-X-STREAM-INF:BANDWIDTH=3000000,RESOLUTION=1280x720,CODECS="avc1.64001f,mp4a.40.2"
720p/h264.m3u8

# HEVC 档（同分辨率更低码率，Safari/iOS 优先选它）
#EXT-X-STREAM-INF:BANDWIDTH=1900000,RESOLUTION=1280x720,CODECS="hvc1.1.6.L120.90,mp4a.40.2"
720p/hevc.m3u8

# AV1 档（Chrome/Android 优先，最省带宽）
#EXT-X-STREAM-INF:BANDWIDTH=1600000,RESOLUTION=1280x720,CODECS="av01.0.08M.08,mp4a.40.2"
720p/av1.m3u8
```

DASH 侧对应：`AdaptationSet@codecs` + `Representation@codecs`，并用 `urn:mpeg:dash:adaptation-set-switching:2016` 标记可切换。

## 4. 播放器：能力探测 + 降级链

```js
const candidates = [
  'video/mp4; codecs="av01.0.08M.08"',   // 最省带宽
  'video/mp4; codecs="hvc1.1.6.L120.90"', // Apple 生态
  'video/mp4; codecs="avc1.64001f"',      // 兜底
];

const supported = candidates.find(c => MediaSource.isTypeSupported(c));
console.log('picked codec:', supported ?? 'fallback to native HLS');
```

**各端现状（上线前务必用真机矩阵实测，变化很快）**：

| 平台 | H.264 | HEVC | AV1 |
|---|---|---|---|
| Safari / iOS | ✅ | ✅ 硬件 | ⚠️ 仅 A17 Pro / M3+ 等新硬件 |
| Chrome / Edge | ✅ | ✅ 硬件解码可用时 | ✅ |
| Firefox | ✅ | ⚠️ 支持落后，需实测 | ✅ |
| Android | ✅ | ✅ | ✅ 新机型 |

## 5. 转码策略：Transmux 优先

**关键省钱点**：如果主播推的就是 HEVC/AV1，**直接 remux 成 CMAF 发出去，零转码成本**。只有当需要给老客户端提供 H.264 时，才付出转码代价。

这是 Twitch 推 "Enhanced Broadcasting" 的底层逻辑 —— **把转码成本从服务器转移到主播的 GPU**。

## 6. ⚠️ HEVC 的专利问题（商业产品必须评估）

| 编码 | 版税 | 说明 |
|---|---|---|
| **H.264** | 有，但已广泛覆盖/历史包 | 基础盘 |
| **HEVC** | 🔴 **有专利池**（Access Advance / MPEG LA 等） | 商业产品要认真评估授权成本与风险 |
| **AV1** | ✅ **免版税** | AOMedia 主导，长期方向 |

再叠加：AV1 编码虽贵，但 **SVT-AV1 软件编码速度已可用**，NVIDIA 40 系 / Intel Arc 有**硬件 AV1 编码**，成本在快速下降。

> **结论**：如果做商业平台，**HEVC 要谨慎，AV1 是终局**。Cloudflare Stream 的 AV1 播放支持（beta）官方口径是 **比 H.264 省约 46% 带宽**。但你如果重度依赖 HEVC，注意 **Cloudflare Stream 目前并不以 HEVC 见长** —— 需要 HEVC 就得自建打包链路。

# 零、先修正两个前提，不然后面全是弯路

**① `nginx-rtmp` 不要用。** 它自 2019 年起基本停止维护：不支持 SRT、不支持 LL-HLS、不支持 HEVC/AV1、不支持 WebRTC。今天还拿它做源站，等于给自己的技术债开了一张没上限的信用卡。替代品：**MediaMTX**（轻量）、**SRS 5+**（集群/HEVC）、**OvenMediaEngine**（原生 WebRTC + LL-HLS）。

**② 「源站切片」这个动作，规模不同，归属不同。**

| 规模 | 谁来做切片 |
|---|---|
| 小（<1k 并发） | Ingest 服务器兼职（SRS/MediaMTX 自带 HLS 输出） |
| 中（1k–50k） | 拆出独立 **Packager**，ingest 只负责接流 |
| 大（50k+） | Ingest → Remux → Packager → 对象存储，全部解耦，各自独立伸缩 |

单体兼职的边界在于：ingest 是**有状态长连接**，packager 是**无状态可扩展**。把两者绑死，你就只能在接入机扩容，非常贵。

# 一、源站 → CDN 的 path：两条路线

## 路线 1：直连回源（CDN pull from ingest）

```text
主播 ──RTMPS──▶ SRS/MediaMTX ──(内置 HLS 输出 :8080/live/xxx.m3u8)──▶ CDN ──▶ 播放器
                     ▲                                                  │
                     └──────────────── 回源拉清单 + 拉分片 ──────────────┘
```

- ✅ 部署最简单，零外部依赖，改一行配置就能跑
- ❌ **接入机成为 CDN 的源站**，回源 QPS 直接打在长连接进程上；主播一多、回源一抖，推流就可能被杀
- ❌ 单点，无冗余；跨机房回源成本高
- 适合：**方案 A 的起步阶段**，或纯内网/局域网场景

## 路线 2：对象存储中转（Packager → R2 → CDN）【推荐】

```text
主播 ──RTMPS──▶ Ingest ──内网──▶ Remux/Transcode ──▶ Packager ──S3 API──▶ R2
                                                                          │
                                                     CDN ◀──回源──────────┘
```

- ✅ **ingest 和分发彻底解耦**。回源压力全在对象存储上，跟推流进程无关
- ✅ R2 天然多副本、**零出口费**，回源成本 ≈ 0
- ✅ 可水平扩展 packager（消费同一路流，多副本写不同 key 也行）
- ✅ 天然支持 DVR/回放：分片已经在存储里了
- ❌ 要维护 packager + 存储写入链路；清单更新有几十~几百 ms 的额外延迟

**我的建议：起步用路线 1（一周上线），一旦并发破千就切路线 2。** 两者的 URL 结构可以设计成一致的，切换时播放器侧零改动 —— 这是必须提前规划的。

# 二、路径规范与清单策略（这是「path」最实的部分）

## 2.1 URL 布局：`session_id` 是命根子

```text
media.example.com/
  └─ {room_id}/
      └─ {session_id}/                 ← ⚠️ 每次开播必须换新的！
          ├─ master.m3u8               （HLS 多码率清单）
          ├─ manifest.mpd              （DASH 多码率清单）
          ├─ video/
          │   ├─ 720p/init.mp4
          │   ├─ 720p/000001.m4s
          │   └─ 1080p/...
          └─ audio/
              └─ 128k/init.mp4, 000001.m4s
```

**为什么 `session_id` 必须有：**

如果你用固定路径（比如 `/room123/live.m3u8`），上一场直播的分片会被 CDN 缓存住，新一场开播时观众可能拉到**上一场的画面**。更糟的是 `immutable` 的分片缓存一年，你连删都删不掉。

> 正确做法：`session_id = timestamp + random`，开播时由控制面生成并写入 JWT。**新 session = 全新命名空间 = 缓存天然隔离 = 过期即自然淘汰。**

## 2.2 清单 vs 分片：两套完全不同的策略

| 资源 | Cache-Control | 理由 |
|---|---|---|
| `*.m4s` / `init.mp4` | `public, max-age=31536000, immutable` | 路径含 session+序号，**内容永不改变**，可永久缓存 |
| `master.m3u8` / `manifest.mpd`（直播） | `public, max-age=1, s-maxage=1, stale-while-revalidate=2` | 内容随分片持续变化，必须秒级刷新 |
| `*.m3u8` / `*.mpd`（VOD） | `public, max-age=31536000, immutable` | 已完结，永不改 |
| API / 鉴权 | `no-store` | 绝不缓存 |

**Cache Key 归一化（重申，因为这是最容易漏的）：** 在 CF Cache Rules 里剔除 `token`/`exp`/`sig`/`hdnts`。不剔除的话，每个观众的签名不同 → 每个请求都是独一无二的 → 命中率归零 → 回源流量 = 码率 × 观众数。

## 2.3 清单更新机制：三选一

| 方案 | 实现 | 增加延迟 | 适用 |
|---|---|---|---|
| **A. 短 TTL 轮询** | 清单 `max-age=1`，播放器每 1s 重拉 | +1~2s | ✅ 最省事，**方案 A/B 首选** |
| **B. Worker 长轮询** | Worker 持住请求 + 轮询 R2/DO，实现 blocking reload | +0.1~0.3s | 方案 B 进阶/方案 C |
| **C. 清单动态源** | 清单由 ingest/packager 直接服务（不进 CDN 缓存），只有分片走 CDN | +0 | 清单 QPS 小的时候可以 |

**方案 C 的隐患**：LL-HLS 的 blocking reload 会让每个观众**长期持有一个到源站的连接**。10 万观众 = 10 万条长连接打到你的源站。所以规模化下 C 必须配 A 或 B。

**⚠️ 关于 `ffmpeg`**：截至现在，FFmpeg 的 HLS muxer **不会输出 `EXT-X-PART`**，也就是**它做不了 LL-HLS**。真正能产出 part 的开源实现是 **MediaMTX / SRS / OvenMediaEngine 自身**，或自研 packager。别在这条路上耗时间。

# 三、转封装 vs 转码：决策树

直播项目 80% 的成本浪费，来自「无脑全量转码」。

```text
主播推上来的编码 == 观众需要的编码？
   │
   ├─ 是 → 【Remux 转封装】成本 ≈ 0 ✅
   │        唯一要求：GOP 结构合法、关键帧对齐分片边界
   │
   └─ 否 → 【Transcode 转码】
            ├─ 需要 ABR 阶梯（弱网降档）? → 多档转码（GPU）
            └─ 只是兼容老客户端?     → 只加 1 档低清 H.264
```

**三条降本铁律：**

1. **passthrough 优先**：能用 copy 就绝不 encode
2. **热门流才上 ABR**：78% 的直播间观众 <10 人，给他们转 4 档纯属烧钱
3. **关键帧对齐**：`-g` 设成帧率 × 分片秒数（30fps + 1s 分片 → `-g 30`），否则玩家切换码率时必然黑屏卡顿

# 四、三套技术栈方案

## 方案 A：初创 / 低预算（轻量敏捷型）

> **目标：1–3 天上线，月成本 < $100**

| 层 | 选型 | 说明 |
|---|---|---|
| Ingest | **MediaMTX** × 1 VPS | 单二进制，RTMP/SRT/WebRTC/LL-HLS 全包 |
| 转码 | **不做** | 纯 passthrough，主播推什么就发什么 |
| Packager | MediaMTX 内置 | 直接输出 LL-HLS |
| Origin | **Cloudflare R2** | 零出口费 |
| CDN | **Cloudflare CDN** | 免费计划够用 |
| 控制面 | CF Worker + Durable Object | 鉴权、房间状态、签名 URL |
| 应用面 | DO WebSocket | 弹幕、礼物、信令 |

**成本**：VPS $15–30 + R2 ~$1 + CF $0 ≈ **$25/月**

**能扛**：约 100–500 并发（受限于单机带宽，Hetzner/DO 一般给 20TB/月出网）

**瓶颈与升级路径**：单点无冗余 → 并发破千即上方案 B

---

## 方案 B：中型规模 / 注重性价比（自建核心 + CDN）★ 我最推荐

> **目标：5k–50k 并发，单位成本最优，可平滑演进**

| 层 | 选型 | 数量 | 说明 |
|---|---|---|---|
| Ingest | **SRS 5+** | 2×（主备，跨机房） | 支持 SRT/HEVC/集群 |
| Remux | SRS 内置 or FFmpeg | — | `-c copy`，零成本 |
| Transcode | **NVENC GPU 节点** | 按需 1–3 台 | T4/A10 或消费级卡，只给热门流转 ABR |
| Packager | **SRS HLS/LL-HLS** → 可选 Shaka Packager | — | 输出 CMAF + HLS/DASH 双清单 |
| Origin | **R2** | — | Packager 通过 S3 API 写入 |
| CDN | **Cloudflare + Tiered Cache + Origin Shield** | — | ⚠️ Cache Key 归一化必做 |
| 控制面 | Worker + DO + KV | — | JWT 签发、状态机、计费回调 |
| 应用面 | DO WebSocket（按房间分片） | — | 单 DO 撑不住超热房间，需分层扇出 |
| 互动（可选） | **LiveKit** | 1–2 台 | 连麦/PK 场景，别用它做广播 |

**成本测算（1 万并发 × 4 小时场次）**：
- Ingest VPS（2×CPX41）：$60/月
- GPU 转码（1× T4 突发）：$50–200/月
- R2 存储 + 回源：$5–20/月
- CF CDN（Enterprise 或按量）：$0–500/月
- **单场边际成本 ≈ 几美元**

**⚠️ 必须提前核对的风险**：Cloudflare 自助服务条款中有一条关于「**不成比例的非 HTML 内容**」的约定，历史上被用于限制把免费/Pro 计划当纯视频 CDN 使用。R2 本身零出口费，但**通过 Cloudflare CDN 分发大流量视频**时，请提前核对条款，或直接走 Enterprise / 专门的视频产品。别等量起来了才发现要重做架构。

---

## 方案 C：大厂 / 高并发 / 预算充足（全托管）

> **目标：SLA 兜底，团队聚焦业务，不为基建分心**

| 层 | 选型 |
|---|---|
| Ingest + 转码 + 打包 + 分发 | **Cloudflare Stream Live**（RTMPS/SRT 入，自动 ABR，HLS/DASH 出） |
| 亚秒级场景 | **Stream WebRTC**（WHIP 推 / WHEP 看）或 **Cloudflare Realtime SFU** |
| 备选托管 | **AWS MediaLive + MediaPackage + CloudFront** ／ **Mux Video** |
| 控制面 | CF Worker + DO |

**成本测算（官方公开价）**：

| 项 | 单价 |
|---|---|
| 分发 | $1 / 1,000 分钟 |
| 存储（自动录制） | $5 / 1,000 分钟 |
| WebRTC 分发 | $1 / 1,000 分钟 |

$$\text{1 万并发} \times 4\text{h} = 10^4 \times 240\text{min} = 2.4 \times 10^6 \text{ min} \Rightarrow \$2{,}400$$

**结论**：单场 $2.4k。如果你的直播是**低频、大事件型**（发布会、赛事、电商大促），全托管几乎无脑选。但如果是**高频、长尾、海量时长**（7×24 直播间、UGC 平台），这个数字会线性膨胀，这时候**方案 B 的边际成本优势就体现出来了**。

**⚠️ Cloudflare Stream 的已知限制（查文档确认过）**：
- Immutable 的坑：**WebRTC (WHIP) 输入的流，不能同时出 HLS/DASH 播放、不能录制、不支持 simulcast** —— 也就是说「亚秒延迟 + 大规模 + 可回放」这三者，不能只靠它一个产品同时满足
- 不以 HEVC 见长（强项是 H.264 + AV1 播放）
- LL-HLS 走的是它自己的实现，你无法调 part 时长等参数

## 5.3 延迟预算表（LL-HLS 目标 2–4s）

| 环节 | 典型 | 优化手段 | 可压到 |
|---|---|---|---|
| 采集 + 编码 | 100–300ms | 关闭 B 帧、低延迟预设 | ~50ms |
| 上行网络 | 50–150ms | SRT + 就近接入 + FEC | — |
| 接入缓冲 | 500–2000ms | 调小 SRT latency / jitter buffer | ~200ms |
| 转码（chunked） | 1000–2000ms | 缩小 chunk / 用 copy | ~300ms |
| 打包切片 | 1× part | part 缩到 200ms | ~200ms |
| 源站 → CDN 回源 | 50–200ms | Origin Shield | ~30ms |
| 播放器缓冲 | 3000–6000ms | LL-HLS 用 part 而非整片 | ~600ms |
| **合计** | **5–10s** | | **2–3s** |

真正的大头在**播放器缓冲**和**接入缓冲**，不在网络传输。这是很多人调优时搞反的地方。

# 一句话收尾

你的思路完全正确 —— **动静分离、职责清晰**。真正决定成败的只有三件事：

1. **`session_id` 换路径**（不做，CDN 会让你串场）
2. **Cache Key 剔除签名参数**（不做，CDN 等于没有）
3. **passthrough 优先**（不做，转码费会吃掉你所有利润）

至于方案选择，我的建议是：**绝大多数团队应该从方案 A 起步，直接向方案 B 演进，只在「低频大事件」时才考虑方案 C。** 因为 A→B 的架构是连续的（只是把 ingest 拆开、把源站换成 R2），而 C 是一次性的买断决策，量级不匹配时会非常难受。

需要的话，我可以把**方案 B 的 Terraform / docker-compose 完整清单**写出来：SRS 双机 + GPU 转码 + R2 写入 + Worker 控制面 + Cache Rules 配置，直接 `docker compose up` 能跑那种。

# 二、最容易被低估的 5 个「隐形工程」

这几点才是 Stream 真正的护城河 —— 不是「帮你省了台服务器」，而是**帮你省掉了一类你根本想不到要写的代码**。

<details>
<summary><b>1. 动态码率估算：不信任主播上报的数字</b>（这是我认为最有价值的一条）</summary>

**自建时的经典事故**：主播在 OBS 里填了 6000kbps，实际画面复杂度只值 2500kbps。你的清单写着 `BANDWIDTH=6000000`，播放器据此判断「观众带宽不够」→ **主动降档到 360p** → 观众明明有 200Mbps 光纤，却看着糊画质。

Stream 的做法（官方文档专门讲了）：**它不信任主播上报的码率，而是分析实际收到的画面复杂度，动态写入 HLS/DASH 清单的带宽估算值。**

- 低复杂度内容（PPT、聊天画面）→ 清单里带宽估值更低 → 更多观众能留在最高档
- 高复杂度内容（体育、快速平移）→ 估值更高 → 弱网观众及时降档，不卡顿

**这段逻辑你自己实现，需要**：VMAF 计算、per-segment 复杂度分析、清单动态改写、ABR 策略调参…… 这是一个专职音视频工程师几周的工作量，而且**你的用户根本不会告诉你有这个问题** —— 他们只会觉得「卡」「糊」，然后流失。
</details>

<details>
<summary><b>2. 断线重连接管的语义</b></summary>

自建时最烦的不是「主播断了」，而是「主播断完重连了，然后呢？」

- 新建 session？还是挂回原来那个？观众端的 `room_id` 怎么不变？
- 上一场的分片缓存怎么隔离？（我在上一轮强调的 `session_id` 问题）
- 重连期间的 3 秒空白，怎么让播放器不闪断？

Stream 的语义很简单：**只要推流软件自动重连，Stream 就继续接收**。加上 **Persistent Live Stream IDs**（开播/停播都不用换播放器 URL），这套状态机它替你管了。
</details>

<details>
<summary><b>3. 编码规范校验（`live_input.errored` webhook）</b></summary>

Stream 会在这些情况主动告警：**不支持的编码、GOP/keyframe 间隔异常、配额耗尽**。

这等于**免费帮你做了一层编码合规检查**。自建时，主播推了个 `-g 250` 的流（关键帧间隔 8 秒），你的 ABR 切换会疯狂花屏，但你**根本不知道是编码器配置问题** —— 你会以为是 CDN 的锅，查一整周。

有了这个 webhook，你可以直接给主播弹提示：「请把关键帧间隔设为 2 秒」。
</details>

<details>
<summary><b>4. 潮汐负载 vs 按量付费</b></summary>

直播是极端潮汐负载：平时 50 人看，一晚上突然 5 万人。

**自建模式下，你必须为峰值买容量**，而容量在 99% 的时间里闲置。这是自建最容易被低估的成本 —— 不是服务器贵，是**利用率低**。

托管模式把这个风险转移给了云厂商：你按分钟付费，峰值由它扛。
</details>

<details>
<summary><b>5. 渲染层的物理距离</b></summary>

「全球低延迟」在自建语境下意味着：多区域 PoP、跨境专线、和各国运营商的 BGP 关系、边缘节点机位。**这不是软件工程问题，是资本开支问题。** 而 Cloudflare 的 300+ PoP 已经在那儿了。
</details>

# 三、Stream **不**覆盖的部分（这些你还得自己搭）

别指望它是银弹，它只管媒体面。

| 你仍然必须自己做的 | 说明 |
|---|---|
| **用户体系 / 房间管理** | 注册登录、权限、订阅关系、主播管理（它只有一个 `creator` 字段） |
| **开播鉴权 / 业务状态机** | 谁可以播、付费才能看、开播倒计时、违禁词审核 |
| **弹幕 / 聊天 / 礼物 / 连麦信令** | 完全不管 —— 你的 Durable Object + WebSocket 那一层保留 |
| **前端产品** | 网站、App、开播页、播放页 UI |
| **计费与结算** | 给主播分账、观众付费、发票 —— 它只告诉你消耗了多少分钟 |
| **HEVC 全链路** | ⚠️ Stream 强项是 H.264 + AV1 播放，**不以 HEVC 见长** |
| **亚秒级的「大规模 + 可回放」** | ⚠️ **WHIP 输入的流不能同时出 HLS/DASH 播放、不能录制、不支持 simulcast** —— 三者兼得必须自己搭 relay |
| **深度参数调优** | part 时长、GOP、自定义 ladder 全不可调 |
| **数据主权 / 行业合规** | 视频存在 Cloudflare；医疗、金融、政企场景可能不合规 |
| **成本可控性** | 高频长尾（7×24 UGC）下，$1/1000 分钟会线性膨胀 |

# 四、什么时候该用 / 不该用

```text
你的直播形态是？
  │
  ├─ 低频 · 大事件 · 团队小 · 要快上线
  │     → ✅ 用 Stream。省下的工程量 > 溢价
  │
  ├─ 中频 · 要控制边际成本 · 有音视频工程师
  │     → ⚖️ 混合：Stream 做 ingest + 转码，分发自建走 R2 + CDN
  │
  └─ 高频 · 长尾 · 7×24 · 海量时长（UGC 平台）
        → ❌ 别用全托管。按分钟计费会吃掉你所有利润
             走方案 B（SRS + R2 + CF CDN）
```

**粗略的工程量对照**（供参考，非精确）：

| | 自建 | Stream |
|---|---|---|
| 需要的音视频工程师 | 2–4 人 | 0.5 人（写 API 调用） |
| 上线周期 | 2–6 个月 | **1 天** |
| 峰值容量风险 | 你承担 | 云厂商承担 |
| 单位成本（高频场景） | **更低** | 更高 |
| 单位成本（低频场景） | **更高**（闲置） | 更低 |

# 结论

Stream 省掉的不是「几台服务器」，而是**三类隐性成本**：

1. **编码质量与兼容性的长尾知识** —— 动态码率估算、GOP 校验、播放器矩阵
2. **潮汐负载的容量风险** —— 从资本开支变成运营开支
3. **全球化的物理成本** —— 多区域 PoP 与运营商关系

它把媒体面变成一个**幂等的 API 调用**，从而让你的团队可以把全部精力放在**控制面、应用面和产品差异化**上 —— 而这三块，恰恰是竞争对手抄不走的部分。

> 反过来说：**如果你的产品差异化本身就在媒体面**（比如自研超低延迟协议、私有编码器、特殊硬件对接），那 Stream 就不适合你。选型的第一性问题永远是：**你的竞争力在哪一层？**
