# Moonlight与Sunshine码率控制差异解析

## 🧑‍💻 User

moonlight为什么只有目标码率没有最大码率，为什么sunshine是cbr+qp码率控制

---
## 😀 默认助手 (7)

## 一句话概括

**Moonlight 只有一个“目标码率”，是因为在 CBR 下“目标”在数学上就等于“上限”，再设一个 max 没有意义；Sunshine 采用 CBR 并暴露 QP，是因为这条链路（UDP + 静态 FEC + 小抖动缓冲 + 无拥塞控制）只能使用一个预先声明的硬性上限，而 CBR 本身无法规定质量下限，因此 QP 作为补充参数出现。**

---

## 1. 为什么只有目标码率，没有最大码率

### 1.1 在 CBR 的约束定义中 max 就是 target

H.264/HEVC 的 HRD/CPB（VBV）模型保证的是**任意长度为 $T$ 的窗口内**的比特数满足：

$$B(T) \le R \cdot T + \text{BufferSize}$$

- **CBR**：$R$ 就是唯一的 $R$，瞬时超出只能由 buffer 那一点余量兜住，所以 $\text{peak} \approx \text{target}$。
- **VBR**：才有 $\text{averageBitRate}$ 和 $\text{maxBitRate}$ 两个独立量，窗口平均受 average 约束、瞬时受 max 约束。

所以 Moonlight 的滑块语义是**“我这条管道最多能通过这么多”**，并未表示“请给我这个画质”。管道容量只有一个数字，这是逻辑上的必然结果，与产品设计上的取舍无关。

### 1.2 传输层无法容忍码率超出上限

Moonlight 使用 RTP/UDP，并采用 Reed-Solomon FEC 与 IDR 请求重传，**没有 GCC/TWCC 这类自动码率自适应**。FEC 开销按比例计算：

$$C_{req} = R_{peak} \cdot (1 + f_{\text{fec}})$$

用户是按 $R_{target}$ 去规划 Wi-Fi/网线的。如果中途某个镜头爆炸让 $R_{peak}$ 瞬间变成 $3R$，$C_{req}$ 直接翻三倍 → 丢包 → 花屏/卡顿 → 疯狂请求 IDR → 更炸。客户端根本没有能力反馈“你降一点”。

### 1.3 延迟等于排队延迟，VBR 码率尖峰等于卡顿

客户端只有约一帧的 dequeue 队列，所以延迟主要由**网络队列**决定：

$$D_{queue}(t) = \frac{1}{C}\int_0^t \max\bigl(0,\; R(\tau) - C\bigr)\,d\tau$$

CBR 下 $R(\tau) \lesssim C$，积分恒为 0，延迟稳定。VBR 在一次复杂场景里攒下 $(P-C)\cdot T_{scene}$ 字节的积压，就是几百毫秒到几秒的“越玩越卡”——而这恰好发生在游戏最激烈的时候。

### 1.4 协议里只有一个字段

GameStream/Moonlight 的 RTSP SDP 协商中只带一个码率属性（`x-nv-video[0].averageBitRate`，不同版本字段名略有差异），Moonlight 作为该协议的一种实现，**没有第二个字段可以填**。要增加 max bitrate，就必须修改协议。

<details>
<summary>为什么不用 VBR（即使它同码率下画质更好）</summary>

- 实时低延迟 VBR **没有前视（lookahead）**，无法预知下一帧复杂度，退化成“记账更松的 CBR”，收益极小。
- 硬件编码器（NVENC/AMF/QSV 的 low-latency 模式）在 ULL/ULL-HQ 下基本只对 CBR 做了充分优化。
- 两遍/VBR with lookahead 需要缓冲若干帧 ⇒ 直接增加编码延迟，与串流目的冲突。

</details>

## 2. 为什么 Sunshine 采用 CBR + QP 码率控制

### 2.1 CBR 是唯一“可预先声明瞬时上限”的模式

| 模式 | 瞬时上限可保证？ | 需要前视？ | 延迟 | 适合串流？ |
|---|---|---|---|---|
| CQP / CONSTQP | ❌ 完全不可控 | 否 | 低 | 带宽不可预测 |
| VBR | 部分（HRD window） | 需要 | 中 | 峰值超出上限 |
| **CBR** | ✅ 近似硬上限 | 否 | 最低 | ✅ |
| CBR + QP 锚点 | ✅ | 否 | 最低 | ✅✅ |

CBR 是**唯一能在编码前就承诺“不会超过 X Mbps”**的低延迟模式——而这正是 FEC 预算、管道规划和小抖动缓冲所必需的前提。

### 2.2 CBR 的问题，正是需要 QP 的原因

CBR 只回答**“这一帧给多少比特”**，它完全不关心**“这些比特该换取什么画质”**。于是出现两个失效方向：

1. **简单画面（桌面/菜单/加载界面）**：率控为了让实际码率达到目标，会把 QP 逼近下限，用大量比特去编码一堆“几乎没变化”的内容。结果浪费带宽，VBV buffer 被填满，**真正的场景切换到来时容易出现量化波动**。
2. **复杂画面（爆炸/烟雾/粒子）**：率控必须把 QP 抬到很高才能装进预算，画质塌方、出现块效应。
3. **刚连接 / 刚发生 IDR**：率控刚从“未知状态”起步，没有初始 QP 时前几帧画质会很差。

QP 参数就是在这条带宽轴上再叠加一条**质量轴**：

- 它给率控一个**起点 / 锚点**（连接后、IDR 后不至于从最差 QP 开始）；
- 它给简单内容设一个**质量限制**，让码率可以低于目标（消耗不满不是问题，反而避免浪费 buffer 和带宽）；
- 它允许用户在“固定带宽”的前提下，于**画质与延迟稳定性之间**取得可预期的手动平衡。

换用大白话就是：**CBR 决定“预算多少”，QP 决定“这笔预算怎么花、花到什么程度就停止”**。只有预算而没有质量约束，率控对简单内容的处理会很不合理。

> ⚠️ 注意：`qp` 在不同后端的实际含义不完全一致。NVENC 侧它进入 `NV_ENC_RC_PARAMS` 的 QP 约束/初值字段（`constQP` / `initialRCQP` / `minQP` 各版本有差异），AMF 和 VAAPI 的语义也各有不同，Sunshine 只是把它当作一个可移植的“质量锚点”透传下去。这也是为什么很多用户反馈“把 QP 调太低反而码率会超限”——本质上是 QP 下限压过了 CBR 的预算约束。（具体行为建议以你的 Sunshine 版本 + 编码器后端的说明为准。）

## 3. 这套设计的代价（以及什么时候该换）

<details>
<summary>代价：你对“简单场景”会欠用带宽</summary>

CBR + QP 限制在纯静态画面上会主动**低于目标码率**。有人认为这是“浪费”，但从低延迟串流角度看恰恰是优点：不浪费管道、不让 VBV 积压、给下一次场景切换留有缓冲。

真正的问题是**高码率局域网**下 CBR 的“强行填满预算”会显得不经济——这也是 Apollo / Artemis 这类分支增加 VBR / CQP / 动态码率选项的动机。
</details>

**如果你确实需要“最大码率”这个概念**，可行路径是：

1. 换用支持 VBR/CQP 的 Sunshine 分支（Apollo 等）或较新的 Sunshine 构建，同时接受“峰值不可预知”；
2. 或者保持 CBR，把目标码率按链路能力的 **70–80%** 设置，用 Moonlight 的统计浮层观察实际码率与丢包；
3. 想要“同码率更高画质”，优先换 **HEVC / AV1** + 提高码率，而不是换码控模式。

## 总结表

| 你的疑问 | 根本原因 |
|---|---|
| 为什么没有最大码率？ | CBR 的 HRD 约束使得 max 与 target 是同一个数；协议 SDP 里也只有一个码率字段；语义上滑块代表的是“管道容量”而非“画质” |
| 为什么用 CBR？ | 无拥塞控制 + 静态 FEC + 小抖动缓冲 ⇒ 必须有一个**编码前就能承诺**的瞬时上限，而 CBR 是唯一满足的低延迟模式 |
| 为什么还要 QP？ | CBR 只规定预算，不规定质量；QP 提供质量锚点，避免简单画面被塞满、复杂画面严重劣化、IDR 后起步过差 |

## 简短回答

**默认情况下不会有额外延迟。** `NV_ENC_PARAMS_RC_VBR` 是一个**因果的、单帧单次的反馈控制器**，不需要先缓存几帧来“观察复杂度再决定码率”。每个 `nvEncEncodePicture` 调用依然立即吐出一帧。

你担心的“先缓冲几帧”这件事，是 **x264/x265 的 `rc-lookahead`（默认 40 帧）和两遍编码（缓冲整个文件）**，不是 NVENC 的 VBR。

**但 VBR 的代价不在编码器延迟上，它在网络排队和画质呼吸上，那才是用户真正感知到的“延迟”。**

---

## 1. 三个被混淆的概念

### 1.1 VBV/HRD buffer ≠ 帧缓冲

最常见的误解。VBV 是一个**比特的“漏桶”模型**，记录的是“我刚花了多少比特、还剩多少额度”，它是一个整数变量，而不是一段帧队列：

$$F_n = \mathrm{clamp}\bigl(F_{n-1} + b_n - R\cdot\Delta t,\; 0,\; B\bigr)$$

- $b_n$：第 $n$ 帧实际用的比特
- $R$：目标码率，$B$：VBV 大小

这个递推是**完全因果的**。它允许 $b_n > R\Delta t$（这就是 VBR 的本质——在额度允许时多花），但不需要知道未来。

### 1.2 VBV buffer 是“解码器缓冲”的模型，不是编码器输出队列

NVENC 不会把编码好的帧攒起来等 VBV 填满再发。帧编完就交出去。VBV 只是让码流**在 HRD 意义上合法**，让解码器的缓冲不溢出。

### 1.3 真正引入帧延迟的是这三样东西，与 VBR 无关

| 机制 | 是否引入帧级延迟 | 说明 |
|---|---|---|
| **B 帧**（`frameIntervalP > 1`） | ✅ 延迟 = B 帧深度 | 需要重排序，输出比输入晚 |
| **lookahead**（`enableLookahead` / `lookaheadDepth`） | ✅ 延迟 ≈ 深度 | SDK 提供，**默认关闭**；需显式开启 |
| **multi-pass（two-pass）** | ⚠️ 可能 | 是计算开销，通常不改变每帧一出的接口契约（具体行为随 SDK/GPU 而异） |
| **VBR rate control 本身** | ❌ | 纯因果反馈 |
| **VBV buffer 大小** | ❌ | 只影响码率波动幅度 |

So: **VBR ≠ 延迟。B 帧和 lookahead 才等于延迟。** 而 Sunshine 这类低延迟串流场景里，`frameIntervalP` 恒为 1（无 B 帧）、tuning 选 `ULTRA_LOW_LATENCY`，lookahead 不开启——所以即使换成 VBR，编码器侧延迟仍然是 0。

<details>
<summary>为什么 NVENC 的 VBR 不需要“看未来”</summary>

NVENC 的率控是**滑动窗口反馈**，它依据的是：

- 过去若干帧的实际比特消耗（VBV 里已有的余额）
- 当前帧的**帧内**统计（`aqStrength` / adaptive quantization 在帧内部做空间分析）
- 场景切换检测（可由 lookahead 或单帧统计得到）

它**并不需要下几帧的复杂度**来做决策。这也是为什么 NVENC 能在“一次调用一帧”的接口下实现 VBR。

对比 x264：`--rc-lookahead 40` 意味着它真的持有 40 帧做综合分配，因此有 40 帧延迟。这两者的区别是**反馈式 vs 前视式**，不能一概而论。
</details>

---

## 2. 但 VBR 的“延迟”藏在别处，而且往往更严重

如果只问“编码器是否多缓存了帧”，答案是**否**。但如果问“端到端是否更卡”，答案往往是**是**，原因完全不同：

### 2.1 网络排队延迟（最主要）

链路上 $R_{peak} > C$ 时，积压的字节就是你感知到的延迟：

$$D_{queue}(t) = \frac{1}{C}\int_0^t \max\bigl(0, R(\tau)-C\bigr)\,d\tau$$

一次 IDR 或一次爆炸场面，$b_n$ 可以瞬间是 $R\Delta t$ 的 3–5 倍。这一帧的字节要全部塞进容量为 $C$ 的管道，短暂排队 $\approx \dfrac{b_n - R\Delta t}{C}$。用户感受到的是“突然一顿”，与编码器延迟无关，但**主观体验完全一致**。

这也是 VBV 必须开小的原因：**大 VBV 等于允许 encoder 存下更多比特，然后在未来某一帧集中爆发**。所以 VBV 是延迟的间接来源——并不是因为它缓冲帧，而是因为它允许比特被集中占用并爆发。

### 2.2 画质“呼吸”

VBR 在场景从复杂转简单时，率控会有一段“还债期”，QP 波动几秒。这不是延迟，但会让人感觉“画面在忽好忽坏”，对静态桌面场景尤为明显。

### 2.3 IDR 的超量

VBR 下 I 帧的额度更松，容易出现超大 IDR，形成最大的一次突发。NVENC 为此提供了 `lowDelayKeyFrameScale`（压缩 I 帧强度）。

## 3. 如果要在 Sunshine 分支里试 VBR，怎么配才不引入延迟

<details>
<summary>点击展开配置要点</summary>

| 参数 | 建议值 | 原因 |
|---|---|---|
| `frameIntervalP` | **1** | 禁用 B 帧，否则 B 帧深度就是帧延迟 |
| `tuningInfo` | `ULTRA_LOW_LATENCY` | 关闭 lookahead 等特性 |
| `enableLookahead` / `lookaheadDepth` | **0 / 0** | 显式关掉，这是唯一会真正缓存帧的开关 |
| `multiPass` | `DISABLED` 或 quarter-res | 避免额外开销 |
| `vbvBufferSize` | **≤ 1–2 帧的比特量** | 大 VBV = 允许比特爆发 = 网络排队延迟 |
| `maxBitRate` | 别设太高（≤ 1.3× target） | 直接决定突发上限 |
| `lowDelayKeyFrameScale` | 适当调高（如 2–4） | 压制 IDR 突发 |

核心思想：**VBR + 严格小的 VBV + 小 maxBitRate，其行为会退化得非常接近 CBR**——这本身就说明，在“无拥塞控制 + 静态 FEC + 小抖动缓冲”的链路里，VBR 的自由度是没地方用的，你只能把它手动收紧回去。

</details>

## 结论

| 你的疑问 | 答案 |
|---|---|
| `NV_ENC_PARAMS_RC_VBR` 需要缓冲几帧来调节码率吗？ | **不需要**，它是因果反馈控制器 |
| 会因此引入高延迟吗？ | **编码器侧不会**（前提是无 B 帧、无 lookahead），**但系统侧可能严重变差**，因为突发比特会变成网络排队 |
| 什么才会引入帧延迟？ | B 帧、lookahead、两遍编码；以及**过大的 VBV/maxBitRate** 造成的比特爆发 |
| 那 Sunshine 为什么不默认用 VBR？ | 原因在于这条链路用不上 VBR 的自由度，VBR 的峰值不可事先声明与预算；与延迟无关 |

> ⚠️ 不同 SDK 版本对 `lookaheadDepth`、`enableLookahead`、`multiPass` 的支持和语义有差异（部分字段在较新 SDK 中已被 tuning info 取代），具体以你使用的 `nvEncodeAPI.h` 注释和实测为准。
