# 远程桌面丢包解决方案

## 🧑‍💻 User

众所周知，由于udp滥用太严重了，运营商的骨干网infra吃不消一般会在高峰期做udp qos，怎么解决4g网络下远程桌面，延迟~30ms带宽~10mbps但是udp丢包10-30%下的正常使用
已知可以的做法：
1. host端发包逻辑设置按会话码率限速，靠 pacer 约束发包避免瞬时流量拥塞（典型场景是码率输出比带宽大很多然后帧只能排队不然就直接丢包）
2. 自研的abr算法自动控制qos，网络波动大自动降低码率分辨率
3. 更激进的fec percentage如果可用带宽足够（牺牲有效码率，增加冗余）
已知不行做法：
1. 重传pack（不能重传的缓冲区大了延迟怎么办，不如丢包就直接丢帧保延迟）
2. 重新传个idr帧（问题是idr帧很大大概率又会堵死小水管 感觉没招）

似乎最简单办法就是降分辨率和码率

## 😀 默认助手 (7)

先给结论：**你列的三个"已知可行"方向都对，但优先级排错了，而且你现在的策略正在形成一个正反馈死循环。**

真正的死循环是：

```
高丢包 → 丢帧保延迟 → 参考链断裂 → 必须发 IDR → IDR 是巨帧 → 瞬间超发 → policer 丢更多 → 丢包更高
```

要跳出这个循环，只需要同时做三件事：**① 让 pacing 不越过 policer 的拐点；② 让"丢帧"不破坏参考链（不再触发 IDR）；③ 用 FEC 处理残余丢包。** 这三件事里，降分辨率是最后才该动的手段。

---

## 0. 先做诊断：丢包类型决定一切

在 policer 场景下，丢包是**你发送速率的函数**，不是随机事件。所以第一件事是用 `iperf3` 扫描一遍发送速率：

```bash
for r in 1 2 4 6 8 10; do
  iperf3 -u -c <host> -b ${r}M -l 1200 -t 20
done
```

看 `loss vs offered rate` 曲线：

| 现象 | 真实原因 | 主要解决方向 |
|---|---|---|
| loss 在某个速率**突然阶跃**到 20–30% | policer / shaper 拐点 | **细粒度 pacing + 延迟型 CC**（最重要） |
| TCP 能跑满、UDP 大量丢 | UDP 定向 QoS（DPI/DSCP/端口） | 换传输 / 隧道 / 降 UDP 占比 |
| 均匀随机丢 | 无线误码、弱覆盖 | FEC + 交织 |
| 连续 burst 丢 | 队列尾丢 / eNB 调度 / 切换 | 交织 FEC + 平滑 + jitter buffer |
| 只在高峰期丢 | 容量不足 | 降码率 + 多路径（无法根治） |

还要确认三件事：

- **方向**：4G 上行通常远差于下行，host 在 4G 和 viewer 在 4G 是完全不同的问题。
- **TCP 对照**：如果 TCP 吞吐正常而 UDP 丢 30%，基本可以确定是 UDP 定向策略，而不是整条链路拥塞。
- **丢包模式**：接收端记录 seq，看是均匀还是 burst，以及 burst 长度。这直接决定交织深度。

## 1. 最高杠杆：两级 pacing + 延迟型拥塞控制

这是唯一能**从源头消掉大部分丢包**的手段。

**编码器层（帧级平滑）**

用 VBV 强制编码器自己不要突发：

```
-x264-params vbv-maxrate=6400:vbv-bufsize=640   # buf ≈ 0.1s
```

大帧（keyframe、场景切换）必须被 VBV 摊平，否则一帧就能打穿 policer。

**网络层（包级平滑）**

- 目标发送速率 = **0.7 ~ 0.8 × 实测 policer 拐点**。
- pacer 粒度 ≤ 1–2 ms，burst 必须小于 policer 的 CBS（通常几 KB 到几十 KB）。
- Linux 上用 `SO_TXTIME` + `tc etf` 做精确时间戳调度，比用户态 busy-loop 稳。QUIC/TCP 的话 `tc qdisc add dev X root fq` 就自带 pacing。
- ⚠️ **关掉 UDP GSO / `UDP_SEGMENT`**（或让段大小 × 段数 < CBS）。GSO 会在网卡处炸成一个 microburst，policer 一定丢——这是非常常见的隐性超发来源。

**拥塞控制**

- **不要用丢包作为主要拥塞信号。** 你的丢包是外生的（policer/无线），不是拥塞。用丢包做 CC 会直接把码率打到地板。
- 主信号用 **OWD 排队延迟趋势**（trendline / min-RTT + delay gradient，类似 BBR / GCC 的 delay 部分），loss 只做上限保护 + 低通滤波 + **rate floor**。
- 在 pacer 内部做优先级 WFQ：FEC > 关键帧/base layer > 增量帧，保证预算被正确使用。

> **为什么这条最重要**：在 policer 下，ARQ 是**正反馈**（丢 20% → 重传 20% → offered 1.2× → 丢更多 → 风暴）；FEC 是**开环、有界**的。只有"少发 + 平滑"是负反馈。做好 pacing，10–30% 往往能直接降到 0–3%。

---

## 2. FEC 要按丢包"模式"设计，不能只按丢包率

- **选码**：均匀低丢用 XOR/FlexFEC 或 RS(10,3)；高丢、变丢用 **RaptorQ（RFC 6330）fountain**，overhead 接近理论最优，且不依赖"哪几个包丢了"。
- **overhead 预算**：均匀丢包 $p$ 下，块恢复率 ~99% 需要约

$$
\text{overhead} \approx \frac{1}{1-p} - 1 + \text{统计余量}
$$

  $p=20\%$ → 25% 起步，实际给 30–35%。

- **交织（interleaving）是必须的**：burst 丢包会整块打穿 RS。交织深度 ≥ 实测 burst 长度。这是"FEC 好像没用"最常见的原因。
- **分级保护**：base layer / 关键帧高 FEC，增强层低保护或不保护。
- **自适应但要限速**：按滑动窗口调 overhead，但对调整速率做限幅，避免和 CC 互相震荡。
- 注意 FEC 修复包自己也会丢，冗余要按**有效恢复率**算，别按理论值。

---

## 3. 重传：你的判断只对了一半

你说"重传不行，缓冲区大了延迟受不了"——**在 RTT 30ms 的场景下，延迟其实完全够**：一次重传 30ms，2–3 帧 jitter buffer = 66–100ms，来得及。

真正让 ARQ 在这里失效的不是延迟，是**带宽正反馈**：20% 丢包下重传 20% 会自己把自己淹死。

所以正确的解法不是"不用重传"，而是 **HARQ-lite：FEC 做主力，NACK 做有预算、有截止时间的机会性补救**：

- 只对**高价值包**发 NACK（帧头、base layer、IDR 分片首包）。
- **硬预算**：RTX 流量 ≤ 总预算 5%。
- **硬 deadline**：$t_{now} + RTT + margin < t_{decode}$ 才发，否则不发。
- **非阻塞**：重传不阻塞渲染，帧该丢就丢（你已经在做）。
- 只在 pacer 队列有空余时才发 RTX。

这样收益是"白捡的可靠性"，成本有上界，不会形成风暴。

---

## 4. IDR 问题的正解：根本不发大 IDR

这是跳出死循环的关键。周期性 IDR 和"丢包就 IDR"都是浪费，正确做法是让**丢帧不破坏参考链**：

- **Intra refresh**：把 I 宏块条带分散到 N 帧，每帧大小正常。恢复时间 $= N / fps$。30fps + N=30 → 1 秒恢复，远程桌面可接受。
- **LTR（长期参考帧）**：丢包后不重置编解码器，引用上一个已知完好的 LTR 帧继续预测。只有 LTR 也不可用时才走 intra refresh。
- **SVC / 时域分层**：base layer 重点 FEC，几乎不丢 → 几乎不需要 IDR；增强层随便丢。
- **依赖描述符 / frame marking**：decoder 知道帧间依赖，只丢依赖链断掉的帧，不做全局 reset。
- 万一必须发 intra：**切片 + 低优先级 + pacing 摊到多帧**，绝不一帧塞满水管。

> 这一步和"丢帧保延迟"是配套的。你现在丢帧导致链断、链断导致 IDR、IDR 导致超发，所以"丢帧"这条策略需要靠 codec 的 error resilience 兜住，否则越丢越糟。

## 5. 把传输层当成可选项

<details>
<summary>UDP 不是唯一选择（点击展开）</summary>

- 如果是 **DPI/端口定向** QoS：TCP 隧道、QUIC（UDP/443，DPI 看不进去）可能拿到不同待遇。若策略是"所有 UDP 一刀切"，QUIC 也无效。注意合规。
- **纯 TCP + BBR**：远程桌面能容忍 100–200ms，30ms RTT、10Mbps 下 TCP 其实工作得不错，是很好的兜底。HOL blocking 只在 burst 丢包时疼。
- **WebRTC TURN over TCP/TLS 443**：伪装成 HTTPS，可绕过部分 DPI。仅作合规前提下的 fallback。
- **多路径**：Wi-Fi + LTE 聚合、或双 SIM。这是**唯一能在容量层面绕过单链路 policer** 的办法。
- **PLPMTUD，禁分片**：分片会放大丢包（丢一片 = 丢整包），保持 ≤1200 字节。

</details>

## 6. 应用层：把"要传的东西"变小，比降分辨率划算

- **Dirty region / damage-based encoding**：只传变化区域。IDE、终端、文本编辑场景带宽接近 0——这是远程桌面最大的杠杆。
- **帧率优先于分辨率**：读文字需要分辨率而非高帧率。**先降帧率，别急着降分辨率。**
- **Screen content codec**：H.264 SCC / AV1 screen content tools，文本用近无损。
- **ROI**：注视区域高质量，周边降质。
- 关 B 帧、`tune=zerolatency`、`sliced-threads=1`。

## 7. 一个可落地的预算示例

设实测可达 10 Mbps、policer 拐点在 ~8.5 Mbps（10 Mbps offered 时丢 20%）：

- offered 目标：$0.75 \times 8.5 \approx 6.4$ Mbps
- FEC overhead 30%：$6.4 / 1.3 \approx 4.9$ Mbps 媒体
- RTX 预算 5%：$\approx 0.3$ Mbps
- jitter buffer 2 帧（30fps → 67ms），总延迟 30 + 67 ≈ 100ms
- 编码：1080p30 H.264 SCC，VBV 5Mbps，intra-refresh 30 帧

**4.9 Mbps 对 1080p30 桌面内容完全够**（静态画面为主）。所以在这个场景里，**你根本不需要降分辨率**，只需要不超发 + 平滑 + intra-refresh。如果 pacing 把丢包压到 2–3%，FEC 可降到 8–10%，媒体带宽升到 ~5.8 Mbps，画质反而更好。

## 8. 对你结论的修正

"最简单是降分辨率和码率"——方向对，但顺序应该是：

1. **先修 pacing + 延迟型 CC** ← 可能直接消掉大部分丢包，收益最大
2. **再上按 burst 模式设计的自适应 FEC + 交织**
3. **再改编码策略**（intra-refresh / LTR / dirty region / 帧率）
4. **最后才降分辨率** ← 分辨率对文本可读性影响最大，是最后手段

而且要"降"的是 **offered load 到 policer 以下**，不是"降了分辨率然后继续超发"。后者只是把巨帧变小，policer 照样丢。

**如果只能做一件事**：把 pacer 做到 1ms 粒度、目标 0.75×拐点、并关掉 UDP GSO。这一步大概率把 10–30% 丢包变成个位数，后面的 FEC 和 ABR 才有意义。
