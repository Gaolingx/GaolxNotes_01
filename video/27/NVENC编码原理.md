## 😀 默认助手 (7)

## 一句话回答

NVENC 的 RDO 确实是**固定功能硬件电路**（在 GPU die 上一块专用的 ASIC 子系统）加**跑在内嵌微控制器上的闭源固件**共同完成的，**不占用 CUDA Core / 可编程着色器**。它是“硬件数据通路 + 固件决策逻辑”的混合体，并非纯硬件电路，也并非纯软件。与 x264/x265 这类完整软件实现相比，它的 RDO 在**搜索空间、代价模型、熵编码精度、以及可调性**上被系统性地裁剪，根本约束是**固定周期预算**。

## 1. NVENC 内部的三层结构

```text
┌─────────────────────────────────────────────┐
│ 驱动 / NvEncodeAPI / ffmpeg nvenc wrapper   │  ← 你调的 preset / tune / multipass
├─────────────────────────────────────────────┤
│ 内嵌微控制器 + 固件 (firmware blob)          │  ← 码控、决策流程、部分启发式、参数解析
├─────────────────────────────────────────────┤
│ 固定功能数据通路 (固定功能硬件)               │  ← SAD/SSD 阵列、插值、变换/量化、
│                                             │     CABAC/CAVLC 引擎、去块、行缓冲 SRAM
└─────────────────────────────────────────────┘
```

几个关键事实：

- **编码流水线不经着色器。** 的整个 encode pipeline（ME → 模式决策 → 变换量化 → 熵编码 → 重建/去块）都在专用硅上跑。这也是它能做到 4K60 只吃几瓦的原因。旧的 NVENC SDK 允许你用 CUDA 做**前处理**和 **lookahead**（`rc-lookahead` / B 帧判决需要 CUDA interop），但那是在编码器**外面**加一圈，核心 RDO 仍在硬件里。
- **不是纯组合逻辑硬连线。** NVENC 内部有嵌入式处理器核跑固件，控制流、码控、部分模式决策的“策略”是固件代码。这解释了两件事：① 驱动更新能改善编码质量（NVIDIA 多次这么做过，比如 2019–2020 年针对 Turing/Ampere 的 NVENC 质量提升、以及 HEVC/AV1 的调优基本都是随驱动下发的固件变更）；② 逆向驱动能 dump 到 `nvEnc` 固件 blob。
- **算法细节未公开。** NVIDIA 不发布 RDO 的具体算法，公开信息只有专利、驱动字符串和黑盒实测。下面凡涉及“具体怎么做”的部分，都是从专利和实测行为反推的，标注为推断。

## 2. 硬件 RDO 与软件 RDO 的算法差异

RDO 的本质没区别，都是最小化

$$ J = D + \lambda \cdot R $$

差异全在**怎么估 $D$、怎么估 $R$、在多大的候选集上算 $J$**。

<details>
<summary><b>硬件常用的近似手段（展开）</b></summary>

1. **两级筛选，先粗后精。** 先用 SAD/SATD 做一遍廉价筛选（几乎全部候选），只把极少数候选送进真正的 RD 精算。软件编码器也会分两级，但硬件的第一级筛选更激进、送进第二级的候选更少（x264 `--subme 11` 会把大量候选跑完整 RDO）。
2. **代价模型用 SAD/SSD 而非 SATD/精确 SSE 混用。** 硬件里 SSD 阵列面积大，很多路径退化成 SAD，或者用近似的 $\lambda$ 查表而不是按 QP/帧类型动态推导。
3. **码率 $R$ 用查表/线性模型估计，不数真实 CABAC bin。** 这是最本质的一条。CABAC 是**逐 bin 串行**的，硬件里做“真编码一遍再数比特”代价极高（面积+串行延迟）。软件编码器 `rdcost` 就是真的编码一遍数比特。硬件普遍用基于上下文状态的近似估计器，或只对 DC/部分系数精确计数。
4. **分区/模式候选集裁剪。** HEVC 的 64×64 CTU 四叉树如果做完整 RD 递归搜索非常贵，硬件用层级化剪枝（上层代价外推下层），跳过大量 8×8/4×4 组合；H.264 的 9 种 4×4 帧内模式通常不会全跑 RDO。
5. **无 RDOQ / trellis。** 据公开实测和 NVIDIA 从不提供相关开关来看，NVENC **没有** x264 `--trellis 2` / x265 `--rdoq-level 2` 那种“量化系数级的率失真优化”。这是低码率下码率效率差距的主要来源之一。
6. **运动搜索是工程化搜索，不是 TZ/UMH。** 硬件用规则的、可流水线化的搜索图样（分层 + 小范围细化），没有 x264 那种带复杂early-termination 的六边形/UMH 搜索，参考帧数和 MV 候选也少。
7. **没有多 pass 统计。** NVENC 的 `multipass` 只是在同一次编码里跑一个低分辨率（quarter res）或全分辨率的**前置 pass** 给码控喂数据，不是 x264 的 `--pass 1/2` 那种独立的、可做 mbtree 的统计分析。
8. **预处理基本没有。** psy-rd、mbtree、VAQ（variance AQ）、fgo、胶片颗粒合成（AV1 有）、自定义量化矩阵、deblock 参数微调——这些软件编码器的“画质外挂”硬件基本都没有。NVENC 只暴露 `spatial-aq` / `temporal-aq` 这类粗粒度开关。
9. **码控是逐行/逐帧的固件启发式。** HRD/VBV 精确填充、CBR 严格贴合不如软件。硬件历史上 CBR 抖动偏大、VBV 超调偶发，就是固件决策粒度粗导致的。

</details>

<details>
<summary><b>软件编码器有、硬件编码器没有的能力清单</b></summary>

| 能力 | x264/x265/SVT-AV1 | NVENC |
|---|---|---|
| Trellis / RDOQ（量化系数级优化） | ✅ | ❌ |
| 真实 CABAC 比特计数做 RDO | ✅ | 近似 |
| 完整分区树 RD 递归 | ✅ | 强剪枝 |
| 多 pass + 统计（mbtree 等） | ✅ | ❌（只有内部 prepass） |
| psy-rd / 心理视觉优化 | ✅ | ❌ |
| 自定义量化矩阵 | ✅ | ❌ |
| 可变搜索深度（越慢越好） | ✅（slow/veryslow/placebo） | ❌（P1–P7 有限档位） |
| 逐帧/逐 MB 任意 QP、zones | ✅ | 有限 |
| 编码器算法本身可改 | ✅（开源） | ❌（闭源固件） |

</details>

## 3. 为什么必须近似：算力预算差 2–3 个数量级

这是理解一切差异的根。硬件是**同步流水线**，必须保证确定吞吐，不能“这一帧难就多算一会儿”。

以 4K60、NVENC 引擎约 1.2 GHz 粗算（示意，非实测）：

- H.264 16×16 MB：$3840\times2160/256 \times 60 \approx 1.94\times10^{6}$ MB/s ⇒ 平均每 MB 约 **600 个引擎周期**
- HEVC 64×64 CTU：约 $1.2\times10^{5}$ CTU/s ⇒ 平均每 CTU 约 **1 万个引擎周期**

而 x265 在 4K 上跑 `medium` 只有几 fps，多核算下来每 MB 的有效算力是 $10^{5}$–$10^{6}$ 周期量级。也就是说软件有 **100–1000 倍**的预算去做搜索和精确代价计算。硬件靠的是超宽 SIMD 阵列（一次算几十上百个 SAD）把这个差距压下来，但**串行依赖的部分（CABAC、递归决策、上下文自适应）压不下来**——这就是为什么硬件 RDO 天然偏向“并行友好但精度低”的近似。

## 4. 实际影响：差距有多大、什么时候用哪个

- **BD-rate**：Turing 之后的 NVENC（尤其 `P7` + `multipass=fullres` + `lookahead` + `spatial-aq`）大致接近 x264 `faster`～`medium`、x265 `fast` 的水平。比 `veryslow`/`placebo` 差 10–30% 码率是常态。
- **差距会被场景放大**：低码率、动漫/线条、强噪声、暗场、频繁场景切换（码控 + RDO 双重吃亏）。高码率、高分辨率、低延迟直播时差距明显缩小。
- **NVENC 的绝对优势**：每像素功耗低 1–2 个数量级、延迟确定、不占 CPU、可多路并发（会话数受驱动限制）。这是固定功能电路的胜利，跟算法优劣无关。
- **代际差异很大**：Kepler→Maxwell→Pascal 质量提升有限，**Turing 是分水岭**（NVENC 重做、HEVC 10bit、B 帧、更好的 RDO），Ampere 是 HEVC/AV1 增强，Ada 加 AV1。所以“NVENC 画质差”这个结论要按代看。

典型可调项（ffmpeg 侧真实存在的选项）：

```bash
ffmpeg -i in.mp4 -c:v hevc_nvenc \
  -preset p7 -tune hq \
  -multipass fullres \
  -rc-lookahead 32 \
  -spatial-aq 1 -temporal-aq 1 -aq-strength 8 \
  -b_ref_mode middle \
  -rc vbr -cq 26 -b:v 0 out.mp4
```

这些参数本质上就是在**有限的硬件配置寄存器 + 固件策略表**里，向“更接近软件编码器的搜索/决策”方向拨一点点。

## 5. 需要打折扣的地方

- NVIDIA **未公开** NVENC 的 RDO 具体算法，“无 RDOQ”“近似比特估计”“强剪枝”这些结论来自专利、固件逆向和黑盒 BD-rate 测量，属于高置信度推断而非官方文档。
- “固件 + 硬件”的边界在每一代都不一样，NVIDIA 有时把更多决策挪到固件（可更新）里，有时干脆硬化。
- 上面那个周期预算数字只是量级示意，用来表达“差 2–3 个数量级”这个结论，不是可引用的实测值。

**总结**：NVENC 的 RDO 是硬件电路 + 固件实现的**精简版 RD 优化**——它确实在算 $J = D + \lambda R$ 并做模式决策，但候选集被剪、$R$ 用近似估计、缺 RDOQ、缺心理视觉工具，全部源于固定吞吐的流水线预算。与完整软件编码器的差距不是“实现得不好”，而是**架构约束下的必然取舍**。

## 😀 默认助手 (7)

先说清楚一个容易混淆的点，因为它是理解后面一切的钥匙：

> **这里有预算，而且是两种，别混为一谈：**
> - **比特预算**（bit budget）：每帧/每 GOP 多少 bit。QP 分配就是在花这个预算。
> - **周期预算**（cycle budget）：每个 CTU 有多少个引擎时钟可以花。RDO 搜索、ME 就是在花这个预算。
>
> NVENC 的码控（花比特预算）做得相当成熟，接近软件编码器，这是因为码控是**标量、串行、低算力**的活，正适合固件运行；而 RDO/ME（花周期预算）被砍得很狠，因为它们需要**海量并行搜索 + 精确串行熵计数**。这个不对称性解释了 NVENC 几乎所有的行为特征。

**证据等级声明**（重要）：NVIDIA 不公开这些算法。下面分为三档标注——`[文档]` 官方 SDK/文档有据；`[专利/逆向]` 从 NVIDIA 专利、驱动固件字符串、开源驱动（nova）推断；`[实测]` 黑盒行为测量；`[推测]` 我基于硬件编码器通用架构的合理推断。NVENC 具体公式没有任何公开来源。

# 一、码率 → QP：三层嵌套的反馈控制

NVENC 的码控是**分层**的，不是"给个码率算个 QP 就完事"。`[文档+实测]`

## 1.1 三个控制环

```text
外层：GOP / 序列级   → 目标码率、VBV 容量、GOP 结构（谁是 I/P/B、B 的层级深度）
  ↓ 每帧的 bit 配额
中层：帧级 QP        → 解 R-Q 模型 + VBV 约束，得到 base QP
  ↓ base QP + 空间偏移
内层：CTU / 行级 QP  → AQ（activity）微调，少量 delta
```

**外层：阈值 + GOP 决策。** 给定 `-b:v 6M`，60fps，先算出每帧平均配额：

$$ \bar b = \frac{R}{f} = \frac{6\times10^6}{60} = 100\ \text{kbit/frame} \approx 12.5\ \text{KB} $$

然后根据**场景切换检测**（lookahead 里做，见下）把某些帧标成 I 帧，其余按 B 层级金字塔分配相对 QP 偏移。硬件不能自适应 GOP 深度（周期预算固定），所以 GOP 结构基本是参数固定的，只有 I 帧位置可被场景切换提前触发。`[实测]`

**中层：帧级 QP 求解。** 核心是一个 **R–Q 模型**加 **VBV 反馈**。经典形式（软件编码器也用，NVENC 大概率是它的变体）`[推测]`：

$$ R(Q) \approx \frac{K \cdot C}{Q^{\alpha}} \quad\text{或}\quad R = \frac{a}{Q} + \frac{b}{Q^2} $$

其中 $C$ 是**当前帧复杂度代理**，$Q = 2^{(QP-4)/6}$ 是量化步长（H.264/HEVC 的对数 QP 映射）。解出目标 $Q$ 后取对数得 QP。$\lambda$ 随之定：

$$ \lambda = c\,Q^2,\qquad \lambda_{\text{motion}} = \sqrt{\lambda} $$

这个 $c$ 就是 preset（P1–P7）会动的东西之一。`[推测]`

**VBV/HRD 约束**（这是硬件码控的主要弱点）`[实测]`：

$$ B_{n+1} = \min\!\left(B_{\max},\; B_n + \frac{R}{f} - b_n\right),\qquad B_n \ge 0 $$

若预测 $B_{n+1}$ 会溢出，就抬高下一帧 QP。硬件的问题在于**决策粒度粗**（帧级/行级，不是 MB 级）且**前瞻短**，所以 CBR 抖动、VBV 超调比 x264 明显——这不是算法不会，是固件跑在有限的片上状态里，看不到足够远的未来。

## 1.2 复杂度代理 $C$ 从哪来 —— 这就是 lookahead / multipass 的真正用途

NVENC 不能像 x264 那样做独立的两遍统计（`--pass 1/2` + mbtree）。它有的是：`[文档+实测]`

| 机制 | 实际作用 |
|---|---|
| `-multipass fullres` | 同一次编码内先跑一个全分辨率前置 pass，**产出每帧的 SATD/复杂度**，喂给中层码控。这是硬件版的"pass 1"，但只服务于码控，不做 mbtree |
| `-multipass qres` | 同上，但前置 pass 在 1/4 分辨率跑，便宜 |
| `-rc-lookahead N` | 需要 **CUDA interop**（前置 pass 在着色器上跑！），产出 N 帧的复杂度曲线，用于场景切换检测 + B 帧结构 + 码控前瞻 |
| `-spatial-aq` / `-temporal-aq` | 帧内/帧间质量再分配，见 §2 |

注意最后一点很有意思：**lookahead 是唯一明确跑在可编程硬件（CUDA core）上的部分**。固定功能电路负责编码，着色器负责"看一眼未来"。这恰好说明了分工逻辑——需要灵活性的分析可以外挂，需要确定性吞吐的编码必须硬化。`[文档]`

## 1.3 一个数值直觉

1080p60 @ 6 Mbps，HEVC，CTU=64：每帧 $30\times17=510$ 个 CTU。若一帧预算 100 kbit、I 帧占大头，一个 P 帧可能只有 ~50 kbit ⇒ **平均每 CTU 约 100 bit**，约 1 bit/像素。这就是"预算"的残酷程度：码控要在 100 bit 的尺度上决定这个 CTU 该给多少 QP，而 RDO 还要在同一预算下选模式。

# 二、质量怎么"动态分配"

## 2.1 三档粒度 + 一个关键接口

<details>
<summary><b>展开：NVENC 实际暴露的质量分配旋钮</b></summary>

1. **帧级**：码控自动决定 base QP。你无法直接指定（除非 CQP 模式）。
2. **区域级（ROI）**：较新的 `NvEncodeAPI` 有 **QP delta map / QP 数组**类接口，允许外部逐块给 QP 偏移。`[文档，需按 SDK 版本核对字段名]` 这是把 mbtree 那种"外部算好再灌进去"的路子留给了应用层——**硬件不做传播分析，但允许你把分析结果喂进来**。这是很重要的一点：NVENC 的设计哲学是"分析外置，决策硬化"。
3. **CTU/行级（内部 AQ）**：由固件按 activity 自动偏移。

</details>

## 2.2 空间 AQ：activity 驱动的 QP 偏移

原理和 x264 的 `--aq-mode` 同源，但公式未公开。`[实测]` 通用形式：

$$ \Delta QP_i = -\,\gamma \cdot \log_2\!\left(\frac{a_i}{\bar a}\right) \quad\text{或}\quad qscale_i \propto \left(\frac{\bar a}{a_i}\right)^{\gamma} $$

其中 $a_i$ 是局部 activity（方差 / SATD / 梯度能量），$\bar a$ 是全帧均值，$\gamma$ 对应 `-aq-strength`。直觉：**平坦区域（天空、墙面）降码率几乎不影响主观质量，把省下的比特给纹理密集区**。因为人眼对平坦区的量化误差极其敏感于"带状/块状"，但这个可以用很小的码率避免；而纹理区多给比特的边际收益高。

**为什么硬件版本效果弱于 x264 的 AQ+mbtree**：
- 硬件 AQ 的 $a_i$ 一般是**纯空间方差**，没有 mbtree 的**时间传播**（一个块被后续多少帧参考、传播成本多高）。没有传播信息，就无法区分"高方差但没人参考"和"低方差但被大量参考"的场景——后者恰恰是最该保质量的地方。`[推测]`
- 偏移量被量化到有限档位（delta QP 是整数且范围受限），且粒度是行/块组，不是逐 MB。

## 2.3 temporal AQ：用参考关系分配质量

`-temporal-aq` 的存在说明 NVENC 确实有某种**帧间重要性**代理。`[实测]` 典型做法：帧被参考的次数越多（B 层级越高、越是"参考锚点"），QP 越低（质量越高）。这和 x264 的 B-pyramid 权重思路一致。但在硬件里这只能做到**帧级**，不是 mbtree 的逐块传播。

**一句话总结质量分配**：NVENC 在**比特预算**上分配得不错（帧级 + AQ 偏移），但在**质量的空间/时间精细度**上远落后于软件——因为它缺少 mbtree 式的图传播分析，而这类分析是图算法，串行依赖强、状态大，正好是固定功能电路最不擅长的。NVIDIA 的解法是把这块**外置**（lookahead 用 CUDA、ROI 用 QP map）。

# 三、运动矢量怎么估

这是硬件最擅长的部分——ME 本质是**海量独立的小块 SAD 比较**，高度数据并行，正好匹配 SIMD 阵列。所以 NVENC 的 ME 反而不算"被砍得最狠"的环节，砍的是**搜索图样的灵活性**。

## 3.1 金字塔 + 分层细化（标准硬件套路）`[专利/推测]`

```text
Level 2 (1/16 降采样)  ── 全搜索，抓大位移、全局运动
        ↓ MV 作为预测
Level 1 (1/4 降采样)   ── 小范围细化
        ↓
Level 0 (全分辨率)     ── 整数像素细化 + 亚像素
```

为什么必须这样：全分辨率下 ±64 甚至 ±128 的搜索窗，单是 16×16 块的 SAD 数量就是 $(2\cdot128+1)^2 \approx 6.6\times10^4$ 个/块。在 §四算出的每 8×8 块只有约 150 引擎周期的预算下，**全分辨率全搜索在物理上不可能**。降采样把粗搜索的成本压到 1/16~1/256，再用小窗细化——这是所有硬件编码器（NVENC、QuickSync、VCN）的共同解法。软件编码器（x264 `--me umh`/`esa`）可以不做降采样直接全分辨率搜，这是它能赢的地方之一。

## 3.2 SAD 阵列 + "SAD tree" 共享计算

关键工程技巧：**一次 SAD 计算，同时产出多个分区的代价**。计算 $16\times16$ 块的 SAD 时，用行/列求和树可以顺带得到 4 个 $8\times8$、2 个 $16\times8$、2 个 $8\times16$ 的 SAD：

```text
    16x16 区域的行 SAD 累加
    ┌────┬────┐
    │ 8x8 │ 8x8 │  ← 行和相加得到 16x8
    ├────┼────┤
    │ 8x8 │ 8x8 │  ← 列和相加得到 8x16
    └────┴────┘
    所有 8x8 之和 = 16x16  ← 只是加法树，零额外访存
```

同样，HEVC 的 64×64 CTU 可以先算 64 个 $8\times8$ 的 SAD，然后**用加法树合并出 32×32、16×16 的所有分区代价**。这条"可加性"性质在 §四会变成遍历策略的核心。

## 3.3 亚像素与 MVP

- 整数 MV 出来后，在 ±1 邻域做 1/2 像素细化（6-tap 或双线性插值），再 1/4 像素细化。硬件用专用的插值单元，行缓冲里缓存插值后的参考像素。`[推测]`
- **MVP 预测**：中值预测（H.264 的 A/B/C 中值）或 AMVP 候选列表（HEVC），先算 MV 差值，代价 $J_{mv} = \text{SAD} + \lambda_{\text{motion}} \cdot R(\Delta MV)$。如果 MVP 的 SAD 已经足够好，直接 early-exit，省下整个搜索——**这是数据相关的省预算手段**，但"最多省多少"是编译器时代就固定好的，实际吞吐由最坏情况决定。
- **参考帧数受限**：NVENC 的 ref 数、B 帧层级深度都有上限，这不是算法限制而是**参考帧缓冲的片上 SRAM 与带宽限制**。`[推测]`
- **B 帧双向**：需要同时持有前向/后向插值结果，做平均后算 SAD。硬件通常对 B 帧只做"双向 + 单向 + skip"三选一的粗判，不做完整双 MV 联合搜索。

`[实测]` 的典型现象印证了上述推断：NVENC 在**大平移、低纹理、快速运动**场景的 MV 质量明显差于 x264 medium——因为降采样在最粗层就把小物体"抹掉"了，MV 被全局运动主导，产生拖影和蚊噪。这也是为什么直播场景里快速运动的画面 NVENC 更吃码率。

# 四、CTU 怎么遍历搜索 —— 硬件版的四叉树 RD

这是最反直觉的部分。软件编码器（x265）的 CTU 搜索是**递归深度优先**：函数调自己 4 次下钻到 8×8，带回代价再比较要不要 split。硬件**不能递归**（没有灵活调用栈，延迟不定），所以必须换一种等价但可流水线化的写法。

## 4.1 核心障碍：RD 代价不可加

$$ J = D + \lambda R $$

$D$ 可加（$D_{\text{CTU}} = \sum D_{8\times8}$），但 $R$ **不可加**——CABAC 有上下文自适应，编码 4 个 8×8 的比特数 ≠ 编码 1 个 32×32 的比特数，而且依赖左/上邻居的上下文状态。

**硬件必须绕开这一点**。解法（`[专利/推测]`）：

> **把 $R$ 换成一个"可加的近似估计"**：每个块用基于 SATD、QP、MV 幅值的查表模型估出 $R_i$，使 $R_{\text{parent}} \approx \sum R_{\text{child}} + \delta_{\text{split}}$。一旦 $R$ 可加，四叉树的除选就退化成**加法树归约**——这正是硬件最擅长的事。

这解释了为什么硬件 RDO 天生不精确：**为了让决策可并行，它主动放弃了熵编码的真实比特反馈**。软件编码器的 `rdcost` 是真的编码一遍数比特，硬件不行。这是上一轮我说"无 RDOQ"之外的另一个根因。

## 4.2 遍历顺序：Z-order / 波前

- **CTU 内**必须按 **Z-order（光栅化的四叉树顺序）** 处理，因为 CABAC 和重建邻居依赖要求这个顺序。`[文档，标准要求]`
- **CTU 间**按光栅序，但硬件用**波前（wavefront）流水**：CTU 行 $k$ 处理时，行 $k-1$ 在做熵编码/去块。需要 **1–2 个 CTU 行的高度 + 左边若干列的行缓冲**（去块/SAO 还要多一行）。这是固定功能电路的经典布局。

## 4.3 具体怎么"遍历"四叉树

85 个节点（$1+4+16+64$）的全 RD 搜索不可行。硬件有三种可行方案，很可能**混用**：

| 方案 | 做法 | 代价 |
|---|---|---|
| **A. 自底向上归约** | 并行算全部 64 个 8×8 的 $J$（宽 SIMD）→ 加法树合并出 32×32/16×16 → 每层比较 $\sum J_{\text{child}}$ vs $J_{\text{parent}} + \delta$ → 得最优划分 | 最大的并行度，但依赖 §4.1 的可加近似 |
| **B. 逐深度迭代** | 对同一 CTU 分 4 遍扫（深度 0/1/2/3），每遍只做该深度的模式决策，中间结果存 CTU 级 SRAM（64×64×1.5×10bit ≈ 6 KB/CTU） | 需要 CTU 级缓存和多次往返，但每遍简单 |
| **C. 自顶向下剪枝** | 先定 64×64 和 32×32 的模式（用廉价特征+SAD），只对"有希望"的分支下钻 | 最省预算，精度最差 |

**保守推断**：NVENC 大概是 **C 的粗剪枝 + A 的并行归约**结合——先用 SAD/SATD 排除明显不划算的分区，剩下的用可加代价做并行除选；preset P1→P7 变化的正是"下钻多少层、每层保留多少候选"。`[推测]`

## 4.4 周期预算的残酷数字

4K60 HEVC，一个 NVENC 引擎约 1.2 GHz：`[计算示意]`

$$ \text{CTU/帧} = \left\lceil\tfrac{3840}{64}\right\rceil \times \left\lceil\tfrac{2160}{64}\right\rceil = 60 \times 34 = 2040 $$
$$ \text{CTU/s} = 2040 \times 60 = 1.22\times10^{5} \;\Rightarrow\; \text{每 CTU} \approx \frac{1.2\times10^{9}}{1.22\times10^{5}} \approx 9800\ \text{引擎周期} $$

一个 CTU 有 **64 个 8×8 块**，摊下来每块约 **150 个周期**。在这 150 个周期里，要为这个 8×8 块完成：帧间多参考 ME + 双向 + 帧内多方向预测 + 变换量化重建 + 代价计算 + 上下文估计。**这在任何意义上都不可能精确**。这就是为什么硬件必须靠宽 SIMD（几百个并行 PE，把这些周期乘以 PE 数变成几百万次运算）加近似模型，而不是靠更聪明的算法。

软件编码器在同样位置有 $10^{5}$–$10^{6}$ 个 CPU 周期/块。差距的 3 个数量级**不是工程能力，是功耗墙**——固定功能电路用 1/100 的能量做这件事，代价就是算力预算。

# 五、把四个问题串起来

```text
用户给:  -b:v 6M  -preset p7  -rc-lookahead 32  -spatial-aq 1
              │
              ├─→ [CUDA 着色器] lookahead 前置分析 → 每帧复杂度曲线 + 场景切换点
              │                                      （这是唯一"灵活"的部分）
              ├─→ [固件] 帧级码控: R-Q 模型 + VBV 反馈 → base QP
              ├─→ [固件] AQ: activity → 逐 CTU/行 delta QP
              │
              └─→ [固定功能电路] 每 CTU:
                     降采样金字塔 ME (SAD 阵列) → 整数/亚像素 MV
                     → 分区除选 (可加代价的加法树归约)
                     → 变换/量化/重建 (流水线)
                     → CABAC (串行，是吞吐瓶颈)
```

**四条结论：**

1. **能决定 QP**，是因为码控是标量低算力任务，固件完全可以做，而且做得接近软件水平——只要你不要求 mbtree 级的精细度。
2. **质量动态分配**靠的是"帧级模型 + AQ 偏移 + 可选的 QP delta map"，缺的是图传播分析；NVIDIA 的答案是把它外置（CUDA lookahead / ROI 接口）。
3. **MV 估计**是硬件强项（数据并行），弱在降采样导致小位移/小物体丢失。
4. **CTU 遍历**是硬件最吃亏的地方，因为它必须把"不可加的 RD 代价"改造成"可加的近似代价"，才能用并行加法树代替递归——**这个改造本身就是精度损失的根源**。

**一句话**：NVENC 不是"把 x265 简化后塞进 ASIC"，而是**围绕"固定吞吐、无递归、代价可加"这三个硬约束，重新设计了一套近似 RD 框架**。它的参数（P1–P7、AQ、lookahead、multipass）本质是在这套固定框架里拨几个旋钮，而不是像软件那样改变算法本身。

**再次提示证据边界**：§一、§三的模型形式、§四的遍历方案 A/B/C、以及所有具体公式，都是基于通用硬件编码器架构和 NVIDIA 专利的**推断**，NVENC 真实实现无公开资料。上面的周期数字是量级示意，不可作为实测引用。

## 三、有没有别的信息源？有，但都有边界

### 3.1 专利 —— 最"合法且信息量大"的一手来源

NVIDIA 在视频编码方向有大量专利（搜索 "NVIDIA + rate control / adaptive quantization / motion estimation / video encoder"）。但要注意专利的**固有局限**：

- 专利是**公开换取保护**，所以文字是真的，但权利要求会写得尽量**上位和宽泛**，实施例往往是泛化描述（"在一个实施例中，可使用方差作为活动性度量……"），**不会给出 NVENC 的实际参数值**。
- 你几乎不可能从专利里复现出 NVENC。但你能从中拿到**算法族的候选名单**——比如确认"确实用 activity 驱动的 QP 偏移""确实有分层 ME"，从而把 `[推测]` 升级成 `[专利有载]` 但仍不是 `[NVENC 实测]`。
- 专利公开 ≠ 可以实施。有专利保护意味着要授权，不是"免费技术文档"。

### 3.2 学术黑盒测量 —— 我上一轮 `[实测]` 档的真正来源

这是研究者最常用的路，而且完全合法：**跑码流，分析码流**。

### 3.3 逆向（固件/驱动）—— 法律灰色，不建议

- `nvEnc` 固件是**签名二进制**，随驱动下发。反汇编在技术上可行，但 NVIDIA 的 SDK/驱动 EULA 通常明确禁止反向工程，且各地法律态度不同。
- **开源驱动帮不上忙**：nouveau / nova 之所以无法还原编码器逻辑，正是因为**编码不是驱动做的**——驱动只是把命令和固件交给硬件。这是理解 NVENC 架构的一个关键事实：**开源驱动的不透明性本身证明了编码逻辑在固件+硅里，不在驱动里。**

### 3.4 die shot / 芯片剖析 —— 能看到"有多大"，看不到"怎么算"

TechInsights 之类的剖析能给出 NVENC 模块面积、SRAM 容量估算。这能量级验证（比如"这块面积装不下全分辨率全搜索"），但给不出算法。

## 四、一个被忽略的关键点：**比特流是公开标准，所以黑盒逆向信息量极大**

这是我觉得最实用的一条，也是我上一轮结论的实际依据：

> H.264/HEVC/AV1 的**语法**是完全公开的标准。NVENC 输出的码流，你可以 100% 合法地解析出：
> - 每个 CTU 的**划分深度**（`split_cu_flag`）→ 直接观察它的四叉树遍历结果
> - 每个 PU 的 **MV 和参考帧**→ 直接观察它的 ME 结果
> - 每个 CU 的 **QP**（`cu_qp_delta`）→ 直接观察它的 AQ 分配粒度（是行级？CTU 级？）
> - 每种模式的**比特占比** → 反推代价模型偏好

所以"硬件怎么遍历 CTU"这个问题，**不需要看硬件，看输出就能反推 80%**。举几个具体可做的实验：

```text
实验 A（AQ 粒度）：固定码率编码一个 50% 平坦 + 50% 纹理的合成图，
   dump 每个 CTU 的 QP，看它是逐 CTU 变化还是逐行/逐 slice 台阶变化
   → 直接判定 AQ 的作用粒度

实验 B（遍历策略）：编码全静止画面（理想 skip 场景），
   统计 split_cu_flag 分布
   → 若一个 64x64 都不 split，说明有强剪枝 + skip 优先
   → 若出现大量非最优 split，说明剪枝是"自顶向下"式的

实验 C（ME 图样）：编码纯平移 + 小物体，dump MV 场，
   看 MV 是否呈"块状一致"（金字塔粗搜的痕迹）还是"逐块精细"
   → 能间接判断金字塔层数和细化范围

实验 D（代价模型）：编码极低码率，看是否出现 RDOQ 特征
   （量化系数是否被"清尾"优化）
   → 判定有无 trellis
```

**这就是我上一轮那些"实测"结论的来源方式**——不是看 NVIDIA 文档，是看它的输出。这也是学术界做硬件编码器质量研究的通用方法论。

## 六、想深挖的操作建议

<details>
<summary><b>展开：按投入产出比排序的路径</b></summary>

1. **先读 `nv-codec-headers`**（半天）。字段名是最硬的证据，成本最低。重点看 `NV_ENC_RC_PARAMS`、`NV_ENC_CONFIG_H264/HEVC/AV1`、`NV_ENC_PIC_PARAMS`。
2. **读官方 Programming Guide 的 feature 矩阵**（几小时）。能划出"哪些能力在哪一代有"，把代际差异钉死。
3. **做 §四 的 A/B/C/D 四个实验**（几天）。这是唯一能拿到"NVENC 实证"的方法，也是学术论文的做法。工具：`ffmpeg` + 自己写个 HEVC/H.264 语法解析器（或 `HM`/`dav1d` 的解析模式）。
4. **搜专利**（Google Patents，assignee: NVIDIA，关键词 rate control / adaptive quantization / hardware encoder）。用来验证算法族的存在性，别指望拿到参数。
5. **读学术界的硬件编码器评测论文**。做 BD-rate + 逐块 QP/MV 统计对比 NVENC vs x264/x265 的论文不少，直接给你实测数据。
6. **不要碰的方向**：反汇编签名固件、逆向驱动。技术上没壁垒，法律上是 EULA 雷区，且对理解算法帮助远小于 §四。

</details>

---

**一句话总结**：NVENC 的**接口是公开工程**，**算法和微架构是商业机密**，中间隔着一层"可以合法用黑盒码流分析去逼近"的地带。你问的那四块，NVIDIA 文档里确实一个字都没有——但它们并非不可知，只是**只能从输出反推，不能从文档查到**。我上一轮的价值在于给出了一套自洽的架构解释，而它的证据强度，诚实地说：API 层的事实是硬的，公式和遍历方案是软的。
