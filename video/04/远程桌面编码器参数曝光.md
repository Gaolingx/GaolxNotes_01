# 远程桌面编码器参数曝光

## 🧑‍💻 User

remote desktop开发中，qmin / qmax、qp_cb_offset / qp_cr_offset、strict_gop到底要不要暴露让用户调整

---
## 😀 默认助手 (7)

下面按“**该不该让终端用户拧这个旋钮**”来拆，而不是“这个参数技术上能不能调”。核心原则一句话：

> **暴露 intent（画质/延迟/带宽的意图），不要暴露 mechanism（QP、offset、GOP 这些编码器内部机制）。**

---

## 先给结论

| 参数 | 终端用户可调？ | 建议暴露层级 | 一句话理由 |
|---|---|---|---|
| `qmin` / `qmax` | ❌ 不直接给 | 专家面板 / 配置文件；或折算成“画质档位” | 与码控耦合，用户乱调会码率爆炸或画面糊 |
| `qp_cb_offset` / `qp_cr_offset` | ❌ 绝不 | 内部默认 / OEM 调优 | 色度感知极不直观，99% 场景应固定 |
| `strict_gop` | ⚠️ 不直接给 | 传输层策略，非用户项 | 是错误恢复/兼容性策略，不是画质选项 |

---

<details>
<summary><b>qmin / qmax —— 该不该暴露</b></summary>

### 它到底在干什么
QP（量化参数）是码控的质量-码率杠杆。`qmin/qmax` 只是给码控**加了个上下限钳位**：

- `qmax` 太低 → 高复杂度画面时被迫用大量码率，CBR 下超出目标 → 拥塞、丢帧/卡顿
- `qmax` 太高 → 桌面文字/UI 被量化得模糊、发虚（远程桌面最忌讳这个）
- `qmin` 太低 → 静态画面时码率冲高（远程桌面大量静止帧，这个尤其危险）

### 为什么不该直接暴露
1. **和码控打架**：用户设 `qmax=20` 想“要清晰”，但码率上限没动，码控满足不了上限 → 要么破坏帧率，要么突破带宽。两个旋钮耦合，用户只拧一个是灾难。
2. **画质感知非单调**：桌面场景里，文字清晰度对 QP 很敏感，但用户无法把“糊”映射到 QP 数值。
3. **支持成本**：出了画质问题，你无法判断是网络还是用户把 `qmax` 拧到 51 了。

### 该怎么暴露
- **终端用户**：给 `画质档位`（如 流畅/标准/高清/无损），内部映射到一组 `qmax` + 码率目标。典型映射：

| 档位 | qmax 建议 | 说明 |
|---|---|---|
| 流畅 | ~40–45 | 省带宽，可容忍文字发虚 |
| 标准 | ~32–36 | 桌面文字基本清晰 |
| 高清 | ~26–30 | 需更高码率 |
| 近无损 | ~20–24 + 码率下限保护 | 必须同时提高码率上限，否则卡 |

- **管理员/集成商**：可暴露 `最小画质下限`（即 `qmax`）作为“带宽保护”，但要**只暴露 qmax 一个方向**，`qmin` 保持内部。
- **专家/调试**：放进隐藏高级面板或配置文件，并在 UI 上标注风险。

</details>

<details>
<summary><b>qp_cb_offset / qp_cr_offset —— 该不该暴露</b></summary>

### 它到底在干什么
它给**色度平面**（Cb / Cr）的 QP 加一个相对亮度的偏移。也就是：亮度用好码率，色度可以糙一点（人眼对色度分辨率本就不敏感）。

### 为什么不该暴露
1. **桌面内容色度几乎是平的**：文字/窗口大量是黑灰白，Cb/Cr 变化极小。你把色度 QP 偏移调高，视觉上大概率**看不出来**；调低则纯浪费码率。
2. **感知极不直观**：没人能说出“我想让 Cb 的 QP 比 Y 高 3”对应什么画面效果。
3. **强内容/色彩空间相关**：4:2:0 vs 4:4:4、BT.601 vs 709、是否有 SCC 色彩工具，都会影响最优值。这属于编码器/预置档该自动决定的东西。

### 该怎么暴露
- **默认固定为 0**（或跟随编码器推荐值）。
- 只在**固化预设**里按色彩空间/子采样调整。
- 真要给，也只进 OEM/配置文件，给做色彩敏感行业（如医疗影像、设计）的集成商，不进交互 UI。

</details>

<details>
<summary><b>strict_gop —— 该不该暴露</b></summary>

### 它到底在干什么
强制 I 帧（关键帧）严格按配置的 GOP 长度/关键帧间隔出现，**关闭基于场景切换的自适应插入**（`strict_gop=0` 时编码器可按内容动态插入或调整 I 帧）。

- `strict_gop=1`：关键帧间隔可预测，错误恢复/新加入端体验可预测，但**静态桌面会周期性浪费 I 帧码率**。
- `strict_gop=0`：省码率、更高效，但关键帧时机不可预测。

> 注意：不同编码器语义有差异（NVENC `strictGOP`、QSV、x264 的 `scenecut`/`keyint_min` 组合），别假设完全等价。

### 为什么不该作为用户选项
它是一个**传输/错误恢复策略**，不是画质偏好：
- 它决定的是“**网络抖/丢包时多久能恢复**”和“**新端多久能出画面**”，这应该由**会话/传输层**根据网络状况决定。
- 用户没能力判断该开还是该关。

### 该怎么暴露
- **不要作为用户项**。由应用内部根据传输协议（RTP/WebRTC、是否需等距关键帧）自动设置。
- 若要给管理员控制，暴露**“关键帧间隔（秒/帧）”**这一 intent，内部再决定 strict 与否。
- 弱网场景可暴露一个 `周期性关键帧`（稳定恢复）开关，而非赤裸的 `strict_gop`。

</details>

## 落地建议：三层暴露模型

```text
L1 终端用户（意图层）
  ├─ 画质档位（流畅/标准/高清/近无损）  → 内部映射 qmax + 码率目标
  ├─ 带宽上限 / 帧率上限
  └─ 延迟模式（低延迟 / 均衡）

L2 管理员 / 集成商（策略层）
  ├─ 码率、帧率、编码器、色度格式、GOP 长度/关键帧间隔
  ├─ 最小画质下限（= qmax 单向暴露，防糊）
  └─ 周期性关键帧开关（弱网稳定用）

L3 专家 / 调试（机制层，隐藏或配置文件）
  ├─ qmin / qmax 完整范围
  ├─ qp_cb_offset / qp_cr_offset
  └─ strict_gop 等编码器原生开关
```

**判断某个参数放哪一层的三个问题：**

1. 用户能否用**画面/网络的可观察结果**描述它？（否则不进 L1/L2）
2. 拧错它是**降低体验**还是**直接把会话拧坏**？（会拧坏 → 越靠下）
3. 它是否和另一个参数**强耦合**、必须成对调？（是 → 折叠成一个档位，别拆成两个旋钮）

对你这三个参数：`qmin/qmax` 和码率强耦合 → 折叠成档位；`qp_*_offset` 感知不可见 → 封进预置；`strict_gop` 是策略 → 交传输层。

**一句话收尾：默认值要能在 90% 场景下“不用调就够好”；旋钮留给那 10% 里既懂原理又能承担后果的人，而且尽量收敛成更少的 intent 控件。**
