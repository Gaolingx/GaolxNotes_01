# Sunshine(RTSP/RTP)对比 WebRTC 类商用远控的短板

## 结论先行

Sunshine 的 RTSP 握手 + RTP/UDP 媒体,本质是一套**"媒体分发 + 会话控制"协议**,它的隐含前提是:**客户端能直接路由到主机**。向日葵 / ToDesk 这类方案真正的护城河并不是"用了 WebRTC",而是 WebRTC 背后的整套公网实时通信设施:

- **ICE / STUN / TURN** —— 自动打洞 + 云端中继兜底
- **GCC / transport-cc + pacer** —— 动态带宽估计与拥塞控制
- **NACK / RTX / FEC / SVC** —— 抗丢包与分层自适应
- **DTLS-SRTP** —— 强制端到端加密
- **浏览器原生解码** —— 免安装客户端

所以差距不在"RTSP 这个协议好不好",而在两个层面:**连接可达性**和**弱网自适应能力**。下面按重要性排序。

---

## 核心差距总览

| 维度 | Sunshine(RTSP + RTP/UDP) | WebRTC 类(向日葵 / ToDesk) | 实际影响 |
|---|---|---|---|
| 连接模型 | 主机即服务器,需被直接访问 | 双端 + 信令 + ICE,对等/中继 | **最致命** |
| NAT 穿透 | 无 STUN/TURN,需端口映射或 VPN | 自动 hole punching + TURN | CGNAT / 对称 NAT 下直接不可用 |
| 端口需求 | 多个:`47984/47989/47990/48010` TCP + `47998–48002` UDP | ICE 单端口复用(BUNDLE)+ 443 中继 | 企业防火墙几乎必然拦掉 Sunshine |
| 中继回退 | **无** | TURN 中继,一定能连上 | Sunshine 打不通就是打不通 |
| 拥塞控制 | 无,固定码率 | GCC + transport-cc + 平滑发送 | 共享链路 / 4G 上 Sunshine 要么卡要么顶满 |
| 丢包恢复 | FEC 固定百分比,无重传 | NACK + RTX 重传 + 自适应 FEC | 丢 1 个包 = 一个色块,直到 I 帧 |
| 码率自适应 | 手动设定,不随网络变 | 实时探测并动态降/升 | 移动网络下体验差距明显 |
| 分层编码 | 无 simulcast / SVC | VP9/AV1 SVC 或 simulcast | 无法一次编码多档适配不同终端 |
| 会话迁移 | 换网即断,需重连 | ICE restart,WiFi↔LTE 无缝 | 移动端体验差距大 |
| 安全模型 | 可选加密,取决于配置 | DTLS-SRTP 强制、每次会话密钥 | 默认安全等级不同 |
| 客户端形态 | 必须装 Moonlight 原生客户端 | 浏览器 / 小程序即可 | 分发与接入成本 |

---

## 一、最致命:连接可达性

Sunshine 是**直连模型**:RTSP 服务监听在 `48010/TCP`,媒体走 `47998–48002/UDP`。它没有任何 NAT 穿透机制——没有 STUN 去发现公网映射,没有 ICE 去尝试多条候选路径,没有 TURN 做兜底。结果是:

- 同一局域网:完美,延迟极低
- 有公网 IP + 端口转发:可以,但暴露端口有风险
- **CGNAT(家宽/移动网络)、对称 NAT、双层 NAT、企业防火墙:直接失败**

向日葵 / ToDesk 的流程是「信令服务器交换候选地址 → ICE 打洞 → 失败则走 TURN 中继」。这带来两个 Sunshine 完全没有的能力:

1. **"任何网络都能连"** —— 中继是保底,不依赖运气
2. **单端口 + 443 回退** —— TURN over TCP/443 看起来就是 HTTPS,能穿过绝大多数企业网络

Sunshine 的多端口 UDP 特征在防火墙眼里也非常显眼,容易被 DPI 或端口策略直接掐断。

---

## 二、没有带宽估计与拥塞控制

这是体验层面差距最大的一点。

Sunshine 的码率是**客户端手工设定**的固定值,主机按这个速率**只管发**。它不探测链路容量,不因丢包/延迟升高而降码率,不做平滑发送。典型后果:

- 起步瞬间突发丢包(没有 pacing,没有 startup ramp)
- 4G / 弱 WiFi 上,要么设太低糊,要么设太高持续丢包花屏
- 在共享链路上不友好,容易制造 bufferbloat

WebRTC 则有完整的闭环:延迟梯度/丢包驱动的 GCC、transport-cc 反馈、pacer 平滑发包、probe 探测上限。码率是**跟网络实时协商出来的**,而不是拍脑袋填的。

端到端延迟可以粗略拆成:

$$L_{e2e} = L_{capture} + L_{encode} + L_{network} + L_{jitter} + L_{decode} + L_{display}$$

Sunshine 在 LAN 上把 $L_{jitter}$ 压到很低(几乎没有抖动缓冲),这是它局域网延迟能压到十几毫秒的原因;但代价就是**没有任何缓冲来吸收网络抖动**,一旦上公网,$L_{network}$ 的波动会直接变成卡顿。

---

## 三、抗丢包能力弱

WebRTC 有三级防线:**NACK 重传 → RTX 独立流重传 → (U)LPFEC / FlexFEC 前向纠错**,再加自适应抖动缓冲。Sunshine/Moonlight 协议只有**固定百分比的视频层 FEC**,没有 NACK 重传机制。

区别在于:

- 丢的是可重传的包 → WebRTC 补回来,**画面无损**;Sunshine 只能等下一个 I 帧或靠 FEC 覆盖,覆盖不到就是糊/花
- FEC 是固定开销,意味着有效带宽被固定吃掉一块:

$$B_{eff} = \frac{B}{1 - f_{fec}}$$

`f_fec` 设高了浪费带宽,设低了弱网顶不住,而它**不会自动调**。

另外 WebRTC 支持 VP9/AV1 的 SVC 空间/时间分层,弱网时直接丢顶层而保住基础层;Sunshine 单层编码,降级只能整条流重来。

---

## 四、会话无法迁移

RTSP 会话绑定在具体的 socket / 五元组上。手机从 WiFi 切到 4G、笔记本休眠唤醒、路由器换 IP——Session 直接失效,必须重新 DESCRIBE / SETUP / PLAY 走一遍完整握手。

WebRTC 有 **ICE restart**:底层连接断了可以在同一会话内重新协商候选地址,上层应用无感知。对移动端和长时间挂机场景,这是刚需。

补充一个细节:Sunshine 的控制通道跑在 RTSP 的 TCP 上,**单点故障 + 队头阻塞**——这条 TCP 一卡,整场会话的控制指令(按键、请求关键帧)都跟着卡。WebRTC 把控制放 SCTP over DTLS data channel,和媒体共享 ICE 传输但互不阻塞。

---

## 五、安全模型默认不同

WebRTC 强制 **DTLS-SRTP**,每次会话协商临时密钥,证书指纹通过信令绑定,并具备前向保密。Sunshine 的加密是**配置项**:可以启用 TLS / 加密控制流,但媒体是否加密、证书怎么配,取决于部署者,很多自建场景干脆是裸奔的。从"默认安全"的角度,两者不在一个量级。

---

## 六、客户端生态

- WebRTC 意味着**浏览器即客户端**:免安装、跨平台、可分享链接、可被现有 Web 基础设施复用(录制、SFU、转码)
- Sunshine 必须配套 Moonlight 原生客户端;手机端、电视端各有各的安装包

对"帮我连一下我爸妈电脑"这种场景,免安装的价值极大。

<details>
<summary><b>七、为什么"给 Sunshine 加个配置"救不了 —— RTSP/RTP 的协议层先天限制</b></summary>

- **RTSP 是文本式请求-应答的会话协议**,设计目标是 IPTV / 媒体服务器点播,不是交互式 NAT 穿透。SETUP / PLAY 是重握手,中途改码率、改分辨率、改编码没有标准化的再协商流程
- **RTP 只管送达,不管可靠性和拥塞**:可靠性要靠 RTCP 反馈(PLI / NACK / REMB),而 Sunshine 只用了其中很小的子集,既没有重传也没有带宽估计
- **BUNDLE / 端口复用**是 WebRTC 的概念,RTSP 天然多端口;如果把媒体塞进 RTSP 的 TCP interleaved 模式,又会引入队头阻塞,对实时画面是灾难
- **没有 simulcast / SVC 的信令标准**,无法一次编码多档
- **没有 ICE**,所以补 NAT 穿透等于在协议之外再造一个 WebRTC

换句话说,要补齐这些,基本就是**换成 WebRTC 或自研 UDP 实时栈**,而不是调参数。

</details>

<details>
<summary><b>八、公平起见:Sunshine 反而更强的地方,以及现实补救方案</b></summary>

**Sunshine 的优势必须承认:**

- **局域网延迟更低**:无抖动缓冲、无拥塞控制开销,配合 NVENC/AMF/QSV 低延迟档,同网下比 WebRTC 方案低不少
- **画质规格更高**:4K/120、HDR、高码率、5.1 声道,面向游戏而生;商用远控通常为保连通性牺牲画质
- **完全自托管、无云端依赖**:隐私可控,无时长/并发限制,无广告

**现实中的通行补救做法:**

| 缺口 | 补救方案 |
|---|---|
| NAT 穿透 | Tailscale / ZeroTier / WireGuard 组网,让主机"看起来在同一局域网" |
| 中继兜底 | 自建或使用 VPN 的 DERP 中继(如 Tailscale DERP) |
| 弱网自适应 | 无解,只能手动降码率 / 分辨率 |
| 会话迁移 | 无解,依赖 VPN 层重连 |

**一句话定性**:Sunshine 是"**同网 / 有可达网络下的低延迟高画质游戏串流**";向日葵 / ToDesk 是"**任意网络下的高鲁棒性通用远控**"。前者的短板是公网可达性与弱网鲁棒性,后者在局域网延迟和画质上限上反而打不过 Sunshine——这是两种不同的设计取舍。

</details>

---

## 收尾

如果你要把 Sunshine 用于**跨公网、移动网络、企业网络**,RTSP 这套架构的短板会依次暴露:**连不上 → 连上也不稳 → 稳也怕断线换网**。这三个问题分别对应 ICE/中继、拥塞控制与抗丢包、会话迁移——恰好就是 WebRTC 相对 RTSP 最有价值的三块。用 VPN 覆盖层能补上第一块,后两块在协议层面基本无解。
