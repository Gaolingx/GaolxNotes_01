# 4G丢包场景下nonRefP无法避免整体变糊

## 🧑‍💻 User

nvenc enableNonRefP为什么感觉不能提高画质，也不能省码率（VBR）

---
## 😀 默认助手 (7)

## 简短回答

`enableNonRefP` 的本质是**给编码器的 GOP 结构增加一条约束**，并不是提高编码效率的功能。它在 NVIDIA 文档里归属 **“错误恢复/低延迟”** 特性，不在“画质/码率”那一类。所以在 VBR 下观察不到画质提升、也省不下码率，是**符合预期**的。

---

## 1. 它到底做了什么

设某帧为 $n$，其在参考链上的“后代帧数量”为 $w_n$。总失真近似为

$$D_{\text{total}} \approx \sum_n w_n D_n$$

普通 P 帧 $w_n>1$（它的失真会传播到后续依赖它的帧），所以码控不敢把 QP 抬太高。标记为 non-ref 后 $w_n=1$，失真不再传播，**码控就可以合法地把这帧 QP 调高**，也就是“这帧可以糊一点”。

关键点：**这个标志只提供“可以更狠地压这帧”的许可，并不会自动产生任何压缩增益。** 更准确地说，它是 RD 优化中的一个**约束**：

$$J = D + \lambda R \quad\xrightarrow{\text{加约束}}\quad \min J \ \text{在} \ \{n \notin \text{RPS}\} \ \text{下}$$

约束只会让可行集变小，所以单帧 RD 最优解只可能**变差或不变**。它唯一的价值是“给码控松绑”，让本来被传播代价压住的 QP 得以放开。

---

## 2. 为什么 VBR 省不下码率

<details>
<summary><b>四个叠加原因（点开）</b></summary>

**① VBR 的核心机制就是“把省下的比特花回去”。**
VBR 追的是时间窗口内的平均码率 $\bar R$。你在第 $n$ 帧省了 $\Delta R$，码控（buffer fullness 反馈）会在后续帧把这笔额度花掉，否则平均码率就低于目标。**结果是总比特几乎不变，只是分布变了**——而分布变化的幅度又受 QP 上下限（`minQP`/`maxQP`）和 VBV 约束。

**② 生效的帧占比本来就小。**
`enableNonRefP` 是“允许/自动插入”，插入频率是内部启发式决定的，通常只是 GOP 里少数几帧。假设 1/8 的帧是 non-ref，每帧省 15% 比特：

$$\frac{1}{8}\times 15\% \approx 1.9\%$$

再被码控重分配掉，实测基本落在噪声里。

**③ 目标码率没有处于紧约束状态时，等于无效。**
如果你设的 `-b:v` 远高于内容自然所需（码控长期贴着 QP 下限跑），或在纯质量模式下（CQ/`-cq`），码率约束根本没在起作用 → 这个标志的影响是**零**。这是最常见的原因。

**④ 丢一个参考是有代价的。**
non-ref 帧不能被后续帧引用，等于**减少了一个候选参考**，后一帧的预测变差、比特上升。省下的（抬 QP）和赔掉的（预测变差）大致抵消，净收益趋近 0，甚至为负。

</details>

---

## 3. 为什么画质不涨

- 上面第 ④ 点：RD 上是**零和或负和**，同码率下 PSNR/SSIM/VMAF 一般持平或略降。
- **B 帧已经把这个思路做得更好**。金字塔 B 帧（`-bf` > 0）本身就是“便宜的、不被引用的中间帧”，压缩效率远高于“IPPP 里插 non-ref P”。开着 B 帧时，这个标志往往**被忽略或几乎无效**——它是“B 帧不可用时的穷人替代品”（超低延迟场景）。
- **AQ 已经覆盖了同一块收益**。`spatial-aq` / `temporal-aq` + `aq-strength` 做的正是“按传播价值分配 QP”，而且是在整条 GOP 上全局优化的，比逐帧标记精细得多。
- 你对“画质”的观感来自**连续、平滑的失真分布**。non-ref P 会让个别帧 QP 明显跳高 → 反而可能出现**局部帧质量起伏/闪烁**，主观上更像“变差”。

---

## 4. 它真正有用的场景

| 场景 | 价值 |
|---|---|
| 有丢包的网络 / RTP 传输 | 断链不会一路糊下去，错误不传播 |
| 超低延迟（禁用 B 帧、禁用 lookahead） | 唯一的“便宜帧”手段 |
| 需要周期性随机接入点 | 可做轻量参考刷新，替代完整 IDR（省 I 帧码率） |
| 需要限制 DPB / 降低解码端参考压力 | 减少参考帧管理 |

注意最后一条：**用 non-ref P 替代频繁 IDR 来刷新参考**，这才是它可能真正省码率的地方——但它省的是 I 帧开销，不是 P 帧开销，而且会被 `intra-refresh` 覆盖。

## 5. 想真的提画质/省码率，按收益排序

```
1. -rc vbr -cq 23 -b:v 0        # 让 RC 在真正起作用的区间跑
2. -rc-lookahead 32 (或 20+)    # 收益最大的单项
3. -multipass fullres
4. -bf 4 -b_ref_mode middle     # 金字塔参考
5. -spatial-aq 1 -aq-strength 8 / -temporal-aq 1
6. -maxrate / -bufsize 收紧     # 让 VBR 真正被约束
7. -tune hq / -preset p6-p7
```

`enableNonRefP` 不在这张表里。它的位置在“错误恢复”那一栏。

---

## 6. 先确认它是不是真的生效了

这一步经常被跳过，而结论很有可能是**这个标志根本没起作用**：

```bash
# 1) 确认参数被接受（有些封装会把未知选项吞掉）
ffmpeg -h encoder=hevc_nvenc | grep -i nonref

# 2) 确认码流里真的出现了 non-ref 帧
#    H.264: 找 nal_ref_idc == 0 的 slice
#    HEVC : 解析 slice header，看该帧是否被后续帧列入 RPS
ffprobe -show_frames -select_streams v -show_entries frame=pict_type,key_frame out.mp4
```

- H.264 里 non-ref P 的判据是 **`nal_ref_idc == 0`**；HEVC 里看该 POC 是否出现在后续帧的 RPS/RefPicList 中。
- 如果**帧序列里一个 `nal_ref_idc=0` 的 P 都没有**，那就是驱动/编码器静默忽略了该 flag（常见于：该 codec 不支持、驱动版本、与 B 帧/temporal SVC 冲突、或需要特定 `frameIntervalP`）。
- 换个角度验证：同码率下跑 PSNR/VMAF，若差值 < 0.1 dB，那它在你的配置下**客观上就是没有作用**，不用再纠结调参。

---

## 一句话结论

`enableNonRefP` 是**错误恢复与延迟特性**，作用对象是“失真传播”，不是“信息量”。VBR 会把任何帧级节省重分配回平均码率，而它本身又在 RD 上引入约束、拿走一个参考——所以“不省码率”是码控的工作方式决定的，“不提画质”是 RD 约束决定的。要用它，请在有丢包或超低延迟 IPPP 的场景下用；要画质和码率，请去动 lookahead / B 帧 / AQ / VBR 约束这四件事。

## 😀 默认助手 (7)

## 结论

**不能。** 你这两个条件放在一起，恰好把 `enableNonRefP` 仅存的两种理论收益都限制住了：

- **120ms 的 VBV 太小** → 省下的比特在 3~4 帧内就被 RC 花回去，无法形成长期积累；
- **滚屏内容是“相邻帧参考价值最高”的极端情况** → 拿掉一个参考后，下一帧的码率开销上涨，甚至超过省下的部分。

而且在滚屏场景里，多出来的这点收益会被**文本质量的抖动**抵消，主观上更差。

---

## 1. 120ms VBV 的量化后果

设目标码率 $R$、帧率 $f$、VBV 时长 $T_{vbv}=0.12\,\text{s}$：

$$B = R \cdot T_{vbv}, \qquad N_{buf} = f \cdot T_{vbv}$$

| 目标码率 | 帧率 | 缓冲大小 $B$ | 可吸收帧数 $N_{buf}$ |
|---|---|---|---|
| 6 Mbps | 30 | 720 kbit ≈ 90 KB | **3.6 帧** |
| 6 Mbps | 60 | 720 kbit | **7.2 帧** |
| 15 Mbps | 60 | 1.8 Mbit | 7.2 帧 |

而 1080p30 的滚屏内容，单帧比特分布是**双峰**的：

- 静止文档帧：$5\sim20$ kbit
- 滚屏中的帧：$200\sim600$ kbit（文本全屏位移，ME 只能给出全局向量，残差仍很大）

也就是说，**一帧滚屏 ≈ 30 倍平均帧预算**。$N_{buf}=3.6$ 意味着：

$$\text{一帧滚屏} \gg B/2 \quad\Rightarrow\quad \text{RC 必须立刻提高 QP 摊还}$$

所以这个 VBV 下，编码器的 QP 反馈几乎是**逐帧局部**的。它的“时间常数”就是 120ms。你在第 $n$ 帧省下的 $\Delta R$，在 $n+1 \sim n+4$ 帧内必然被花掉，否则平均码率就低于目标。

$$\bar R = \frac{1}{T}\int R(t)\,dt \ \text{固定} \quad\Rightarrow\quad \sum \Delta R_{\text{nonref}} + \sum \Delta R_{\text{rest}} = 0$$

**它无法累积，只能改变比特分布。** 这正是上次说的机制，只是 VBV 越小，机制生效得越快、越彻底。

## 2. 为什么偏是滚屏场景不行

<details>
<summary><b>三个独立理由（点开）</b></summary>

**① 参考价值在这里是最高的，不是最低的。**
`enableNonRefP` 的收益模型是“$w_n$ 小的帧可以狠压”。$w_n$ 是**码流拓扑**上的后代数。但滚屏时相邻帧是**全局平移**关系，时间上最近的参考帧预测残差最小。把它从 RPS 里去掉，下一帧只能拿更远的帧做参考 → 残差变大 → **下一帧比特上升**。

省的是“抬 QP 省下的”，赔的是“预测变差的”，而后者在滚屏里通常是前者的大头。这就是为什么上次说“净效应 ≈ 0 或为负”，**而滚屏是“为负”的那一端**。

**② $w_n$ 和“感知重要性”在这里是脱钩的。**
滚屏时，观众视线跟着文本走，**画面正在动的那几帧恰恰是唯一被认真看的帧**。对它们抬 QP 换来的“拓扑上无损”，在观感上是文本边缘发虚、笔画粘连。指标（$w_n$）对了，感知权重错了，优化的是错的目标。

**③ 会和 RC 自己的高频调节互相冲突。**
120ms VBV 下 QP 本来就在剧烈波动（为了摊还滚屏突发）。再叠加一个 **GOP 级的启发式插帧策略**，两种不同时间尺度的控制叠在一起 → 表现为文本**清晰/模糊周期性抖动**（quality pumping）。这比“平均 QP 高 1 点”难看得多。

</details>

---

## 3. 真正的瓶颈：双峰码率对不上 120ms 缓冲

滚屏内容的理想码控是**长时间积累、短时间透支**：静止期攒下大量额度，滚屏期一次性花掉。这需要的缓冲量级是：

$$T_{vbv} \gtrsim \text{一个完整滚屏动作的时长} \approx 0.5\sim2\ \text{s}$$

你给了 120ms，等于**禁止积累**。结果是每个滚屏突发都被 QP 尖峰强制削掉。这个损失远大于任何 flag 能带来的收益——量级上差一两个数量级。

所以先问清楚：**120ms 是硬性要求吗？**

| 场景 | 可否放宽 VBV | 做法 |
|---|---|---|
| 录制 / 文件输出 | ✅ 完全可以 | `-bufsize` 提到 1~2 秒等效值，`-maxrate` 只做上限 |
| 云桌面 / 串流，有端到端延迟预算 | ⚠️ 可以适度 | 缓冲只影响**发送端 HRD 等价延迟**，不影响编码器本身延迟；非严格 CBR 链路上 300~500ms 通常可接受 |
| 严格 CBR over 网络（真有 HRD 约束） | ❌ | 只能靠降分辨率/降帧率换，flag 无用 |

## 4. 翻文档 / 滚屏 的实际优化项（按收益排序）

```bash
# 起点：屏幕内容不要用"平均码率 VBR + 小 VBV"
-rc vbr -cq 26 -b:v 0 -maxrate 12M -bufsize 24M      # 质量优先 + 只封顶
#   或纯 CQP：
-rc constqp -qp 28 -maxrate 12M -bufsize 12M

-fps 30                                              # 60→30，省 ~40%，文档滚屏几乎无感
-pix_fmt yuv444p -profile:v rext                     # ★ 文本边缘，性价比最高的一项
-g 240 -bf 3 -b_ref_mode middle                      # 滚屏利于 B 帧双向预测
-spatial-aq 0                                        # 文本/UI 场景 AQ 常帮倒忙
-tune hq -preset p6 -multipass fullres
-rc-lookahead 20                                     # 主要用来提前发现滚屏开始
```

<details>
<summary><b>为什么 4:4:4 比任何 flag 都值（点开）</b></summary>

4:2:0 下文本色度被水平和垂直各减半采样，细笔画（1~2px）直接丢色度信息，这是文档场景“糊”的**首要原因**，和码率关系不大——你给到 20 Mbps 也一样糊。Ampere 及以后的 NVENC 支持 HEVC 444（`rext` profile），**同码率下文本可读性提升明显**，这是本题里唯一“花小钱办大事”的开关。

代价：444 不被部分硬件解码器/浏览器支持，需确认播放链路。

</details>

**硬件编码器的固有短板，无法靠参数绕过**：HEVC/AV1 的**屏幕内容编码工具**——Intra Block Copy（IBC）、Palette（调色板模式）、transform skip——NVENC 全都不支持，AV1 硬件编码器目前也不带。而滚屏文本恰恰是 IBC 收益最大的内容（滚屏后大量块是“从上一帧同位置平移来的”，IBC/调色板能给出接近 0 比特的编码），软件编码器上通常有 **15~30%** 的码率节省。

如果你在 6~8 Mbps 下还是不满意，**这不是调参问题，是编码器选型问题**：

- **SVT-AV1**：`--scm 2`（screen content mode，含 IBC + palette），文件/录制场景首选
- **x265**：mainstream 无 SCC；需要 SCC 扩展构建才有效，实际支持一般
- NVENC 留作实时链路，高质量归档走软件编码

---

## 一句话

`enableNonRefP` 在 120ms VBV 下省不下码率（省下的 4 帧内就被花掉），在滚屏内容上还会**亏**（相邻帧参考价值最高，拿掉参考的代价大于抬 QP 的收益），并且大概率带来文本清晰度的周期性抖动。要改进的话，优先改三件事：**放宽 VBV 到能覆盖一次完整滚屏、上 4:4:4、降帧率**；如果要再上一层，换 SVT-AV1 的 `--scm 2`。

## 结论

**能帮，但完全帮不到你说的这个问题。**

`nonRefP` 减少的是**“一次丢包引发污染的概率”乘以 non-ref 帧的占比**；而你现在这个场景里真正需要降低的是**“污染持续的时间”**。在 2–10% 丢包下，系统已经进入**饱和态**——降概率几乎不会被感知到，只有降时长才有意义。

## 1. 先分清“丢”的三种形态

`nonRefP` 只对**第一种**有效，而且只对 non-ref 帧有效：

| 形态 | 现象 | nonRefP 有用？ |
|---|---|---|
| **整帧丢失**（参考帧被丢） | 后续帧全部引用不存在的帧 → 全局渐糊、直到下一个 IDR 才恢复 | ✅ 有效（仅限该帧是 non-ref 时） |
| **部分切片丢失**（最常见） | 帧内出现块状破损、局部花屏，但**继续正常传播**（因为该帧整体还是被解码了，破损内容成了参考） | ❌ 完全没用 |
| **迟到被丢**（jitter） | 抖动导致乱序超时 | ❌ 没用，加 jitter buffer |

**关键点**：2% 的**包**丢率不等于 2% 的**帧**丢率。设每帧 $k$ 个 RTP 包：

$$p_{\text{frame}} = 1 - (1-p_{\text{pkt}})^{k}$$

720p30 / 8 Mbps / 1200B MTU → $k \approx 23$：

| 包丢失率 | 每帧含至少一个丢包的概率 | 每秒受影响帧数（30fps） |
|---|---|---|
| 2% | **37%** | 11 帧/s |
| 10% | **91%** | 27 帧/s |

也就是说你的主导故障模式是**部分切片丢失 / 帧损坏**，而不是“干净地丢掉整帧”。这部分 `nonRefP` 一点忙都帮不上——因为破损帧仍然被解码、仍然进了参考，于是污染照样传播。

> 这就是为什么你会看到“整个画面变糊”：不是 non-ref 丢帧造成的，而是**破损帧当参考**造成的。

## 2. 饱和态论证：为什么降概率没用

设每次丢包引发的污染持续时间为 $\tau$，单位时间内的丢包事件数为 $\lambda$。系统处于“永久污染”的稳态当且仅当：

$$\lambda \tau \gtrsim 1$$

取 $G = 60$（2 秒 GOP），污染持续到下一个 IDR，则 $\tau \approx \dfrac{G}{2f} = 1\,\text{s}$，$\lambda = p_{\text{frame}}\cdot f$：

$$\lambda\tau = p_{\text{frame}} \cdot \frac{G}{2}$$

代入 $p_{\text{frame}} = 0.37$（2% 包丢率）：

| 配置 | $p_{\text{frame}}$ 有效值 | $\lambda\tau$ | 主观结果 |
|---|---|---|---|
| 原始 | 0.37 | **11.1** | 永久糊 |
| + `nonRefP`（$r=1/8$） | 0.32 | **9.7** | **永久糊（无区别）** |
| + `nonRefP`（$r=1/2$，激进） | 0.19 | **5.6** | 永久糊，但梯度更差 |
| + 短 GOP $G=30$ | 0.37 | 5.6 | 永久糊 |
| + intra-refresh $T_r=30$ | 0.37 | **5.6 → 但 $\tau$ 封顶 0.5s** | 糊→周期性自愈 |
| **降到 1% 包丢率** | 0.21 | 6.3 | 好转但仍不够 |
| **降到 0.1% 包丢率** | 0.024 | **0.72** | 可用 |

看第二行：$11.1 \to 9.7$，**降了 13%**。而 $\lambda\tau \gg 1$ 时，观感已经饱和在“一直糊”，13% 的降低完全落在不可感知区间。

**要跨过 $\lambda\tau \approx 1$ 这条线，你需要把它降低 10~100 倍。`nonRefP` 只能给你 1.1 倍的改善，差两个数量级。**

## 3. 真正有效的顺序

<details>
<summary><b>① 传输层（收益最大，先做这个）</b> — 点开</summary>

4G 上 2–10% 持续丢包，**90% 的情况是你在超发**。先做这个实验再谈编码器：

```bash
# 把码率砍一半，看丢包率是否掉到 <1%
```

如果掉到 <1% —— 问题就是码率过高，任何 flag 都无意义。然后：

- **NACK + 重传**（WebRTC 的 `rtcp-nack`，jitter buffer 覆盖 100~200ms）→ 能把 2% 包丢率压到实际残余 <0.1%
- **FEC**（FlexFEC / ULPFEC，10~20% 冗余）→ 对突发丢包有效
- **拥塞控制**（GCC / 自适应码率）→ 这才是 4G 场景的正解

做完这层，$\lambda\tau$ 通常已经跨过 1 了。

</details>

<details>
<summary><b>② 缩短污染时长 $\tau$（这是唯一能替代传输层的手段）</b> — 点开</summary>

- **intra-refresh**（NVENC SDK: `enableIntraRefresh` / `intraRefreshPeriod` / `intraRefreshCnt`）：把 $\tau$ 硬性封顶在 `intraRefreshPeriod`，且不像 IDR 那样有码率尖峰。这是针对“整体渐糊”最对症的开关。
  - ⚠️ ffmpeg 的 nvenc 封装**不一定暴露**这个 AVOption，可能需要直接走 NVENC API 或换封装。
- **短 GOP**（`-g 30~60`）：粗糙但有效，代价 5~15% 码率。$G=30$ 时 $\tau = 0.5$s。
- **LTR + 反馈恢复**（WebRTC 级别方案）：NVENC 支持 `ltrMarkFrame` / `NV_ENC_CAPS_NUM_MAX_LTR_FRAMES`。收到 PLI 后用 LTR 做快速重同步，**不需要 IDR**，$\tau$ 可压到 1~2 帧。这是工程上最优解。

</details>

<details>
<summary><b>③ 缩小单次丢包的爆炸半径</b> — 点开</summary>

- **切片化**（NVENC `sliceMode` / `sliceModeData`）：一帧切成 4~8 个 slice，丢一个包只坏 1/8 个画面，且未损 slice 仍能正常参与参考。这对 37% 的帧损坏率来说是**直接减伤**，比 `nonRefP` 有效得多。
- 配合 decoder 侧的 slice-level concealment。

</details>

<details>
<summary><b>④ `nonRefP` 的位置</b> — 点开</summary>

放在最后，且只在满足以下**全部**条件时才有价值：

- 有**整帧丢失**（而非切片丢失），例如切换/切换基站的突发丢包
- 无 B 帧（IPPP 低延迟），因为 non-ref B 帧已经天然提供了同样的隔离
- 无反馈通道（否则 LTR 完胜）
- 能接受 high-ratio 插入（$r \ge 1/4$），而那本身会损伤压缩效率，反而让“糊”更严重

它的真实定位是：**没有反馈、没有 FEC、必须 IPPP 的孤立场景下的兜底**。你的场景（4G + 持续丢包 + 大概率有 WebRTC 反馈通道）不在其中。

</details>

## 4. 一个重要的反向风险

在 **10% 包丢率**下，$p_{\text{frame}} \approx 91\%$。此时：

- 如果激进开 `nonRefP`（大量帧不参与参考），等于**主动放弃了时间冗余**，意味着几乎每帧都要靠帧内/近距预测重建 → **平均画质本身下降 2~4 dB**，码率上升。
- 丢包造成的 33ms 瞬时花屏，频率是 **27 次/秒** → 主观上比“稳定但偏糊”更难受（闪烁、抽搐感）。

**在 10% 丢包这个量级，编码器侧的微调全是负收益。** 正确做法是把链路修好，或者接受降分辨率/降帧率（720p→480p、30→15fps）来换可用的丢包率。

---

## 一句话

`nonRefP` 是降低**污染发生概率**的工具，而你身处 $\lambda\tau \gg 1$ 的饱和区——那里只有降低**污染持续时长**（intra-refresh / 短 GOP / LTR）和**减小丢包本身**（FEC / NACK / 降码率）才有意义。顺带提醒：2% 的**包**丢率对应 37% 的**帧**损坏，你的主导故障是破损帧继续当参考，`nonRefP` 对它零作用。
