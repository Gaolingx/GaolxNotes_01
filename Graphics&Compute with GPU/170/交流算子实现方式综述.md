# 先把概念理清：通信算子并没有"和 torch 绑一块"

torch 只是**前端/调度层**，真正干活的是后端通信库：

| 硬件/场景 | 后端库 | 归属 |
|---|---|---|
| NVIDIA GPU | **NCCL** | NVIDIA |
| AMD GPU | **RCCL** | AMD |
| CPU / 以太网 | **Gloo** | Meta |
| HPC 集群 | **MPI** (OpenMPI/MVAPICH) | 社区 |
| 昇腾 | **HCCL** | 华为 |

PyTorch 里的 `torch.distributed` 是一套 `ProcessGroup` 抽象，`NCCLProcessGroup` 之类只是**薄封装胶水**。所谓"通信算子"，本体在 NCCL 这些库的 CUDA C++ 代码里（NVIDIA 手写、按 NVLink/PCIe/IB 拓扑高度特化），torch extension 充其量是把调用口子露出来。

所以准确说法是：**通信算子的接口绑在 torch 上，实现绑在 NCCL 上。**

补充一个正在变的东西：PyTorch 现在把 collective 往**一等 op** 的方向做（`torch.ops._c10d_functional.*` / functional collectives），目的是让 `torch.compile` 能 trace 到通信、把 comm 和 compute 一起做图优化。这是"通信算子进图"的趋势，但底层传输还是 NCCL。

# 为什么 Triton 写不了通信

Triton 的前提假设是：**一个 program 在单设备上、对可寻址的内存做 tile 级计算**。它的内存模型里根本没有"访问另一张卡的显存"这个原语。而通信的本质是跨设备数据搬运，需要一整套 Triton 压根没暴露、也没打算暴露的东西：

- **跨进程/跨节点寻址**：内存注册、地址翻译、MR (memory region) 管理
- **网络传输原语**：RDMA/ibverbs verbs、NVLink P2P load/store、SHARP 在网计算
- **同步 / 流控 / 死锁避免**：通信是全局协调问题，不是纯数据并行
- **拓扑感知的算法选择**：ring / tree / hierarchical / 多 rail 的自动决策

一句话：**Triton 是"算"的 DSL，不是"通信"的 DSL。** 想在上面拼出 allreduce，等于要求一个 tile 编译器去管网络协议栈，方向就不对。

# 那实际怎么写？分层看

### ① 改通信模式（99% 的人只需要到这层）
不写底层，直接用 NCCL 作为传输原语，在上面重排算法：
- 把一个 allreduce 拆成 allgather + reducescatter
- comm/compute **overlap**（把通信藏进反向计算的间隙）
- 手写自定义 reduce kernel 接在 NCCL 的 p2p 上

DeepSpeed / Megatron 里那一堆 overlap、ZeRO、TP/PP 调度技巧，全在这层，**纯 Python/框架层就能干，不用碰 CUDA**。

### ② NCCL 插件 / 自定义 backend
NCCL 有 plugin API：tuner / net / profiler plugin。接非标硬件写 **net plugin**；要自定义协议栈或 collective 就得自己实现一个 `ProcessGroup` backend，代价很大，一般是框架团队干。

### ③ CUDA + 网络原语"硬写"（你说的那种）
对，就是 `torch.utils.cpp_extension` / `TORCH_LIBRARY` 把 CUDA C++ 包成 op。但更准确的说法是 **CUDA C++ 配合底层传输原语**：

- `cudaMemcpyPeerAsync` 做 P2P copy
- 直接写 **ibverbs / RDMA**（极其痛苦）
- **NVSHMEM**：PGAS 模型，kernel 里直接 `nvshmem_put/get`，GPU 发起通信，不用 host 参与

裸写 ibverbs 基本只有 NCCL 这种团队才做，一般人别碰。

### ④ Symmetric Memory（现在 torch 官方的正道）
`torch.distributed._symmetric_memory`，基于 NVSHMEM / CUDA VMM，让每张卡能**直接 load/store 别人的显存**，然后你在 kernel 里自己写通信逻辑。对应算子 `torch.ops.symm_mem.*`。

**这才是"通信算子用 CUDA 写"的现代正规姿势**——从对称内存原语出发，而不是从网络协议栈出发。

### ⑤ 通信 DSL（前沿，但没成气候）
确实有人想做通信专用 DSL，比如微软的 **MSCCLang**（把 collective 当编译问题）。方向有意思，但生态跟 Triton 完全没法比，也没进主流生产。

# 汇总对比

| 方式 | 能写通信？ | 说明 |
|---|---|---|
| **Triton** | ❌ | 无跨设备内存 / 网络原语，方向不匹配 |
| `torch.distributed` + NCCL | ✅ 但是"用"不是"写" | 调现成 collective |
| NCCL plugin | ⚠️ 部分 | tuner / net / profiler，定制传输层 |
| **symmetric memory / NVSHMEM** | ✅ | 官方推荐的"kernel 内写通信"方式 |
| 裸 CUDA + ibverbs/RDMA | ✅ | 最底层最灵活也最痛苦，NCCL 级团队才做 |
| 通信 DSL（MSCCLang 等） | ✅ | 前沿，未成熟 |

# 直接回你的原话

> "这玩意又不能像 triton 一样写 python like dsl，直接 cuda+torch extension 硬写吗？"

**对，cl 但要把两个更现实的方向补进来：**

1. **大多数场景你根本不需要"写通信算子"**，你需要的是**改通信模式**（overlap、切分、调度），这在框架/Python 层就完成了，不用碰 CUDA。

2. **真要下沉到 kernel 里写通信，现代正路是 NVSHMEM / symmetric memory**，而不是从 ibverbs 裸写。裸写 RDMA 是 NCCL 那种规模团队的工作量。

至于"Python like DSL 写通信"，Triton 这条线走不通是**设计层面的**（它不管跨设备），而不是还没实现。想做的话，得是像 MSCCLang 那种**专门面向 collective 的 DSL**，目前还不是主流选择。
