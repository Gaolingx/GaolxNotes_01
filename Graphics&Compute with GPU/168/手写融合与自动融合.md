## 🧑‍💻 User

## 🤖 Assistant

你说得基本对，但需要把"fusion"这个概念分成两个层次来看，否则容易混。

## 核心结论

`triton.jit` 本身确实**没有跨 kernel 的自动融合（autofuse）能力**——它只是一个**单 kernel 编译器**：一个 `@triton.jit` 函数 = 一次 grid launch = 一个 GPU kernel。

但你的直觉是对的：**把多个小 op 写进同一个 kernel，就等价于"手动 fusion"**。这不是 Triton 帮你做的图级优化，而是你自己在 kernel 内部表达出来的数据流融合。

关键在于区分两种 fusion：

| 层次 | 谁来做 | 例子 |
|------|--------|------|
| **图级 / IR 级 autofuse** | 上层编译器 | TorchInductor、XLA、TVM、TensorRT |
| **kernel 内数据流融合** | 你 + Triton 后端 | 手写 `exp+mul+store` 在一个 kernel 里 |

Triton 位于**第二层**；真正的"autofuse"大脑在**第一层**。

## Triton 内部其实"半自动"做了些什么

虽然 Triton 不会把你的两个 kernel 合并，但在**一个 kernel 内部**，它确实会自动合并 elementwise 算子。因为整个 kernel 就是一个 dataflow program，编译器（TTIR → TTGIR → LLVM）会做 CSE、指令调度，把逐元素操作直接 inline 进 PTX，不会为每个 op 单独开线程/内存往返：

```python
@triton.jit
def fused_silu_mul(x_ptr, y_ptr, out_ptr, N, BLOCK: tl.constexpr):
    offs = tl.program_id(0) * BLOCK + tl.arange(0, BLOCK)
    mask = offs < N
    x = tl.load(x_ptr + offs, mask=mask)
    y = tl.load(y_ptr + offs, mask=mask)
    # 下面这堆 op 全在寄存器里融合，只有一个 kernel launch
    silu = x * tl.sigmoid(x)
    tl.store(out_ptr + offs, silu * y, mask=mask)
```

数学上你是在一个 kernel 里算：

$$
\text{out}[i] = \frac{x_i}{1 + e^{-x_i}} \cdot y_i
$$

这四个"算子"（sigmoid、mul、mul、store）在 Inductor/Torch 里本可能是 3~4 个 kernel，这里被压成 **1 个 kernel、1 次读写**。

## 所以"autofuse"到底谁提供？

让 Triton 真正实现 autofuse 的，是 **TorchInductor**（PyTorch 2.0 的 `torch.compile` 默认后端）。它的工作流正是：

$$
\text{Python/Torch 图} \xrightarrow{\text{Inductor 调度器}} \text{fusion 决策} \xrightarrow{\text{codegen}} \text{Triton kernels}
$$

- Inductor 的 scheduler 做 **vertical fusion**（producer→consumer，如 conv→bias→relu）、**horizontal fusion**（把独立的 elementwise 拼在一起提高 occupancy）、以及 **reduction fusion**。
- 决策完之后，它**生成 Triton 代码**——这时才是你手写那个 kernel 的过程被自动化了。

也就是说：**Triton 是 Inductor 的"下游 codegen 目标"，autofuse 的智能在 Inductor 里，不在 Triton 里。** 这正是为什么单独用 `triton.jit` 没有 autofuse，而 `torch.compile` 有。

<details>
<summary><b>手动把一个 kernel 里的多个 op 融合，有哪些坑？（点击展开）</b></summary>

1. **并行结构必须兼容**。Triton program 是在 *block* 上运算的，fuse 的各个 op 必须能共享同一套 grid / 分块方式。
 - 两个逐元素 op：好融，套同一个 `offs` 即可。
 - 逐元素 + reduction（如 softmax）：要显式写 `tl.max` / `tl.sum`，同一 kernel 内两趟。
 - 逐元素 + matmul：难融，因为 tile 结构不同，通常拆成两个 kernel 或用一个 persistent kernel 分阶段。

2. **reduce / scan 要显式表达**。`tl.sum`、`tl.max`、`tl.reduce`、`tl.associative_scan` 不会自动产生，必须自己写。例如 fused softmax：

$$
\text{softmax}(x)_i = \frac{e^{x_i - \max_j x_j}}{\sum_j e^{x_j - \max_j x_j}}
$$

一个 kernel 里做 max → sub → exp → sum → div，读写只过一次（vs. 朴素 5 个 kernel）。

3. **寄存器压力 / occupancy**。把所有东西塞一个 kernel 会拉高寄存器占用、降低 occupancy，有时反而更慢。融合不是免费的。

4. **layout / swizzle**。涉及 `tl.dot` 时，操作数 layout（`#blocked` → `#mma`）转换可能有额外开销。

</details>

<details>
<summary><b>想接近"自动"，有哪些现实路径？（点击展开）</b></summary>

- **直接用 `torch.compile`（Inductor）**：这是目前最成熟的 autofuse + Triton codegen 组合。想看生成结果：`TORCH_COMPILE_DEBUG=1` 或 `torch._inductor.config.trace.enabled = True`。
- **Inductor 的 `max_autotune` / autotuning**：还会在多个融合方案里挑最优。
- **persistent kernel**：自己写"一个 kernel 处理整段流水线"，把重算/中间读写降到最低（如 fused attention、fused MoE）。
- **手写库级 kernel**：FlashAttention、xformers、Liger 等，本质就是"人肉 autofuse"的产物。
- 其他图级融合器（XLA / TVM / TensorRT）不生成 Triton，是另一条技术路线。

</details>

## 一句话总结

> Triton 不做 autofuse，它做的是 **单 kernel 内的数据流融合**；**跨 op / 跨 kernel 的自动融合**由上层图编译器（TorchInductor 等）完成，而它们正是通过**生成 Triton kernel** 来落地。你把多个小 op 写进一个 `triton.jit`，就是在"手动执行 autofuse 的结果"——逻辑上完全成立。

如果你想，我可以给你一个具体的对照例子（比如 `linear + bias + gelu + dropout` 手写 Triton 融合 kernel vs. Inductor 自动生成版本），帮你直观感受"手动 fuse"和"autofuse"的差别。

## 短答

**可行，而且这基本就是当前让 agent 自动写算子最靠谱的范式之一**——你实际上在设计一个"带 oracle 的逐级 lowering pipeline"。但你的第 3 步有个隐藏假设需要修正：**"tiled PyTorch → Triton" 并不是一对一的**，而这个假设恰恰决定了这套 harness 会不会在最后一步崩掉。

## 为什么这个设计是对的（值得保留的部分）

你其实复刻了编译器"多级 IR + 每级验证"的思想，把它落成**可执行的中间表示（executable IR）**：

$$
\underbrace{\text{autograd}}_{\text{oracle}_0}
\;\to\; \underbrace{\text{手写 fwd/bwd}}_{\text{IR}_1}
\;\to\; \underbrace{\text{tiled PyTorch}}_{\text{IR}_2}
\;\to\; \underbrace{\text{Triton}}_{\text{IR}_3}
$$

每一级比较下一级，等价于把"一次性写对 kernel"这个**高熵任务**，拆成三个**低熵、可自动判定对错**的子任务。这对 LLM agent 极其友好，原因有三：

1. **每步都有 ground truth**：`allclose` / `gradcheck` 就是自动 judge，不需要人肉 review。
2. **错误被局部化**：如果 IR₂→IR₃ 挂了，你知道是"翻译"错，而不是"推导"错。
3. **搜索空间被逐步压小**：最后一步只剩下机械改写。

这比直接 prompt "帮我写个 flash attention 的 triton kernel" 强一个数量级。

## 但是：为什么最后一步不是一对一

这是我要提醒你的核心。Triton **不是"tiled PyTorch 的语法糖"**，两者之间有真实的语义鸿沟：

| 维度 | tiled PyTorch | Triton | 是否一对一 |
|------|---------------|--------|-----------|
| 数据寻址 | slice / gather / reshape | `tl.arange` + `offs` + `tl.load(ptr+offs)` | ❌ 需显式手算索引 |
| 边界 | 自动 | 必须自己写 `mask=`（predication） | ❌ 概念新增 |
| 广播 | 任意广播 | `tl.broadcast_to`，shape 要显式 | ⚠️ 半对 |
| 归约 | `.sum(dim)` | `tl.sum` / `tl.max` 指定 `axis` | ⚠️ 半对 |
| 并行原语 | 无（只是循环/切片） | `program_id` / grid / 多趟 | ❌ 硬件概念缺失 |
| 布局 | 透明 | `#blocked` / `#mma` layout、swizzle | ❌ PyTorch 里根本不存在 |
| 精度 | 一种累加顺序 | fp 非结合，累加顺序影响数值 | ❌ oracle 本身会"抖" |

换句话说：

> **IR₂（tiled PyTorch）表达的是"分块的数据语义"，而 Triton 表达的是"分块的 + 硬件映射的执行语义"。** 后者的信息在 PyTorch 里压根没有被表达出来。

举例，一个 GEMM tile 在 PyTorch 里是：

```python
# IR2：只是把矩阵切成块，纯语义
for i in range(0, M, BM):
    for j in range(0, N, BN):
        acc = A[i:i+BM, :] @ B[:, j:j+BN]   # 你看不见 layout
```

到 Triton 变成：

```python
# IR3：多了 program_id 映射、mask、block pointer、num_warps、K-tiling
pid = tl.program_id(0)
rm = pid // num_n * BM + tl.arange(0, BM)
rn = pid %  num_n * BN + tl.arange(0, BN)
rk = tl.arange(0, BK)
acc = tl.zeros((BM, BN), tl.float32)
for k in range(0, K, BK):
    a = tl.load(a_ptr + rm[:, None]*K + (k+rk)[None, :], mask=...)  # mask 是新增的
    b = tl.load(b_ptr + (k+rk)[:, None]*N + rn[None, :], mask=...)
    acc = tl.dot(a, b, acc)
```

这两段**语义等价，但结构上多了 5 类 IR₂ 里没有的东西**。所以最后一步是"**带语义缺口的重写**"，不是"替换"。

## 真正的深水区：backward

你计划里"forward/backward 都手写"，这点判断非常对，但要知道 **backward 的 tiling 难度远高于 forward**，原因是：

- **归约维度反转**：forward 里 `sum over K`，backward 里常常变成 `outer product scatter`，需要 `tl.atomic_add` 或分块累加，这在 IR₂ 里对应的是"循环外的累加变量"，翻译到 Triton 时行为不一致（atomic 非确定性）。
- **重复输出 / 广播的反向**：`broadcast` 的前向是复制，反向是 `sum`；`gather` 反向是 scatter。IR₂ 里这些是 `.sum(dim)` 一行，IR₃ 里是原子操作或额外归约 kernel。
- **非结合性**：backward 梯度累加顺序一变，`allclose` 可能就不过，你不得不放宽 tolerance——**oracle 变弱了**。

所以更准确地说，你这套 pipeline 在 **forward 上接近"一对一"**，在 **backward 上是"一对多 + 非确定"**。Harness 应该对 backward 单独设计判定策略（见下）。

建议改成显式**四阶段 + 强 oracle + 边界矩阵**：

## 验证矩阵（比一句"验证数值正确性"更可操作）

| 测试 | 手段 | 抓什么 |
|------|------|--------|
| 数值等价 | `torch.allclose(rtol, atol)` | 逻辑错误 |
| 反向正确 | `torch.autograd.gradcheck`（fp64） | 推导错误 |
| 边界 | N 非 BLOCK 倍、N=0/1、超小 shape | mask 漏写 → 越界/错值 |
| 内存布局 | contiguous / transposed / strided 输入 | 索引手算错 |
| 精度 | fp16 / bf16 / tf32 各跑 | 累加顺序导致超差 |
| 竞态 | 多次运行结果一致 | atomic / 缺失同步 |
| 性能 | 只在外层循环后 | 功能对但慢 |

## 一句话结论

> 你的三阶段（列 tile → PyTorch per-tile → 转 Triton）**方向完全正确，是 agent 写算子该走的路**；但要把"**转写**"从"一对一替换"正名为"**带语义缺口的 lowering + oracle**"，并给 backward 单独设计（因为它的 oracle 本身就是非确定的）。补上边界/dtype/竞态测试矩阵后，这套 harness 是**当前最可行的自动写算子方案**，前提是你承认最后一步需要 AI 补足 PyTorch 里不存在的硬件语义，而不是假设它俩同构。

## 0. 先建立"搬运光谱"

不要把"搬运"当成一个动作，它是三种，代价和灵活度完全相反：

| 方式 | 心智 | 依赖 | 灵活度 | 适合场景 |
|------|------|------|--------|----------|
| **A. 直接依赖** | `pip install liger-kernel` | 重（带 transformers 补丁） | 低 | 想一行提速、用 HF 模型 |
| **B. Vendor 单文件** | 复制 `ops/xxx.py` 进自己仓库 | 极轻（只 torch/triton） | 中 | 自研模型、不想引入整包 |
| **C. 参考重写** | 读源码，抄 tiling 思路，自己包 | 无 | 高 | 有特殊 layout/dtype/分布式需求 |

**大多数"集成到自己项目"的真实答案是 B 或 A+B 混用**：底层用它的 kernel，上层自己控制。

## 1. 搬运前的选型 checklist

在动手抄之前，逐条确认（这些是集成翻车的高频点）：

- [ ] **许可证**：Liger 的 license 在 `docs/license.md`，搬运/改动后要按它保留声明。（Unsloth 是 Apache-2.0，flash-attn BSD，Apex BSD-3，各自核对。）
- [ ] **依赖版本**：CUDA 上要 `torch>=2.1.2` + `triton>=2.3.0`；ROCm 要 `torch>=2.5.0` + `triton>=3.0.0`。你项目里 triton 版本不一致是头号杀手。
- [ ] **有没有 autograd**：Liger 的所有 op 都是 `torch.autograd.Function`，**前后向都实现了**（它号称 exact，无近似）。这点比很多"只有 forward"的 kernel 强太多。
- [ ] **dtype/设备支持**：fp16/bf16/fp32、CUDA/ROCm/NPU。
- [ ] **fallback 路径**：它内部会在不支持时退回 PyTorch 实现——你 vendor 时别把这个 fallback 抄丢。
- [ ] **是否需要 transformers**：`liger_kernel.transformers` 下的高层 API 才需要 transformers，**`liger_kernel.ops` 下的底层 kernel 不需要**。这是你能不能"轻量集成"的分界线。

## 2. 三种集成方式的具体写法

### 方式 A：高层一行 patch（最快）

```python
from liger_kernel.transformers import AutoLigerKernelForCausalLM

# 自动 monkey-patch 支持的模型
model = AutoLigerKernelForCausalLM.from_pretrained("path/to/model")
```

或者精确控制替换哪些 op：

```python
from liger_kernel.transformers import apply_liger_kernel_to_llama

apply_liger_kernel_to_llama(
    rope=True,
    swiglu=True,
    cross_entropy=True,
    fused_linear_cross_entropy=False,   # 想省显存就开，但语义会变
    rms_norm=False,                     # 想保守就留 HF 原版
)
# 然后正常实例化模型
```

> ⚠️ 这是"图省事"路径：它靠 monkey-patch，**跟你自己的模型结构强耦合**。自研模型基本用不上，直接跳到 B/C。

### 方式 B：组合自己的模型（推荐）

Liger 暴露了可直接当 `nn.Module` 用的组件：

```python
from liger_kernel.transformers import (
    LigerRMSNorm,            # 替换 nn.RMSNorm / LlamaRMSNorm
    LigerSwiGLUMLP,          # 替换 LlamaMLP
    LigerCrossEntropyLoss,   # 替换 F.cross_entropy
    LigerFusedLinearCrossEntropyLoss,  # 融合 lm_head + CE
    liger_rotary_pos_emb,    # 替换 apply_rotary_pos_emb
)
```

最省显存的用法（**Fused Linear + Cross Entropy**，直接把 `lm_head` 和 loss 融掉，不物化 `[B,S,V]` 的 logits）：

```python
loss_fn = LigerFusedLinearCrossEntropyLoss()
loss = loss_fn(model.lm_head.weight, hidden_states, labels)  # hidden是输入，不是logits
loss.backward()
```

它对 `[B,S,V]` 大词表的显存收益是数量级的（V=128k 时最明显）。

### 方式 C：直接调底层 `autograd.Function`（最灵活）

所有 kernel 的底层都在 `liger_kernel/ops/`，命名规律是 `LigerXxxFunction`：

```python
from liger_kernel.ops import (
    LigerRMSNormFunction,
    LigerSwiGLUFunction,
    LigerCrossEntropyFunction,
    LigerFusedLinearCrossEntropyFunction,
    # ... 见 ops/__init__.py 完整导出
)

# 它们本身就是 autograd.Function，能直接 .apply
y = LigerRMSNormFunction.apply(x, weight, eps, offset, casting_mode)
```

这条路让你**保留完整控制权**：自己管 layout、dtype、并发，只借用它的 kernel 体。

## 3. 通用集成骨架（你项目里应该长什么样）

不管搬哪一个，**在你的项目里包一层 `torch.autograd.Function` + fallback**，这样 kernel 可以随时替换/降级：

```python
import torch
import triton
import triton.language as tl
from typing import Optional

@triton.jit

                         BLOCK: tl.constexpr):
    row = tl.program_id(0)
    offs = tl.arange(0, BLOCK)
    mask = offs < N
    x = tl.load(x_ptr + row * stride + offs, mask=mask, other=0.0).to(tl.float32)
    var = tl.sum(x * x, axis=0) / N
    rstd = 1.0 / tl.sqrt(var + eps)
    w = tl.load(w_ptr + offs, mask=mask, other=0.0).to(tl.float32)
    y = (x * rstd) * w
    tl.store(y_ptr + row * stride + offs, y.to(y_ptr.dtype.element_ty), mask=mask)

class FusedRMSNorm(torch.autograd.Function):
    @staticmethod
    def forward(ctx, x, weight, eps):
        # 1) 契约检查：contiguous / dtype / device
        assert x.is_cuda
        x = x.contiguous()
        N = x.shape[-1]
        y = torch.empty_like(x)
        grid = (x.numel() // N,)
        _rms_norm_fwd_kernel[grid](x, weight, y, N, N, eps, BLOCK=triton.next_power_of_2(N))
        ctx.save_for_backward(x, weight)
        ctx.eps = eps
        return y

    @staticmethod
    def backward(ctx, dy):
        x, w = ctx.saved_tensors
        # 2) 反向单独写（归约维度会变，别指望复用前向逻辑）
        ...

def rms_norm(x, weight, eps=1e-6):
    # 3) fallback：非 CUDA / 不满足契约就走 eager
    if not x.is_cuda or x.dtype not in (torch.float16, torch.bfloat16, torch.float32):
```

**这层 wrapper 的价值**：kernel 是"脏"的（布局/边界/精度假设多），wrapper 负责把契约、fallback、autograd 收口。搬运 Liger 时同理——**直接 import 它的 `Function`，外面再包你自己的 fallback 和 shape 检查**。

## 4. 逐个 kernel 的集成注意点

### Fused Cross Entropy（最值得搬）

数学上是 logsumexp 稳定版：

$$
\mathcal{L} = \frac{1}{N}\sum_i \Big( m_i + \log\sum_j e^{z_{ij}-m_i} - z_{i,y_i} \Big), \quad m_i=\max_j z_{ij}
$$

反向是干净的：

$$
\frac{\partial \mathcal{L}}{\partial z_{ij}} = \frac{1}{N}\big(p_{ij} - \mathbb{1}[j=y_i]\big)
$$

集成时确认这些 flag 都在：`ignore_index`、`label_smoothing`、`reduction`(mean/sum/none)、`lse_square_scale`(z-loss)、`inplace`、以及**词表并行**版本 `vocab_parallel_cross_entropy.py`（张量并行时用）。**Fused Linear CE** 还多一个坑：它内部 chunk 计算，**和 gradient checkpointing、FSDP 的交互要专门测**。

### SwiGLU

$$
\text{SwiGLU}(x) = \text{Swish}(xW_g)\odot(xW_u),\quad \text{Swish}(z)=z\sigma(z)
$$

注意三点：`xW_g` 和 `xW_u` 的 **layout/stride 必须一致**（gate/up 是拼接还是分开）；反向要 `save_for_backward` gate 的中间量；Liger 的 `LigerSwiGLUMLP` 还进一步把 **down projection 融进来**，搬它性能最好但耦合也最深。

### RMSNorm

$$
\text{RMSNorm}(x)=\frac{x}{\sqrt{\tfrac{1}{d}\sum_i x_i^2+\epsilon}}\odot\gamma
$$

真正省的是 **`fused_add_rms_norm.py`**：把"残差加法 + norm"合成一次读写（前向一次 load、反向避免重算），单看 RMSNorm 收益一般，**融合 residual 才是大头**。注意 `offset` / `casting_mode` 参数（Liger 支持在 fp32 累加、按配置 cast）。

## 🤖 Assistant

对，你抓的这三点正好是 **"eager 代码里 HBM 冗余"的三个来源**：控制流、物化、以及 stage 间往返。它们的本质是同一件事——**eager 每个 torch op 之间都是一条 HBM 边界**（每个 op = 一次 kernel launch = 一次写 + 一次读）。Triton 的目标就是把这些边界消掉，让数据停在寄存器/SRAM 里。

下面把三个 smell 逐个对应到具体机制。

## 0. 心法：量化你的优化目标

显存流量：

$$
\text{HBM traffic} = \sum_{\text{each op}} \big(\underbrace{\text{bytes read}}_{\text{load}} + \underbrace{\text{bytes written}}_{\text{store}}\big)
$$

- **下界** = 输入字节 + 输出字节（只有一次读、一次写）。
- eager 如果有 $k$ 个 stage 且每个 stage 物化中间量，你大约是 $k$ 倍下界。
- **每多一个中间张量，就多 $2\times$ 它的体积**（写一次 + 读一次）。

读 eager 代码时，你就数：**有几个 `torch.empty`？有几个中间变量被读了第二次？** 那就是你可以砍掉的 HBM 流量。

## 1. 三个 smell → 三套 Triton 机制（总表）

| Eager 特征 | 本质 | Triton 对应 | 关键 API |
|-----------|------|-------------|----------|
| `for i in range(M)`（外层、独立） | 可并行 | **grid 维度** | `tl.program_id` |
| `for k`（归约） | 串行累加 | **K-loop + 寄存器累加器** | `tl.range` + `tl.dot`/`tl.sum` |
| `torch.empty([大形状])` 中间量 | 物化到 HBM | **寄存器 tile / SRAM** | `tl.zeros`、`tl.dot` |
| `a=op1(x); b=op2(a)` 两趟 | HBM 往返 | **一个 kernel 内的 SSA 链** | 直接内联，不 store |
| `if data_dependent` | 分支 | **mask 化** | `tl.where`、`mask=` |
| `if shape_dependent` | 特化 | **编译期常量** | `tl.constexpr` |
| `.max()/.sum()` 两趟 | 归约 | **在线/单趟归约** | `tl.max`、`tl.sum`、online |

## 2. `for` 循环：拆成"并行轴 + 归约轴"

这是最重要的一条。Triton 里 **Python 的 `for` 有两种命运**，取决于它是不是归约维度：

### 2.1 外层独立循环 → 变成 grid（并行）

```python
# eager：for i 是显式的，但每一步独立
for i in range(M):
    y[i] = f(x[i])
```

```python
# Triton：循环消失，变成 program_id
@triton.jit
def k(x_ptr, y_ptr, ...):
    i = tl.program_id(0)              # 这一行替代了 for i in range(M)
    ...
```

> **判断法**：如果循环体各次迭代互不依赖 → 它就该是 grid 维度，不是循环。

### 2.2 归约维度的循环 → `tl.range` + 寄存器累加器

```python
# eager GEMM 的内核
for i in range(M):
    for j in range(N):
        acc = 0.0
        for k in range(K):            # <-- 归约
            acc += A[i,k] * B[k,j]
        C[i,j] = acc
```

```python
@triton.jit
def gemm(a_ptr, b_ptr, c_ptr, M, N, K,
         BM: tl.constexpr, BN: tl.constexpr, BK: tl.constexpr):
    pid_m = tl.program_id(0)          # 替代 for i
    pid_n = tl.program_id(1)          # 替代 for j
    rm = pid_m * BM + tl.arange(0, BM)
    rn = pid_n * BN + tl.arange(0, BN)
    rk = tl.arange(0, BK)

    acc = tl.zeros((BM, BN), tl.float32)     # ★ 累加器活在寄存器，不落 HBM
    for k in tl.range(0, K, BK, num_stages=3):   # 替代 for k，且做软件流水
        a = tl.load(a_ptr + rm[:, None]*K + (k + rk)[None, :], mask=...)
        b = tl.load(b_ptr + (k + rk)[:, None]*N + rn[None, :], mask=...)
        acc = tl.dot(a, b, acc)              # ★ 累加在寄存器
    tl.store(c_ptr + rm[:, None]*N + rn[None, :], acc.to(c_ptr.dtype.element_ty))
```

三层映射一次讲清：

| 源循环 | 角色 | Triton |
|--------|------|--------|
| `for i` | 独立 | `program_id(0)` |
| `for j` | 独立 | `program_id(1)` |
| `for k` | 归约 | `tl.range(...)` + `acc` 寄存器 |

### 2.3 `num_stages`：自动流水线，隐藏 HBM 延迟

`tl.range(..., num_stages=N)` 让 Triton **自动双缓冲/多缓冲**：第 $t$ 轮在算的时候，第 $t{+}1$ 轮的数据已经在 prefetch。这就是"用并行掩盖 HBM 延迟"，你不用手写 prefetch。

> 老写法是在 `@triton.jit(autotune)` 里调 `num_stages`；新 Triton 支持直接在 `tl.range` 上写（更细粒度）。Hopper+ 还能 `tl.range(..., warp_specialize=True)` 做 producer/consumer warp 分工。

### 2.4 Persistent kernel：把"外层循环"变成 kernel 内的 tile 循环

如果 eager 里有个"每个 batch 迭代一次、但可以复用同一份权重"的循环，可以写成 **persistent**：

```python
@triton.jit
def persistent_gemm(..., NUM_TILES, NUM_SMS):
    start = tl.program_id(0)
    for tile in tl.range(start, NUM_TILES, NUM_SMS):  # 每个 SM 反复吃 tile
        # 一次加载权重到 SMEM，反复复用
        ...
```

省掉的是每次 launch 的重建 + 权重反复从 HBM 搬。

## 3. 大张量实例化 → 寄存器 tile / SRAM

**eager 里每一个 `torch.empty` 都在往 HBM 写。** Triton 里中间量是 SSA 值，天然待在寄存器里。

最典型的例子是 **fused linear + cross entropy**：eager 会物化 `[B, S, V]` 的 logits（V=128k 时能到几十 GB），而 Triton 里那个 tile 是一个 `(BM, BV)` 的寄存器块：

```python
# eager（灾难）：先物化 logits，再 softmax，再 CE
logits = x @ W.T                       # 物化 [B,S,V] → 写 HBM
loss = F.cross_entropy(logits, tgt)    # 把 logits 又读一遍 → HBM

# Triton：logits 从不落 HBM，直接在寄存器里做 logsumexp
acc = tl.zeros((BM, BV), tl.float32)   # ★ 只是一个寄存器 tile，不是 tensor
```

原则：

- **只有最终输出才 `tl.store`**。任何中途结果都不该 store。
- `tl.zeros((BM, BN))` 在寄存器里，`tl.zeros` 的 shape 越大，寄存器压力越大（要 autotune BM/BN）。
- `tl.dot` 的操作数会被编译器自动放进 **SRAM（shared memory）**；你可以用 `num_stages` 控制它缓冲几份。
- 如果某个中间量**大到寄存器放不下**（比如整行 attention score），就转成"**在线/分块**"算法（见下一节）。

## 4. HBM 往返 → 单 kernel 融合 / online 算法

这是你第三点。经典两趟 eager：

```python
# eager softmax：4 次 HBM 往返
m = x.max(-1, keepdim=True)     # 读 x 写 m
e = torch.exp(x - m)            # 读 x,m 写 e
s = e.sum(-1, keepdim=True)     # 读 e 写 s
y = e / s                       # 读 e,s 写 y
```

Triton：**1 读 1 写**，max/sum 在寄存器上做：

```python
@triton.jit
def softmax_fwd(x_ptr, y_ptr, stride, N, BLOCK: tl.constexpr):
    row = tl.program_id(0)
    cols = tl.arange(0, BLOCK)
    mask = cols < N
    x = tl.load(x_ptr + row*stride + cols, mask=mask, other=-float("inf"))  # ① 一次读
    m = tl.max(x, 0)                       # 归约 1
    e = tl.exp(x - m)                      # 寄存器里算
    s = tl.sum(e, 0)                       # 归约 2
    y = e / s
    tl.store(y_ptr + row*stride + cols, y, mask=mask)   # ② 一次写
```

> 注意这里有个细节：`x` 只 load 了一次，两次归约（max、sum）都作用在**同一个寄存器值**上。eager 里它们分别触发一次 HBM 读。

### 当一行太大放不进寄存器 → 在线（online）算法

如果 $N$ 很大（比如 attention 的序列维），不能"先 max 再 sum"，就用**在线 softmax**，边扫边更新：

$$
m' = \max(m, m_{\text{blk}}),\qquad s' = s\,e^{\,m-m'} + s_{\text{blk}}\,e^{\,m_{\text{blk}}-m'}
$$

这就是 **FlashAttention 的核心**：它把 $N\times N$ 的 score 矩阵**分成 block 流式处理**，永远不物化整个矩阵——这正是你把 eager attention（`scores = q@k.T` 物化了 $O(N^2)$）转成 Triton 的关键改动。

<details>
<summary><b>为什么 online softmax 能省 HBM（点击展开）</b></summary>

eager attention 会物化 `[B,H,N,N]` 的 score，$N=8192$ 时 fp16 也要几十 GB，而且：

1. `attn = q @ k.T` → 写 $O(N^2)$
2. `attn = softmax(attn)` → 读 + 写 $O(N^2)$
3. `out = attn @ v` → 读 $O(N^2)$

总流量 $O(N^2)$ 级别。FlashAttention 改成：外循环遍历 KV block，每个 KV block 内部维护 running $(m, s, o)$，**HBM 流量降到 $O(N)$（读 Q/K/V + 写 O）**。这就是"把 HBM 往返变成寄存器计算"的极端形态。

</details>

## 5. `if` 分支：data-dependent → mask，shape-dependent → constexpr

Triton **不允许 Python 的 `if` 依赖张量值**（它在编译期执行）。所以 eager 里的 `if` 必须重写：

**数据相关分支 → `tl.where` mask：**

```python
# eager
loss += 0 if tgt == ignore_index else (lse - logit[tgt])

# Triton（先把分支融进数据流）
valid = tgt != ignore_index
logit_t = tl.load(logit_ptr + tgt, mask=valid, other=0.0)
loss += tl.where(valid, lse - logit_t, 0.0)
```

**形状/配置相关分支 → `tl.constexpr` 特化：**

```python
@triton.jit
def k(..., WITH_BIAS: tl.constexpr):
    ...
    if WITH_BIAS:              # 编译期展开，零运行时开销
        acc += bias
```

**变量长序列 / padding → 直接把 `if` 变成 load 的 `mask`：**

```python
mask = offs < seq_len      # 边界条件从"if x>N"变成 load mask
tl.load(p + offs, mask=mask)
```

> 判断法：**分支频率是"每个元素级"** → `tl.where`；**"整个 kernel 级"**（配置开关、dtype、是否 fuse residual）→ `tl.constexpr`；**"行级"** → 逐行 mask。

## 6. 读 eager 代码的方法论（checklist）

拿到一段 eager，按这个顺序扫：

1. **画数据流，标中间量**：每个 `torch.empty` / 每个被赋值两次以上的变量。
2. **在每个 op 之间画一条 HBM 边界**（eager 事实如此）。你的目标是**删掉这些边界**。
3. **给每个 `for` 分类**：独立 → grid；归约 → `tl.range`/`tl.sum`/`tl.dot`。
4. **给每个 `if` 分类**：data-dep → mask；shape-dep → constexpr。
5. **找大张量**：能不能留在寄存器？放不下就转 online。
6. **数最终 HBM 流量**，对比"输入+输出"下界，算出你的收益。

**eager（~5 趟 HBM）：**

```python
mean = x.mean(-1, keepdim=True)              # 读 x 写 mean
```

```python
def layernorm_fwd(x_ptr, w_ptr, b_ptr, y_ptr, stride, N, eps, BLOCK: tl.constexpr):
    row = tl.program_id(0)                          # 替代 for i
    offs = tl.arange(0, BLOCK)
    mask = offs < N
    x = tl.load(x_ptr + row*stride + offs, mask=mask, other=0.0)   # ① 一次读
    mean = tl.sum(x, 0) / N                         # 归约在寄存器
    xc = tl.where(mask, x - mean, 0.0)
    var = tl.sum(xc * xc, 0) / N
    rstd = 1.0 / tl.sqrt(var + eps)
    w = tl.load(w_ptr + offs, mask=mask)
    b = tl.load(b_ptr + offs, mask=mask)
    tl.store(y_ptr + row*stride + offs, xc*rstd*w + b, mask=mask)  # ② 一次写
```

收益：HBM 从 ~5 趟降到 2 趟。**注意** `xc` 和 `mean` 都是寄存器值，没有 store。

</details>

## 7. backward 的 HBM 优化：store vs recompute

反向里同样的道理，但多一个权衡：**存中间量（写 HBM）还是重算（多花 compute）**。

- **Fused CE backward**：不存 softmax，**从 logits 重算** $p_{ij}$，梯度 $\frac{1}{N}(p_{ij}-\mathbb{1}[j{=}y_i])$。省下 $O(V)$ 的存/读，代价是重算。
- **Attention backward**：前向存 logsumexp（$O(N)$）而不是存整个 $O(N^2)$ score，反向靠它重算。
- 原则：**只存"便宜或必需"的，重算"大而可复现"的**。这就是 activation checkpointing 在 kernel 内部化的版本。

## 8. 一句话总结

> eager 的每个 op 都是一条 HBM 边界。转 Triton 时：**把独立 `for` 变成 `program_id`，把归约 `for` 变成 `tl.range` + 寄存器累加器+`num_stages` 流水；把 `torch.empty` 中间量变成 `tl.zeros` 寄存器 tile；把 stage 间的写→读变成同一个 kernel 里的 SSA 链（放不下就用 online 算法）；把 data-`if` 变 `tl.where`、shape-`if` 变 `tl.constexpr`。** 最后用"HBM 流量 = 输入+输出"这个下界当验收标准，数一数你砍掉了几趟往返。

如果你给我一段具体的 eager 实现（比如某个 model 的 loss 或 attention），我可以按上面的 checklist 逐行标注"这里该变 grid / 这里该留寄存器 / 这里该 online"，并给出对应 Triton 骨架。
