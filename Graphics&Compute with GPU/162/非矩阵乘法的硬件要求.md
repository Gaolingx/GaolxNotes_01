# 非矩阵乘法的硬件要求

---

### 🤖 Assistant

这个问题问得很到点上——它其实触及了 AI 加速器设计里一个常被低估的事实：**GEMM 是最"好伺候"的部分，真正考验架构的是剩下的那些"杂活"。** 下面我从一个统一的分析框架出发，逐类拆解，最后给出综合的架构设计原则。

## 一、先统一框架：算术强度与 Roofline

所有算子都可以放到"算术强度"（Arithmetic Intensity, AI）这个轴上：

$$AI = \frac{\text{FLOPs}}{\text{访存字节数}}$$

| 算子类别 | 计算量 | 访存量 | 算术强度 | 瓶颈类型 |
|---|---|---|---|---|
| GEMM（$M\times N\times K$） | $O(N^3)$ | $O(N^2)$ | 高（随 $N$ 增长） | **Compute bound** |
| Element-wise（ReLU/add/scale） | $O(N)$ | $O(N)$ | 极低（< 1） | **Memory bound** |
| Reduction（sum/max/min） | $O(N)$ | $O(N)$ | 极低 + 有通信 | **Memory + Communication bound** |
| 内存搬移（搬运/转置/KV Cache） | 0 | $O(N)$ | 0 | **纯带宽 bound** |

你说的"GEMM 只是 compute bound 但执行时间可控"，非常准确——因为它的 FLOPs 是固定的 $2MNK$，算力固定，时间就可精确预测，数据流规则，适合静态 tiling、流水线、多核切分负载均衡。

**但关键在于 Amdahl 定律**：一个真实 Transformer 层里，GEMM 占 FLOPs 的 90%+，但 LayerNorm、Softmax、Residual、RoPE、激活函数这些"尾巴"在**延迟**里的占比远超其 FLOPs 占比。GEMM 加速得再快，如果非 GEMM 部分占 10% 时间，整体提速上限也只有 10 倍。所以架构不能只做"GEMM 机器"。

## 二、逐类拆解：每类运算对硬件的具体要求

### 1. GEMM → 要求"高密度 MAC + 喂得饱阵列"

核心矛盾：要把 $2MNK$ 次乘加用最小面积/能耗做完，**同时让 MAC 阵列每周期都不断粮**。

- **大规模 MAC 阵列 / Systolic Array / Tensor Core**：提升 FLOPS/面积、FLOPS/W。
- **数据复用与 tiling**：矩阵乘本身算术强度高，但前提是片上缓存能实现复用（权重复用、输出复用、输入复用），否则数据反复进出 DRAM，优势全无。这对应三种经典 dataflow：
  - Weight-stationary（权重驻留）
  - Output-stationary（输出驻留）
  - Row-stationary（行驻留，如 Eyeriss）
- **片上网络带宽必须匹配阵列吞吐**：一个每周期做 $4096$ 次 MAC 的阵列，每周期要从 SRAM 喂进几百个操作数。**很多设计的真实瓶颈不是阵列本身，而是"喂不饱"**。这要求从 SRAM 到 PE 的高带宽数据通路 + 权重/输入的广播/多播路径。
- **精度分层**：低精度 MAC（INT8/FP8/FP16/BF16）+ 高精度累加器（FP32/INT32），支持混合精度，这是能效的关键。
- **"时间可控"→ 静态调度友好**：编译器可以做静态 tiling、双缓冲、软件流水线，这也是为什么 GEMM 能被优化到接近峰值。

### 2. 内存操作 → 要求"缓解内存墙 + 显式数据管理"

AI 访存模式是**编译期可预知**的，这决定了架构选择：

- **大容量片上 SRAM（Scratchpad）而非纯 Cache**：软件显式管理的 scratchpad 比硬件 cache 命中率更高、能耗更低、时延可预测。AI 数据流太规则，cache 的"猜测"反而是浪费。
- **高带宽外部内存**：HBM / GDDR，多通道，因为外部带宽增长远慢于算力增长（内存墙）。
- **异步 DMA 引擎 + 多级缓冲**：访存和计算必须能重叠，否则搬运延迟直接暴露在关键路径上。现代 GPU 的 `cp.async`、TMA（Tensor Memory Accelerator）就是为此。
- **硬件地址生成单元（AGU）**：多维 tensor 的地址计算（strided access、tiling 偏移、转置）如果靠标量核心算，会拖垮整个流水线。
- **数据压缩/稀疏/量化**：结构化稀疏（2:4）、在线解压、KV Cache 压缩——本质都是"用算力换带宽"。

### 3. 向量计算（Element-wise）→ 要求"必须融合，不能让它落地"

这类算子算术强度 < 1，**单独执行必然是 memory bound**，唯一的出路是"顺手做掉"：

- **与 GEMM 融合**：GEMM 输出不进内存，直接送入向量单元做 bias add + 激活（GEMM→bias→ReLU/GELU 一条流水线），省掉两次内存往返。
- **SIMD 宽向量单元**：与 MAC 阵列并列的向量 ALU，处理 add/mul/scale/clamp。
- **特殊函数单元（SFU）**：Softmax 的 exp、GELU 的 erf/tanh、LayerNorm 的 rsqrt、RoPE 的 sin/cos。这些**吞吐必须匹配主数据速率**，否则一个 exp 就能把整个 softmax 卡死。通常用分段多项式逼近 + 查表实现。
- **低控制开销**：element-wise 算子短、数量多，kernel 启动/指令派发开销占比极高，需要轻量级调度、循环展开、向量化指令。

### 4. Reduction → 要求"跨 PE 通信 + 多遍遍历都在片上"

Reduction 是四类里最"反并行"的：它需要**跨元素通信**，而且往往伴随 `reduce → broadcast → element-wise → reduce` 的多遍数据遍历（Softmax 就是典型）。

- **归约树硬件**：加法树、比较树（max/min），把 $O(N)$ 串行归约降到 $O(\log N)$ 深度。
- **跨 lane / 跨 PE 的通信路径**：
  - GPU：warp shuffle、shared memory 归约、跨 block 原子操作；
  - NPU：PE 阵列内部要有**横向/纵向通信线**，让同一行/列的 PE 能互相归约，而不只是"只进不出"的 systolic 数据流。
- **原子操作单元**：跨 block 的 sum/max 需要硬件原子单元支持，否则只能回退到全局内存往返。
- **片上存储能容纳归约维度**：Softmax 要在"一行"内做 `max → exp → sum → div`，最好整行都留在片上。这要求 SRAM 容量能装下 token 维度的数据（对长序列尤其苛刻）。
- **应对不规则性**：按行/按列归约的长度可能不规整（变长序列、padding、稀疏 attention），硬件要能灵活映射，**不能只有固定 shape 的 systolic dataflow**。

## 三、综合：这些要求如何共同塑造一个 GPU/NPU 架构

把上面四条合起来，可以得到几条贯穿性的设计原则：

**① 分层存储 + 显式数据管理**
`Register → Scratchpad/SMEM → L2 → HBM`，每一层都在"用更大的容量换更高的带宽和更低延迟"。GEMM 靠 tiling 在 scratchpad 层复用数据，element-wise/reduction 靠融合让数据不落地。

**② 异构执行单元协同，而非单一阵列**
- MAC 阵列（/Tensor Core）→ 扛 GEMM
- 宽 SIMD 向量单元 → 扛 element-wise
- SFU → 扛特殊函数
- 归约树/原子单元 → 扛 reduction
- DMA/AGU → 扛数据搬运
- 少量标量/SIMT 核心 → 兜底不规则控制流

**③ 一条能同时服务三种数据流的片上网络**
GEMM 的**权重广播**、向量计算的**流水数据流**、归约的**跨 PE 通信**，三种数据流模式完全不同，片上网络必须同时支持，否则总有一类算子是瓶颈。

**④ 算子融合（编译器 + 硬件共同支撑）**
融合是解决"低算术强度算子"的唯一根本办法。硬件要提供低开销的算子切换（数据不落地、流水线不打断），编译器要做自动融合（如 `GEMM+Bias+GELU`、`LayerNorm+Residual`、`FlashAttention` 式的整段融合）。

**⑤ 计算 / 访存 / 通信三者重叠**
GEMM 的"时间可控"是优势，但前提是访存（DMA）和通信（归约）能被异步隐藏。多级流水、多缓冲、异步执行是标配。

**⑥ 精度分层**
不同算子对精度敏感度不同：GEMM 可以激进低精度（FP8/INT4），但累加要高精度；归约（求和）和激活函数的中间值要谨慎；Softmax 的减法（数值稳定性）需要特定处理。

**⑦ 可编程性兜底**
AI 算子演进太快（RoPE、GQA、Mamba、各种新归一化），专用单元永远追不上。所以架构必须保留一条可编程的"逃生通道"（SIMT 核心 / 标量核心），否则新算子一来，专用单元闲置，利用率崩掉。

---

### 一句话总结

> GEMM 只要求"算得快、喂得饱"，是**静态可预测**的问题；内存操作要求"带宽大、搬得快、能重叠"；向量计算要求"能融合、有 SFU、低开销"；而 reduction 要求"能跨 PE 通信、多遍遍历都在片上、能容忍不规则"。

**一个真正好的 AI 加速器，难点从来不是把 GEMM 峰值做高，而是让那 10% 的"杂活"不把 90% 的 GEMM 优势拖垮。** 这解释了为什么 TPU v1 之后各家都在补"向量单元 + 归约 + 融合"的课，也解释了为什么现代 GPU 里 Tensor Core 之外还有一整套 CUDA Core + SFU + shared memory + 异步搬运的体系——它们不是配角，而是决定真实利用率的关键。
