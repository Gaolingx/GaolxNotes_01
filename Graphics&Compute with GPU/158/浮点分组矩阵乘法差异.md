## 1. MMA 指令 / atom 层差异（最本质的一层）

### SM100/SM103：tcgen05 UMMA，块缩放编码在指令描述符里

`cute/atom/mma_traits_sm100.hpp` 里的 `SM100_MMA_MXF4_SS` / `SM100_MMA_MXF4_2x1SM_SS`（以及稀疏版 `SM100_MMA_MXF4NVF4_SS_SPARSE`）：

- `static_assert(sizeof_bits == 4)`，类型 `float_e2m1_t` / `cutlass::type_erased_dynamic_float4_t`，SF 类型 `ue8m0_t`；
- 每条指令逻辑 K 固定 256bit → `K = 256/4 = 64` 个 FP4 元素；
- `SFVecSize = VS`（16=1x / 32=2x 模式；2x 模式要求 A/B 都是 E2M1、SF 是 UE8M0）；
- 使用 `UMMA::InstrDescriptorBlockScaled`（`mma_sm100_desc.hpp`：`a_format_/b_format_/a_sf_id_/k_size_/max_shift_`，`MXF4Format::E2M1`、`ScaleFormat::UE8M0`），一条指令由**单个线程**发出、覆盖整个 warpgroup，A/B 通过 64 位 smem 描述符寻址，累加器在 tmem；
- 有 1-SM（`tmem_frg_1sm`）和 2-SM（`_2x1SM_SS`，M=128/256，`tmem_frg_2sm`）两种规格。

**SM103 特例**：`cute::SM103` 命名空间下对同一 `SM100_MMA_MXF4_SS` 重新特化了 `MMA_Traits`，`K = 96`，且用统一的 `cute::SM103::mma_unpack` 把**两个 smem 描述符“拼接”**成一条指令（把下一段的 `start_address_` 写进上一段的 `leading_byte_offset_` 并置 `lbo_mode_=1`），从而单次 MMA 吃 2×K；SF 拷贝用 `SM100_UTCCP_4x32dp128bit_2cta`（2-CTA 变体）。这就是 SM103 相对 SM100 “K 翻倍/1.5×”的实现方式。

### SM120：回归 warp 级寄存器 MMA（像 SM80 的 mma.sync）

`cute/arch/mma_sm120.hpp` 里的 `SM120_16x8x32_TN`：

```
mma.sync.aligned.kind::f8f6f4.m16n8k32.row.col.f32.e2m1.e2m1.f32
```

- 寄存器片段：`ARegisters = uint32_t[4]`（16×32 个 4bit）、`BRegisters = uint32_t[2]`、`DRegisters = float[4]`——标准的 **32 线程 warp 级** `mma.sync`；
- 指令本身支持 e2m1/e3m2 × e2m1/e3m2/e2m3/e4m3/e5m2 的混合类型，还有 f16 累加变体（`.f16.e2m1.e2m1.f16`）；
- `mma_traits_sm120.hpp` 定义 `SM120::BLOCKSCALED::SM120_16x8x32_TN_VS` 等 block-scaled 原子，`Shape_MNK = (16, 8, 32)` / `(16,8,64)`，`ThrID = Layout<_32>`，SFA/SFB 是寄存器片段（`SFALayout`/`SFBLayout` 带 2:0/4:0 广播模式）。

**关键的位级差异**：`mma_traits_sm120.hpp` 里专门写了 `fp4_shift_A/B`——SM120 的 `ld.matrix b4x16_p64` 把 FP4 放在 8bit 容器的**低 4 位**（`0b0000ABCD`），而 `mma.sync.kind::f8f6f4` 期望 4bit 数据在**中间位**，所以必须在寄存器里做 `v << 2`（`0b00ABCD00`）。FP6/FP8 不需要这个变换。SM100/103 的 tcgen05 走 smem 描述符，没有这个寄存器重排问题。

## 2. 存储层次与数据通路差异

### SM100/103：tmem 是核心
- 累加器、以及 SFA/SFB 都分配在 **tmem**：`sm100_blockscaled_mma_warpspecialized.hpp` 里的 `TmemStorage{accumulators, tCtSFA, tCtSFB}`，用 `find_tmem_tensor_col_offset` 排布，SF 的 tmem 分配模式 `TmemAllocMode::ScaleFactorDuplicated2by2 / ScaleFactorDuplicated4by1`；
- SF 从 smem 到 tmem 走 **UTCCP**（`SM100_UTCCP_4x32dp128bit_1cta/2cta` + `get_utccp_smem_desc_tensor`）；
- 主循环是经典的 TMA 多级管线（A/B smem）→ tcgen05.mma → tmem，epilogue 从 tmem 读回。

### SM103：把 SF 加载独立成一条管线
`MainloopSm103TmaUmmaWarpSpecializedBlockScaled<LoadABPipelineStageCount, LoadSFPipelineStageCount, SchedulerPipelineStageCount, AccumulatorPipelineStageCount, ...>` —— 相比 SM100，**SFA/SFB 有自己的多级加载管线**（TMA→smem→UTCCP→tmem 单独流水），并且支持运行时数据类型（`args.runtime_data_type_a/b == cute::UMMA::MXF4Format::E2M1` 的检查，`detail::is_sm10x_mxf4nvf4_input()`）；布局也单独在 `cutlass/detail/sm103_blockscaled_layout.hpp`。

### SM120：无 tmem，全寄存器
- `arch.h` 里 `Sm120` 只定义了 `kMinComputeCapability` 和 `kSharedMemoryCapacityBytes`，**没有 `kTmemCapacityColumns`**（SM100/SM103 都有）——即 SM120 没有 Blackwell 风格的张量内存，累加器只能放寄存器；
- 因此 `sm120_blockscaled_mma_tma.hpp` 里 A/B 是 `ElementPairA/ElementPairB`（配对打包的 4bit 元素），TMA 内部元素类型是 `cutlass::detail::float_e2m1_unpacksmem_t`（smem 中“解包”存放），数据路径变为：
  gmem → TMA → smem → `ld.matrix b4x16_p64` → 寄存器（+ `fp4_shift`）→ `mma.sync` → 寄存器累加 → 寄存器 epilogue；
- SF 不再进 tmem，直接以寄存器片段（`tmem_sf_frg` 的对应物变成寄存器 `SFA/SFB`）参与，`SFVecSize` 取自 `TiledMma::Traits::SFVecSize`。

## 3. Grouped GEMM 的差异（调度与内核）

### SM100/103：持久化 group 调度器
- 内核是 `sm100_gemm_tma_warpspecialized.hpp`（以及 array 变体），Grouped 模式配 `PersistentTileSchedulerSm100Group`（`sm100_tile_scheduler_group.hpp`）；
- 它的实现是**把 SM90 的 `PersistentTileSchedulerSm90Group` 包装一层**：因为 grouped 的 problem shape 通常只在 device 上，无法在 host 算 tile 数，所以持久化内核直接**launch 最大 grid**，靠 CLC（cluster launch control）动态取 work tile，支持 CTA rasterization（`RasterOrder::AlongM/N`）、`IsDynamicPersistent`；
- FP4 用 `GemmMode::Grouped` + 每个 group 自己的 scale tensor（对应 `gemm_grouped_per_group_scale.h` / `default_gemm_grouped_per_group_scale.h` 这条入口）。

### SM120：asymmetric-DMA 协同内核 + 通用调度器选择
- 内核是 `sm120_gemm_tma_warpspecialized_cooperative_asymmetric_dma.hpp`：`GemmUniversal` 特化（`is_asymmetric_dma_kernel_tag_of` 使能），**cooperative（grid 内协同）+ asymmetric DMA**；
- 调度器不再是固定的 `Sm100Group`，而是通过 `detail::TileSchedulerSelector<TileSchedulerTag, ArchTag, ...>` 在编译期选择——grouped 场景挂 group 类型的 `TileSchedulerTag`（`TileSchedulerPipelineStageCount` 由 `DispatchPolicy::Schedule` 给出）；
- 内核内部有明显的 asymmetric 结构：A/B 的 smem 缓冲**可配不同 stage 数**（“Asymmetric buffering”）、`LoadWarpOrderBarrier = OrderedSequenceBarrier<1,2>`、producer warp 角色区分 `Warp1` / `LoadNK`、额外的 `TileSchedulerThrottlePipeline`（节流管线）、`NumMmaWarps` + “1 warp for C”；
- 也就是说 SM120 的 grouped 是“一个通用协同内核 + 可插拔 group 调度器”，而 SM100 是“专用持久化内核 + 专用 group 调度器包装”。

## 4. SM120 vs SM121 的关系

`cutlass/arch/config.h` 目前把两者分开登记：
- `CUTLASS_ARCH_MMA_SM120_SUPPORTED`：CUDA ≥ 12.8，`__CUDA_ARCH__ == 1200`；还有 `SM120a`（`__CUDA_ARCH_FEAT_SM120_ALL`）；
- `CUTLASS_ARCH_MMA_SM121_SUPPORTED`：CUDA ≥ 12.9，`__CUDA_ARCH__ == 1210`；`SM121a`、`SM121f` 子变体；
- 但 `cutlass/arch/arch.h` **还没有 `Sm121` 这个 tag**，只有 `Sm120`（`kMinComputeCapability = 120`）。所以 CUTLASS 目前对 SM121 就是**复用 SM120 的 kernel/collective/atom 整条路径**，差异只在编译宏/CUDA 版本门槛上；FP4 的 `kind::f8f6f4` MMA 两代共用同一套 `SM120_16x8x32_TN` 指令描述。

## 5. 迁移/使用层面的注意点（对你写 grouped FP4 kernel 的实际影响）

1. **tmem API 不可用**：SM120 上不能再写 `tcgen05.mma`/`tcgen05.cp`/tmem allocator，要改成寄存器 MMA + `ld.matrix b4x16_p64`；smem 预算也从 ~227KB 掉到 ~101KB（常量值），stage 数和 tile 形状要重新压。
2. **FP4 位布局**：SM120 需要在寄存器里做 `fp4 << 2`（`fp4_shift_A/B`），这是 SM100 没有的；SF 布局也变了（`sm100_blockscaled_layout.hpp` / `sm103_blockscaled_layout.hpp` vs SM120 的 `detail::Sm1xxBlockScaledConfig` + `float_e2m1_unpacksmem_t`）。
3. **MMA 粒度变小**：SM100 单指令 M=64/128、N≤256、K=64；SM120 是 M16×N8×K32，tile 划分、accumulator 布局和 epilogue 都要按 warp 级重写。
4. **2-SM 协作**：SM100/103 有 1CTA/2CTA 的 MMA 与 UTCCP 变体（`IsCtaN1`、`tmem_frg_2sm`），SM120 目前没有 2-SM MMA 原子，跨 CTA 只能靠 cluster/TMA multicast。
5. **调度**：SM120 grouped 走 asymmetric-DMA 协同内核 + `TileSchedulerSelector`，和 SM100 的 `PersistentTileSchedulerSm100Group` 持久化内核在 grid 形状计算、CLC、throttle 管线上的行为不同，性能调优参数（raster order、max_swizzle、A/B 非对称 stage 数）要分开调。

## 1. 计算（Compute）

| | SM100/103 | SM120/121 |
|---|---|---|
| 指令 | `tcgen05.mma`（`kind::f8f6f4`，block-scaled desc） | `mma.sync.aligned.kind::f8f6f4.m16n8k32` |
| 单指令形状 | M=64/128 × N≤256 × K=64（FP4 = 256bit/4bit） | M=16 × N=8 × K=32（另有 16×8×64 VS 变体） |
| 单指令 FLOP（FP4） | $2\times64\times128\times64 \approx 1.05\text{M}$（N=128） | $2\times16\times8\times32 = 8192$ |
| 累加位置 | tmem（warpgroup 共享） | 寄存器（每 warp 独立） |
| 2-SM 协作 | SM103 `MMA2SMConfig` 用 2x1SM（两个 CTA 的 tmem 拼成大 C 块，单条 MMA 吃 2×K，K=96 双 desc LBO 拼接） | **无 2-SM MMA 原子** |

**Megakernel 上的直接后果**：expert 的 M 是动态且往往很小（几十到几百 token）。SM100/103 的 MMA 最小 M 粒度是 64/128，小 expert 会空转 M 维 lanes，所以 megakernel 倾向让一个 CTA 连续吃同一个 expert 的多个 tile（group 内 tile 化）来摊薄；SM120 的 M=16 粒度细、对“碎片化 token 集”更友好，但单指令 FLOP 小两个数量级，纯算力靠高指令率堆出来，小 expert 的启动/切块开销占比反而更敏感。

## 2. 流水（Pipeline）

**SM100/103（warp-specialized，warpgroup 粒度）**
- producer warpgroup：TMA 预取 A +（92 示例）**CPASYNC 预取 B** + UTCCP 把 SF 搬进 tmem；
- consumer warpgroup：tcgen05.mma；
- epilogue warpgroup：tmem→寄存器→写 C。
- SM103 相比 SM100 的关键增强：`MainloopSm103TmaUmmaWarpSpecializedBlockScaled<LoadABPipelineStageCount, LoadSFPipelineStageCount, SchedulerPipelineStageCount, AccumulatorPipelineStageCount, …>`——**SF 加载被拆成独立的多级管线**（SFA/SFB 的 TMA→smem→UTCCP→tmem 与 A/B 解耦），可以预取更深、且每级 stage 数独立调。

**SM120（asymmetric DMA + 协同，warp 粒度）**
- `WarpGroupRole{Producer, Consumer0, Consumer1}` + `ProducerWarpRole{LoadMK, Warp1, LoadNK, LoadMN}`：一个 producer warpgroup 里拆出 4 个子角色，`Warp1` 专门跑调度器 fetch，`LoadMK/LoadNK` 发 A/B 的 TMA；
- **A/B 非对称缓冲**（asymmetric DMA）：A 和 B 可以配不同的 stage 数；
- `LoadWarpOrderBarrier = OrderedSequenceBarrier<1,2>`（1 stage 有序 barrier）；
- 调度器本身有 `TileSchedulerPipeline`（`transaction_bytes = sizeof(WorkTileInfo)`）+ `TileSchedulerThrottlePipeline`（节流，producer=NumMainloopLoadThreads / consumer=NumSchedThreads），只在 dynamic persistent 调度器下激活。

**Megakernel 后果**：SM100/103 的 megakernel 是“一个 CTA 盯一个 expert 的 tile 流”，SF 预取（SM103）可以藏掉 expert 切换时 SF 重载的延迟；SM120 的 producer 结构更细（调度器、A、B 分属不同 warp），吞吐节奏由 throttle pipeline 控制，适合把“调度器 fetch 下一组 expert”和“当前 expert 的 TMA”重叠，但多了一层跨 warp 的 barrier 同步开销。

---

## 3. 数据搬运（Data movement）

- **SM100/103**：`gmem → TMA → smem`（A/B）→ smem 描述符直接喂 `tcgen05.mma`（**数据不经过寄存器**）；SF 走 `gmem → TMA → smem → UTCCP(4x32dp128bit) → tmem`。92 示例特意把 B（各 expert 权重）改成 **CPASYNC** 搬运，理由写在注释里：*“avoid the overhead of updating TMA descriptors”*——MoE 里每个 group 的 B 指针/stride 都不同，逐组更新 TMA 描述符有延迟，CPASYNC 直接按地址拷贝更省事。SM103 的 PtrArray 版本则用 device 端编码 tensor map（CUTE tensor map）支持 per-group 布局（`ptr_SFA, layout_SFA, …` 都是 per-group 的）。
- **SM120**：`gmem → TMA → smem → ld.matrix b4x16_p64 → 寄存器`，SF 也进寄存器（无 tmem 可放）；TMA 内部元素用 `float_e2m1_unpacksmem_t`（smem 里解包存放）。多了一层**寄存器中转**，且 FP4 数据要 `<<2` 移位重排（见下）。
- **Megakernel 后果**：A 是跨 expert 的 token gather（行不连续），B 是每个 expert 的稠密权重。SM100/103 的 B 用 CPASYNC/PtrArray 就是为消除 per-expert 描述符更新；SM120 目前没有对应的 MoE 专用内核，若直接套 `sm120` asymmetric 内核，B 的 per-group TMA 描述符更新开销会重新出现（要么仿照 92 的做法改成 CPASYNC 路径，要么用 PtrArray 变体）。

---

## 4. 指令发射（Instruction issue）

- **SM100/103**：`tcgen05.mma` 由 warpgroup 内**单线程发射**、整组执行；一条指令完成上百万 FLOP。加上 `tcgen05.cp`（tmem 写）、`tcgen05.ld`（epilogue 读 tmem）、UTCCP，指令总数极少，warpgroup 级同步。
- **SM120**：每个 warp 独立发 `mma.sync`（m16n8k32），**发射量约为 SM100 的 128 倍**（按 N=128 对比）；还需新指令 `ld.matrix b4x16_p64`（4bit 矩阵装载）+ **`fp4_shift`（寄存器里 `<<2` 移位）**——因为 `ld.matrix` 把 FP4 放在 8bit 容器低 4 位、而 `mma.sync.f8f6f4` 期望在中间位，这是 SM100/103 完全没有的额外 ALU/位操作开销。
- **Megakernel 后果**：SM100/103 指令少，调度（group 切换、tile 坐标计算）开销占比相对高，所以用大 tile + 硬件 CLC 摊薄；SM120 指令多而小，每发一条 MMA 都要同步 smem barrier，指令发射带宽与 barrier 频率成为新的天花板，megakernel 里“连续多个 expert tile 的 MMA 背靠背发射”的窗口更短。

---

## 5. 寄存器 / 共享内存（Register & SMEM）

| | SM100/103 | SM120/121 |
|---|---|---|
| SMEM 容量常量 | 232448 B（~227KB） | 101376 B（~99KB） |
| 累加器 | tmem（不占寄存器） | **寄存器**（每 warp 片段，大 C tile 要吃很多寄存器） |
| SF 存放 | tmem（`tCtSFA/tCtSFB`，`ScaleFactorDuplicated2by2/4by1`） | 寄存器（SFA/SFB 片段） |
| 寄存器用途 | 地址/描述符/小片段 | A/B/SF/C 全部经寄存器，还要容纳 `fp4_shift` 中间值 |

**Megakernel 后果**：
- SM100/103 可以把 C tile 做得很大（M=128/256、N 到 512）而寄存器不爆，因为累加在 tmem——megakernel 里一个 CTA 处理大 expert 时很从容；
- SM120 无 tmem + 99KB smem：tile 必须缩小（stage 数受限），大 C 累加占满寄存器，epilogue 频率变高（更多 C store）；同一时刻能驻留的 expert 工作状态更少，跨 expert 的寄存器上下文切换（如果做多 expert 并发）成本更高；
- smem 减半直接影响 megakernel 的 B 权重驻留策略：SM100/103 可以在 smem 里多留几组 expert 权重做“组间预取”，SM120 得靠更深的 A/B 非对称流水线去弥补。

---

## 6. Megakernel 工作分配（Work distribution，最关键的一条）

- **SM100/103**：`PersistentTileSchedulerSm100Group` = `PersistentTileSchedulerSm90Group` 的包装（`sm100_tile_scheduler_group.hpp`）。注释明说：*“launches the largest grid possible … and thereafter use CLC query (which can then be linearized and mapped to an appropriate tile coord)”*——因为 grouped 的 problem shape 常只在 device 上、host 算不出 grid，所以**持久内核按最大 grid 发射，每个 CTA 用硬件 CLC（`cluster_launch_idx`）取线性工作号**，近乎零开销；支持 `RasterOrder{AlongM,AlongN}`、`max_swizzle_size`、2SM 内核用 CTA tile shape 做调度。
- **SM120**：`TileSchedulerSelector<GroupScheduler, Sm120, …, GroupProblemShape>::Scheduler = PersistentTileSchedulerSm90Group`（**SM90 原版，不是包装**）。它是 `IsDynamicPersistent=false` 的静态持久调度器：用**全局线性 work 计数器 + warp 协同扫描**（`GroupInfo{group_idx, start_linear_idx, total_tiles, log_swizzle_size}`、`cached_problem_shapes` 双缓冲、32 组一批扫描）取 tile——即 **SM120 的 megakernel 工作获取退回到全局内存原子/线性计数**，没有 SM100 的硬件 CLC 加速，靠内核里的 `TileSchedulerPipeline` 缓冲来抵消 fetch 延迟。
- 另外 SM120 的调度器 pipeline `transaction_bytes = sizeof(WorkTileInfo)` 说明工作块在 warp 间通过 smem 管线传递（producer 的 `Warp1` 角色取块），这和 SM100 的“单 CTA 直接查 CLC”是两套机制。

---

## 小结：如果你的目标是写一个跨两代的 NVFP4 MoE megakernel

1. **计算层**：SM100/103 用 tcgen05+tmem 大指令（M64/128×K64，2-SM 可拼 M256），SM120 只能退到 warp 级 m16n8k32 寄存器 MMA，必须重写 MMA 调度与累加布局，且要处理 `fp4 << 2` 移位。
2. **流水层**：SM103 有独立的 SF 管线 stage 数可调，SM120 是 asymmetric DMA（A/B 独立 stage）+ `OrderedSequenceBarrier<1,2>` + throttle pipeline，barrier 结构完全不同。
3. **数据搬运**：SM100 的 B 可用 CPASYNC 规避 per-group TMA 描述符更新（92 示例），SM103 用 PtrArray + device 端 tensor map；SM120 目前无 MoE 专用内核，这两招都还没有现成实现，需要你自己补（或等 CUTLASS 出 SM120 MoE example）。
4. **指令发射**：发射量差两个数量级，SM120 要盯住 mma.sync 发射率与 smem barrier 频率。
5. **寄存器/smem**：SM120 无 tmem、smem 砍半（227KB→99KB），大 C tile 必须拆小，寄存器预算成为主要约束。
6. **工作分配**：SM100/103 = 持久网格 + 硬件 CLC（近零开销），SM120 = SM90 式全局原子/线性计数 + smem 调度管线（有竞争和延迟，需要 pipeline 掩藏）——megakernel 的 grid 形状、raster/swizzle 策略、以及“何时取下一组 expert”的节奏要按这两套机制分别调。
