## 先说结论

HWRT 真正改变的只有一件事：**找出并返回交点**。它把 SWRT 里那种 `steps × 屏幕空间采样` 的启发式搜索，换成了 **BVH 上的 O(log N) 指针追逐 + 固定功能三角形求交**，并且把“可见性”从屏幕空间移到世界空间。

但它**不改变**三件事，而且这三件恰好是你现在痛苦的根源：

1. **shade 一个 hit 的成本不会消失**，甚至更贵（离屏 hit 没有现成的 GBuffer 可采）。
2. **denoise 仍然必须有**。HWRT 给你的是“正确的可见性”，不是“收敛的积分”。
3. **带宽焦虑不会自动消失**，只是从“深度图反复抓取”变成“BVH 节点反复抓取 + hit 处的材质数据抓取”。

所以实际迁移时，80% 的工作量不在发 ray，而在**重建“离屏几何的着色数据源”**。下面按你实际落地需要的顺序说。

## 1. 具体是怎么执行的：一帧的完整链路

这是你问的“具体怎么做”，先给出可执行的骨架：

```text
[离线/加载时]  mesh → BLAS（bottom-level AS，三角形级 BVH）
                          ↓ 只建一次（或每次变形时 refit）
[每帧 CPU/Compute]  instance 列表 → TLAS（instance 级 BVH，4x3 矩阵 + BLAS 引用）
                          ↓
[每帧]  TLAS 绑定到 descriptor / root SRV
                          ↓
        Dispatch(compute) @ RT 分辨率（1/2 或 1/4，与显示分辨率解耦）
                          ↓
        per pixel:
          世界空间 origin（G-buffer 反投影，只做一次）
          方向（反射 / 余弦半球 / 重要性采样，blue noise 抖动）
          TraceRayInline(…) → Proceed()
          hit? → instanceID + primID + barycentrics
                 → 插值出世界坐标 / 法线 / UV
                 → 取材质（GBuffer 存在则该像素，否则走 Surface Cache）
                 → 着色，输出 radiance + hitDepth + hitNormal
                          ↓
        Denoise（temporal accumulate + 空间滤波）→ Composite
```

**关键差异**：第 5 步的 ray 是**在世界空间里直接发**的，不是“从深度图重建、沿屏幕空间 march、撞到屏幕边缘就 fade 掉”。这就是你“特定 case 出问题”和“精度无法保证”的解药。

## 2. 加速结构（AS）：HWRT 的存储代价

| | BLAS | TLAS |
|---|---|---|
| 粒度 | 单个 mesh 的三角形 | instance（矩阵 + 引用 BLAS） |
| 更新频率 | 静态时一次；蒙皮/变形时 refit 或重建 | **每帧** |
| 内存 | 未压缩 ~32 B/tri，压缩后 ~8–12 B/tri | 每个 instance 几十字节 |
| 1M 三角形 | 约 8–30 MB | 1 万 instance 约 <1 MB |

<details>
<summary>为什么节点要“宽”+“量化”（这是带宽的关键）</summary>

硬件遍历走的是 **BVH4 / BVH8**（一个节点 4 或 8 个子节点），不是教科书上的二叉树。原因：binary BVH 每层只砍掉一半空间，指针追逐深度太深，latency 爆掉。宽节点把深度压到 $\log_8 N$，且一次 cache line 抓 4–8 个 child AABB。

为了塞进 cache line，节点做**量化**：NVIDIA 的压缩 BVH 用 8-bit 存 child AABB 相对父节点的偏移 + 共享指数，一个 64-byte 节点装下整层。这是 HWRT 带宽能接受的核心原因，也是 `BUILD_FLAG_PREFER_FAST_TRACE` 比 `FAST_BUILD` 慢但 trace 快一截的来源。

代价：**BVH 是 cache 不友好的数据结构**。incoherent ray（path tracing、粗糙反射）会让 L2 命中率掉到很低，这时候 HWRT 的带宽优势会大幅缩小 —— 这与直觉相反，但与你的 SWRT 痛点正好镜像。
</details>

## 3. 进入 RT core 后发生什么

<details>
<summary>微架构细节（可跳过）</summary>

每个 SM 挂一组 RT core，做两件固定功能的事：

- **box test**：ray vs AABB（slab 法），吞吐最高（Turing 起约 4 box/clk/SM 量级）
- **triangle test**：ray vs triangle，吞吐约 1 tri/clk/SM（低一个数量级）

求交用 **watertight ray/triangle test**（Woop et al. 2013）：沿主轴把三角形投影到 2D，用 edge function 做保守浮点舍入，保证相邻三角形共享的边**不会漏光也不会重复命中**。这是 SWRT 里你手动 march 永远做不到的——这也是为什么 HWRT 的精度是从原理层面保证的，不是调出来的。

遍历本身是**指针追逐**，所以是 **latency-bound 而非 bandwidth-bound**（桌面端）。这就是为什么：

- 只要能塞进足够多 in-flight ray，带宽就不是瓶颈；
- **ray 数量通常不是瓶颈**。1080p、1 ray/pixel、60 fps 的 GI ≈ $1.24\times10^8$ rays/s ≈ 0.12 GRays/s，对现代桌面 GPU 来说是微不足道（几十 GRays/s 量级）。真正的成本在 **divergence + hit shading**。
- 移动端是例外：TBDR、占用率低、cache 小，延迟藏不住，必须靠“低 ray 数 + 强 reuse”扛。
</details>

## 4. 两种 API 形态：该用哪个

| | RT Pipeline（SBT） | **Inline Ray Query** |
|---|---|---|
| 形态 | RayGen/Hit/Miss 独立 shader，靠 Shader Binding Table 分派 | compute shader 里一行 `TraceRayInline` |
| 适合 | path tracer、需要 any-hit 的 alpha test 材质、多 bounce | **SSGI/SSR 替换、hybrid 管线** |
| 开销 | 要过 SBT 间接分派，短 ray 不划算 | 无 dispatch 开销，可和自定义逻辑交织（早退、循环多 ray、LDS 通信） |

**你的场景几乎一定是 ray query。** 它允许你在同一个循环里做“先试 screen trace，失败了再 inline trace”，这正是 UE5 Lumen 的形态。

```hlsl
RayDesc ray;
ray.Origin    = worldPos + normal * 0.02;   // 自相交偏移，见 §7
ray.Direction = dir;
ray.TMin      = 0.0;
ray.TMax      = 4000.0;

RayQuery<RAY_FLAG_NONE> q;
q.TraceRayInline(TLAS, RAY_FLAG_FORCE_OPAQUE | RAY_FLAG_CULL_BACK_FACING_TRIANGLES,
                 0xFF, ray);
while (q.Proceed()) { /* 需要 alpha test 时在这里判 */ }

if (q.CommittedStatus() == COMMITTED_TRIANGLE_HIT) {
    float  t     = q.CommittedRayT();
    uint   inst  = q.CommittedInstanceID();
    uint   prim  = q.CommittedPrimitiveID();
    float2 bary  = q.CommittedTriangleBarycentrics();
    // bary → UV → 材质 → 着色
}
```

## 5. 逐条对照你现在的问题

| 你的问题 | HWRT 之后 |
|---|---|
| 显存带宽压力大 | **改善，但不是归零**。SWRT 的 `steps × 深度图双线性采样`（每步都可能 cache miss）变成一个 hit 的 $\log N$ 次节点抓取 + 1 次材质抓取。但**别忽略 Hi-Z mip chain 每帧的构建带宽**——那份开销 HWRT 直接没了 |
| 向量单元占用高 | 大幅降低。求交从 ALU 搬到固定功能单元，省下的算力可以给 denoise 或 shading |
| RT 分辨率一高就耗尽资源 | **这是最大的结构性收益**。SWRT 成本 $\propto P \cdot S$（像素 × march 步数）；HWRT 成本 $\propto R \cdot \log N$（**ray 数**，与显示分辨率解耦）。降 RT 分辨率时，HWRT 只是变模糊，SSGI 是变模糊**加变错** |
| 依赖屏幕空间、特定 case 报错 | 消失。屏幕外的物体照样能命中，没有边缘 fade、没有 disocclusion 的“内容凭空出现” |
| 精度无法保证 | 从原理上解决（见 §7） |
| 需要 baked GI / skybox fallback | 这个**不会自动消失**，见 §6 |

成本模型对比：

$$C_{\text{SWRT}} \approx P \cdot S \cdot \left(B_{\text{depth}} + A_{\text{alu}} + B_{\text{hi\text{-}z build}}\right)$$

$$C_{\text{HWRT}} \approx R \cdot \left(d \cdot B_{\text{node}}\right) + P_{\text{hit}} \cdot B_{\text{shade}}$$

其中 $R$ 是 ray 数、$d$ 是平均遍历深度、$P_{\text{hit}}$ 是有 hit 的像素数。注意第二项——**它才是新的瓶颈**。

## 6. HWRT 不解决什么（这是最容易被低估的部分）

### 6.1 命中之后，radiance 从哪来？

这是核心问题。SSR 撞到屏幕外就 fade 到 skybox；HWRT 能撞到真实几何，**但你得能 shade 它**。而离屏几何：

- 没有 GBuffer（这个像素没渲染）
- 没有屏幕空间 reprojection 可用
- 材质可能根本没解压

工业界的三种回答：

| 方案 | 做法 | 代价 |
|---|---|---|
| **Surface Cache / Card Capture** | 每个 mesh 的 6 个正交面捕捉 albedo/emissive/normal 到 atlas，低分辨率（如 128²/面），hit 时按世界坐标查表 | 内存 + 每帧更新开销；高光/薄片几何失真 |
| **Probe / SH 网格** | hit 点查最近的 irradiance probe | 漏光、空间分辨率低 |
| **继续追踪（path continue）** | hit 点再发一次 ray，2–4 bounce | ray 数 ×3–4，divergence 爆炸；必须配 ReSTIR |

> UE5 Lumen 的完整答案就是：**Screen trace（近场）+ Surface Cache + HWRT（远场）+ Radiance Cache + Final Gather**。注意它**第一件事仍然是屏幕空间 trace**——你的 Hi-Z 代码不是白写的。

### 6.2 Denoise 仍然要，但性质变了

- SWRT 的噪声是**结构性错误**（屏幕边缘 fade、disocclusion 抖动、步长过大导致漏检）——时间累积会把错误一起累积，表现为拖影。
- HWRT 的噪声是**统计性的**（1 spp 蒙特卡洛），空间上是白噪声。可以放心用 temporal reprojection + 短历史，收敛更快、拖影更轻。

想少放 ray，现代做法是 **ReSTIR（DI/GI）**：靠 reservoir 在时空上复用已有 ray 样本，把 effective spp 拉高一个量级。这才是“HWRT 省带宽”的真正放大器。

### 6.3 每帧 BLAS 更新

蒙皮、布料、破坏——这些 mesh 的 BLAS 每帧要 update。`refit`（保持拓扑，重算 AABB/三角形）比 `build` 便宜一个量级，但品质会退化，需要周期性重建。这是 HWRT 在动态场景里的隐性 CPU/GPU 开销，你的 SWRT 管线里**没有对应项**，做预算时要算进去。

### 6.4 Divergence

coherent ray（从 G-buffer 逐像素发、邻居打向相似方向）表现很好。一旦做多 bounce 或粗糙度大的反射，warp 内 ray 打向完全不同的 BVH 分支，**固定功能单元空转**。对策：ray sorting / work compaction / Ada 的 **SER（Shader Execution Reordering）**——硬件按 hit 后要跑的 shader 对 warp 重排，Lumen 里实测能省 20–40%。

## 7. 精度：为什么 HWRT 是“原理级”正确

<details>
<summary>展开看细节</summary>

**a) 没有深度反投影这一步。** SWRT 必须从 24/32-bit depth 重建世界坐标，在远平面附近精度会**急剧下降**（尤其 reverse-Z 之外的常见配置）。HWRT 的 ray 直接在 world space 定义，$t$ 是浮点插值出来的，不受深度缓冲量化影响。

**b) Watertight 求交。** 共享边不会漏、不会重，杜绝了 SWRT 里“march 步长跨过薄几何”和“Hi-Z 保守性不足导致漏检”两类错误。

**c) 自相交（self-intersection）。** 这是实际实现时最容易踩的坑，两个手段并用：

```hlsl
// 1) 沿法线偏移 origin（对凹凸表面偏移要按斜率缩放，否则高光处穿帮）
float3 origin = P + N * (0.01 + 0.005 * length(P - cameraPos));
// 2) 抬高 TMin 作为兜底
ray.TMin = 1e-3 * tScale;
```

对于两 sided 薄几何（叶片、布料）要用 `RAY_FLAG_CULL_BACK_FACING_TRIANGLES` 之外的处理，或者干脆 double-sided + 偏移法线取反。

**d) 大世界坐标。** TLAS instance 变换用 float，origin 用 camera-relative（减去相机位置）能显著改善远处抖动。别在绝对世界坐标下算 $P + d\cdot t$。
</details>

## 8. 迁移路线（从你现在的管线改造）

不要一次性替换。按下面顺序走，每步都能独立验证：

**Step 0 — 保留现状。** 你的 Hi-Z + SSR/SSGI 代码保留，它变成 **near-field pass**。Lumen 也这么干，因为屏幕内命中又便宜又准（无需抓 BVH、无需查 Surface Cache）。

**Step 1 — 只换“miss 分支”。** 现在 fullscreen march 失败后你走 skybox fallback。改成：march 失败 → `TraceRayInline` 打同样的方向 → 命中真几何。这一步**不需要 Surface Cache**，因为你已经在 GBuffer 里有屏幕内数据，只在 miss 时才走新路径，可以先退化成“命中就返回 albedo × 环境光 / 或命中点查探针”。

**Step 2 — 验证性能模型。** 此时对比：march 步数衰减到多少时，HWRT fallback 比继续 march 划算。经验上 RT 分辨率降到 1/2、march 限制在 8–16 步，性能会比纯 march 更稳，且画质变好。

**Step 3 — 建 Surface Cache。** 这是最大的工程量。要先解决：卡面生成（mesh → 6 面 atlas）、材质烘焙（albedo/emissive/normal/roughness）、每帧增量更新（只能更新“有变化”的 instance）。

**Step 4 — 引入 radiance cache / probe 层级，把 fallback 的“假光照”替换成真实的间接光。**

**Step 5 — 考虑 ReSTIR GI** 来降低 ray 数，此时再谈“省带宽”才有意义。

## 9. 硬件层面的实际开关

| 开关 | 作用 |
|---|---|
| `PREFER_FAST_TRACE` | BVH 构建慢、trace 快（质量优先）。静态几何用这个 |
| `PREFER_FAST_BUILD` | 每帧重建的 BLAS 用这个 |
| **AS Compaction** | 建完压缩，BVH 体积降 ~30–50%，直接省带宽和 cache。**必开** |
| `ALLOW_UPDATE` + `performUpdate` | 蒙皮 mesh 的 refit 路径 |
| 量化/压缩 BVH | NVIDIA 默认开；某些驱动有 `D3D12_RAYTRACING_ACCELERATION_STRUCTURE_BUILD_FLAG_...` 相关 hint |
| SER / work graphs | Ada+；无此硬件时用软件 ray sorting 替代 |
| 移动端 | 基本只有 **Vulkan `rayQueryEXT`**（无 RT pipeline），RT unit 吞吐低且和 texture unit 竞争，必须 1/4 分辨率 + LDS 批处理 ray + 强 temporal reuse |

## 10. 一句话总结

> HWRT 帮你把“**可见性**”这个问题从启发式搜索变成精确求解，顺带干掉了深度反投影的精度损失、屏幕边缘的 fade 和 Hi-Z 构建的带宽。
>
> 但它把“**shade 一次离屏命中**”这个问题原封不动地留给了你，而且因为不再有屏幕空间兜底，它变得更尖锐——你最终一定要建某种世界空间的材质/辐照度缓存（Surface Cache、probe、radiance cache）。
>
> 所以真正的迁移成本不在 `TraceRayInline` 那一行，而在那之后你打算拿什么去着色。

对，但这里可以再精确区分一个层级：慢的原因在于 **工作量无界、有长尾，而且空区域最贵**。

## 三个具体原因

**1. 每步的“信息效率”极低。** 一次 bilinear depth fetch = 4 个 texel、2 条 cache line、一次插值,换来的信息是“这一小段有没有东西”——1 bit 不到。如果 ray 打向远处掠射角,你贴着表面走 32 步,付出 64 条 cache line,最后还漏检。

**2. 空区域花费最高。** 这是最关键、也最反直觉的一点：

> SWRT 在**空区域**上的开销是**最大**的（必须一步步走过，每步都付满额）。
> BVH 在**空区域**上的开销是**最小**的（一次 box test 直接剪掉整棵子树，甚至不用往下走）。

而 GI ray、长距离反射 ray，**90% 的路径都在空区域里**。两者对场景的代价模型完全相反：SWRT 的成本 ∝ 空间体积，HWRT 的成本 ∝ 实际几何密度。这就是为什么同一个场景，加一堵墙 SWRT 变贵、HWRT 可能几乎不变。

**3. 长尾。** march 步数是不确定的 $S \in [1, 64]$。GPU 上 tile 的完成时间由**最慢的那个 warp**决定，所以一个反光的角落能拖垮整块 tile 的时间。固定功能的 $d$（遍历深度）有硬上界，方差小得多——**这对做到稳定帧率的意义比平均吞吐更大**。

$$W_{\text{march}} = S \cdot (4\,\text{texel} + \text{ALU}), \quad S \text{ 无界}$$

$$W_{\text{bvh}} = d \cdot 64\text{B} + 1\,\text{hit fetch}, \quad d \lesssim 40 \text{ 有界}$$

## 但要纠正一个误解：BVH 一样不 cache 友好

别指望“交给硬件”就解决了 cache 问题。BVH 遍历本质上是**指针追逐**，是教科书级的 cache 反例。真正起作用的只有两个：

- **有界**（可预算，可调度）
- **稀疏跳过**（box test 极便宜，一片区域一次拒绝）

所以 HWRT 的收益来自**把开销从“无界 × 高单价”变成“有界 × 低单价”**，而不是“变 cache 友好”了。

## 你的 fullscreen dispatch 本身不要改

这点很重要：**ray 相干性**才是 cache 友好的关键，不是你用什么方式发射 ray。1 thread / pixel、按屏幕顺序发射，邻居的 ray 会打进 BVH 里相邻的节点——**对你现在的代码结构恰恰是最优的**。

真正让 BVH 变慢的是多 bounce path tracing、粗糙度爆表的半球采样：warp 内 ray 分散到几十个不同子树，RT unit 空转、L2 全 miss。所以：

- **GI / 反射：保持逐像素同序发射，天然相干，表现最好**
- 一旦要加 bounce、加 ReSTIR 重采样，才需要 ray sorting / SER 来把相干性抢回来

## 实操：按 ray 类型决定是否先走 screen trace

别一刀切全丢给 HWRT，那一刀切会亏：

| ray 类型 | 策略 | 理由 |
|---|---|---|
| 镜面 / 低粗糙度反射 | **先 screen trace，miss 再 HW** | GBuffer 刚渲染完，depth 还在 L2 里，这次 screen trace 几乎免费；而且屏幕内的解质量更高（全分辨率、无 BVH 采样） |
| 漫反射 GI / 大粗糙度 | **直接 HW trace，跳 screen trace** | ray 本来就不相干、大部分打向屏外，screen trace 命中率低，纯粹浪费两次 march 的 ALU |
| 任何 ray | 分辨率 1/2 或 1/4 + denoise | HWRT 降分辨率只损失清晰度，不产生错误；SSGI 降分辨率是清晰度 + 正确性双输 |

结论是：**瓶颈是搬家不是消失**——从“向量单元 + 深度图带宽”搬到“occupancy 藏 latency + hit shading divergence + BVH 抓取”。但搬过去的好处是这三个都**能用工程手段压**（降 ray 数、排序、Surface Cache 降质），而 SWRT 那三个是**原理性压不住**的。

移动端单独提醒一句：RT unit 和 texture unit 常常共享流水线/带宽，你的 hit shading 采样材质的时候会和 ray 抢同一个单位，所以那边更要靠 1/4 分辨率 + LDS 打包 ray + 强 temporal reuse，别指望靠“硬件免费”。
