## 结论（先给数）

FP16 矩阵乘（Tensor Core，dense）对比如下，A100 取 SXM/PCIe 80GB（均为 108 SM、1.41 GHz，算力相同）：

| 模式 | RTX 5090 | A100 | 5090 / A100 |
|---|---|---|---|
| FP16 MMA + **FP16 累加** | **419 TFLOPS**（sparse 838） | **312**（sparse 624） | **强约 1.34×（+34%）** |
| FP16 MMA + **FP32 累加** | **≈209.5 TFLOPS**（sparse 419） | **312**（sparse 624） | **只有 A100 的 0.67×（反而弱 ~33%，A100 是它的 1.49×）** |
| BF16（只能 FP32 累加，作参照） | ≈209.5（419） | 312（624） | 0.67× |

**一句话**：5090 只有在用 FP16 累加时 FP16 GEMM 才比 A100 强 1/3；一旦用 FP32 累加（cuBLAS/训练默认），它只有 A100 的 2/3。加不加累加精度这一项，结论会直接反转。

<details>
<summary><b>数字怎么来的 / 为什么会出现这种反转</b>（点开）</summary>

**1. GeForce 对 FP32 累加砍半，A100 不砍**

NVIDIA 官方 *RTX Blackwell GPU Architecture* 白皮书 Table 3 里，5090 的 FP16 Tensor 有两行：
- `Peak FP16 Tensor TFLOPS with FP16 Accumulate = 419`（dense，2:1 sparsity 后 838）
- `Peak FP16 Tensor TFLOPS with FP32 Accumulate ≈ 209.5`（dense，sparse 419）

NVIDIA 论坛（CUDA 板块）有官方 moderator 明确确认过这两行：FP16 + FP16 累加的 dense 峰值就是 **419 TF**；而"acc fp32"那一行是 209T——每 SM 每时钟 1024 FLOP（FP16 累加）→ 512 FLOP（FP32 累加）。

A100 则是**两种累加同速**。NVIDIA Hopper 架构博客 Table 3 列得很清楚：
```
Peak FP16 Tensor TFLOPS with FP16 Accumulate: 312/624
Peak FP16 Tensor TFLOPS with FP32 Accumulate: 312/624
```
即 A100 = 108 SM × 2048 FLOP/SM/clk × 1.41 GHz ≈ 312 TFLOPS，FP32 累加不掉速。

**2. 单 SM 看，5090 其实弱于 A100**
- A100：2048 FLOP/SM/clk（FP16），两种累加都一样
- 5090：1024 FLOP/SM/clk（FP16 累加）/ 512 FLOP/SM/clk（FP32 累加）

5090 总量领先靠的是 **170 SM × ~2.41 GHz** 的堆料 + 更高频率；单 SM 的 FP16 吞吐与 A100 打平（FP16 累加）或被 A100 2 倍碾压（FP32 累加）。

**3. 频率/稀疏性不影响倍率**：sparse 两者都 ×2，比值不变；实测略有 5–10% 出入（boost 频率、功耗墙）。

</details>

## 实操上要注意的坑

- **默认跑不到 419。** cuBLAS 的 FP16 GEMM 默认用 FP32 累加，所以你实测 5090 大约只有 ~210 的理论上限（实际 ~180–200 TFLOPS）。要吃到 419 必须显式启用 FP16 累加，例如 `CUBLAS_COMPUTE_16F`、或 CUTLASS/CUDA kernel 里的 `mma.sync ... f16.f16.f16.f16`（`_F16F16F16F16` 那类指令），PyTorch 里基本没有现成开关。
- **FP16 累加有精度风险。** K 很大时在 FP16 里累加会丢精度，一般靠分块（split-K / block-wise accumulation）补救，适合推理或短规约；正规训练（尤其 BF16）走 FP32 累加，那就只能拿 0.67× A100 的账。
- **算力不是全部。** A100 SXM 80GB 有 2039 GB/s HBM2e + 80GB 显存 + NVLink；5090 是 1792 GB/s GDDR7 + 32GB 且无 NVLink。LLM 解码这类访存密集型任务，A100 常常并不落后。
- A100 还有 **TF32 Tensor（156/312）** 和 **FP64 Tensor（19.5）**，这两项消费卡基本没有可比项。

## 先给结论

你的观察没错，而且**和"FP32 累加被砍半"并不矛盾** —— 问题出在你我前面用的那两组"标称值"都被曲解了：

1. **5090 白皮书里的 209.5 TF 明显偏低。** 用你自己跑的那个工具（`mmapeak`）在 5090 上实测，FP16+FP16acc = **740.8**、FP16+FP32acc = **369.9** —— 台阶是干净的 2:1（说明砍半真实存在），但 fp32acc 的**绝对值 ≈ 370**，已经**超过** A100 的理论峰值 312，更远超白皮书的 209.5（1.77×）。
2. **A100 的 312 是纸面峰值。** 真实 cuBLAS/torch 的 FP16+FP32acc GEMM 在 A100 上通常只有 220–280（70–90%），PCIe 卡 / 功耗受限的服务器里更低。

两个误差方向相反、量级相当 → 实测到实测就"差距很小甚至持平"了。

## 实测证据（mmapeak，5090 / 170 SM）

| 指标 | 5090 fp16+fp16acc | 5090 fp16+fp32acc | 备注 |
|---|---|---|---|
| `mmapeak` 实测 | **740.8** T(fl)ops | **369.9** T(fl)ops | 严格 2:1 |
| 白皮书标称（Table 3） | 419 | 209.5 | 实测是它的 ~1.77× |
| 同卡其它精度实测 | FP8-f16acc 732.3、INT8 740.9、FP4(f32acc) 1463 | FP8-f32acc 369.9、TF32 93.3 | 见下 |

对照 A100：`mmapeak` 这类纯 MMA 微基准效率接近 100%（它在 H100 NVL 上打出 992，而 H100 标称 989），所以 A100 上 `f16f16f16` 与 `f16f16f32` 会给出**几乎相同**的值（≈300 上下，两边都不砍半）。

于是就有了这个"反直觉"的组合：

- 5090：740.8 / **369.9**（砍半，但绝对值仍 ≥ A100 的 312）
- A100：≈312 / ≈312（不砍半，但实测 GEMM 只能吃到 ~220–280）
- torch 里两边都落在 200–260 → **持平**；`mmapeak` 里 370 vs ~310 → **差距很小（+19%）**

旁证：同仓库里 **5090 D** 的实测是 `f16f16f16 = 427.9`、`f16f16f32 = 337` —— 427.9 恰好接近白皮书的 419。所以有可能白皮书那张表的 FP16 行是按被阉割的那一档（或某个较低频率点）给的，而不是满血 5090 的实际能力。

## 所以怎么理解这件事

- **"砍半"是真的**：5090 的 fp32acc 通路只有 fp16acc 的一半，也远低于它自己的 FP8 速率。你在 `mmapeak` 上应该能看到 740/370 这个台阶；看不到就说明没测到 fp32 累加路径。
- **"砍半后仍不输 A100"也是真的**：按实测的 1024 FLOP/SM/clk，5090 的 fp32acc 峰值 = 1024×170×(2.1~2.6 GHz) ≈ **370~450 TFLOPS**；A100 = 2048×108×1.41 GHz = 312（理论）。所以同口径下 5090 反而略高，而不是 0.67×。
- **A100 的 312 基本吃不满**：A100 SXM 80GB 在 cuBLAS 大 GEMM 上通常 240–280；PCIe/降频环境下 200 上下；加上小 shape、K 不够大时效率更低。而 5090 靠 GDDR7 1792 GB/s + 大 L2，在大家常用的 4096³/8192³ 上更容易喂饱张量核。
- **别忘了 FP16 累加那一档才是分水岭**：5090 fp16acc ≈ 740（甚至受限于实测频率还会更高），A100 两种累加都是 312 → **2.2–2.4×**。也就是说结论仍然是"5090 相对 A100 强多少，取决于累加精度"，只是 fp32acc 那一项应该写成**"基本持平/略优"，而不是我上一条里说的 0.67×（那个 0.67 是基于 209.5 这个不可靠的标称值算的）**。

<details>
<summary><b>实操校验建议（避免把两种累加混在一起）</b></summary>

1. `mmapeak` 输出里对照两行即可：`mma_f16f16f16_16_16_16` vs `mma_f16f16f32_16_16_16`；在 A100 上这两行应该几乎相等，在 5090 上是 2:1。
2. torch 侧确认口径：`torch.backends.cuda.matmul.allow_fp16_reduced_precision_reduction`（默认 True，可能让 part-reduction 走低精度累加），以及 cuBLAS 的 `CUBLAS_COMPUTE_32F` / `CUBLAS_COMPUTE_16F`；显式设成 32F 才是纯 FP32 累加。
3. 想吃到 5090 的真正上限：用 FP16/BF16 累加（或 split-K + 周期性 FP32 提升）的 kernel，别用 `CUBLAS_COMPUTE_32F` 的默认路径；但要评估数值精度损失。
4. 别用理论值外推真实性能：5090 的 575W 功耗墙 + 2.0–2.6 GHz 的动态频率，会让"理论 × 效率"的估算在 ±20% 之间摆动。

</details>
