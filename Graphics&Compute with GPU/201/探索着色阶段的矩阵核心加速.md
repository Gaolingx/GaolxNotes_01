## 😀 默认助手 (7)

核心问题其实不在于“着色能不能用 tensor core”，而在于**为什么后处理能轻松用上、着色却一直用不上**。想清楚这一点，后面可选的方向就很清楚了。

## 一、后处理先用上的原因

DLSS、FG、OptiX denoise 的共同点是：**输入本身已经是稠密、统一、屏幕对齐的张量**。整屏像素、固定 stride、无分歧，天然构成 $N \times K$ 的 GEMM 或 batch conv，warp 内 16×8×16 的 fragment 也能轻松填满。

着色的情况正好反过来：每个像素的材质分支和 fetch 数量都不同，warp 内 32 条 lane 可能分属 8 种材质。而你并不是“让 pixel shader 调一下 MMA”就能获得加速，因为 `mma.sync` 是 warp 级协同操作，要求同一 warp 内所有 lane 就 tile 布局达成一致。只要还在 forward 或传统 deferred 的 pixel shader 中，就几乎无法实现这一点。

**所以先决条件是渲染架构**：visibility buffer 加 compute-based material resolve 加按 material ID 压缩排序。只有把着色变成“每批 $N$ 个像素 × 同一套材质参数”之后，才有 GEMM 的形状。这一步不完成，后面的方案都难以推进。

## 二、重构方式

把每个像素的着色计算从“逐像素标量求值”改成 **$N \times K$ 特征矩阵乘 $K \times C$ 权重矩阵**。tensor core 不关心你在算什么，只要求 $M$、$N$、$K$ 足够大。$M = 16$ 或更大（批量像素数），$K \ge 16$（特征维度），$N \ge 8$（输出通道数），这样才有收益。

这样一来，候选方案就可以按“数学上是否精确”分成三档，ROI 差别很大。

## 三、分档候选清单

### 第一档：本来就用矩阵运算表达（精确，无近似风险）

这档是最值得先做的，因为收益是实打实的，而且不需要容忍精度损失。

| 方向 | 数学形式 | 备注 |
|---|---|---|
| **SH、PRT、probe 求值** | $L_o = M \cdot L_i$，或逐像素 $\sum c_i Y_i$ | DDGI 或辐照度体积的逐像素 probe 混合是 $N{\times}4 \times 4{\times}27$，完全精确 |
| **LTC 面光源** | Heitz 2016 的 $M^{-1}$ 变换 + 逐像素 matvec | 批量化后变成 GEMM，面光源数量多时 ALU 开销大，正是适合用 tensor core 的场景 |
| **多光源累积** | 紧凑光源 list × BRDF 矩阵 | 稀疏 GEMM，per-pixel 光源数决定了 $K$ |
| **材质层混合** | $\text{out} = W_{N\times L} \cdot C_{L\times C}$ | 层数 $L$ 少、通道 $C$ 小时过于窄，属于退化情况；但如果你有 subsurface 或多层 PBR 的 20~30 个 feature channel，就划算了 |
| **SH 旋转、光照传输矩阵** | 纯矩阵乘 | 旋转一次即可处理整批 |

这档的潜在方向虽然清晰，但要注意：**$L=4$ 层、$C=3$ 通道的“瘦”矩阵，在 16×16×16 的 MMA 上是能够运行的，但大部分算力都浪费了**。必须先把 feature 维度做大，思路才对：与其用 4 层 × RGB，不如用 4 层 × 40 个中间特征再降到 RGB，这样才填得满 tensor core。

### 第二档：神经近似（有先例，但要容忍精度和训练成本）

- **Neural radiance cache**（Müller 2021）—— 把间接光缓存换成一个 MLP 加 latent grid，推理就是 batch GEMM。这是最直接“着色里跑 tensor core”的工程化案例。
- **神经材质 / 程序化噪声的 MLP 拟合** —— procedural shading 是典型的 ALU-bound 且稠密，用一个小 MLP 拟合 fbm，逐个纹素或像素批量推理。
- **NTC（Neural Texture Compression）** —— 压缩解压就是卷积层，按 texel 批量执行，能获得很不错的 GEMM 形状。
- **Path guiding / importance sampling**（Neural Importance Sampling 2017、Neural Control Variates 2020）—— 每条 path 一次推理，主要靠批处理来摊薄。

### 第三档：离线烘焙（风险很低，建议先做这一档，用来验证整条链路）

- lightmap 或 SH 投影：$\text{coeff} = \int L(\omega) Y(\omega) d\omega$，一堆巨大的 GEMM，属于裸 tensor core 的理想场景。
- GGX、环境贴图预滤波。
- 大气 LUT（Hillaire 那套 multiple scattering 迭代）。

这档不需要改动运行时架构，可以直接验证“tensor core 做数学 + 精度补偿够不够”这个问题，也不会把运行时性能搞砸。建议第一步就做这个。

## 四、关键约束速查

<details>
<summary>精度、形状、带宽——点开看细节</summary>

**精度**：这是最容易出问题的一点。

- TF32 只有 10 bit 尾数，相对误差 $\sim 10^{-3}$。漫反射、间接光这类计算没问题，但大面积平滑渐变上会出现肉眼可见的 banding，而且完全破坏帧间确定性。
- FP16 的指数只有 5 bit，上限 65504，HDR 场景中很容易溢出。
- BF16 的指数是 8 bit，但尾数只有 7 bit，精度更差。如果要接近 FP32，可以用 3×BF16 拆分（Ozaki 那类误差补偿）——在 H100 上等效算力仍有 FP32 CUDA core 的 ~5×，是可接受的折中方案。CUDA 12.8 之后 cuBLAS 有 FP32 emulation 路径，可以关注。

**注意消费级 GPU 上收益会衰减**：RTX 4090 的 FP32 是 ~82 TFLOPS，TF32 tensor 是 ~165 TFLOPS，**只有大约 2 倍**。而 H100 上 TF32 对 FP32 是 ~7 倍、FP16 是 ~15 倍。因此，在消费级显卡上使用 TF32 做着色加速，收益很可能被数据搬运和调优成本抵消，而用 FP16/BF16 的神经类方案会相对更划算。

**形状**：$M{=}1$ 的 GEMV 在 tensor core 上没有收益，所以“一个像素一个 MLP”的做法行不通，必须跨像素或跨 texel 批量处理。

**带宽**：大多数引擎的着色瓶颈是纹理 fetch，而不是 ALU。tensor core 只减少 ALU 时间。**只有在 ALU-bound 且足够稠密的着色上，收益才成立**——比如复杂分层材质、多光源、体积积分、程序化着色。

**接口**：D3D12 没有官方 MMA。实际可使用的路径是 Vulkan 的 `VK_KHR_cooperative_matrix`（以及 `VK_NV_cooperative_matrix2`，支持更灵活的 tiling 和 sparsity），或者 CUDA 的 `wmma`、`tcgen05`；如果使用 Blackwell，还要额外考虑 TMEM 的 capacity。

</details>

## 五、建议的验证方式

我倾向于按以下三步进行，因为你现在的架构大概率还不支持第二步：

1. **离线烘焙，替换单个 kernel**：选择 lightmap SH 投影或环境预滤波中一个已有实现，用 tensor core 版本替换，然后对比数值误差和耗时。如果精度不可接受，就不用再往下做了。
2. **架构验证**：测量一次你的材质 resolve 在 visibility buffer 下的**每像素 ALU 占比**和**批次密度**。如果 warp 内材质一致性不到 ~70%，就说明要么需要先做 material ID 排序，要么这个方向暂时不适合，需要先修复 incoherent deferred 本身。
3. **按类别重构单个最贵的 shader**：只挑 **ALU-bound 且批次密集**的那一个（通常是分层材质或多光源 BRDF 累积），把它改成 $N \times K \times C$ 的形式做 A/B 对比。不要一开始就把整个 shading 都改成矩阵形式。

另外，建议先检查一个数字：**当前帧 shading 阶段的 ALU busy 占 GPU 时间的比例**。如果只有 20%，即使把 tensor core 派上用场也只能节省几个百分点，那它还不如去打磨 denoise 或 FG。如果这个数字是 50~60%，而且集中在两三个 shader 上，那这个方向就很值得做。

## 一、你的判断只对了一半，有个硬账要算

“矩阵密集 = tensor core 友好”这一步跳得太快。tensor core 优化的是 **算术强度（FLOP/byte）**，不是 FLOPs。H-matrix 恰恰是专门为了**省 FLOPs** 设计的。这两个方向**相反**。

先建个模型。一个 $H^2$ 式的低秩块，$U, V \in \mathbb{R}^{b \times r}$，批量作用在 $m$ 个查询点上：

$$Y = U\,(V^\top X), \quad X \in \mathbb{R}^{b \times m}$$

每个查询点的 FLOPs $= 4br$，流量 $\approx 2b + \frac{2br}{m}$ 个元素（输入 $b$、输出 $b$，$U,V$ amortize 到 $m$ 个点上）。于是

$$\text{AI} \;\approx\; \frac{4br}{4(2b + 2br/m)} \;\xrightarrow{m \to \infty}\; \frac{r}{2}$$

**关键结论：算术强度只由秩 $r$ 决定，把 batch 开多大都救不回来。** $m\to\infty$ 时 $\text{AI} \to r/2$。

对照机器的 ridge point：

| 卡 | FP32 ridge | FP16 TC ridge |
|---|---|---|
| RTX 4090 (~1 TB/s) | ~82 FLOP/B | **~330 FLOP/B** |
| H100 SXM (~3.35 TB/s) | ~20 FLOP/B | **~295 FLOP/B** |

H-matrix 的典型 rank 是 8~32，也就是 $\text{AI} \approx 4 \sim 16$ FLOP/B。要喂饱 FP16 tensor core，你得有 $r \approx 600$ ——那已经不叫低秩块了。

所以：**低秩块的 matvec 在结构上就是 memory-bound，tensor core 对它是零收益。** 你把 WNRT 的 H-matrix 遍历搬到 tensor core 上，只会看到 SM 在等 L2。这不是实现问题，是数学性质。

## 二、那 tensor core 到底在哪用得动

按你描述的结构，能真正变成 GEMM 的只有三处，而且 AI 是够的：

| 位置 | 形态 | 估算 AI |
|---|---|---|
| **NN 训练**（前向+反向） | 宽 $w$ 的 MLP，$m$ 个样本批量 → $m{\times}w \cdot w{\times}w$ | $\approx w/2$，$w{=}256$ 时 ~128 FLOP/B |
| **dense near-field 块** | $b{\times}b$ 权重常驻 SMEM | $\approx b/4$，$b{=}128$ 时 ~32 |
| **批量 MLP 求值**（把整个 cache 的查询点一次性灌进去） | 同训练前向 | 同上 |

注意第一行的含义：**训练那一步才是 tensor core 的真正用途**，而且这正好和你说的“现场训练 NN 当光线缓存”对上了。更妙的是，训练需要 ground truth —— 那得靠 RT 去 trace 路径。

于是每帧的异构循环是：

```
[RT trace 少量路径] → [生成训练样本] → [SGD step：tensor core GEMM]
        ↑                                         ↓
        └────────── [用更新后的 NN 批量求值 cache] ←─┘
```

RT 是**训练数据的生产者**，tensor core 是**学习者 + 求值者**。这个 RT↔MMA 的每帧生产者-消费者依赖，比“RT 出几何 + TC 算着色”那种松散拼接有意思得多，也是你编程模型难得的好靶子。

顺带一个能省的优化：**小波变换不要放在运行时**。基变换是固定的线性算子 $\Phi$，直接离线折进权重 $W' = W\Phi^{-1}$，运行时那一步就不存在了。别把它当工作负载的一部分。

## 三、对你“证明 programming model”这个目标，这反而是好消息

因为你的 claim 不该是峰值 FLOPs —— 那个按上面的账本来就是输的。应该换成：**不规则、数据相关、异构的任务图，调度得好**。

WNRT 里真正难调度的正好是这四件事：

1. **H-tree 遍历是数据相关的** —— 每个查询点落在不同深度的块里，warp 内分歧严重。解法是 level-synchronous 分桶，但这本身就是个调度决策。
2. **块稀疏的 gather/scatter** —— 块列表是运行时生成的，形状不固定，没有静态 tiling 可用。
3. **RT 与 MMA 的流水线交织** —— 上面那个每帧循环，两个单元的利用率互相牵制。
4. **权重常驻** —— 你 scene 的 $U,V$ 基本静态，但 NN 权重每帧在变，常驻策略要分开处理（双缓冲 + EMA，否则帧间闪）。

这四件事是手写 kernel 真的会调得很痛苦的地方，也正是编程模型能证明价值的地方。**把 claim 从“我让它更快”改成“我让它可表达且在同量级性能内”，这两条你都守得住。**

## 一、先量化：这两个 workload 差 150 倍

**普通 LBS 蒙皮**，每顶点 4 bone × $3\times4$：

- FLOPs $= 4 \times 12 \times 2 \approx 96$
- 流量（矩阵已常驻寄存器/常量区）：24 B 进 24 B 出
- $\text{AI} \approx 96 / 48 = \mathbf{2\ FLOP/B}$

RTX 4090 的 FP32 ridge 是 ~82 FLOP/B。所以蒙皮**比 ridge 低 40 倍**，是个纯粹的 bandwidth-bound 操作——tensor core 在这里零意义，你说的对，而且还不只是“可能更快”，是完全没得比。

**ML Deformer**（Epic 那套 vertex delta MLP），假设 $64 \to 256 \to 256 \to 3$：

- FLOPs $= 2(64{\cdot}256) + 2(256{\cdot}256) + 2(256{\cdot}3) \approx 165{,}000$
- 流量：64 float 进 + 3 float 出 $\approx 268$ B（权重按顶点数摊薄）
- $\text{AI} \approx 165000 / 268 \approx \mathbf{615\ FLOP/B}$

| | AI | vs FP32 ridge (82) | vs FP16 TC ridge (330) |
|---|---|---|---|
| LBS 蒙皮 | ~2 | 差 40× | 差 165× |
| ML Deformer | ~615 | **超 7×** | **超 1.9×** |

**关键：ML deformer 即使跑 FP32 都已经是 compute-bound 了。** 所以它不是“带 ML 之后情况不一样了”，而是**根本换了一个问题类别**——从搬运问题变成了计算问题。这也是为什么这两个东西放在同一个 pipeline 里、却需要完全不同的后端。

对写东西来说，这个 2 vs 615 的表比任何文字描述都有力。

| **Dionne & de Lasa 2013** — *Voxel Skinning* | 体素加速的权重扩散 |
| **Xu et al. 2020** — *RigNet* | GNN 自动 rigging（骨架/权重生成，不是 deformer） |

这一档的阅读价值：它们都在**省 FLOPs 和带宽**（更少的 bone、更压缩的权重、更大的 batch），从头到尾没有 tensor core 的位置。这是你论文里“control group”的文献基础。

### B. ML Deformer 谱系（真正和 tensor core 相关的）

**Epic 的生产路线：**
- **UE5 ML Deformer Framework**（5.0 起）——运行时 NN 拟合高质量形变（肌肉 sim / blendshape），修正 LBS 结果。内置模型有 *Vertex Delta*（MLP）和 *Nearest Neighbor*，后续版本加了 *Neural Morph*。
- 依赖 **Neural Network Inference (NNI)** 插件。⚠️ 这条要核实：据我所知 NNI 默认走 CPU runtime，Windows 上有 DirectML 后端但不是默认优化路径——**如果属实，这就是你要找的那条缝**：把逐顶点 MLP 推理批量化上 GPU tensor core，天然是 $V \times d \cdot d \times w$ 的 GEMM。

**学术前身（必引）：**
- **Bailey et al. 2018** — *Fast and Deep Deformation Approximations* (ACM TOG / SIGGRAPH)。**这是整个 ML deformer 思路的源头**，rig 参数 → 细节形变的 MLP 回归，生产级。你的 related work 里它应该是第一句。
- **Loper & Black 2014** — SMPL。PCA 基 + LBS，统计模型路线的起点。
- **Li et al. 2021** — *Learning Skeletal Articulations with Neural Blend Shapes* (SIGGRAPH)。逐顶点权重网络。
- **Gilles et al. 2020** — *NiLBS: Neural Inverse Linear Blend Skinning*。用 MLP 解 LBS 的逆问题，和你说的“小 NN 替代矩阵运算”思路最接近的一篇。
- **Deng et al. 2020** — *NASA: Neural Articulated Shape Approximation* (ECCV)。
- **Chen et al. 2021** — *SNARF* (ICCV)。可微前向蒙皮 + 隐式形状。
- **Peng et al. 2021** — *Animatable NeRF*。同一条线，但走体积渲染，和实时管线距离较远。

**布料/软体（同一类“用 NN 换掉物理解算”）：**
- **Sanchez-Gonzalez et al. 2020** — GNS / *Learning to Simulate Complex Physics*
- **Pfaff et al. 2021** — *Learning Mesh-Based Simulation with Graph Networks*
- **Bertiche et al. 2022** — *SNUG: Self-Supervised Neural Dynamic Garments*
- **Grigorev et al. 2023** — *HOOD: Hierarchical Graphs for Clothing Dynamics* (CVPR)

**面部（GPU 推理已经跑通的生产案例，值得拿来打对比）：**
- **Lombardi et al. 2018** — *Deep Appearance Models* (SIGGRAPH)。实时，decoder 在 GPU 上跑。
- **NVIDIA Audio2Face** —— blendshape 生成，走 GPU tensor core，是“有 ML 就能喂满”的现成证明。

### C. Tensor core 进几何/形变的尝试

这一档文献**薄**，正好是你的机会。我能想到的方向：
- **降阶/子空间 sim**（von Tycowicz, Schulz, Seidel 系列；**Bouaziz et al. 2014** *Projective Dynamics*）——本质是 $U^\top f$ / $U q$ 的矩阵乘，可以被改写成 GEMM，但原始实现都在 CUDA core 上。
- **骨骼矩阵作为 block-sparse GEMM**：蒙皮矩阵 $\mathbf{S} \in \mathbb{R}^{3V\times 3V}$ 是每行 4 个 $3\times3$ 块的块稀疏阵。用 $16\times16\times16$ 的 MMA 去算 $3\times3$ 的块，**tile 利用率不到 4%**，这直接印证了上面的 AI 数字。
- 也有以“按主导 bone 排序分桶”为基础的批处理思路：$X_j' = M_j X_j$，$X_j \in \mathbb{R}^{4\times N_j}$，当 $N_j$ 大时确实变成正经 GEMM——但 blending 那步又把收益吃回去了，且总流量不变。**这个失败案例本身值得写。**

## 三、真正的 gap 在哪

把上面拼起来，空白是清楚的：

1. **ML deformer 的推理批量化**。逐顶点 MLP → 顶点 batch → GEMM，这是教科书级的 tensor core 场景（AI 615），但我没见到公开的、把这部分做到 GPU tensor core 上并给出 utilization 数字的工作。Epic 的实现细节不透明，学术界又大多在离线重建。
2. **同一管线内两种后端的共存与切换**。蒙皮（AI 2，要 SIMT + 带宽优化 + 量化压缩）和 ML deformer（AI 615，要 MMA）在同一个 frame 里相邻执行，共享同一份顶点缓冲。**调度器要能识别这两类并分配不同后端**——这恰好是你编程模型的卖点，而且这个例子自带定量依据。
3. **训练侧**。ML deformer 的训练（对每个角色拟合）是离线大 GEMM，对应你第一条消息里说的“第三档：烘焙”。这块是现成的 quick win。
4. **AI 交叉点的经验曲线**。$d$、$w$、骨骼数怎么变会让 tensor core 从“亏”翻到“赚”——这个曲线我没查到有人系统报过。

## 四、给你编程模型的一个用法建议

别把蒙皮当主角，把它当**反证**：

> 一个声称“自动把矩阵负载映射到最优后端”的 programming model，必须在**蒙皮**上预测出“SIMT 更快”并且真的更快，同时在 **ML deformer** 上预测出“tensor core 快 3-5 倍”并且真的更快。只有两个方向都对，这个 model 才有可信度。

否则你所有的 case study 都是“矩阵密集 → tensor core 快”，那说明不了模型能分辨，只能说明你挑了好的 workload。

要不要我帮你做两件事之一：
1. 把 ML deformer 的逐顶点 MLP 推理写成 vertex-batched GEMM 的 kernel 骨架，扫 $w \in \{64,128,256,512\}$ 看 utilization 曲线——这个实验一两天能出，而且直接就是你论文里第 2 和第 4 点的证据；
2. 把 LBS 的 block-sparse 形式写成形式化分析，算出 MMA tile 利用率的上界，作为“为什么不能”的定量论证。
