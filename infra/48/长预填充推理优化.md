# 长预填充推理优化

## 🧑‍💻 User

llm e2e agentic generation推理的时候小bs但long prefill和大bs但short prefill两种业务场景有什么区别，哪种是low latency/low batch size的，如何针对性优化inference engine和集群调度？

## 😀 默认助手 (7)

## 一、先给结论：这两种场景在系统上的本质差异

| 维度 | **A：小 BS + 长 prefill** | **B：大 BS + 短 prefill** |
|---|---|---|
| 典型业务 | 交互式 Coding / Deep Research Agent、单会话超长上下文多轮 tool-call、Computer Use | 高并发在线 chat、多 Agent fan-out 汇总、RL rollout、离线合成与评测 |
| Roofline 位置 | **compute-bound**（计算瓶颈） | **memory-BW-bound**（显存带宽瓶颈） |
| 核心瓶颈 | TTFT（prefill 算力 + KV 容量） | TPOT / ITL（每 token 需要读取权重） |
| 主指标 | TTFT p99、单步 e2e 延迟 | tokens/s/GPU、goodput@SLO |
| 关键优化手段 | prefix cache、PD 分离、并行 prefill、KV 压缩 | 连续批处理、chunked prefill、量化、大 batch |
| 集群形态 | 少副本、大 TP/CP、会话亲和 | 多副本、小 TP、大并发 |

**哪种是 low latency / low batch size？** 是 **A（小 BS + 长 prefill）**。在 agentic e2e 场景里，它对应的就是“用户盯着屏幕等下一个 token 或 tool call”的交互式链路：SLA 由 TTFT 主导，并发被 KV 显存和延迟要求限制在个位数。B 是追求吞吐的另一种场景：这时更大并发是为了提高吞吐，而不是满足延迟要求。

但要强调一点：batch 大小和上下文长度只是**负载形态**，延迟还是吞吐是**SLA 属性**，这两个维度正交。所以，离线长文档摘要（长 prefill + 小 bs）也可以是吞吐型。只是在 agentic e2e 中，“小 bs + 长 prefill”与“延迟敏感”高度重合，因为它就是交互式那条链路。

## 二、为什么两者会分裂：先用公式看清楚

**Prefill 计算量**（单序列长度 $L$）：

$$
C_{\text{pre}} \approx \underbrace{2PL}_{\text{线性层}} + \underbrace{4\,n_{\text{layer}}\,d_{\text{model}}\,L^2}_{\text{attention}}
$$

当 $L$ 从 8K 到 128K 时，attention 项按 $L^2$ 增长并迅速主导。关键是：单条长序列的 GEMM 形状是 $[L, d]\times[d, d']$，$L$ 足够大时**一条序列就能把 GPU 的 GEMM 单元打满**，所以 prefill 阶段 batch=1 并不低效，重点已经从提高利用率转为降低总工作量，因此优化方向是拆分、并行、复用，而不是简单增加 batch。

**Decode 计算强度**（batch = $b$，权重 bf16）：

$$
\text{AI} \approx \frac{2bP}{2P} = b \ \text{FLOP/byte}
$$

H100 的算力/带宽比约为 $989\text{T} / 3.35\text{TB/s} \approx 295$，所以 **$b \lesssim 300$ 之前 decode 全是带宽受限**。这解释了为什么 B 场景必须把 batch 拉大；在 A 场景中，decode token 数量很少（通常只有几百个 tool-call JSON），因此不值得优化。

**KV 容量反而限制了 A 的并发**：

$$
M_{\text{kv}} = 2 \cdot n_{\text{layer}} \cdot n_{\text{kv}} \cdot d_{\text{head}} \cdot L \cdot b \cdot \text{bytes}
$$

以 70B GQA（80 层 / 8 KV heads / 128 dim / bf16）为例，**每 token ≈ 0.33 MB**，128K 上下文单会话就是 **≈ 42 GB**。8×H100（640 GB）扣掉 140 GB 权重后，只剩 1~2 条长会话的空间。

> 因此 **A 场景的小 batch 不仅是延迟选择，更由 KV 容量限制决定**。这是最关键的结构性认知，也直接决定了优化方向。

## 三、场景 A（小 BS + 长 prefill）：降低 TTFT 的工程手段

<details>
<summary><b>引擎侧（按投入产出比排序）</b></summary>

**1. Prefix caching 是第一优先级，收益通常远大于其他优化**
Agent 每一步新增 token（tool 输出、用户话）远小于历史上下文，命中率 90%+ 时 TTFT 从 $O(L)$ 直接降到 $O(\Delta L)$。落地要点：
- 块粒度哈希（如 16/32 token 一块）+ radix tree（SGLang RadixAttention 思路）支持前缀共享与分叉
- 淘汰策略按 **session 活跃度** 而非全局 LRU；长会话很容易被短请求冲刷掉
- 分层：GPU → CPU DRAM → 远端 KV 池（LMCache / Mooncake / 3FS），冷启动只付传输代价
- 多 Agent 共享 system prompt / tool schema 时，可跨请求共享同一段 prefix KV

**2. 并行 prefill，而不是只加大 TP**
TP 沿 hidden 维切分，**不会缩短序列长度维度**，对 TTFT 帮助有限。需要：
- **Context / Sequence Parallel**（Ring Attention、Ulysses）把 $L$ 切到多卡，TTFT 近似 $\div N$
- 跨节点 prefill（DeepSeek 式 prefill 集群），长上下文是少数值得使用跨机 RDMA 的场景
- FlashAttention varlen 避免 padding 到固定长度造成额外计算浪费

**3. PD 分离（Prefill-Decode Disaggregation）**
把长 prefill 放到独立资源池，避免它阻塞同节点的 decode 请求。好处：prefill 池可以配大 TP/CP，decode 池配适中 TP + 大 KV 空间，并**独立扩缩容**。代价是 KV 传输，必须走 NVLink / 同 rack IB。

**4. 不要对延迟关键请求使用 chunked prefill**
chunked prefill 的价值是避免 decode 因长时间得不到调度而无法执行，但**单请求场景下它不降低 TTFT**，反而引入 KV 写回/重读往返和调度开销。正确做法：
- 交互式请求走 prefill 独占 + 高优先级
- 或反向使用，即整体采用 decode-maximal batching，把 chunk 留给非关键的批处理流量

**5. 压缩 KV 是提高并发的直接手段**
选型阶段优先 GQA / MLA 架构（MLA 的 KV 可压缩 10× 量级）；工程上加 FP8 KV；长历史做 **context 压缩**（tool 输出截断或摘要、只 RAG 相关 chunk、丢掉已完成的中间步骤）。这是提高 A 场景并发能力最根本的手段。

**6. 降低小 batch 下的固定开销**
batch=1 时，kernel launch、Python 调度、detokenize、采样可能占 30%+ 延迟：
- decode 步 CUDA Graph 捕获
- async scheduling / 计算与调度 overlap
- tool-call 解析与下一轮 tokenize 并行；流式尽早吐出首个 token
</details>

## 四、场景 B（大 BS + 短 prefill）：提高吞吐和 ITL 稳定性

<details>
<summary><b>引擎侧</b></summary>

1. **连续批处理 + token budget 调参**：`max_num_seqs` 拉大，`max_num_batched_tokens` 决定每步能插入多少 prefill token，是 ITL 平顺性 vs 吞吐的核心旋钮
2. **chunked prefill 在这里是必需的**：把新到的短 prefill 拆块塞进 decode step，保持 step 时间恒定、ITL 无尖峰，同时消除 padding 浪费
3. **量化直接换取吞吐**：FP8 / W4A8 权重 + FP8 KV，decode 是纯带宽问题，权重压缩多少几乎线性的转换为吞吐
4. **piecewise CUDA graph** 覆盖 batch size 跳变的各种 shape，避免每步重捕获
5. **少 TP、多副本**：decode 受带宽限制，TP 的 all-reduce 延迟摊薄收益低，单卡大 batch × 多副本更容易线性扩展；MoE 走 EP + 大 batch 才能摊薄 all-to-all
6. **抢占用 recompute 而非 swap**：短 prefill 重算成本低，swap 会带来 KV 抖动
7. prefix cache 仍然值得开（共享 system prompt 通常有 20~40% 命中），但这不是主要收益点
</details>

## 五、集群调度：两类流量应使用两个独立资源池

**1. 池化与隔离**
- **Latency Pool（A）**：少副本、高 TP/CP、PD 分离、大显存（或 KV offload）、会话亲和
- **Throughput Pool（B）**：多副本、小 TP、低成本/高带宽机型、大 batch
- 混部会直接冲突：长 prefill 抢占 SM 会导致 B 的 ITL 毛刺，而 B 的高并发会冲掉 A 的 prefix cache。若必须混部，用 MPS / 优先级 / 时间片隔离，不要只靠“更大集群”。

**2. Cache-aware 路由（agentic 场景的第一优化点）**
路由决策顺序应是 **prefix 命中 > 负载均衡**：按 `session_id` / `prefix_hash` 一致性哈希把同一会话钉在同一副本，命中率从 ~0 提到 90%+ 带来的 TTFT 收益，远超任何负载均衡算法。在线服务的“least outstanding requests”只在 cache miss 时兜底。

**3. KV 作为集群一等资源**
建分布式 KV 池，prefix 可跨副本复用；scheduler 打分应包含 `(cache locality, queue depth, 预期生成长度)`。预期生成长度很重要：tool-call 短请求不应排在长代码生成后面，应使用 SJF / 最短预期作业优先，能显著降低 p99。

**4. 弹性伸缩信号**
不要用 GPU util 作为扩缩容依据（长 prefill 时 util 高但服务是健康的；大 batch decode 时 util 低但已经过载）。用 **队列长度 + TTFT p99 + KV 占用率**。扩容慢的根因是权重加载，因此要镜像预热、权重常驻 sidecar、或 CRIU 快照。

**5. 优先级与抢占**
交互式 > 在线批 > 离线。RL rollout / 评测天然可 checkpoint，可被抢占并放到 spot / 低峰；大 TP 作业用 **gang scheduling**，避免被切碎产生碎片；bin-packing 时优先把大 TP 组整体塞进同一 NVLink 域。

**6. 需要监控的指标**
TTFT p50/p99、ITL p99、**队列时间 vs 计算时间拆分**（能立刻区分是容量不够还是调度慢）、prefix cache 命中率、KV 利用率与抢占率、prefill:decode token 比、goodput@SLO。

## 六、快速判断你的业务属于哪一类

在 trace 里统计每个请求的 `prefill_tokens : decode_tokens`：

$$
\frac{L_{\text{pre}}}{L_{\text{dec}}} \gtrsim 10 \Rightarrow \text{A 型（先攻 prefix cache + PD 分离 + CP）}
$$

$$
\frac{L_{\text{dec}}}{L_{\text{pre}}} \gtrsim 5 \Rightarrow \text{B 型（先攻连续批处理 + chunked prefill + 量化）}
$$

两者接近（如长上下文长输出）时，不要二选一地搞，直接做 PD 分离 + 两池异构，让 prefill 和 decode 各自走最适合的并行策略。

## 七、四个常见误区

1. **“长 prefill 就要 chunked prefill”**：在单请求延迟场景中，它不降 TTFT，只增加开销；它主要服务于大小混合批的 ITL 平顺性。
2. **“小 bs 就是 GPU 利用率低”**：prefill 阶段单条长序列就能占满 GEMM 单元；真正利用率低的是小 bs decode，而 A 场景 decode token 本来就少。
3. **“加大 TP 就能降低 TTFT”**：TP 不切序列维，长 prefill 必须上 **CP/SP 或跨节点 prefill**。
4. **“混部提高利用率”**：A 和 B 的 SLO 会互相破坏，尤其在 agentic 场景，长 prefill 是典型的“CPU 式长任务”，会把尾延迟拉高一个数量级。
