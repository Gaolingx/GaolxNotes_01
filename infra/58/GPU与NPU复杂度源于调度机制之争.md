# GPU与NPU复杂度源于调度机制之争

## 🧑‍💻 User

对比NPU，感觉gpu复杂度很大程度就是为了自由的gather/scatter还有dynamic dispatch去应对不规则和稀疏的负载，为了复杂控制流的考量

---
## 😀 默认助手 (7)

你的直觉方向是对的，但它把因果关系放低了一层：gather/scatter 和 dynamic dispatch 只是**症状**，真正的分野在于**调度是静态的，还是动态的**。GPU 的复杂度，本质是为“不可预测性”支付的保险金；NPU 没有省掉这份复杂度，只是把它从硬件转移到了编译器。

## 一、真正的分野：硬件动态调度 vs 编译器静态排布

NPU 使用 Cube/脉动阵列并配 DMA 描述符，前提是**编译器能提前把每一拍算清楚**。它能做到这一点，靠的是 tiling、bank 划分、双缓冲和软件流水。一旦写出“每个 tick 谁在读哪块 SRAM，谁在算”的时间表，硬件就只需要一个简单的状态机，既不需要 scoreboard，也不需要重排序，更不需要在 64 个 warp 里挑选一个 ready 的来发射。

GPU 选择的是相反方向：**把时间表交给硬件，在运行时现场生成**。

- 一个 SM 上驻留几十个 warp，warp scheduler 每个周期挑一个 ready 的发射；
- load 发出后不等，scoreboard 挂着，靠**别的 warp** 填这个 stall；
- block 到 SM 的映射由 GigaThread 引擎动态分配，谁空给谁。

所以 GPU 的“复杂度”花钱买的核心能力是：**不需要一个足够聪明的编译器，也能跑满**。这对不规则负载是决定性的——因为不规则负载的定义就是“编译器提前算不出来”。

## 二、你那三个例子各自的硬件账单

| 能力 | GPU 上的硬件代价 | NPU 的替代策略 | NPU 失去什么 |
|---|---|---|---|
| gather/scatter | 每 lane AGU 生成地址 + coalescer 合并（32 个地址 → 32B sector 集合）+ LSU/MIO 队列 | 多维 strided DMA 描述符（affine 访问）+ 片上 permute/bank 切换 | **真随机**索引（embedding、MoE routing、稀疏卷积），只能退化成 per-element DMA 或落到 vector 单元，带宽/效率暴跌 |
| 控制流 / 分支 | SIMT 栈 + reconvergence；Volta 之后 per-thread PC（近乎 MIMD 模拟），寄存器成本极高 | predication（向量掩码）+ 标量单元；**没有 per-lane 分支，没有变长循环** | 数据相关的早退、动态循环、条件派发 |
| dynamic dispatch | warp 级动态发射 + block 级负载均衡调度器 | 编译期固定核心映射 / 静态切片 | **负载倾斜**（attention 变长序列、MoE 专家热点） |

这里有个很能说明问题的数字：一个 warp 的 32 个 lane 若命中 32 条不同 cache line，需要 32 次 sector 传输，相对合并访问放大 $32\times$——但硬件**依然正确地完成了**。这就是用带宽和面积换通用性。分支同理：if/else 两支都跑，成本是 $T_1+T_2$ 而不是 $\max(T_1,T_2)$，最坏利用率掉一半。

而在 NPU 上，同等倾斜的负载会直接体现为：加速比 $\approx \dfrac{\text{平均负载}}{\text{最大负载}}$。这就是为什么“负载不均”是 NPU 部署里的头号痛点。

所以更准确的表述是：**GPU 是“低效但鲁棒”，NPU 是“高效但脆”**。不规则和稀疏打中的不是“算力不够”，而是“静态假设被破坏”。

**1. “sparse”要分两种，别混在一起。**
- **结构化稀疏**（2:4、块稀疏）：两边都有专用通路，GPU 的 sparse tensor core、NPU 的零跳过逻辑，本质都是把稀疏**编译成静态模式**，这恰恰是 NPU 擅长的。
- **动态稀疏**（数据决定模式）：embedding 海量随机查表、MoE token 路由、GNN 邻接聚合、点云。这才是 GPU 的护城河，因为模式在**运行时**才出现。

- 虚拟内存 / TLB / 多租户 / 抢占 / MIG：这是“通用加速器”的必需品，NPU 作为固定功能数据流机通常直接放弃；
- 统一内存模型 + L2 一致性 + 原子操作：支撑任意并行编程模型，而不只是喂给矩阵乘法；
- 精度谱系（FP64/FP32/TF32/BF16/FP8/INT8）与 SIMT 和 tensor core 共存；
- 还有一个**商业**理由：一颗芯片摊薄图形、HPC、DL、数据库所有负载的 NRE。复杂度是市场结构决定的，不全是技术最优解。

顺带说个面积事实：在纯 dense GEMM 场景下，tensor core 只占芯片一小块，寄存器堆、L1/SMEM、NoC、调度器占了大部分。**你那句“复杂度过剩”在纯稠密推理上是成立的**——这正是 NPU 存在的经济基础。

## 四、最有说服力的证据：两边在互相抄作业

这个趋势反过来印证了你的判断：

- **GPU 在学 NPU 的静态调度**：Hopper 的 TMA 就是个硬件多维 DMA 描述符引擎（本质是 NPU 的搬运单元），warp specialization 是手工软件流水（生产者/消费者 warp，不再是“靠硬件随机挑选”），thread block cluster + distributed shared memory 是把片上通信显式化；Blackwell 的 Tensor Memory 把 tensor core 操作数从寄存器堆搬到专用 SRAM——**operand 供给方式几乎就是 NPU 的 bank + operand collector**。目的很明确：把 dense matmul 里动态调度的那部分开销“静态化”掉。
- **NPU 在学 GPU 的动态能力**：TPU v4 专门加了 **SparseCore**，就是为了 embedding 这种大规模随机 gather——脉动阵列结构上做不了，只能另辟硬件。这就是“不规则负载逼着 NPU 长出一块 GPU 式的器官”。

所以更准确的图景不是“GPU 复杂、NPU 简单”，而是**复杂度沿“静态—动态”这条轴滑动**，谁能把负载的不确定性吃在自己那一侧，谁就赢。

## 五、判定规则

- 负载**形状固定、稠密、高批量、算子集封闭**（CNN、dense LLM prefill 的定长 GEMM）→ NPU 的面积/功耗优势是结构性的，GPU 的调度器纯属浪费。
- 负载**数据相关**（MoE、embedding、变长 attention、beam search、动态 shape、稀疏卷积、自回归 stopping 条件）→ 动态调度的保险费开始回本。
- 还有一个反噬点值得警惕：NPU 把复杂度推给了编译器，于是**编译器成了单点故障**。tiling/流水排不好，硬件再干净也发挥不出一半峰值；而 GPU 上“写得烂但能跑”的下限高得多。这也是为什么实际部署里 NPU 的“有效算力/峰值算力”比值经常比理论差距更难看。

一句话收束：**GPU 不是为了 gather/scatter 而复杂，是为了“不假设编译器猜得对”而复杂**；gather/scatter、dynamic dispatch、warp 分歧都只是这个总原则在不同子系统上的投影。

## 🧑‍💻 User

为什么不把执行单元直接做成静态的，确定性调度，然后全部交给驱动或者编译器去决定而是要很复杂的硬件电路做scheduler

---
## 😀 默认助手 (7)

一句话：**“确定性”不是一个可以随意选择的属性，它受制于内存系统。而静态调度的前提，是编译器知道延迟。**

但先纠正一个前提——现代 GPU 已经在它力所能及的地方做了静态化。

## 一、你已经有一半在这么做了

NVIDIA 的 SASS 里，每条指令都带 **control bits**：编码了“到下一条依赖指令之前等几个周期”以及 barrier。这就是**编译期静态调度**，只不过它只对**定点延迟**成立——ALU、FMA、甚至 tensor core 的时延都是固定的，编译器可以精确排拍。

真正落到硬件动态处理上的，只有**可变延迟**的指令：load/store。

所以更准确的问法是：**为什么内存这部分不能也静态？** 这就是全部答案所在。

## 二、延迟为什么无法在编译期确定

静态调度要成立，需要 $\text{latency} = \text{compile-time constant}$。这在三个层面同时断裂：

1. **Cache 是自适应的。** 命中 L1 约三十拍，命中 L2 约两百拍，落 HBM 五六百拍以上。哪一级命中取决于**输入数据**和**其他 SM 的行为**——编译器无论如何都算不出来。
2. **DRAM 是排队系统。** 就算你强行假设“一定落 HBM”，实际延迟还取决于 bank 冲突、行缓冲命中、刷新、以及此时有多少个 SM 在抢这条总线。它是个统计量，不是一个常数。
3. **系统状态是外生的。** 虚拟内存、页错误、多租户共跑、抢占、MIG 分区、降频、被 floor-sweep 掉的坏 SM……这些在编译时全都不存在，运行时全是事实。

要让静态调度“正确”，你只有两个选择：

- **按最坏情况插空泡** → 平均损失可能几倍；
- **消灭可变延迟** → 见下节。

顺带一个具体机制：为什么“多线程软件流水”救不了？因为**静态多线程同样要求停顿长度已知**。若 warp A 的 load 要等 300 拍还是 30 拍不定，编译器就无法确定该在第几拍插入 warp B 的指令。动态调度器做的事情本质极简单——**谁 ready 就发谁**——但它把“延迟长度”这个信息**推迟到了运行时才用**。这是信息论层面的胜利，不是电路层面的。

## 三、消灭不确定性需要付出什么面积代价

要让延迟真的确定，你必须干掉所有自适应结构：没有 cache，没有共享 L2，全部换成编译器显式管理的 SRAM（bank 划分在编译期定死），并且**独占整颗芯片**。

这条路真的有人走，而且走得通——代价写在面积里：

- **Groq LPU**：约 230 MB 片上 SRAM，无 cache，全部由编译器静态排拍，因此延迟完全确定。
- **Cerebras WSE**：整个晶圆当一颗芯片，几十 GB 片上 SRAM。

也就是说：**确定性 = 用 SRAM 面积换的**。GPU 选的是反方向——用便宜的 HBM + 一层统计复用的 cache，把“容量/成本”拿到手，代价是延迟不确定，于是必须买一份“动态调度保险”。

还有一层常被忽略的：cache 不只自适应**时间**，还自适应**内容**。哪些数据是热的，对 embedding 表、KV cache、图遍历这类负载是随输入变化的。静态划分拿不到这份统计复用收益。

## 四、历史判决书：Itanium

这不是假设题，2001 年 Intel 下过这个赌注。EPIC/VLIW 的整个设计哲学就是“硬件要简单，编译器全包”：128 个通用寄存器、64 个谓词寄存器、显式并行指令束。

结果是一场教科书级的失败：

- 编译器**无法预测内存延迟**，也做不好别名分析，静态排出的流水线在真实负载上大面积空转；
- 硬件被迫**把动态机制加回来**：data speculation + ALAT（advanced load）就是为了兜住编译器猜错的 cache miss；
- 最致命的一条——**静态调度把微架构写进了二进制**。调度表依赖具体实现的时延，换一代芯片就得重编译；硬件和编译器被双向锁死，谁都不敢改。一个要做十年生态的通用芯片，这条是自杀。

对比 GPU：动态调度器**吸收**了微架构差异，SM 的内部时序可以一代代改，软件栈却能积累。这份“可移植性”是免费附送的。

## 五、澄清成本结构：真正贵的是并发，而不是调度器

这一点值得单独说，因为它推翻了题设的一部分。

warp scheduler 本身**非常小**——一个优先级仲裁器 + 每 warp 几 bit 状态，量级是 SM 面积的百分之一。真正昂贵的是它**使能**的东西：

$$\text{面积} \approx \underbrace{\text{寄存器堆}}_{\text{最大项}} + \underbrace{\text{MSHR/队列/LSU}}_{\text{处理不规则}} + \underbrace{\text{scoreboard 状态}}_{\text{记在飞}}$$

而“用几十个 warp 的并发去覆盖几百拍的延迟”，等价于说：$$\text{需要的并发度} \; n \gtrsim \frac{\text{memory latency}}{\text{issue interval}}$$

这个 $n$ 直接换算成寄存器堆面积。**调度器是廉价的控制器，它买的资源是“在飞请求数”**——而这份资源正是 NPU 用“编译器预取 + 双缓冲”省掉的那份。所以真正的对立不是“调度器 vs 编译器”，而是：

> **用片上并发（面积/功耗）吸收延迟** ⟷ **用编译期流水重叠隐藏延迟（要求延迟已知）**

## 六、静态化的隐藏代价：裕量与性能悬崖

NPU 的“确定性”也不是免费的，它其实**是用时序裕量买来的**。

DMA 完成时间在现代 NPU 上同样不完全确定（DDR 争用、多核抢带宽），所以 NPU 照样得有 event/barrier 同步；只是它**没有能力动态重排**，只能靠“预留足够裕量”。裕量就是性能损失——这直接解释了为什么 NPU 的实测有效算力/峰值算力比值常年难看。

两种设计的失败曲线完全不同：

- **动态调度**：性能对负载不敏感，损失是**有界的常数**（发射效率、面积）。是保险。
- **静态调度**：性能对负载高度敏感，假设一破就是**悬崖和长尾**。是押注。

对一颗要跑未知负载、多年生态的通用芯片，买保险比押注理性。

## 七、那什么时候该静态？

判据很干净：**封闭世界（closed world）**。

- 负载集合封闭、shape 固定、算子集已知、**独占整机**、且能接受“换模型就重编译”；
- 或者对延迟抖动零容忍的场景（实时推理、交易系统），此时 Groq 那类确定性机器反而是正解。

而 GPU 自己正在把**粗粒度**的部分静态化，这恰好印证了“决策应放在信息可得的那一层”：

| 已经静态化 | 仍然动态 |
|---|---|
| grid/block 分解（程序员定） | block → SM 映射（GigaThread） |
| 定点延迟指令排拍（SASS control bits） | 内存依赖（scoreboard） |
| TMA 多维拷贝描述符 | 数据相关的索引 |
| warp specialization / 软件流水 | warp 发射选择 |
| CUDA Graph / persistent kernel | 尾部负载均衡 |

看这张表会发现一个规律：**凡是“编译期 information 充分”的地方，GPU 早就静态化了；凡是“只有运行时才知道”的地方，才留硬件。** 动态调度器的存在范围，正好是编译期信息缺失的边界。

## 结论

不是“为什么不用静态调度”，而是：

1. **已经静态化的部分你没看见**（定点延迟、网格分解、TMA）；
2. 剩下的部分静态化会**要求消灭 cache 和 HBM 的经济性**，代价是面积和容量，以及最致命的**二进制与微架构锁死**；
3. 硬件调度器本身很便宜，它买的是**并发**——用面积换“不需要编译器猜对延迟”；
4. 静态调度把风险从硬件搬到了编译器：编译器对了省电省面积，猜错了就是性能悬崖，且**无法跨租户、跨 kernel、跨代芯片**。

真正的架构原则是：**让决策发生在“做这个决策所需的信息刚好可得”的那一层。** 编译器有全局静态信息，硬件有局部实时信息。GPUNPU 的分野，就是这条原则在不同断点上切出来的结果。
