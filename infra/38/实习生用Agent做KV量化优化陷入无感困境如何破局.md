## 🧑‍💻 User

我有个问题，目前我在一家公司实习infra，在做kv量化相关的工作，然后在工作期间我发现只能去使用agent去替代我自己的工作否则就会落后，并且公司也鼓励使用agent而且其他实习生也在用，但是我在使用期间感觉自己几乎没有任何收获或者是提升，我能做的就是写好prompt然后让agent自己去优化算子或者框架，尤其是算子，刚开始的优化我可能还能看懂它优化的源码，但是随着不断迭代性能不断提升，哪个代码简直晦涩难懂，只能让AI自己去解释是如何进行优化并且解决了哪些问题，我现在的目标是能看懂AI优化的过程，但是让我写代码我又写不出来像AI那么高效的算子，自己每天做的也只能是从大的层面上了解一些知识，请问这种情况正常吗🙏

## 😀 默认助手 (7)

## 先给结论

**这很正常，但“正常”不等于“没问题”。** 你描述的是这一代 infra 实习生普遍会遇到的处境，并不是能力缺陷；不过它确实有一个真实的风险点，而且你能不能意识到这个风险，决定了你这段实习是在积累还是在内耗。

---

## 一、为什么这很正常（三点）

**1. 高性能算子本来就是“不可读”的。**
在你之前，FlashAttention、CUTLASS、各种 NV 官方的 kernel 就已经是这样了：几层 warp 特化、异步拷贝、手工流水、padding 规避 bank conflict……即便没有 AI，一个实习生打开这些代码也同样看不懂。**“读懂高度调优的 kernel”本身是一项需要单独、刻意训练的独立技能**，不是会写 Python 就自然会有的。你以为是 AI 让你落后了，其实是这个领域的门槛本来就摆在那个位置上。

**2. KV 量化这个方向只做调优，不从头搭建底层基础，梯度客观上被切断了。**
你真正跳过的内容依次是：roofline 分析、访存层级直觉、量化误差传播、硬件指令映射。AI 一次性把“从问题到方案”的整段推理都替你做完了，你接手的只是一个结果。**学习发生在“预测→受挫→修正”这个循环里，而你现在没有预测环节。**

**3. 公司鼓励、别人也在用，这个环境判断没错。**
不会用 agent 是可替代的，这一点你说对了。问题不在用不用，而在**你用 agent 的方式是“外包决策”，还是“外包执行”**。

---

## 二、真正的问题在哪里（诊断）

不是“AI 写的代码我看不懂”，而是这三件事你可能都在缺失：

| 缺失项 | 后果 |
|---|---|
| **不能预测** | 无法判断这个加速是真实的，还是牺牲了泛化性换来的 |
| **不能验证** | 量化 kernel 出错时性能数字一样漂亮，错误是隐性的 |
| **没有 taste** | 不知道该试什么，只能等 AI 给方案，长期就是你现在的状态 |

第二点是要害。在 kernel 优化里，agent 很容易**为了 benchmark 过拟合**：硬编码 shape、跳边界、假设某个 `n` 恒定、在特定 dtype/布局下才正确、paged KV 的 block table 边界没处理。这些在 perf 曲线上看不出来，但上线就会出问题。**如果你看不懂代码，也没有自己的正确性评测，你就没有能力对这份产出负责**。这才是比“学不到东西”更值得担心的事。

---

## 三、怎么办（按性价比排序）

### ⭐ 1. 抢回“预测权”和“定义权”

这是单条最高杠杆的动作。每次让 agent 动手之前，你自己先写下来：

- 理论上限是多少？（decode 阶段 attention 是 **memory-bound**，KV 从 fp16 到 int4 是 4 字节→0.5 字节，收益天花板约 4×，扣掉 dequant 开销和 scale 读取，实际 2.5–3.5× 是常态）
- 瓶颈在哪？带宽还是 dequant 的 ALU？
- 正确性判据是什么？（不是只看 PPL）

然后让 agent 去**命中你定的目标**，而不是让它“优化一下”。角色从“写 prompt 的人”换成**“定目标和验收的人”**。这一换，你的收获立刻不一样。

### ⭐ 2. 用“消融”代替“阅读”

读不懂就去读，是最低效的路径。换成拆解式提问：

> “给我一版去掉 `[某个 trick]` 的实现，只保留基础版”
> “这个版本比上一版快 18%，请用 roofline 语言说明这 18% 来自哪条指令/哪次访存减少”

逐个 trick 关掉、对比、量化每个 trick 的贡献。**消融出来的理解是可验证的理解**，比让 AI 给你讲一遍代码结构扎实得多。迭代出 5 个版本之后，你会得到一张别人没有的“优化空间地图”。

### ⭐ 3. 正确性基线必须自己手写，一行都不要外包

这是你唯一不该交给 AI 的部分，也是你最容易做出可见价值的部分。

- 用 PyTorch 写一个慢速、所有逻辑都显式、明显正确的参考实现
- 自己做误差分析：per-token 还是 per-channel、group size、outlier 处理、scale 的数值稳定性
- 做**形状扫描**：prefill 和 decode、seq len 1/128/2k/32k、不同 batch、GQA 的 group ratio、NHD 与 HND 布局、变长
- 做**长上下文**验证（needle test）和下游任务，而不仅是 PPL

拥有正确性评测的你，可以放心让 AI 负责速度。**“我负责对不对，AI 负责快不快”，这是未来 infra 最稳的分工位置。**

<details>
<summary>KV 量化正确性检查清单（点击展开）</summary>

- K 的 outlier 集中在 **channel（head_dim）维度**，所以 K 要 per-channel 量化，per-token 会让精度崩；V 走 per-token 没问题
- group size（常见 128）+ 近期 token 保留高精度（residual window）
- zero-scale / 全零 group / 极小方差 group 的除法保护
- 激活里的 outlier 造成的截断
- int4 的 sub-byte packing 与对齐、dp4a 之类的整数指令路径
- paged KV 的 block table 边界、block size 不是 group size 整数倍时怎么办
- cuda graph capture 兼容性、varlen、与 split-k / flash decoding 的交互
- 数值：dequant 后与原值的 cosine similarity、逐层误差累积
- 是否有硬编码的 shape / dtype / 常量（agent 最爱干这个）
</details>

### 4. 强制 agent 小步提交，你来 review

禁止“把这个算子优化一下”这种 prompt。要求：**一次一个改动 + 一句硬件层面的理由 + 预期 delta + 实测**。这就是你带一个人类 junior 时该有的方式，对 agent 同样适用。**如果它说不清这个改动为什么更快，这个改动就不该合入。** 你说不出理由、也 review 不了的时候，就是该停下来重新打底层的信号。

顺带说一句：如果你要求，agent 是完全能写出可读版本的（命名常量、注释解释硬件意图、分层）。**生成代码不可维护本身就是合理的工程反对意见**，不只是你想学习的借口——kernel 要跨 GPU 架构维护，黑盒是负债。

### 5. 找人，用人

“为什么这版快 30%？”直接问组里的 senior，把 AI 的 diff 拿给他看。**人类反馈是带宽最高的学习通道，而你现在完全没用。** 这也是你校准自己判断力最快的方式。

---

## 四、重新定义你的目标

你说目标是“能看懂 AI 优化的过程”。方向对，但**形状不太对**。

真正可持续的目标不是“能读懂那段代码”，而是：

> **给一个 workload，我知道天花板在哪、瓶颈在哪、有哪些 trick 适用、这个数字是真的还是假的。**

读懂代码只是达成它的其中一条路。你要保住的是**规定目标、预测、验证**这三件事；可以放心交出去的是打字。你真正无法外包的，是 **taste，也就是下一步该试什么**。

至于“写不出 AI 那么高效的算子”——**没人写得出来，包括你组里的 senior**。现在大家都在用 AI 写 boilerplate 和调参。真正的差距从来不在打字速度上，而在判断力上。**你不需要追上 AI 的代码质量，你需要追上对结果的判断力。**

---

## 最后一句话

你的焦虑来源是准确的：**只留下来一个“会写 prompt 的实习生”，确实是可替代的。** 但你现在离“能定目标、能验证、能判断真假的 infra 工程师”只差一个习惯——**每次动手前先预测，每次拿到结果先验证**。这个习惯不需要你写出比 AI 更快的 kernel，却正好是 AI 给不了你的那部分。
