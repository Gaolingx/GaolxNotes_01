# SGLang vs vLLM:推理框架选型对比

两个都是当前最主流的开源 LLM 推理/服务框架,性能经常互有胜负,选哪个**高度依赖你的具体负载**。下面按维度拆解。

## 一句话结论

| 场景 | 推荐 |
|------|------|
| 追求**最广模型支持 + 最成熟生态** | **vLLM** |
| 重度**前缀共享**(多轮对话 / RAG / Agent)、**结构化输出** | **SGLang** |
| 想要**开箱即用、社区资料最多** | **vLLM** |
| 想压榨**高并发吞吐 + 复杂编排** | **SGLang** |

## 核心差异

| 维度 | vLLM | SGLang |
|------|------|--------|
| 核心创新 | **PagedAttention**(分页 KV cache) | **RadixAttention**(基数树前缀缓存) |
| 前缀复用 | 支持,但非核心设计 | **强项**,自动跨请求复用公共前缀 |
| 结构化/约束解码 | 有(xgrammar 等) | **强项**,JSON/regex/文法解码更快更灵活 |
| 编程范式 | 主要做服务化(OpenAI 兼容 API) | 内置前端 DSL,适合复杂多步 LLM 程序 |
| 模型覆盖 | **最广**,新模型几乎第一时间支持 | 覆盖也很广,但略慢于 vLLM |
| 硬件支持 | NVIDIA / AMD / Intel / TPU 等 | 主要是 NVIDIA,逐步扩展 |
| 生态成熟度 | **最高**,集成/文档/社区最大 | 快速成长,部分场景更活跃 |
| 易用性 | 上手简单,库+服务两种用法 | 前端 DSL 有学习曲线,但服务模式同样简单 |

## 性能:别只看跑分

- 两者**常在同一量级**,许多 benchmark 互有胜负,差距通常在 **10%~20%** 以内,且随版本迭代快速变化。
- SGLang 在**高前缀重复率**(共享 system prompt、多轮、RAG、few-shot)的负载里经常明显领先——这正是 RadixAttention 的用武之地。
- vLLM V1 引擎重写后,通用吞吐和延迟也大幅提升,纯批量生成场景两者已非常接近。
- **结构化输出密集**的场景,SGLang 的约束解码通常更快、表达力更强。

> ⚠️ 结论:**必须用自己的模型 + 真实流量压测**,别照搬别人的数字。硬件型号、并发模式、序列长度分布都会翻转结论。

## 各自适合谁

<details>
<summary><b>选 vLLM,如果…</b></summary>

- 你要部署**很多不同模型**,或追求对新模型的快速支持
- 需要**生产级稳定性 + 庞大社区**背书
- 团队想**低门槛**起服务,用 OpenAI 兼容接口接现成工具链
- 硬件多样(AMD / Intel / TPU 等)
- 你就是标准的高并发批量推理,没有特别的前缀共享需求

</details>

<details>
<summary><b>选 SGLang,如果…</b></summary>

- 负载是**多轮对话 / Agent / RAG**,大量请求共享同一段前缀
- 需要**严格的结构化输出**(JSON schema、正则、文法)
- 想用**前端 DSL** 把多步 LLM 调用编排成一条流水线
- 在**NVIDIA 单卡/多卡**上追求极致吞吐,愿意调参
- 团队接受一定学习成本换取性能

</details>

## 实践建议

1. **先都用 OpenAI 兼容接口跑一遍**,因为两者都支持,迁移成本低。
2. 用**真实 prompt 分布**(含长度、并发、前缀重复率)做压测,看 **P99 延迟 + 吞吐 + 成本**。
3. 如果拿不准,**从 vLLM 起步**更稳(生态成熟);等发现前缀共享/结构化输出成为瓶颈,再切 SGLang 往往能拿到收益。
4. 两者迭代都很快,**定期重新对比**,去年的结论今年可能不成立。

**总结:** 没有绝对赢家——生态与通用性看 **vLLM**,前缀共享与结构化/编排场景看 **SGLang**。最靠谱的做法是拿自己的业务压测。
