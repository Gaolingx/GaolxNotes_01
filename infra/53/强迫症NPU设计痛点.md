## 先给结论：会痛苦，但主要原因不在 xcvu13p

真正的痛苦来自**反馈环长度和确定性的丧失**，跟“强迫症”本身关系没那么大：强迫症意味着你需要可控、可收敛、可解释，而大 FPGA + NPU 这套组合恰好把这三样东西全拿走了。

### xcvu13p 到底是个什么量级

| 项 | 数量 |
|---|---|
| Logic Cells | ~3.78 M |
| DSP48E2 | 12,288 |
| BRAM | ~94.5 Mb（2,688 × 36Kb） |
| UltraRAM | ~360 Mb（1,280 × 288Kb） |
| SLR（Super Logic Region） | **4** |
| GTY | 最多 76 路 |

关键数字是最后一个：**4 个 SLR**。这颗芯片在物理上是由 4 个 die 拼成的，跨 SLR 的线要走硅中介层，延迟和布线资源都跟片内不是一个量级。这意味着你写的“逻辑”最终会被“物理”重新定价。

<details>
<summary><b>折磨点逐条拆：为什么强迫症会在这里破防</b></summary>

**1. 反馈环变成小时级。** 一个中等利用率的 NPU 全流程（synth + opt + place + route + timing）在 VU13P 上跑 6–20 小时很正常，高利用率加拥塞能到 30 小时以上。强迫症的本能是“我再试一个想法”，而这里的成本是半天。你的迭代直觉直接失效。

**2. 确定性消失——这是最致命的一条。** 同一份 RTL，换个 seed 或 directive，WNS 能差 200 ps；改一行语法等价、综合结果相同的代码，布线全变，时序崩掉。你会本能地想“一定有最优解，我只差再试一次”，但这个问题**没有收敛判据**。开放性搜索 + 完美主义 = 无限递归，这是真正的陷阱。

**3. “代码即真相”的安全感被剥夺。** 你精心写的 RTL，最终表现由 floorplan、pblock、SLR 分配决定。你不得不在 RTL 之外再去控制一个物理层，而那层的工具（opt_design 的 retiming、phys_opt）是黑盒，它悄悄帮你改了网表，你不知道改了什么。控制欲在这里被正面击穿。

**4. NPU 的验证空间是爆炸的。** 128×128 systolic array 跑几千 cycle，波形根本没法用眼睛过。你必须接受“靠 assertion + 参考模型 co-sim + 覆盖率来信任”，而不是“我再看一眼 wave”。对一个想逐条确认的人，这一步是心理关，不是技术关。

**5. 资源账本细到令人发指。** DSP48E2 里 int8 打包塞几个、URAM cascade 怎么接、BRAM 碎片怎么拼、LUT 当 distributed RAM 剩下的零头……利用率到 95% 以上时你还想再榨 2%，而每榨一次又是 10 小时。

### 但别急着代入受害者

在“超大工程”这个语境下，强迫症的很多特质其实是**优势**，只是需要换个用法：

- 严格的命名/接口规范/时钟域约定 → 几十万行 RTL 里这是保命的
- 天然想把流程脚本化、可复现 → 这正好是对抗不确定性的唯一武器
- 精细的资源账本 → NPU 本来就是资源敏感型设计，这个习惯值钱

问题不在于“要不要细”，而在于**你把细致用在了不可控的地方**（去追那 1% 的布线运气），而不是可控的地方（自动化、断言、回归）。

### 生存指南（本质是把分母做大）

1. **全 Tcl 化 + non-project mode**，每次 run 产出 checkpoint，任何结果都能从脚本重放。
2. **固定 directive/seed**，把每次 impl 的输入 hash、report 存档，用数据说话而不是用感觉判断——这也顺带治好“我觉得这次会好一点”的幻觉。
3. **早做 floorplan**：pblock 按 SLR 切，跨 SLR 路径单独约束，别等布线炸了才想这事。
4. **OOC 综合 + 增量实现**，把单模块反馈环从小时级压到分钟级，这是唯一能救你理智的东西。
5. **建立收敛判据再开工**：比如 WNS ≥ 0、资源 < 90%、吞吐达标，就停手。这句话对强迫症最难，但必须有。
6. **接受统计性信任**：结构正确 + 断言覆盖 + 回归通过 = 可以交付，不需要肉眼确认每一个 cycle。

痛苦程度大致是：

$$\text{Pain} \approx \frac{\text{完美主义强度} \times \text{反馈环时长}}{\text{自动化程度}}$$

VU13P + NPU 把分子做到了很大，而你唯一能动的只有分母。**把分母做大，痛苦就从“生理性”降到“可管理”。**

顺便说一句：真按这个流程走下来，你会发现自己不是被治好了，而是被训练成了一个会在“该停的地方停”的工程师——这大概是强迫症在硬件行业里最好的结局。
