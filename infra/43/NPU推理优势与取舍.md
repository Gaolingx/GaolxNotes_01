## 一、“上限更好”这句话要配一个指标才有意义

推理（尤其是 decode）的瓶颈并不在 MAC 阵列的密度。decode 阶段每 token 要读一遍权重，算术强度极低，通常只跑到峰值 FLOPs 的个位数到 20% 区间。**这个阶段是 HBM 带宽和容量受限，而不是算力受限。**

所以：

$$\text{tokens/s} \approx \frac{\text{HBM BW}}{\text{每 token 需要搬运的字节数}}$$

你把 SM 的指令流水线、warp scheduler、寄存器堆全删了，换成纯 dataflow 阵列，MAC/mm² 也许能提升 2–3 倍——**但对 decode 的吞吐几乎零收益**，因为瓶颈不在这里。你省下来的是面积和功耗（这是真的，perf/W 会好看），但换不成 HBM 带宽。而 HBM 容量和带宽受 CoWoS、PHY、封装层数限制，跟你有多少逻辑面积无关，而且它是市场定价的——ASIC 厂买 HBM 不会比 NVIDIA 便宜。

这是一个很关键的约束：**你能删掉的约束都是便宜的那种（调度器、指令译码、通用性），你继承的约束都是贵的（HBM、先进封装、光互联、供电）。** 省几个百分点的 die area 对总成本曲线几乎没有影响。

> prefill 确实是算力受限，那里 dataflow 的优势是真的。但 prefill 在总成本里的占比在往下走（context caching、disaggregation、chunked prefill 都在削它），而且 GPU 在 prefill 上本来就不弱。

## 二、逐条拆你的三个论点

<details>
<summary><b>1. “删掉一堆 NoC 调度器腾出空间”——方向对，量级错了一个数量级</b></summary>

大芯片的面积账，粗略量级：

- **SRAM 是大头**：寄存器堆（H100 约 132 SM × 256KB ≈ 33MB）+ L2（约 50MB），两项合计往往占 die 的两三成
- **网络本体**：crossbar/NoC 的线宽和交换节点，5–10%
- **NoC 里的“调度器”**：仲裁、VC 分配、credit 管理——这是网络成本的**小零头**，全删了大概省 1–3% 面积
- **warp scheduler + 指令发射**：占 SM 面积的个位数百分比

真正的大头是**整个 SIMT 执行模型**（寄存器堆 + 通用指令流水线），不是调度器。把它换成静态 dataflow，compute tile 能省 15–20% 面积——这才是有意义的量。但注意：推理恰恰**需要更多** SRAM 做 staging（B200 上 192MB 的片上内存不是浪费，是刚需），所以你省下的 SRAM 压力马上又被吃回去。

所以“腾出更大空间”这句话，实际能腾出来的空间比想象中小很多，而且腾出来也没地方用。
</details>

<details>
<summary><b>2. “不用维护 GPU 的一致性传统”——这里有个误解</b></summary>

GPU 从来**不是** CPU 那种 cache-coherent 机器。NVIDIA 的模型是 **weakly ordered + scoped synchronization**：L1 不跨 SM 一致，靠 `__threadfence`、acquire/release、scoped atomics 由软件管理。

GPU 真正背的包袱不是“一致性”，是**内存模型的通用性**：任意地址的原子操作、多 scope 的 fence、任意粒度的 load/store。这确实要占 L2 和 NoC 的面积和延迟。

NPU 可以把这个丢掉——但代价是它变成一台**只能跑静态图**的机器。而这里有个反讽：Hopper/Blackwell 的 **TMA** 就是硬件描述符驱动的批量异步拷贝，本质已经是“消息传递”了。GPU 一直在往 NPU 的 dataflow 形态收敛，而 NPU 站在原地不动——**两者的差距在缩小，不是拉大。**
</details>

<details>
<summary><b>3. “暴露 NUMA、消息传递替代共享内存”——这条最有价值，但你自己也说收益不好说</b></summary>

这条我给的评价最高，理由不是芯片层面，是**系统层面**：

- 现在 scale-up 域（NVL72、GB200 rack）里，NVSwitch 故意把拓扑做成**扁平**的，就是为了让程序员不用管 NUMA。这是被逼的工程妥协，不是最优解。
- 推理服务的拓扑是**静态已知**的：模型并行度、TP/EP 切法、batch 调度策略在部署时就定了。**静态 placement 本来可以赢过动态 uniform。** 这是你论点里最强的一个版本。
- 而且 disaggregated prefill/decode 让通信模式**本来就在往消息传递漂**（KV cache 跨节点搬）。你的直觉和产业方向是一致的。

但是：
- **MoE 的动态路由、KV cache paging、dynamic batching 都强烈想要远端 load/store 语义**。纯消息传递在这些场景会成为瓶颈。
- message passing 和 remote DMA 的界线在实际实现里是糊的（RDMA 也是“写远端内存”），真正的区别是**谁做地址翻译、谁做完成通知**。
- 真正有戏的不是“消息传递”，是**无 NVLink 包袱的 fabric 全新设计**：光交换、memory-semantic fabric（类似 Enfabrica 那类）、in-network reduction 做到 collective 原生。这是新玩家唯一能真正跳过去的地方——因为不用背 NVLink 的向后兼容。
</details>

## 三、AI 解决编程难度：真实边界在哪

这是我认为**被高估最多**的一条。

AI 能解决的是“写 kernel”。但 ASIC 的真实护城河不在 kernel 代码里，在：

1. **性能模型的调试**。静态调度的机器没有 graceful degradation——GPU 上映射不好的 kernel 跑 30% 速度；dataflow NPU 上映射不好直接**装不下**，或者慢 10 倍。尾部风险完全不同量级。
2. **生态是分布式的**：每个库、每个数值边界情况、每个 framework 的 lazy/eager 语义差异、每个 collective 实现。AI 降不了这部分。
3. **对手也在用 AI**。用 AI 写 kernel，两边都获得 10 倍，而且 GPU 侧的收益是累积的（Triton、autotuning、TVM 系一直在吃这个红利）。**它压缩 NPU 的劣势，但同时抬高 GPU 的天花板。**

净效果：AI 让 NPU 的**差值**变小，但没改变**方向**。

## 五、我会下注的地方

如果我是你，我会把赌注从“删调度器”挪到这三个：

1. **decode 专精的 serving 芯片**：目标不是算力，是 $\text{HBM bytes}/\$/\text{watt}$ 最大化。放弃所有 SIMT 通用性，把逻辑面积压到最小，把每一分功耗和面积都换成 HBM 和更宽的片上 SRAM。这里的上限确实更高，因为 GPU 在 decode 上浪费了大量面积在它用不到的通用性上。

## 一、显式调度：省下的是寄存器堆，调度器本身占比很小

<details>
<summary><b>展开：warp scheduler 的真实成本</b></summary>

硬件 warp scheduler 在一颗 SM 里被复制 4 份，逻辑量大概占 SM 的 1–2%。**它本身不是面积问题。**

它真正的代价是**它存在的前提**：你需要“足够多的 warps 来隐藏延迟”，于是要 64 warps/SM，于是要有巨大的寄存器堆（H100 约 132×256KB ≈ 33MB），于是 occupancy 成了第一设计约束。**寄存器堆才是那笔账。** 硬件调度器只是“用 TLP 藏延迟”这个策略的执行者。

所以你的判断方向是对的——但收益应该记在“删掉寄存器堆，把它换成 staging buffer”，而不是“删掉调度器”。

而且有个反直觉的事实：**变压器推理里 90%+ 的时间已经在跑硬件序列化的东西了。** Hopper 的 `wgmma` 是一条指令完成整个 MMA 流水，异步、不经过 warp scheduler；TMA 是描述符驱动的批量搬运；mbarrier 是硬件同步。warp scheduler 只处理 prologue/epilogue 和 softmax 那些碎片。**你想“显式化”的部分，NVIDIA 已经显式化得差不多了。**

真正的限制在别处：**HBM 延迟不是确定性的**（受拥塞影响可差 2–3 倍）。纯静态调度要求编译期知道延迟，所以必然需要保留若干记分牌/队列做动态兜底。片上 SRAM 命中的延迟是可预测的——**所以“显式调度”在片上能成立，到 HBM 边界就必然退化。** 这就是为什么所有 NPU 最后都长出了一些动态机制。
</details>

## 二、L2 的问题：你要的是“共享 SRAM”，不是“cache”

你括号里那个问题——**“推理没有几个 core 在 L2 共享一个 tile 的情况吗？有就逃不掉”**——答案是有，但关键区分是 **cache（tag/替换/一致性）vs scratchpad（软件管理的共享 buffer）**。

**需要共享的场景（真实存在）：**

| 场景 | 是否需要跨 core 共享 | 需要的是 |
|---|---|---|
| TP 按 head 切（dense 变压器主流） | **不需要**，每个 core 独占自己的 head 和 KV 分片 | 无 |
| batch 维度切分（同一层权重被多个 core 读） | **需要广播** | 共享 buffer |
| All-reduce（输出投影、TP 归约） | **需要集合通信汇合点** | 共享 buffer + 原子 |
| Split-K GEMM 部分和合并 | **需要** | 共享 buffer |
| MoE 专家权重（多 token 命中同一专家） | **需要** | 共享 buffer |
| Sequence parallel | **需要** attention 归约 | 共享 buffer |

所以结论是：**dense 变压器按 head 做 TP 时，真的可以没有共享 L2。** 这是你直觉里最成立的一块——而且这不是偷懒，是 workload 真的允许。

但注意 L2 在 GPU 上不只是 cache，它同时承担四件事：

1. **带宽放大器**——把 32B sector 聚合成 128B line，省 HBM 带宽。删掉 L2 你就得自己保证访问全是大块连续
2. **原子操作引擎**——推理里 split-K、work-stealing、continuous batching 的计数器都需要原子
3. **TLB/地址转换的汇聚点**
4. **跨 GPC 的汇合点**

删 L2 不是“省了”，是**这四件事你得换个地方做**。换成一个“buffer 网络”完全可行，但那是重新设计，不是免费删除。

**关于 QoS 你说得对，但可以更精确**：共享 L2 的尾延迟来自 **bank 冲突 + MSHR 饱和**，这是 p99 杀手。但解法不一定非得删 L2——NVIDIA 自己有 L2 分区/set-aside。不过对推理 SLA 来说，“确定性延迟”确实是可以直接卖的产品特性，这比吞吐更值钱。

## 三、“多 die 肯定比单 die 好”——良率这个说法，算术上是不成立的

这条流传很广，但**在同一个节点、同样的总面积下，切 die 不改善良率，甚至略差。**

用负二项模型 $Y = (1 + A D_0/\alpha)^{-\alpha}$，取 $D_0 = 0.09/\text{cm}^2$，$\alpha = 4$：

**单片 800mm² ($A=8\text{cm}^2$)：**
$$Y = (1 + 0.72/4)^{-4} = 1.18^{-4} \approx 0.516$$

**切成 2×400mm²（两颗都要好）：**
$$Y_{\text{单颗}} = (1+0.36/4)^{-4} = 1.09^{-4} \approx 0.708,\quad Y_{\text{成对}} = 0.708^2 \approx 0.502$$

$0.516 > 0.502$。**单片略好。**

真正的驱动是这三个，跟良率无关：

1. **reticle limit（约 858mm²）**——1700mm² 的 die 物理上不存在。B200 是 2×近 reticle，**是被迫的，不是选的**
2. **异质节点**——大 SRAM 阵列和高密度逻辑分开流片（把 defect 密集的 SRAM 放成熟节点），这才是良率收益的真实来源
3. **known-good-die 测试**——不让坏 die 进昂贵封装；以及可以 bin 降级卖

所以“单 die 没啥不好”你的判断是对的——**单 die 通常是更好的，多 die 是被 reticle 和异质集成逼出来的。**

## 四、核心问题：内存语义 vs 消息传递，对底层实现到底有什么影响

你问的这个，是最有价值的一问。差异不在“快慢”，在**你把面积和复杂度花在哪、把正确性责任交给谁**。

<details>
<summary><b>展开：六个具体实现层面的影响</b></summary>

**1. 地址空间与路由方式（最基础的分野）**

- **内存语义**：fabric 必须按**地址**路由。你需要一张全局地址映射表、目标端地址译码、以及（如果地址不静态划分）远端 ATC/TLB。地址空间一旦分配就固定，buffer 不能随便搬家。
- **消息传递**：只需要**目的 rank/ID + 偏移**。目标端把消息写进一个编译器分配的 buffer，地址完全由编译器决定。**不需要全局地址空间，不需要远端翻译。**

后者的简化幅度很大——你省掉了整个地址一致性基础设施。

**2. 排序模型（这是最大的一笔）**

- **内存语义**：必须有内存序保证。requester 端要有 MSHR、outstanding 表、fence 语义；两端要有 reply buffer。**这是面积和验证成本的主要来源**，而且一致性协议的验证是整个 SoC 里最贵的部分之一。
- **消息传递**：**完全没有硬件排序要求**。顺序由程序用 barrier/令牌定义。硬件只需要保证单条消息不丢不乱，不需要跨消息保证任何东西。

这一条就是你怀疑的“快速上线”驱动——**是的，非常是。** 砍掉一致性协议的验证，时间线能省掉一大块，这不是省钱，是省命。

**3. 死锁与虚通道**

- **内存语义**：请求和响应在通用拓扑上会形成环，你必须用虚拟通道、escape VC、或者 up*/down* 无死锁路由。**VC 数量直接乘以 router 的面积和延迟。**
- **消息传递**：静态调度下通信图是 DAG，**死锁自由是可证明的**，VC 可以砍到很少甚至 1 个。

少 VC = 更简单的 router = 更低延迟 + 更小面积。这是很硬的一笔。

**4. 延迟隐藏的结构**

- **内存语义**：需要足够深的 MLP（同时挂很多 outstanding request）才能藏住往返延迟 → 深缓冲 → 面积 + 功耗。
- **消息传递**：用双缓冲 + 软件流水线，缓冲深度由 schedule 决定，**上界可静态算出**。

**5. QoS 的实现难度（反而内存语义更难）**

- **内存语义**：流量是**涌现的**——你不知道下一秒谁会访问谁。做 QoS 必须给每个 transaction 打 tag + 仲裁，成本高且不完美。
- **消息传递**：流是**已知的**、有限的。按流静态分配带宽/优先级，可以给出确定性保证。

**这就是为什么 Groq 能承诺确定性延迟，而 GPU 不能。**

**6. 粒度分界线（最实用的一条经验）**

$$\text{传输} < \text{几百字节，或需要细粒度 scatter} \Rightarrow \text{load/store}$$
$$\text{传输} > \text{KB 级，连续} \Rightarrow \text{DMA/消息}$$

这就是为什么 TMA 存在、为什么 Hopper 同时又给了 DSMEM（cluster 内远端 load/store）和远端原子。**不是二选一，是按粒度分段。**

</details>

**收敛判断：真实设计从来不选边，而是分工。**

```
粗粒度 bulk（权重流、KV 搬运）  → 消息/DMA/TMA   （省 header、可静态排、可证无死锁）
细粒度控制面（原子、标志、scatter）→ 远端 load/store （灵活、低延迟）
```

**纯消息传递的设计，赌的是“通信图在编译期完全已知”。** dense 变压器按 head 切 TP 时这个假设成立；一旦上 MoE（动态 all-to-all）、paged attention + prefix sharing（跨请求 KV 转发）、或者 prefill/decode 分离（KV 跨节点搬），这个假设就崩了。

## 五、那家做隔离内存域的推理芯片：业务驱动是什么

你的怀疑是对的，而且不止一个驱动：

1. **没有一致性协议要验**——时间线（你说的快速上线）
2. **没有大 L2**——die 更便宜、更容易挤进成本线
3. **p99 可承诺**——推理 serving 卖的是 SLA，不是吞吐。共享 L2 的内部干扰让你无法对 p99 打包票，隔离域可以
4. **而且在 dense 变压器 TP-over-heads 这个场景下，它真的是对的**——每个 core 拿自己的权重分片和自己 head 的 KV，**唯一跨 core 流量是 collectives**，那本来就是消息

所以这不是纯偷懒，是 **workload 真的允许**。风险在于断崖：模型一变成 MoE / 长上下文 agent，静态切分就开始掉效率，而且**掉得很陡**——这正是 Graphcore IPU 的教训，它技术上成立，编译器负担把它拖死了。

## 六、把取舍摆成一张表

| 维度 | 偏内存语义 | 偏消息传递 |
|---|---|---|
| 面积花在 | MSHR/reply buffer/排序表/多 VC | SRAM 双缓冲 |
| 验证成本 | **高**（一致性协议） | 低 |
| 死锁 | 需 VC/escape，硬件成本 | 可证明无死锁 |
| QoS | 涌现流量，难保证 | 已知流，可保证 |
| 灵活性 | 高（MoE/动态路由友好） | 低（编译期必须已知） |
| 断崖风险 | 低 | **高** |
| 上手难度 | 低 | 高（编译器就是护城河，也是坟墓） |

**你原来那句“各有各的取舍，不是哪种一定更好”是对的，但可以再收一格：**

> **约束可以删，但不会消失，只是转移到编译器身上。** 你删掉的一致性协议、动态调度、L2 缓存，全部变成了“编译器必须在编译期算对的东西”。而编译期算不对的部分——HBM 抖动、请求到达的不规则、模型结构变化——最终还是要靠硬件里的动态机制兜底。

**所以“约束少”这件事，对硬件是减法，对整个系统是加法。** 这正是为什么 AI 降编程难度这个论点只在“你拥有整个栈”（TPU 路径）时能兑现，而在做 merchant 加速器时不成立——**因为 merchant 的客户不打算按你的编译期假设来写模型。**
