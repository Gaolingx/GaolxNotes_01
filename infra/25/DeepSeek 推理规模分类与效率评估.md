## 先给结论

**硬件属于“千卡级”集群，服务吞吐却达到“超大规模（hyperscale）级”。** 这组数字真正表达的重点在于：**单卡产出的 token 数**属于第一梯队的量级，而非“全球最大的推理集群”。2400 张 B200 是中型集群的规模，却提供了头部厂商用数万卡到十万卡才撑起的服务量。

## 一、把口径换算成可比的数

| 指标 | 换算结果 |
|---|---|
| 日均 tokens | $1.55\times10^{14}$ |
| 聚合吞吐 | $\approx 1.79\times10^{9}$ tok/s（约 **179 万 tok/s**） |
| 单卡吞吐（含缓存） | $\approx 6.46\times10^{10}$ tok/天 ≈ **74.7 万 tok/s/卡** |
| 年化 | $\approx 5.7\times10^{16}$（**5.7 京** tokens/年） |
| 集群 FP8 峰值算力 | $2.4\times10^{3}\times4.5\times10^{15}\approx$ **10.8 EFLOPS** |
| IT 功率 / 总功率 | 约 **3–4 MW / 4–5 MW**（按 B200 单卡 1.2–1.7 kW、PUE 1.2 估） |
| 资本开支量级 | 约 **0.7–1 亿美元**（按单卡 3–4 万美元估） |

对照参考：Google 曾公开提到月处理约 1.3 千万亿（1.3 quadrillion）tokens，折算约 **4.3 万亿/天**（公开表述与每月天数估算，仅作量级参考）。也就是说，DeepSeek 对外给出的 155 万亿/天，**大约是这一数字的 3–4 倍**；但支撑它的 GPU 数量少一到两个量级。这正是“普惠”二字的技术落脚点。

## 二、关键：155 万亿要分两层看

96% 缓存命中率是关键前提。**它把“服务规模”和“真实算力规模”拆成了两个完全不同的数：**

- **服务规模（对外计费/统计口径）**：155 万亿/天 → 1.79 M tok/s
- **真实算力规模（4% 未命中）**：约 **6.2 万亿/天** → $7.2\times10^{7}$ tok/s，即单卡约 **3 万 tok/s 的实算吞吐**

第一层数字（74.7 万 tok/s/卡）在物理上不可能是解码或预填充的真实计算量；第二层（3 万 tok/s/卡）才是 GPU 真正需要的计算量。对稀疏 MoE 的预填充来说，这一量级是合理的，也说明**“155 万亿”并非算力堆出来的，而是靠缓存与调度节省出来的**。

## 三、属于什么“档位”

1. **服务量级：超大规模（hyperscale）**。日处理 tokens 与全球头部 API 平台同处第一梯队，年化 5.7 京 tokens 已经是“国家级基础设施”的计数方式。
2. **集群量级：中型（千卡级）**。对比前沿训练集群（xAI、Meta、MSFT 动辄十万卡级），2400 张 B200 只是它们的 $\tfrac{1}{50}$–$\tfrac{1}{100}$，属于“单区域可交付”的规模，不是“最大规模”。
3. **效率量级：远超其卡数应有的水平**。若按常规吞吐/卡效率估算，同等服务量通常需要万卡以上；它用约 2400 卡做到了，**等效算力被放大约 3–10 倍**。
4. **用户侧体验量级**：230 tok/s 是“远高于人类阅读速度”的档位（人类阅读约 5–10 tok/s），意味着**即使在高负载下，用户也不容易察觉排队**。按 230 tok/s × 数万级并发估算，解码侧聚合吞吐在 $10^{7}$ tok/s 量级，属于“消费级产品 + 企业级并发”的混合负载特征。

## 四、需要注意的口径风险

- **155 万亿是否包含缓存命中的重复 token**、是均值还是峰值日，直接决定结论相差一个数量级（若实为 1.55 万亿/天，则单卡实算吞吐仅约 300 tok/s，明显偏低，反而不自洽；因此 155 万亿更可能成立）。
- **230 tok/s 是单流 decode 速率还是含排队后的端到端速率**，会改变并发规模推算。
- **2400 卡是否包含 PD 分离中的 Prefill 与 Decode 全量**、是否含冗余，会影响“等效卡数”的比较基准。

**一句话总结**：这是**“中型集群 + 超大规模吞吐 + 顶级单卡效率”**的组合，即**以千卡级硬件提供万卡级的服务能力**，属于当前开源/自建部署阵营里效率最高的那一档，但并非绝对算力规模最大的那一档。
