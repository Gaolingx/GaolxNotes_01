# GGUF量化是软件层分块+仿射/LUT，MXFP4/NVFP4是硬件原生浮点微缩放格式

## 🧑‍💻 User

gguf的q量化是lut查表+分块吗？

---
## 😀 默认助手 (7)

## 一句话结论

**分块：是，而且全部是。** GGUF 里每一种 Q 量化都是“定长块 + 每块独立的 `scale`(和 `zero/min`)”的分块量化，块大小固定为 32 或 256。

**LUT 查表：只有一部分是。** 要分两个家族看：

| 家族 | 例子 | 反量化方式 | 是 LUT 吗 |
|---|---|---|---|
| 传统仿射 | `Q4_0` `Q4_1` `Q5_0/1` `Q8_0` | $w=d\,q$（或 $+m$） | ❌ 纯乘加 |
| K-quants | `Q2_K`…`Q6_K` | 两级 scale 的仿射：$w=d\,s\,q-d_{min}m$ | ❌ 纯乘加（但内核里有 mask 查表） |
| **i-quants** | `IQ1_S` `IQ2_XXS/XS/S` `IQ3_XXS/S` `IQ4_NL` `IQ4_XS` | 索引 → **码本/格点表** → 值 | ✅ 真 LUT |

所以准确的说法是：**GGUF 的量化 = 分块 +（K-quants 的两级仿射 / i-quants 的码本查表）**，而不是“整体都靠 LUT”。

---

## 1. 分块结构（全部格式）

GGUF 只是容器，量化方案由 ggml 的 tensor type 指定（文件里每个 tensor 只存一个枚举，如 `Q4_K`、`IQ4_XS`）。

**传统格式：块大小 32**

| 格式 | 存储 | 反量化 |
|---|---|---|
| `Q4_0` | `d`(fp16) + 16B nibbles | $w=d\,(q-8)$ |
| `Q4_1` | `d`,`m` + 16B | $w=d\,q+m$ |
| `Q5_0` | `d` + `qh` + 16B | $w=d\,(q+16h-16)$ |
| `Q8_0` | `d` + 32×int8 | $w=d\,q$ |

**K-quants：超级块 256，两级量化（关键差异）**

| 格式 | 超级块 | 子块 | scale 位宽 | 反量化 |
|---|---|---|---|---|
| `Q2_K` | 256 | 16×16 | 4-bit scale + 4-bit min | $w=d\,s\,q-d_{min}m$ |
| `Q3_K` | 256 | 16×16 | 6-bit | $w=d\,s\,(q-4)$ |
| `Q4_K` | 256 | 8×32 | 6-bit scale + 6-bit min | $w=d\,s\,q-d_{min}m$ |
| `Q5_K` | 256 | 8×32 | 6-bit + 1 个高位 | 同上 |
| `Q6_K` | 256 | 16×16 | 8-bit signed | $w=d\,s\,(q-32)$ |

注意这里 `d` 和 `d_min` 才是 fp16，**`s` 本身也被量化成 4/6 bit**，这就是所谓的 double quantization；它是 K-quants 反超 `Q4_0` 的全部秘密之一，约等于把元数据开销从 2B/32 降到约 0.5B/32。

## 2. LUT 到底出现在哪

<details>
<summary><b>(a) i-quants 的码本 / E8 格点表（真正的 LUT）</b></summary>

每组权重量化时不取最近的整数，而是取最近的**格点/码本向量**，只存索引：
- `IQ4_NL`：每 32 权重一块，16 项非线性表 `kvalues_iq4nl[16]`（约 `{-127,-104,-83,-65,-49,-35,-22,-10,1,13,25,38,53,69,89,113}` —— 非均匀，靠近 0 更密），$w=d\cdot\text{LUT}[q]$。
- `IQ2_XXS / IQ2_XS / IQ2_S`：约 256 / 512 / 1024 项码本。
- `IQ3_XXS / IQ3_S`：约 256 / 512 项码本。
- `IQ1_S`：约 2048 项码本（再叠加符号位）。

每个索引一次解出 4~8 个权重（格点打包），再乘符号位掩码和逐子块 scale。**块大小仍是 256**（`IQ4_NL` 是 32），所以“分块”这条从未缺席。
</details>

<details>
<summary><b>(b) 内核层的“小查表”（容易被误当成量化 LUT）</b></summary>

K-quants 是仿射的，但 SIMD 内核里确实有查表：
- `Q4_K` AVX2 路径用 `_mm256_shuffle_epi8` 配合 `kmask1/2/3` 这类 16 字节常量，把打包的 6-bit scale 拆出来；(标量路径对应 `get_scale_min_k4`)
- `IQ4_NL` 的 `ggml_vec_dot_iq4_nl_q8_0` 直接用 `_mm256_shuffle_epi8(kvalues_iq4nl, ...)` —— 一条 `pshufb` 就是一次 LUT 查表。
- CUDA 端把 i-quant 码本放 `__constant__`/只读缓存，也是 LUT。

这些是**指令级实现技巧**，与“量化方案本身是不是码本”要分开看。
</details>

<details>
<summary><b>(c) 编码端的 LUT 搜索（为什么 i-quant 量化那么慢）</b></summary>

`quantize_row_iq*` 要对每个子块在码本里做**最近邻搜索**（枚举索引 + 符号组合），计算量与码本规模成正比，所以 `--type iq2_xxs` 量化一个 7B 模型可能要几十分钟到几小时；K-quants 只是算 min/max 再除一下，秒级完成。
</details>

---

## 3. 一个常见误解：推理时并不“反量化成 fp32 再乘”

实际 `mul_mat` 走的是 `vec_dot`，权重保持量化态，**激活被在线量化成 8-bit**（`Q8_0`；i-quants 用 `Q8_K`，256 块 + fp32 逐子块 scale），然后做**整型点积**再乘回 scale。所以：

- 传统/K-quants：$\sum q_w q_a$ 的整数点积 × 两个 scale → 不需要任何逐权重浮点表
- i-quants：码本查表得到 $\pm$ 小整数 → 同样做整数点积

---

## 4. 为什么这么设计（取舍）

| | 分块仿射（Q4_K 等） | 码本 LUT（IQ*） |
|---|---|---|
| 逐元素操作 | 乘加，完美向量化 | 不规则 gather |
| 同 bit 下误差 | 一般 | 更低（格点/非均匀） |
| 硬件友好度 | 极高（含各类 NPU/移动端） | 差（随机访存、分支） |
| 典型用途 | 通用默认 | 极限低比特（2~3 bit）或极致质量（IQ4_XS） |

所以 `Q4_K_M` 这类“仿射 + 两级 scale”是主流默认，而 LUT 家族是为 **2-bit 附近**（此时均匀量化已经不可用）以及**同 bit 数下追求最低困惑度**服务的。

<details>
<summary><b>速记版（想背下来的话）</b></summary>

- GGUF = 容器；量化方案 = ggml tensor type。
- **全部格式都分块**：32（legacy / `IQ4_NL`）或 256（K-quants / i-quants）。
- **`Q*_0` / `Q*_1` / `Q*_K`：仿射，$d\cdot q$ 或 $d\,s\,q-d_{min}m$，无码本。**
- **`IQ*`：码本/格点 LUT 查表，`IQ4_NL` 是 16 项非线性表。**
- K-quants 的 “K” = 超级块 256 + 两级（scale 也量化）；i-quants 的 “i” = importance-matrix 友好的码本量化。
- 推理用 `vec_dot` 整型点积，不做整块反量化到 fp32。
</details>

（码本项数/子块划分按 llama.cpp `ggml-common.h` 量级给出；不同版本略有调整，具体以你所用版本的 `ggml-common.h`、`ggml-cpu-quants.c` 为准。）

## 先厘清比较对象：两者不在同一个维度上

**GGUF 的 Q\* / IQ\* 是“软件存储格式”**：它预先确定整数网格或码本，在 CPU/SIMD 内核里做 dequant + 整型点积。

**MXFP8 / NVFP4 是“硬件可直接处理的数据类型标准”**（OCP MX 规范和 NVIDIA Blackwell），目标是由 tensor core 在同一指令内完成“取元素 → 乘 block scale → FP32 累加”。

但把参数对齐到约 4.5 bpw 后，两者可以直接比较，而且会发现它们其实是同一思路的两个时代、两个阵营：

| | **Q4_K** | **IQ4_XS** | **MXFP4** | **NVFP4** |
|---|---|---|---|---|
| 元素格式 | int4 均匀网格 | 4-bit **索引**→16 项非线性表 | **FP4 E2M1**（1 符号+2 指数+1 尾数） | FP4 E2M1 |
| 块大小 | 256（8×32） | 256（8×32） | **32** | **16** |
| 块内 scale | fp16 `d` + **6-bit** `s` + 6-bit `min` | fp16 `d` + 6-bit `s` | **E8M0**（8-bit 纯指数，只有 2 的幂） | **FP8 E4M3** + 全局 FP32 |
| 是否有零点 | ✅ `d_min`（非对称） | ❌（表内隐含） | ❌ 对称 | ❌ 对称 |
| 实际 bit/weight | **4.5** | **4.25** | **4.25** | **4.5** |
| 非均匀性来自 | 无（均匀）；IQ 才靠表 | 码本表 | **元素自带指数** | 元素自带指数 |
| 激活 | q8_0 / Q8_K（**W4A8**） | Q8_K（W4A8） | 通常 W4A16/A8，Blackwell 可 W4A4 | 设计目标 **W4A4** |
| 谁在加速 | CPU 带宽 | CPU | Blackwell 张量核（2× FP8） | Blackwell 张量核 |

两者 bit 预算几乎完全一样，**所以差别全部在“这些 bit 怎么分配”**。

## 三个本质区别

<details open>
<summary><b>① 浮点元素 vs 整数仿射：非均匀性由谁承担，这是关键区别</b></summary>

FP4 的 16 个码值集合是：
$$\{0,\ \pm 0.5,\ \pm 1,\ \pm 1.5,\ \pm 2,\ \pm 3,\ \pm 4,\ \pm 6\}$$
这是个**对数式（相对精度）网格**：块内动态范围 12:1，越靠近 0 越密。

int4 只有 16 个**等距**电平（`0..15` 或 `-8..7`），块内动态范围只有 15:1 但间距均匀，只能靠 `scale`（和 `min`）平移缩放；它没有内在的非均匀性。

**GGUF 通过两套方案处理这件事：**
- `Q4_K`：接受均匀网格，靠 **6-bit 精细 scale + dmin 零点** 弥补（用更好的“偏移和缩放”换均匀）
- `IQ4_NL`：改用 16 项**查表**，表就是人为设计的非均匀网格 $kvalues=\{-127,\dots,-10,1,13,25,38,53,69,89,113\}$（注意：**没有精确的 0**）

所以 **IQ4_NL 和 FP4 在数学上是同一类事物**：都是“16 项非均匀网格 × 一个共享 scale”。区别只在于：FP4 的非均匀性是**指数结构自带的**（硬件免费），IQ4_NL 的非均匀性是**表驱动的**（硬件要查表）。

</details>

<details>
<summary><b>② scale 精度与元素动态范围：此消彼长的设计互补（最深的一点）</b></summary>

| | scale 分辨率 | 元素自身动态范围 | 结论 |
|---|---|---|---|
| MXFP4 | E8M0 = **每 octave 只有 1 级**（最差可差 2×） | FP4 有 12:1 | 粗 scale 靠“元素是浮点”兜住 |
| NVFP4 | E4M3 = 每 octave **8 级** | FP4 有 12:1 | 折中 |
| Q4_K | fp16 + 6-bit = 每 octave **约 64 级** | int4 等距，12:1 都不到 | 必须靠细 scale |
| IQ4_XS | fp16 + 6-bit（同 Q4_K） | 表内非均匀 | 双保险 |

**设计上必须遵守的约束**：给均匀整型配 E8M0（只有 2 的幂）是灾难——一个块的最大值会被量化到 2× 偏差；给浮点元素配 E8M0 则能容忍，因为元素自己的指数还在。MX 之所以选择 E8M0，纯粹因为它让乘法退化成**指数相加**，硬件几乎零成本。

GGUF 选反方向：既然整数点积（dp4a/VNNI）已经足够快，就把 bit 花在**精细 scale** 上，用 2B fp16 + 6-bit 换掉“元素要自带指数”的成本。这就是为什么 Q4_K 只要 4.5 bpw 却能胜过早期 Q4_0。

</details>

<details>
<summary><b>③ 两级 scale：GGUF 比 MX 更早采用，NVFP4 才追上</b></summary>

- **K-quants（2023）**：`d`(fp16，每 256) + `s`(6-bit，每 32) + `d_min`(fp16，每 256) —— 即 **microscaling + double quantization**。
- **NVFP4（2025）**：FP32(每 tensor) + E4M3(每 16) —— 同样是两级。
- **MXFP4**：**只有一级**（E8M0 每 32，per-tensor scale 可选），层次最少。

所以如果你的直觉是“NVFP4 和 Q4_K 很像”，**这个直觉是对的**，两者都是“共享 scale 的微缩放”：区别是 NVFP4 把这套做法做成浮点元素和硬件可选格式，Q4_K 做成整数元素和 CPU 宏。

</details>

## 工程层面的差异（决定实际使用感受的部分）

| 维度 | GGUF Q\*/IQ\* | MXFP8 / NVFP4 |
|---|---|---|
| **数据布局** | scale **内联**在同一个字节流里（连 mmap 即可） | 数据张量 + **独立 scale-factor 张量**，并按 MMA 需要 swizzle/padding |
| **量化算法** | absmax/min-MSE per sub-block + **imatrix**（用校准激活给权重做重要性加权） | RTN 或 GPTQ 式 scale 搜索 + **Hadamard/随机旋转**（把权重高斯化，适配 FP4 的对数网格）+ 有时感知激活 |
| **激活量化** | 刻意保持 8-bit（W4A8），因为 4-bit 激活很难 | 目标 W4A4（NVFP4 主推），依赖旋转抑制离群值 |
| **CPU 可行性** | 原生（整型点积） | 需先把 FP4 查表转成整数或 fp——**MXFP4 在 CPU 上退化成“16 项 LUT + q8 点积”，与 IQ4_NL 几乎同构** |
| **GPU 收益** | 软件 dequant 到寄存器/shared → 只能用 FP16 tensor core 或 int8 mma，利用率低 | 原生 FP4 张量核，相对 FP8 理论 2×（相对 FP16 4×） |
| **生态** | llama.cpp / Ollama / LM Studio / 各种 GGUF 推理器 | TensorRT-LLM / vLLM / SGLang / Transformer Engine；`gpt-oss` 就用 **MXFP4** 原生导出 |

> 顺带说：llama.cpp 后来也直接加了 `MXFP4` 这个 tensor type（为 gpt-oss 服务），所以“GGUF vs MX”现在已经在同一个 runtime 里正面交锋——这也反过来证明两者是**同 bit 预算下的竞品**，而并非完全不同的东西。

## 质量直觉（同 ~4.5 bpw 时）

- **大致同一档**，都是“4-bit 权重量化可接受”的水平，差距在零点几个困惑度百分点里，且强依赖量化算法（imatrix / rotation / GPTQ）而非格式本身。
- **K-quants 的优势**：零点（`d_min`）+ 细 scale，对**有偏分布/通道间方差大**的权重更稳；不需要校准也能用（有 imatrix 更好）。
- **FP4 系列的优势**：格式简单、硬件通吃；**在 Blackwell 上快 2× 以上**，这是它唯一但决定性的理由。
- **FP4 系列的劣势**：E2M1 只有 3 个可表示的非零正幅值档（1, 1.5, 2, 3, 4, 6 中的一部分），对重尾权重靠**旋转**保底；没有零点，对偏移分布不友好。
- **MXFP8 vs Q8_0**：Q8_0 是 fp16 scale + int8／32 元素 = 8.5 bpw；MXFP8 是 E8M0 + E4M3／32 = 8.25 bpw。MXFP8 省 0.25 bit 但 scale 只有 2 的幂（略损精度），实际质量通常 Q8_0 略好——**这是“GGUF 用精细 scale 换 bit”策略最清楚的胜利案例**。

---

## 一句话总结

> **两者是同一类做法（分块共享 scale 的微缩放）的两种具体形式**：
> GGUF = **整型/码本元素 + 精细 fp16/6-bit scale（+零点）**，为 CPU 带宽和整型点积服务；
> MX/NV FP4 = **浮点元素（自带指数即非均匀网格）+ 粗粒度 E8M0/FP8 scale**，为硬件张量核的“指数相加 + FP32 累加”服务。
> 16 项的 `IQ4_NL` 表 ≈ FP4 的 16 个码值集合，只是把“非均匀性”从**格式**移到了**查表**里——所以你原来问的“LUT 查表 + 分块”，其实正是 MX/NVFP4 在 CPU 上被迫实现时必然会退化成的东西。
