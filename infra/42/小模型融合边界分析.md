## 一、先把“launch bound”这个词拆开

你的直觉基本是对的，但“开了 CUDA graph 还 launch bound”这种说法容易被误用。我觉得要分四层：

| 类型 | 机制 | CUDA Graph 能否消除 |
|---|---|---|
| host dispatch | 每次 launch 的驱动/API 开销 | ✅ 基本消除 |
| device dispatch | graph 节点在 device 侧仍有 0.5–2 µs 的派发 | ❌ 只便宜一点 |
| **边界屏障（drain + ramp）** | 每个 kernel 边界都是全局屏障，要等满 grid 排空，再重新填满 SM | ❌ **完全无法消除** |
| wave quantization / tail | grid 填不满 132 SM，或最后一波只有几个 CTA | ❌ |

最后两类才是关键。若标度取决于**边界数量**，叫 `boundary bound`（或 fixed-cost bound）比 launch bound 精确得多；CUDA graph 解决的是第一层，而 megakernel 解决的是第三层。一个 300-kernel 的图即使 graph 化了，边界开销是 $300 \times (\text{dispatch} + \text{drain}) \approx 300 \times 2\text{–}4\,\mu s$，CUDA graph 一分都省不掉。**所以“开了 cudagraph 还 bound”不是错觉，只是 bound 的对象换成了边界而非 host。**

## 二、论文给出的判据：$S(b) > F$

它把问题形式化得非常干净，我觉得比“越激进越好”有用：

- 一个区域变成 persistent，付一份**固定成本** $F$（每 step 的 launch、host 协议、内部同步、cache 驻留）
- 换来一份**随 batch 增长的节省** $S(b)$（消除的边界开销 + 中间 traffic 不再落 HBM）
- $F$ 不随 batch 缩小 → **区域值得融合，当且仅当 $S(b) > F$**

因为 $S(b)$ 可以涨、可以跌、可以持平，最优融合程度就成了 batch 的函数，而且不同模型方向不同。论文据此分出四类（两类观测到，两类是预测）：

```
                 大 batch 也不亏        大 batch 反而亏
小 batch 划算    stable (NH-TTS)       receding (Qwen3-TTS)
小 batch 都不划算 advancing (预测)      averse (预测, 大模型prefill)
```

实证：Qwen3-TTS 到 B32 需要 4 个 megakernel，从 **B48 开始一个都不要**（lead 从 B16 的 15.9 ms 掉到 B64 的 0.65 ms，而 $F$ 始终是 0.7–1.1 ms）。同一份模型，边界答案直接翻转。这就是你说的“不容易”的根源：它不是模型属性，是 $(model, batch, objective)$ 的属性。

## 三、三个“更激进反而更慢”的实例（这才是你关心的那半句）

**1. 寄存器压力让融合自噬。** Llama-1B 把 prefill+decode 合成一个 megakernel，比拆成两个 megakernel **更慢**——因为合并后的 entry 寄存器溢出到 local memory，planner 实测每个 prefill layer 慢约 15%（316 vs 276 μs @ B1）。注意它慢的连 TTFT 都输，不只是吞吐。

**2. 更快的内核会让 pipeline 更慢。** producer megakernel 从 80 CTA 放到 88 CTA，**单独跑快 2.2%**，但和 conventional codec 共驻时这一对**慢 30.3%**——因为 codec 少了 8 个 CTA。旁边换成 codec megakernel，同样改动就变成快 2.0%。

**3. 切割本身可以是中性的，赢的是 specialization。** NH-TTS 八个全-megakernel 切法预测值全是 37.067 ms；monolith 和双-megakernel 实测差 0.5% 以内。monolith 输给三-megakernel 的真实原因：它给所有 phase 用 512 threads，而三-megakernel 给 Stage 0 用 256 threads。

> 第 3 条直接回答了“合理的 size 是多少”：**融合的代价是失去 specialization**。所以融合粒度的自然单位不是“一个 op”也不是“整个模型”，而是——**一个 launch configuration 等价类**：在这一组 op 上，(thread-block shape, register budget, tile geometry) 是同一个且近最优。跨出这个类，融合就开始吃自己。

对你说的“要 match 合理 size”，这是最可操作的一句。

## 四、另一个容易忽略的点：目标是 max，不是 sum

它优化的 first-publication 时间是
$$
T_{\text{pub}} = \max(F_{\text{chunk}_1},\; F_{\text{producer}_h}), \qquad h = d + c_1 + l
$$
是**两条分支取 max**（chunk 就绪 vs producer 多走 outlook $l$ 步）。论文那个 illustrative 计算很说明问题：chunk 20 ms 就绪，剩余 producer/codec 串行 4/6 ms，88/44 切分下 6/8 ms —— 加上切换成本后，串行 $20+4+6+0.1=30.1$ ms，overlap $20+\max(6,8)+0.2=28.2$ ms。**重叠方案里两个分量都更慢，但赢。** 一旦你把目标函数写成“sum of stage latencies”，就会系统性地选错边界。TTFT/TTFA/ITL 都是 critical-path max 型指标，这一点在实际调优里被低估得厉害。

## 五、实用决策流程

我把论文的方法压缩成可以直接上手的形式（它只需要 conventional profile + 单 kernel benchmark，NH-TTS 只花了 4.6 GPU-min，这点很香）：

```
1. profile conventional graph
   → 每 kernel 时长、gap、占用率、node 数
2. 算三个 floor，看谁在顶
   roofline = weight_bytes / BW_peak        (decode B=1 时通常就是这个)
   boundary = n_kernel × (dispatch+drain)
   compute  = FLOPs / peak
3. 判型
   实测 ≈ 1.5× roofline  → 带宽受限，fusion 白干，去量化 / 加 batch
   实测 >> roofline 且 kernel 时长 ≲ 几 μs → 边界受限，值得融合
4. 聚类：把 op 按"最优 launch config"分桶，只在桶内融合（不要跨桶）
5. 切点优先级：执行频率变化处（once / per-step / per-chunk）> 分支汇合处 > 其他
6. 需要共驻时：两边都必须是 persistent；persistent + conventional 混搭是最坏情况
7. 扫 batch，预期会翻型；batch 波动大就备两套 engine + 运行时切换
```

第 6 条来自 Observation 2 那个 7.57× vs 1.23×：conventional codec 挨着 producer megakernel 慢 **7.57 倍**，而 codec megakernel 挨着同一个东西只慢 1.23 倍。这否定了“只把热路径 megakernel 化、剩下留给 TensorRT”这个最常见的偷懒做法——它在共驻时可能是三种方案里最差的。要么都 persistent，要么都别。

## 六、和你的“小模型”判断对一下

你的直觉方向对，但有条件：

- **小模型在该融合的理由不是“融合激进”，而是“可融合的边界多”** —— 因为单 op 工作量小、$S(b)$ 相对 $F$ 占比高、且 phase 之间速率差异大。这是结构性的，成立。
- **但小模型的更优解顺序是：batch ↑ → CUDA graph → 量化 → 融合**。融合是成本最高、最容易翻车的那个。launch bound 本质是**小 batch 现象**；能 batch 就不要靠 fusion 硬扛。
- **小模型真正该"激进"的地方可能是时间维而非算子维**：投机解码 / multi-token / step fusion / cross-request persistent kernel。这些是把 $S(b)$ 里的 $b$ 换成"每 launch 的有效工作量"，绕开了 launch config 等价类的限制，不吃 specialization 的亏。论文没覆盖这条，但它和论文的 $S(b)>F$ 框架是兼容的。

所以准确的说法可能是：**不是"小模型要更激进 fusion"，而是"小模型的融合收益/风险比更依赖配置精度"**。大模型 fused 错了亏 3%，小模型 fused 错了可能亏 30%——因为小模型本来余量就薄。这和你的结论一致：fusion 更多不等于更好，match 到合理 size 才是全部难点。

## 一、成本并非同构：逐项拆开看

| 成本项 | 机制 | 小模型相对更贵还是更便宜 |
|---|---|---|
| 几何专用化丢失 | 一个 region 只能有一个 thread-block shape、tile geometry | **更贵** |
| 寄存器压力 → occupancy 下降、spill | 融合后 per-thread live values 变多 | **更贵** |
| wave quantization | grid 填不满 132 SM，或跨波边界 | **明显更贵** |
| CTA 占用 / 共驻干扰 | persistent launch 一直持有 CTA，挤压同驻邻居 | **更便宜** |
| $F$ 固定成本 | 每 step 的 launch/protocol/sync，不随工作量缩小 | **中性 → 极小程序变成致命** |
| 搜索成本 | $n$ 组 → $2\cdot 3^{n-1}$ 个 cover | **更贵**（小模型 op 更碎，$n$ 更大） |

两个“更贵”的可以严格论证：

**wave quantization：** 若一个 region 的 grid 是 $G$ 个 CTA、单 CTA 耗时 $w$，时间约 $\lceil G/132\rceil \cdot w$。融合逼你统一 $w$，一旦让 $G$ 跨过 132 的整数倍，最坏是 **2× 惩罚**。对大 region（waves $\gg 1$），偏一波只损失 $1/\text{waves}$；对小 region，一次误判就是翻倍。**小模型的量化损失是相对量级之差，并非百分点之差。**

**occupancy：** 大模型 decode 时 HBM 已被权重流打满，occupancy 从 4 CTA/SM 掉到 2 CTA/SM 基本免费（只要并发够饱和 3.9 TB/s）。小模型在 latency-bound 区（依赖链、memory latency 没被 hide），occupancy 直接换算成时间。所以同一个 spill，大模型可以忽略，小模型会致命——论文里 Llama-1B 合并 prefill+decode 后每个 prefill layer 掉 15%（316 vs 276 μs）就是这类，而且它是**更小的那个模型**在吃亏。

反过来，“会便宜”的那项也很明确：Observation 1/2 那些吓人的数字（30.3%、7.57×）都出现在**两边都想吃满整卡**的场景。小模型小 batch 时 GPU 本来就没满，持有 CTA 不抢资源，所以共驻惩罚自然小。

> 所以严格讲你的不等式是：**收益↑（对），成本↑（也成立）**——两个方向同增，不存在“所以更激进”的传递性。

## 二、收益也要拆成两个方向相反的机制

$$S(b) = \underbrace{S_{\text{boundary}}}_{\text{每个边界常数，与工作量无关}} + \underbrace{S_{\text{traffic}}}_{\propto \text{激活字节} \propto b}$$

- $S_{\text{boundary}}$：每个被消掉的 kernel 边界省一份常数。op 越小，占比越高 → **小模型赢**。
- $S_{\text{traffic}}$：省下的中间激活 HBM 往返。但 decode 小 batch 时流量几乎全是权重：

100M 模型、hidden 768、fp16、$b=1$，单 op 中间张量 $768\times2 = 1.5$ KB，200 个 op ≈ 300 KB；而权重是 200 MB。**中间流量占 0.15%。** 纵向融合在 traffic 上几乎零收益，全部价值来自消除边界。

这条推论挺重要：**“小模型更激进”应该翻译成“小模型更该以减节点为目标”，而不是“小模型更该做深纵向融合”。** 减节点可以用水平融合（把形状相近的独立 op 拼进一个 kernel，按 block 特化分工），它几乎不吃几何专用化；而纵向融合正是吃几何专用化的那种。这两个方向对成本表的冲击完全不同。

## 三、自变量换掉：per-op 的“2 微秒定律”

有个很方便的心算锚点：2048×2048 的 bf16 矩阵从 HBM 读一遍是

$$\frac{2048^2 \times 2\ \text{B}}{3.9\ \text{TB/s}} \approx 2.1\ \mu s$$

而一个 kernel 边界（device dispatch + drain + ramp，CUDA graph 之后仍然存在）也是 **~2 µs**。

> **判据：batch=1 时，任何权重小于 2048² 的 GEMM，边界成本和权重流成本同量级甚至更高。**

2048² = 4.2M 参数。所以 0.1B 模型（hidden 768，GEMM ~0.6M 参数）单层权重流只要 0.3 µs，边界要 2.5 µs —— **8× 开销**。这不就是你说的 launch bound 的真实来源嘛。

固定 $b=1$、假设 ~2.5 µs/边界，粗算一张表（只求量级）：

| 模型 | 权重 (bf16) | 单 token 权重流 floor | 估计边界开销 | 开销/有效工作 |
|---|---|---|---|---|
| 0.1B | 0.2 GB | 51 μs | ~150×2.5 = 375 μs | **7.4×** |
| 1B | 2 GB | 513 μs | ~200×2.5 = 500 μs | **~1.0×** |
| 8B | 16 GB | 4.1 ms | ~400×2.5 = 1.0 ms | **0.24×** |
| 70B | 140 GB | 36 ms | ~600×2.5 = 1.5 ms | **0.04×** |

**同样是 batch=1，激进程度从 7.4× 单调掉到 0.04×。你的直觉在这张表上是被数据支持的。** 这就是论文为什么在 B1 对三个模型全都上 megakernel。

但注意自变量：**"模型大小"只是"per-op work"的一个粗糙代理，它们不等价。** 两个反例：

1. **MoE 的窄专家**。70B 的总参数很大，但单个 expert（比如 512×512）在 $b=1$ 时权重只有 0.5 MB → 0.13 µs，边界 2.5 µs → **20× 开销**。一个“大模型”的 decode 因为 fine-grained MoE 反而是边界受限的。这时模型大小完全误导。
2. **同一模型的不同 phase**。论文自己的表：Llama-1B 对 TTFT 是 megakernel-stable（prefill 单次大工作量），对 ITL 是 receding（decode 每步小工作量）。**模型没变，phase 变了，结论翻转。**

batch 的交叉点也能直接算出来（hidden $d=k=2048$，有效算力 $8\times10^{14}$）：

$$t_{\text{compute}} = \frac{2b d k}{P} = 10.5\,\text{ns}\cdot b \quad\Rightarrow\quad b^\* \approx \frac{2.5\,\mu s}{10.5\,\text{ns}} \approx 240$$

也就是说，**小模型要靠 batching 逃出边界受限，大概得 B≈200–400**。对吞吐型 serving 可能可以；对 TTFT/流式这类延迟敏感的场景，batch 被 SLO 死锁在小数 —— 于是**小模型在你的场景里会永久坐在边界受限区**。这个论证让结论反而更硬了。

## 四、极小程序会质变（我认为这是你漏掉的那点）

论文给的 megakernel 固定成本 $F \approx 0.7$–$1.1$ ms/step（含 host protocol、内部同步）。对 NH-TTS，B1 的 TTFA 是 27.5 ms，$F$ 占 4%，无所谓。但对我表里那个 0.1B 模型：

$$F = 1\ \text{ms} \quad\text{vs}\quad \text{整个 decode step} = 51\ \mu s$$

**$F$ 是整个 step 的 20 倍。** 这时候你根本不该谈“切几个 region megakernel”——切几个都亏。正确的解只有一种：**把整个 loop 搬进 kernel 里**，一个 kernel 连续跑 N 个 step / N 个 token，$F$ 摊到 N 步上。

也就是说，对极小模型而言，应当彻底改变执行模式，而不是在同一个旋钮上往“更激进”拧：

$$\text{区域级 megakernel（切 1–4 段）} \;\longrightarrow\; \text{persistent loop kernel（跨 step）+ 投机/多头解码}$$

机制上正好对着 $S(b)>F$ 的两边：你不能让 $F$ 变小（它是设计的常数成本），就只能**放大每次 launch 覆盖的有效工作**——而这在算子维已经寸步难行（每层只有 0.3 µs 的活），只剩时间维。所以小模型真正的激进方向是 **fusion across time**，不是 fusion across ops。这也解释了为什么这类模型上 speculative / multi-token / lookahead 的收益比 megakernel 大得多：它同时在放大 $S$ 和摊薄 $F$。

**如果要给你的推理修一个版本，我会这么写：**

$$\text{激进程度} \;\propto\; \frac{\text{work per launch}}{c + F_{\text{amort}}} \quad\text{而不是}\quad f(\text{model size})$$

其中 work per launch $\approx$ max(每 op 权重字节 / BW, $2b \cdot d \cdot k / P$)。分子小、分母是常数 2 µs 量级 → 该融合。**于是真正的排序轴是 $(\text{命中 op 的形状}, \text{batch}, \text{phase})$，模型大小只是它的一个投影。** 你的直觉在“小模型 + 小 batch + 延迟敏感”这个角落里非常准；一旦移出这个角落（大 batch 吞吐型 serving、MoE 窄专家、极小程序撞 $F$ 天花板），要么失效，要么质变成另一种优化。

它那套四分类里，**advancing（小 batch 不划算、大 batch 划算）这一类是预测的、没观测到**。三个模型 × 五个 batch，全都是 stable 或 receding，也就是**“batch 变大 → 需要更少 megakernel”是单向的**。它的验证池最小也只有 1B、最小 batch 就是 1，所以“模型更小 → 更该激进”这件事它没有、也无法证伪 —— 它只证明了“在 B1，所有测试模型都上 megakernel”。你那个命题目前是**在没有反例的区间里成立的**，不是被验证的。

另外一个没被它解决的问题：它假设你能拿到 source-declared contracts（几何、存储、编译 entry 成员、同步）。这个工程量不小，对你自己搭的模型可控，对用 TensorRT/vLLM 的黑盒就卡住了 —— 这大概也是为什么你的经验里“match 到合理 size 不容易”，很多时候不是算不出来，是**拿不到算所需的输入**。
