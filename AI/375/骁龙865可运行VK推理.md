### 🤖 Assistant

# ONNX Runtime Vulkan 在骁龙865 GPU 上运行

## 简要结论

**可以运行**，但需要注意构建配置、算子支持和性能调优。骁龙865 搭载的是 Adreno 650 GPU，原生支持 Vulkan 1.1+，满足 ONNX Runtime `VulkanExecutionProvider` 的运行条件。

---

## 详细分析

<details>
<summary>硬件与驱动支持</summary>

- 骁龙865 的 GPU 为 **Adreno 650**，支持 Vulkan 1.1。
- Android 系统从 9.0 开始逐步内置 Vulkan 驱动，骁龙865 设备出厂驱动版本普遍可用。
- 可通过 `vulkaninfo` 命令或 `VkPhysicalDeviceProperties` 查询具体驱动版本和扩展支持。

</details>

<details>
<summary>ONNX Runtime 构建方式</summary>

官方预编译的 Android AAR 包默认不包含 Vulkan EP，需要**自行从源码编译**：

```bash
git clone --recursive https://github.com/microsoft/onnxruntime.git
cd onnxruntime

# Android + Vulkan EP 构建示例
./build.sh --config Release \
  --build_shared_lib \
  --android \
  --android_abi arm64-v8a \
  --android_api 29 \
  --android_sdk_path /path/to/android-sdk \
  --android_ndk_path /path/to/android-ndk \
  --use_vulkan \
  --cmake_extra_defines onnxruntime_USE_VULKAN=ON
```

关键 CMake 选项：
- `onnxruntime_USE_VULKAN=ON`：启用 Vulkan EP
- `onnxruntime_DISABLE_VULKAN_PROVIDERS=OFF`：确保不禁用
- 需要安装 Android NDK r21+ 和 Vulkan headers

</details>

<details>
<summary>API 调用方式</summary>

```cpp
#include <onnxruntime_cxx_api.h>

Ort::Env env(ORT_LOGGING_LEVEL_WARNING, "test");
Ort::SessionOptions session_options;

// 启用 Vulkan EP
OrtSessionOptionsAppendExecutionProvider_Vulkan(session_options, 0);

// 设备 ID 0 通常对应第一个支持 Vulkan 的物理设备
Ort::Session session(env, model_path, session_options);
```

Java/Kotlin 调用示例：
```java
OrtEnvironment env = OrtEnvironment.getEnvironment();
OrtSession.SessionOptions options = new OrtSession.SessionOptions();
options.addVulkan();
OrtSession session = env.createSession(modelBytes, options);
```

</details>

<details>
<summary>注意事项与限制</summary>

| 事项 | 说明 |
|------|------|
| 算子覆盖 | Vulkan EP 支持的算子远少于 CPU/NNAPI，需检查模型是否覆盖；可用 `GetCapability` 查看可被加速的节点 |
| 精度 | 主要支持 FP32 与 FP16，部分算子仅 FP32 |
| 性能 | 小模型在 Adreno 上 Vulkan EP 可能不如 NNAPI EP；大卷积/GEMM 类算子收益较明显 |
| 驱动 Bug | 部分 Adreno 驱动存在 SPV 不稳定问题，建议测试多台机器 |
| EP 优先级 | 若同时注册 NNAPI 与 Vulkan，注意顺序，避免节点全被 NNAPI 接管 |

</details>

<details>
<summary>性能调优建议</summary>

1. **FP16 推理**：在 SessionOptions 中启用 `enable_fp16`，Adreno 650 对 FP16 吞吐显著高于 FP32。
2. **内存布局**：Vulkan EP 倾向 NHWC，模型转换时建议固定为 NHWC。
3. **输入尺寸对齐**：尽量让通道数和空间维度对齐到 $4$ 或 $8$，利于 SIMD 和工作组划分。
4. **Group Conv 优化**：深度卷积在 Adreno 上有专用路径，效率较高。
5. **替代方案对比**：若 Vulkan EP 不达预期，可对比：
   - `QnnExecutionProvider`（高通官方，性能通常最佳）
   - `NnapiExecutionProvider`
   - `CoreML/ DirectML`（其他平台）

</details>

---

## 推荐决策路径

```
模型转换 → 检查算子覆盖 → 编译带 Vulkan EP 的 ORT
   → 小批量基准测试 → 与 QNN/NNAPI EP 对比 → 选择最优 EP
```

骁龙865 上建议优先评估 **QNN EP**（高通 AI Engine Direct），其针对 Adreno/HVX/HTP 有深度优化；Vulkan EP 适合需要跨平台一致性和开放标准驱动的场景。

### 🤖 Assistant

# 在骁龙865上推理 <4B 多模态 MoE LLM 的可行性分析

## 简要结论

**理论上勉强可行，但实际体验会非常差**，不推荐直接使用 ONNX Runtime Vulkan EP 来做这件事。存在多个严重的工程和性能障碍。

---

## 核心挑战分析

### 1. 内存占用瓶颈

<details>
<summary>内存计算详情</summary>

| 精度 | 4B参数占用 | + KV Cache (2K seq) | + 多模态编码器 | 总计需求 |
|------|-----------|---------------------|---------------|---------|
| FP32 | ~16 GB | ~1 GB | ~0.5 GB | **>17 GB** ❌ |
| FP16 | ~8 GB | ~0.5 GB | ~0.3 GB | **~9 GB** ❌ |
| INT8 | ~4 GB | ~0.3 GB | ~0.2 GB | **~4.5 GB** ⚠️ |
| INT4 | ~2 GB | ~0.2 GB | ~0.1 GB | **~2.3 GB** ✅ |

骁龙865 典型设备内存为 8-12 GB，系统可用通常只有 4-6 GB。

**关键点**：MoE 架构虽然每次只激活部分专家，但**所有专家参数必须同时驻留内存**，无法按需加载（否则 I/O 延迟不可接受）。

</details>

### 2. ONNX Runtime Vulkan EP 的算子支持问题

<details>
<summary>LLM/MoE 相关算子覆盖情况</summary>

```
❌ MoE 路由机制：top-k selection, gating network
❌ 动态形状：自回归生成的动态 seq_len
⚠️  Attention：标准 attention 可支持，但 FlashAttention 变体不支持
⚠️  KV Cache：需手动管理，Vulkan EP 无内置优化
⚠️  RoPE/ALiBi：部分实现支持，但效率存疑
❌ 多模态融合：image-text cross attention 通常需要自定义算子
```

Vulkan EP 目前主要针对计算机视觉模型优化，对 LLM 的支持非常有限。

</details>

### 3. 推理速度估算

<details>
<summary>性能推算</summary>

骁龙865 Adreno 650 理论算力：
- FP16: ~1.3 TFLOPS
- INT8: ~2.6 TOPS

对于 4B 参数模型（假设 MoE 每次激活 1B 参数）：

```
单 token 生成所需计算量 ≈ 2 × 激活参数量 = 2 × 10^9 FLOPS

理论极限：1.3 × 10^12 / 2 × 10^9 = 650 tokens/s

实际考虑：
- 内存带宽瓶颈：44 GB/s / (1GB 激活参数 FP16) = 44 tokens/s
- 算子调度开销：×0.3
- MoE 路由开销：×0.7
- 实际预估：~9-15 tokens/s (FP16)
- INT4 量化后：~20-30 tokens/s
```

但这是**乐观估计**，Vulkan EP 的实际开销可能让速度再打 3-5 折。

</details>

### 4. 多模态的特殊挑战

<details>
<summary>多模态推理流程问题</summary>

```
图像输入 → ViT/Swin 编码 → 投影层 → 与文本 embedding 融合 → LLM 推理

问题：
1. ViT 通常用大分辨率输入，显存占用大
2. 图像 token 与文本 token 的 cross-attention 需要自定义实现
3. ONNX 导出时多模态模型的动态控制流容易出问题
4. 各模态的预处理 Pipeline 在移动端需要单独实现
```

</details>

## 更现实的方案对比

| 方案 | 可行性 | 推理速度 | 实现难度 | 推荐 |
|------|--------|---------|---------|------|
| ORT + Vulkan EP | ⚠️ 勉强 | 3-8 t/s | 极高 | ❌ |
| ORT + NNAPI EP | ⚠️ 勉强 | 5-10 t/s | 高 | ❌ |
| ORT + QNN EP | ✅ 较好 | 15-25 t/s | 中 | ⭐ |
| MLC-LLM | ✅ 好 | 20-40 t/s | 中 | ⭐⭐⭐ |
| llama.cpp + Vulkan | ✅ 好 | 15-30 t/s | 低 | ⭐⭐⭐ |
| MediaPipe LLM Inference | ✅ 好 | 优化后较高 | 低 | ⭐⭐ |

## 推荐路径

### 如果你的目标是「在手机上跑多模态 MoE LLM」

1. **首选 llama.cpp**
   - 原生支持 Vulkan 后端
   - 内置 MoE 支持（Mixtral、DeepSeek-MoE 等）
   - GGUF 量化（Q4_K_M 等）可将 4B 模型压到 ~2.5GB
   - 社区有 LLaVA 等多模态实现

2. **次选 MLC-LLM**
   - 基于 TVM/TIR 优化，Android 支持好
   - 支持 INT4 量化和 Vulkan 后端
   - 已有 LLaVA、Phi-3-vision 等多模态模型支持

3. **如果必须用 ONNX Runtime**
   - 使用 QNN Execution Provider 而非 Vulkan
   - 考虑将模型拆分为 Vision Encoder + LLM 两部分分别部署
   - 使用 ONNX Runtime 的 INT4 量化工具

### 如果你的目标是「学习/研究 ORT Vulkan EP」

建议从简单的模型开始：
```
ResNet50 → MobileBERT → 小型 GPT (<500M) → 逐步增加复杂度
```

---

## 结论

虽然 ONNX Runtime Vulkan EP 理论上可以在骁龙865 上运行 <4B 的多模态 MoE LLM，但：
- 内存勉强够用（需 INT4 量化）
- 算子支持不全（MoE 路由、动态形状）
- 性能无法保证（预计 <10 tokens/s）

**建议转向 llama.cpp 或 MLC-LLM**，它们对移动端 LLM 推理有更成熟的工程实现和优化。
