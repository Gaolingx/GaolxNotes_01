# 结论：**结构失衡 —— update 侧富余，rollout 侧大概率不够**

对 30B-A3B（3B 激活）来说，**48×H200 做 policy update 是充足的、甚至偏富余**；**128×H20 做 long-horizon agentic rollout 才是瓶颈**。按默认配置跑，训练卡会长期空转（我估算利用率只有 **20%–30%**），实际吞吐由 rollout 决定。

---

## 1. 硬件底座对比

| 项目 | H200 | H20 | H20 / H200 |
|---|---|---|---|
| 显存 | 141 GB HBM3e | 96 GB HBM3 | ≈ 0.68 |
| 显存带宽 | 4.8 TB/s | 4.0 TB/s | ≈ 0.83 |
| BF16 dense | ≈ 990 TFLOPS | ≈ 148 TFLOPS | **≈ 0.15** |
| FP8 dense | ≈ 1980 TFLOPS | ≈ 296 TFLOPS | ≈ 0.15 |

关键点：H20 是**算力残废、带宽尚可**的卡。这决定了它适合 **bandwidth-bound 的长上下文 decode**，但在 **compute-bound 的 prefill 和训练** 上极弱。

$$\text{峰值算力比 } \frac{128\times148}{48\times990}=\frac{18{,}944}{47{,}472}\approx 0.40$$

也就是说，**rollout 池的总峰值算力只有 update 池的 40%**，而这还没算 MFU 差异。

---

## 2. 为什么必然 rollout-bound

### 2.1 训练侧吞吐（48×H200）
30B-A3B 每 token 训练 FLOPs（含 fwd+bwd，粗略）：

$$2\times N_{act}\times 3 \approx 18\ \text{GFLOP/token（短上下文）}$$

长上下文再加 attention 的 $O(L)$ 项，32k 时约到 $30\text{–}40$ GFLOP/token。按 25%–35% MFU：

$$\frac{48\times990\times10^{12}\times0.3}{2.4\times10^{10}}\approx 5\times10^{5}\ \text{tokens/s}$$

即便悲观到 15% MFU，也还有 $\sim 3\times10^{5}$ tokens/s。

### 2.2 Rollout 侧吞吐（128×H20）
Decode 是**显存带宽 bound**，每生成 1 token 要读一遍激活权重 + 整批 KV：

$$\text{bytes/token} \approx \frac{6\,\text{GB}}{B} + L\times K_{token}$$

以典型 GQA（$K_{token}\approx 96$ KB/token，4 KV heads）为例，聚合带宽 $128\times4.0 = 512$ TB/s：

| 上下文长度 $L$ | KV/序列 | 估算 rollout 吞吐 |
|---|---|---|
| 8k | 0.75 GB | ~300k tok/s |
| 32k | 3.1 GB | ~120k–150k tok/s |
| 128k | 12.6 GB | ~35k–45k tok/s |

**rollout 在长上下文被 KV cache 读取直接压死**，而 agentic long-horizon 恰恰动辄 32k–128k。

<summary>展开：一个具体 step 的配比演算</summary>

假设每步 DAPO：512 prompt × 8 rollout = 4096 条轨迹，平均模型生成 8k token：

- rollout 总量 $= 4096\times8000\approx 3.3\times10^{7}$ tokens
- rollout 耗时 $=3.3\times10^{7}/1.2\times10^{5}\approx 275$ s
- update 耗时 $=3.3\times10^{7}/4\times10^{5}\approx 82$ s

$$\text{训练卡利用率}\approx \frac{82}{275}\approx 30\%$$

若要把两侧拉平，48 张里其实只需要 **~12 张** 做 update，其余 36 张相当于在等。

## 3. 长上下文 agentic 的放大项（H20 尤其吃亏）

1. **Prefill 占比高且算力密集**：每轮 tool call 都要把新增 observation 重新 prefill，H20 的 prefill 算力只有 H200 的 15%，这块极慢。
2. **多轮串行 + 环境延迟**：turn 之间必须串行等待工具返回，GPU 会间断闲置，除非高并发 oversubscribe，而 96GB 显存限制了并发度。
3. **KV cache 显存墙**：128k 上下文下单条序列 KV 可达 10 GB+，96GB 卡上并发只有个位数，进一步压低吞吐。
4. **权重同步**：H200 训练 → H20 推理的**异构跨池同步**。30B BF16 约 60GB 权重要走网络广播，每步一次。若两池不在同一 RDMA 域，这一步可能直接成为隐藏瓶颈。

---

## 4. DAPO 特有的注意点

- **步内 batch 极大**（DAPO 靠大 batch + dynamic sampling + clip-higher），单步 rollout token 量本就远超 PPO 类。
- **多 mini-epoch（$\mu>1$）** 虽然提高了 update 侧样本复用，但**不改变 rollout 是数据来源**这一事实，反而进一步说明 update 算力过剩。
- 无 KL、无 ref model，省显存但不省 rollout。
- **dynamic sampling 若筛选不当**（大量全对/全错样本被丢弃），会白白烧掉 rollout token——在 rollout 紧张时这尤其致命。

---

## 5. 到底“够不够”：分场景

| 目标 | 判断 |
|---|---|
| 研究级实验、8k–16k 上下文、工具轮数 ≤30、可接受 1–2 周出结果 | **勉强够**，需精细调优 |
| 32k+ 上下文、50–200 轮 tool call、想要高利用率 | **rollout 明显不足**，训练卡闲置严重 |
| 生产/前沿级 long-horizon（100k+ 上下文） | **不够**，需要显著加大 rollout 池或改架构 |

---

## 6. 调优 / 再平衡清单

**优先做（低成本高收益）**
- Rollout 用 **FP8 权重 + FP8 KV cache**：H20 FP8 ≈ 2× BF16，且 KV 减半 → 长上下文吞吐近乎翻倍。
- **Prefix caching**：system prompt、工具 schema、历史前缀复用，agentic 场景收益巨大。
- **上下文压缩/摘要**：主动截断、observation 摘要，把 $L$ 从 128k 压到 32k 级别，吞吐直接 ×4。
- **异步 / partial rollout**（如 AReaL 类）：让 48 张 H200 永远有数据可训，把 rollout 变成唯一伸缩旋钮。

**结构性调整**
- 把部分 H200 划给 rollout 或直接 **colocate**（同一批卡推理/训练交替）以消除空转——但异构卡无法共享池。
- 若要扩，**优先扩 rollout 卡数**（+64 H20 的边际收益远大于 +16 H200 给 update）。
- 保证两池在**同一高速 RDMA 域**，否则权重同步会吞噬收益。

**Harness 层**
- 控制 group size，避免 dynamic sampling 浪费；工具调用并发化，让 GPU 不被环境延迟饿死。

## 一句话总结

**update 侧（48×H200）对 3B 激活的 30B-A3B 绰绰有余；瓶颈在 rollout（128×H20），且 H20 的弱算力 + 长上下文 KV 读取让你大概率训练卡利用率仅 ~30%。** 默认配置能跑但要靠 FP8 rollout、prefix cache、上下文压缩和异步 rollout 才能把利用率拉到可接受水平；若要真正跑 long-horizon（32k+）并保持高效，**应该把算力向 rollout 倾斜，或加卡补 rollout**。
