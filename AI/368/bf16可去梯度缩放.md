# bf16可去梯度缩放

### 🧑‍💻 User

从fp16amp迁移到bf16amp能否把gradscaler去掉，提高训练速度？

---

### 🤖 Assistant

# 结论先行

**可以，而且应该移除。** 切换到 BF16 后 `GradScaler` 就完全不需要了，PyTorch 官方文档也明确 BF16 场景只使用 `torch.autocast`（CPU/GPU 皆如此）。但要注意一个关键点：**"训练变快"主要不是来自移除 GradScaler，而是来自硬件对 BF16 的支持程度**。移除 scaler 本身节省的开销很小，真正的加速取决于你的 GPU 型号。

---

## 1. 为什么 BF16 不需要 GradScaler

核心是**动态范围**（指数位）的差异：

| 类型 | 指数位 | 尾数位（含隐藏位） | 最小正规数 | 最大表示 |
|---|---|---|---|---|
| FP16 | 5 bit | 11 bit | $\approx 6.1 \times 10^{-5}$ | $65504$ |
| BF16 | 8 bit | 8 bit | $\approx 1.2 \times 10^{-38}$ | $\approx 3.4 \times 10^{38}$ |
| FP32 | 8 bit | 24 bit | $\approx 1.2 \times 10^{-38}$ | $\approx 3.4 \times 10^{38}$ |

- **FP16** 指数只有 5 位，小梯度会下溢成 0（underflow），大值会溢出成 inf。所以必须用 loss scaling 把梯度乘一个大系数（默认 $65536$）再反传，`optimizer.step()` 前再 `unscale_` 回去，并做 inf/nan 检查。
- **BF16 的指数位和 FP32 完全一样**（8 位），动态范围与 FP32 相同，不存在下溢/上溢问题，因此 scaling 机制失去了存在意义。官方文档原话：

> *"automatic mixed precision training with datatype of torch.float16 uses torch.autocast and torch.amp.GradScaler together… As shown in the CPU example section… with datatype of torch.bfloat16 only uses torch.autocast."*

注意 PyTorch 文档还有一个反例提醒：**很多 BF16 预训练模型在 FP16 数值范围内反而会溢出**（因为参数分布超出 65504），这也是 GradScaler 在 FP16 下可能把 scale 降到 1 以下的原因。

## 2. "提速"到底来自哪里

### 2.1 移除 GradScaler 本身：收益很小（约 1–3% 甚至可忽略）

Scaler 的实际开销只是：
- 反传前乘一个 scale 系数（逐元素乘，几乎免费）
- `unscale_`：一次逐元素除法 + 一次 inf/nan 归约检查
- 偶尔的 `update()`（每 2000 步一次）

这些和 forward/backward 的算力开销相比微不足道。**如果你期望"删掉 scaler 就明显变快"，会失望。**

### 2.2 真正的速度差异：BF16 vs FP16 的硬件吞吐

这才是决定性的因素，取决于 GPU 架构：

| GPU 架构 | BF16 Tensor Core | 结论 |
|---|---|---|
| Volta / Turing（V100、T4、RTX 20 系） | **不支持**（软件模拟，慢） | ❌ 不要切 BF16 |
| Ampere（A100、A30、RTX 30 系） | 与 FP16 **同速**（A100 均为 312 TFLOPS） | ✅ 可切，速度持平 |
| Hopper（H100、H200） | **部分算子 BF16 是 FP16 的 2 倍**（989 TFLOPS） | ✅ 可切，有额外收益 |
| Ada / Blackwell（RTX 40/50 系） | 与 FP16 同速或更高 | ✅ 可切 |

所以在 Ampere 及更新的卡上，切 BF16 **不会比 FP16 慢**，在 H100 等卡上还可能更快；而在 RTX 30 系这类"同速"卡上，切 BF16 的主要收益是**数值稳定性 + 代码简洁**，而不是吞吐提升。

## 3. 精度的代价（必须注意）

BF16 用"更大的动态范围"换来了**更低的尾数精度**（8 位 vs FP16 的 11 位有效位，即相对精度从 $2^{-11}$ 降到 $2^{-8}$ 左右）：

- 前向激活、权重更新的**相对精度下降约 8 倍**；
- 对 loss landscape 平滑、噪声大的训练（如 RL、部分生成模型）可能出现收敛变差或需要调 LR；
- 实践中大多数 LLM/CNN 用 BF16 训练效果良好（这也是大模型默认做法），但如果你的任务对精度敏感，建议用相同 seed 跑少量 step 对比 loss 曲线；
- **主权重和优化器状态仍保持 FP32**（autocast 只影响计算精度，不影响参数存储），这一点和 FP16 AMP 一致。

## 4. 迁移代码示例

```python
# ============ 迁移前（FP16） ============
scaler = torch.cuda.amp.GradScaler()          # 旧 API，已弃用
for x, y in loader:
    optimizer.zero_grad()
    with torch.autocast(device_type="cuda"):   # 默认 dtype=torch.float16
        loss = loss_fn(model(x), y)
    scaler.scale(loss).backward()
    scaler.unscale_(optimizer)                 # 若要做梯度裁剪，必须先 unscale
    torch.nn.utils.clip_grad_norm_(model.parameters(), max_norm)
    scaler.step(optimizer)                     # 内部会跳过 inf/nan 的 step
    scaler.update()

# ============ 迁移后（BF16） ============
for x, y in loader:
    optimizer.zero_grad()
    with torch.autocast(device_type="cuda", dtype=torch.bfloat16):
        loss = loss_fn(model(x), y)
    loss.backward()                            # 直接反传，无需 scale
    torch.nn.utils.clip_grad_norm_(model.parameters(), max_norm)  # 直接裁剪
    optimizer.step()
```

可选追加优化：
```python
torch.set_float32_matmul_precision("high")  # 允许 TF32/bf16 加速 FP32 矩阵乘
model = torch.compile(model)                # 编译后通常再快 10–30%
```

## 5. 注意事项汇总

1. **API 已弃用**：`torch.cuda.amp.autocast` / `torch.cuda.amp.GradScaler` 均弃用，统一用 `torch.amp.autocast("cuda", ...)` 和 `torch.amp.GradScaler("cuda", ...)`。
2. **硬件检查**：切换前用 `torch.cuda.is_bf16_supported()` 确认；Volta/Turing 老卡切 BF16 反而变慢。
3. **配合 `torch.compile`**：如果 forward 在 autocast 内、backward 在 autocast 外，需设置 `torch._functorch.config.backward_pass_autocast = "off"`，否则编译语义可能与预期不一致（官方文档明确提示）。
4. **梯度累积**：BF16 下梯度累积可以照常做，但累积到 FP32 比累到 BF16 更稳（autocast 只包 forward 时，`.grad` 默认就是 FP32）。
5. **不要残留 scaler**：如果保留 `scaler.step()` 却不 `scale(loss)`，会静默出错或白白多一次 unscale 开销；彻底删除即可。

## 总结

| 维度 | FP16 + GradScaler | BF16（无 scaler） |
|---|---|---|
| 是否需要 GradScaler | 必须 | **不需要** |
| 动态范围 | 窄（易下溢/上溢） | 与 FP32 相同 |
| 相对精度 | 高（11 bit） | 低（8 bit） |
| Ampere+ 吞吐 | 基准 | 同速或更快（H100 翻倍） |
| 代码复杂度 | 高（scale/unscale/clip 顺序敏感） | 低 |
| 主要风险 | inf/nan 需调参 | 精度敏感任务可能需调 LR |

**结论**：切 BF16 + 移除 GradScaler 是正确的工程决策——代码更简洁、数值更稳、几乎不可能更慢（Ampere+）；但"提速"请优先归因于**硬件 BF16 吞吐**，而不是删掉 scaler 本身。若在 RTX 30 系且吞吐没变，别奇怪——它的收益本来就在稳定性和简洁性上。
