# How to Prepare a Computer-Use Agent Dataset

A "computer-use agent" dataset consists of **trajectories**: sequences of `(observation → action)` pairs that let an agent learn to operate a GUI (browser, desktop, mobile) from screenshots. Below is a practical end-to-end guide.

---

## 1. Understand the Core Data Unit

Each trajectory typically contains:

| Component | Description | Example |
|-----------|-------------|---------|
| `task` / `instruction` | Natural-language goal | "Book a flight from NYC to London for next Tuesday" |
| `observations` | Screenshots or accessibility trees at each step | PNG frames, DOM snapshots |
| `actions` | What was done at each step | `click(x=412, y=238)`, `type("London")`, `scroll(down)` |
| `rewards` / `verifiers` | Success signal per trajectory | Task-completion checker, LLM judge |
| `metadata` | Environment, user agent, resolution, timestamps | OS, browser version, 1280×800 |

**Action space** is the most important design decision. Typical primitives:

```
mouse:    click, double_click, right_click, move, drag
keyboard: type(text), key_combo("Ctrl+C"), press(Enter)
scroll:   scroll(up|down, amount)
system:   wait, screenshot, open_app, close, submit
```

---

## 2. Data Collection Methods (with trade-offs)

| Method | How | Pros | Cons |
|--------|-----|------|------|
| **Human demonstrations** | Crowdworkers/experts perform tasks while recording | High quality, realistic | Expensive, slow, noisy |
| **Teleoperation** | Remote humans operate VMs/containers | Controlled, scalable to remote workers | Still human cost |
| **Synthetic generation** | Scripted agents (Playwright, Selenium) + templates | Cheap, massive scale | Less diverse, biased toward scripts |
| **Self-supervised / RL exploration** | Agent explores, verifier scores outcomes | No human labels needed | Needs robust reward signals |
| **Model-in-the-loop** | Existing agent (e.g., a frontier model) generates trajectories, filtered by verifier | Scalable, decent quality | Inherits model biases |

> **Most practical today:** start with human/synthetic demos, then scale with model-in-the-loop + verifier filtering.

---

## 3. Recommended Schema (JSONL)

One trajectory per line is the de-facto standard:

```jsonl
{"id": "task_001", "instruction": "Find the price of iPhone 15 on amazon.com",
 "environment": {"type": "browser", "resolution": [1280, 800], "url": "https://amazon.com"},
 "steps": [
   {"step": 0, "screenshot": "s3://.../t001/f0.png", "action": {"type": "type", "text": "iPhone 15"}, "timestamp": 0.0},
   {"step": 1, "screenshot": "s3://.../t001/f1.png", "action": {"type": "click", "x": 512, "y": 340}, "timestamp": 1.2}
 ],
 "success": true, "verifier": "llm_judge", "score": 0.95}
```

Store screenshots **out-of-band** (S3/GCS/blob) and keep only paths in the JSONL to keep files manageable.

## 4. Step-by-Step Pipeline

### Step 1 — Define tasks & environment
- Curate tasks from real user needs, organized by category (navigation, form-filling, transactions, data entry).
- Sandbox everything: Docker containers, VMs, or headless browsers with **isolated profiles**.
- Pin a **stable resolution and browser/OS** so observations are consistent.

### Step 2 — Record trajectories
```python
# Minimal browser recording loop (conceptual)
from playwright.sync_api import sync_playwright

with sync_playwright() as p:
    browser = p.chromium.launch()
    page = browser.new_page(viewport={"width": 1280, "height": 800})
    page.goto(start_url)
    steps = []
    for action in human_or_agent_actions:   # from teleop, script, or model
        steps.append({
            "screenshot": save_frame(page.screenshot()),
            "action": action
        })
        execute(page, action)               # apply the action
```

### Step 3 — Add a verifier (success signal)
- **Rule-based:** check DOM state, final URL, form values, or API results.
- **LLM judge:** prompt a model with task + final screenshot(s) → pass/fail + score.
- Combine both: rules for determinism, LLM for fuzzy/visual goals.

### Step 4 — Clean & filter
- Drop trajectories that are too short (< 3 steps) or extremely long (> 100 steps).
- Remove **invalid actions** (out-of-bounds coordinates, empty text).
- Deduplicate near-identical trajectories (e.g., hash the instruction + action sequence).
- **Privacy scrub:** blur/redact emails, names, credit cards, personal screenshots.

### Step 5 — Balance & split
- Balance across action types (avoid "click-only" datasets) and task categories.
- Split by **task**, not by step, to prevent leakage (a task's steps must stay together).
- Build `train / val / test` with a held-out set of unseen tasks for true generalization.

---

## 5. Key Pitfalls to Avoid

1. **Coordinate fragility** — absolute `(x,y)` overfits to resolution/layout. Consider relative coordinates or accessibility-tree grounding (element IDs).
2. **Task leakage** — splitting at the step level lets the model memorize tasks. Split at the task level.
3. **Action imbalance** — most raw data is clicks; ensure typing, scrolling, and keyboard combos are represented.
4. **No success signal** — trajectories without verifier scores are nearly useless for RL and hard to filter for SFT.
5. **Non-deterministic pages** — A/B tests, ads, and timers break reproducibility. Freeze the environment or record with a deterministic proxy.

## 6. Existing Datasets & Benchmarks to Learn From

| Dataset / Benchmark | Domain | Notes |
|---------------------|--------|-------|
| **WebArena** | Web | Realistic self-hosted sites with rule-based verifiers |
| **Mind2Web** | Web | Large-scale web task dataset with DOM grounding |
| **OSWorld** | Desktop | Real OS + apps (Ubuntu/Windows/macOS) with execution-based eval |
| **WindowsAgentArena** | Windows desktop | 150+ real Windows tasks |
| **AgentBench** | Multi-env | OS, DB, web, games |
| **ScreenSpot / ScreenSpot-Pro** | GUI grounding | Tests where to click/type on screenshots |
| **AndroidControl / AITW** | Mobile | Android app control trajectories |

Studying their **schemas, verifiers, and sandboxing** will save you months of design mistakes.

## 7. Minimal Tech Stack

| Layer | Tools |
|-------|-------|
| Environment | Docker, VMs, Playwright/Selenium (web), PyAutoGUI/pywinauto (desktop) |
| Recording | Playwright tracing, `ffmpeg` screen capture, custom teleop harness |
| Storage | S3/GCS for frames, Parquet/JSONL for trajectories |
| Labeling | Argilla, Label Studio, or custom queue |
| Verifier | Deterministic rules + LLM-as-judge (e.g., GPT-4o/Claude) |
| Processing | Pandas/DuckDB for filtering, `img2dataset`-style pipelines for frames |

## TL;DR

> Collect **task → (screenshot, action) trajectories** with a **verifier success signal**, in a sandboxed, fixed-resolution environment, stored as **JSONL + external screenshots**. Filter for quality, balance the action distribution, and split by **task** (not step) to avoid leakage. Start small with human/synthetic demos, then scale with model-in-the-loop + verifier filtering.
