# How to Prepare a Dataset for a Computer-Use Agent

A computer-use agent (CUA) looks at a screen, decides on an action (click, type, scroll, and so on), carries it out, and repeats until the task is finished. Your dataset needs to teach this loop. Here is how to prepare one, step by step.

---

## 1. Define the interface first

Before you collect anything, decide what the model will see (observation space) and what it can do (action space). Every later step depends on these choices.

| Decision | Common options |
|---|---|
| **Observation** | Screenshot only (pure vision), accessibility tree / DOM, or both |
| **Resolution** | Fixed (e.g., 1280×720), or native with resizing |
| **Coordinates** | Absolute pixels, normalized `[0,1]`, or `[0,1000]` (used by Qwen-VL and UI-TARS) |
| **Action space** | `click(x,y)`, `double_click`, `right_click`, `drag(x1,y1,x2,y2)`, `type(text)`, `hotkey(keys)`, `scroll(dx,dy)`, `wait`, `done/fail` |
| **Platform** | Web, desktop (Windows/macOS/Linux), mobile (Android) |

**Tip:** Copy the action format of the base model you plan to fine-tune, such as Qwen2.5-VL, UI-TARS or OpenCUA. Fighting its pretraining wastes data.

---

## 2. Choose your data types

A strong CUA dataset usually mixes three layers:

1. **Grounding data:** single-step pairs of screenshot + instruction → coordinate. Example: "Click the Save button" → `(512, 88)`. Teaches the model to perceive the UI. This is cheap and comes in large volumes.
2. **Trajectory data:** multi-step task demonstrations. Example: "Book a flight from NYC to LA on May 3" → 15 steps. Teaches planning.
3. **Reasoning data:** trajectories annotated with the reasoning behind each step (a "thought" before each action). This greatly improves generalization.

---

## 3. Get the data

### A. Start from existing public datasets
| Dataset | Type | Platform |
|---|---|---|
| **Mind2Web / Multimodal-Mind2Web** | Trajectories | Web |
| **AITW, AndroidControl, GUI-Odyssey, AMEX** | Trajectories | Android |
| **OS-Atlas, UGround, SeeClick, ShowUI** | Grounding | Cross-platform |
| **AgentNet (OpenCUA)** | Trajectories + reasoning | Desktop |
| **OmniACT, GUIAct, Aguvis data** | Mixed | Mixed |
| **ScreenSpot / ScreenSpot-Pro** | Grounding (eval) | Cross-platform |
| **OSWorld, WebArena, AndroidWorld** | Interactive environments (eval/RL) | Mixed |

### B. Record human demonstrations
Build or use a recorder that saves, for every action:
- a screenshot **before** the action
- the raw input event (mouse position, keys)
- optionally the accessibility tree / DOM and the active window or app
- a timestamp

Useful tools: the AgentNet Tool (OpenCUA's recorder), `pynput` + `mss` for DIY, Playwright tracing for web, and `adb` + `uiautomator` for Android.

A minimal DIY recorder:
```python
import mss, json, time, os
from pynput import mouse, keyboard

os.makedirs("traj/shots", exist_ok=True)
steps, sct = [], mss.mss()

def snap():
    path = f"traj/shots/{len(steps):04d}.png"
    sct.shot(mon=1, output=path)
    return path

def on_click(x, y, button, pressed):
    if pressed:
        steps.append({"t": time.time(), "screenshot": snap(),
                      "action": {"type": "click", "x": x, "y": y, "button": str(button)}})

def on_press(key):
    if key == keyboard.Key.esc:          # stop recording
        json.dump(steps, open("traj/steps.json", "w"), indent=2)
        return False
    steps.append({"t": time.time(), "screenshot": snap(),
                  "action": {"type": "key", "key": str(key)}})

mouse.Listener(on_click=on_click).start()
with keyboard.Listener(on_press=on_press) as l:
    l.join()
```
**Caveat:** this sketch grabs the screenshot inside the event callback, so it may capture the screen *after* the click has started. Production recorders keep a rolling buffer of frames and use the last frame taken before the event.

### C. Generate synthetic data
- **Grounding:** crawl web pages or apps and pull element bounding boxes from the DOM or accessibility tree. Then turn the element text into instructions, either with templates ("click the {label} button") or with an LLM.
- **Trajectories:** run a strong agent (Claude computer use, GPT-based agents, UI-TARS) in sandboxed VMs or Docker on tasks an LLM proposes. Keep only the successful runs, judged by a checker script or an LLM/VLM judge. This is rejection sampling.
- **Reverse instruction:** let an agent explore freely, then have an LLM write the task description that matches what happened ("hindsight relabeling").

---

## 4. Process raw recordings into clean steps

Raw event logs are noisy. Turn them into meaningful actions:
- **Merge keystrokes** into one `type("hello world")` action.
- **Combine** mouse-down + move + mouse-up into `drag`. Detect double-clicks.
- **Collapse** many scroll ticks into one `scroll` action.
- **Remove** idle moves, accidental clicks, and redundant steps.
- **Pair** each action with the screenshot from *just before* it.
- **Normalize** coordinates to your chosen scheme and resize images consistently.
- **Scrub private data:** emails, passwords, names, tokens. Blur sensitive regions in screenshots.

---

## 5. Annotate

For each trajectory:
- **Task instruction:** a clear, specific, high-level goal.
- **Step reasoning (recommended):** have a VLM write a short thought for each step, given the before/after screenshots and the action. OpenCUA's reflective long chain-of-thought format includes: what's on screen → what was achieved → plan → action.
- **Step quality labels:** mark wrong or redundant steps. These are useful for filtering, or as negatives for training with preference data or RL.
- **Success label:** did the trajectory actually complete the task?

---

## 6. Store it in a standard format

**Trajectory schema (JSONL, one trajectory per line):**
```json
{
  "id": "traj_000123",
  "platform": "windows",
  "app": "chrome",
  "instruction": "Find the cheapest flight from NYC to LA on May 3",
  "success": true,
  "steps": [
    {
      "screenshot": "images/traj_000123/000.png",
      "a11y_tree": "a11y/traj_000123/000.json",
      "thought": "The Google Flights page is open. I need to set the origin first.",
      "action": {"type": "click", "x": 0.312, "y": 0.284},
      "action_text": "click(x=312, y=284)"
    },
    {
      "screenshot": "images/traj_000123/001.png",
      "thought": "The origin field is focused. I'll type the city.",
      "action": {"type": "type", "text": "New York"},
      "action_text": "type(text='New York')"
    }
  ]
}
```

**Convert to chat-style SFT samples (one sample per step):**
```json
{
  "messages": [
    {"role": "system", "content": "You are a GUI agent. Available actions: click(x,y), type(text), scroll(dx,dy), hotkey(keys), done()..."},
    {"role": "user", "content": [
      {"type": "text", "text": "Task: Find the cheapest flight...\nPrevious actions:\n1. click(x=312,y=284)"},
      {"type": "image", "image": "images/traj_000123/001.png"}
    ]},
    {"role": "assistant", "content": "Thought: The origin field is focused...\nAction: type(text='New York')"}
  ]
}
```
**History design matters.** Common choices:
- Include the last *N* screenshots (e.g., 1–3) plus a text summary of earlier actions.
- Include only the previous thoughts and actions as text, to save tokens.

---

## 7. Control quality and balance

- **Validate actions:** coordinates must fall inside the image, and click targets should land on real elements (check against the accessibility tree if you have it).
- **Remove duplicates:** drop near-identical trajectories and screenshots (perceptual hashing works well).
- **Balance the mix:** across apps, platforms, action types (clicks tend to dominate, so upsample `drag`, `hotkey`, `scroll`), task lengths, and screen resolutions.
- **Include recovery behavior:** add trajectories where the agent makes a mistake and then fixes it. These are very valuable for robustness.
- **Include terminal actions:** explicit `done()` and `fail()` / "infeasible" examples.
- **Review samples by hand:** a viewer that replays trajectories step by step is worth building.

---

## 8. Split and evaluate

- **Split by task, website or app**, not by step. Otherwise the test set leaks into training.
- **Hold out entire apps or domains** to measure generalization.
- **Offline metrics:** step-level action accuracy and grounding accuracy (ScreenSpot-style: does the click land inside the target bounding box?).
- **Online metrics:** task success rate in live environments (OSWorld, WebArena, AndroidWorld). This is the metric that really counts.

---

## 9. Optional next step: data for reinforcement learning

Once supervised fine-tuning works, set up **verifiable environments**: VMs or containers with tasks and checker scripts (as OSWorld does). Then run online RL (GRPO/PPO) or rejection-sampling loops. In that setup, your "dataset" becomes a set of tasks plus reward functions rather than fixed trajectories.

---

### Suggested starting recipe
1. Fine-tune on **public grounding data** (OS-Atlas, UGround) plus **public trajectories** (AgentNet, Mind2Web, AndroidControl).
2. Record **a few hundred human demos** in your target apps.
3. Have a VLM add **step-level reasoning** to them.
4. **Generate synthetic trajectories** with a strong agent, keeping only verified successes.
5. Evaluate online, find failure patterns, collect targeted data for them, and repeat.
