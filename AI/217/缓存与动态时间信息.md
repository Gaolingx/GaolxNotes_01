---

### 🤖 Assistant

# 结论先行

**会失效，但失效范围取决于时间字符串在 prompt 中的位置和缓存断点（cache breakpoint）的设置——而不是必然导致整个 system prompt 全部失效。** 因为主流 LLM 的 prompt 缓存是**基于"最长公共前缀"的**，不是把整条 prompt 当一个原子缓存条目。

当代 agent 的核心思路就一句话：**把"静态的大块内容"和"动态的小块内容"按顺序分离，让静态部分永远构成一个稳定前缀。**

---

## 1. 缓存机制回顾（为什么位置决定一切）

Prompt 缓存（Anthropic 的 `cache_control`、OpenAI/Gemini 的自动前缀缓存）本质是**内容寻址的前缀匹配**：

- 缓存键是「开头的若干 token」。
- 请求到来时，服务端找「与已缓存前缀的最长公共前缀」。
- 命中的前缀直接复用（读缓存很便宜，Anthropic 约 0.1×），未命中的尾部要重新 prefill。

所以假设 system prompt 结构是：

```
S = [ A | t | B ]
    静态   时间  静态
```

第二次请求时间从 `t` 变成 `t'`：

- `A` 是稳定前缀 → **命中**；
- 从 `t'` 开始，前缀与缓存的 `[A|t]` 分叉了 → `t'` 和 `B` 全部 **miss**。

**关键点：`B` 明明是静态的，也会因为排在 `t` 之后而一起失效。** 这就是「顺序敏感」。

于是得到三条经验法则：

| 时间放的位置 | 后果 |
|---|---|
| 放在 system prompt **开头** | 整个 prompt（含所有消息）全部 miss |
| 放在 system prompt **中间** | 时间点之前命中，时间点及其后全部 miss（连累后面的静态内容） |
| 放在**静态块之后、独立成动态块**（配 breakpoint） | 静态大块命中，只有尾部小动态块重算 |

---

## 2. 当代 agent 的实际做法

### ① 静态前缀 + 动态后缀，用 cache breakpoint 切开

这是最主流、最标准的做法。把「角色设定、规则、工具定义、few-shot 示例」这些**大而稳定**的内容放最前，紧随其后放一个缓存断点；把「当前时间、cwd、git 状态、平台信息」这些**小而易变**的内容放到断点之后。

```python
system = [
    {
        "type": "text",
        "text": STATIC_INSTRUCTIONS_AND_TOOLS,     # 大块、稳定
        "cache_control": {"type": "ephemeral"},   # 断点：缓存到这儿为止
    },
    {
        "type": "text",
        "text": f"<env>current date: {today}</env>",  # 小块、动态，每次重算
    },
]
```

效果：静态前缀（往往占整个 prompt 的绝大部分 token）每次命中；只有末尾几十个 token 的时间/环境块每次重算，代价可忽略。**这就是"告知时间"与"高缓存命中"同时满足的核心手段。**

### ② 时间量化（降低变化频率）

与其写 `2025-01-17 14:32:51.123`（秒级甚至毫秒级，几乎每次请求都变），不如写：

- `Today is Friday, 2025-01-17`（**日期级**，一天才变一次），或
- 最多精确到小时（`2025-01-17 14:xx`）。

这样即使时间块处于缓存区域内，缓存条目也能在整段量化窗口内保持有效。大多数 agentic 场景（写 commit message、规划、回答"今天星期几"）**根本不需要秒级精度**，日期级完全够用。

### ③ 时间做成工具（tool），按需获取

把系统提示里**完全不写时间**，而是暴露一个工具：

```json
{ "name": "get_current_time", "description": "Return the current date and time" }
```

- 优点：system prompt 100% 静态 → 缓存命中率理论最优；
- 代价：多一轮 tool-call 往返（延迟 + 多花一点 token），且模型未必会主动查时间。

实际工程里常是**混合策略**：system prompt 里放**日期级**的粗粒度时间（低频变化），精确到秒的需求交给 `get_current_time` 或 `shell(date)` 工具。

### ④ 配合 TTL 与多轮节奏

Anthropic 缓存默认 **5 分钟无访问即失效**（写缓存 1.25×，读缓存 0.1×）。agentic 的多轮 tool-use 循环里，相邻请求通常间隔几秒，稳定前缀会一直保持"热"状态。因此：

- 静态前缀要**足够大**才值得缓存（太小的块写缓存反而亏）；
- 别把易变的小块也打上 `cache_control`（白白付出 1.25× 写成本）。

## 3. 一个完整的最小示例（Anthropic 风格）

<details>
<summary>展开查看完整请求结构</summary>

```python
# 静态部分：可能上万 token，几小时不变
STATIC = """You are a terminal coding agent.
[角色规则、编码规范、安全策略……]
Available tools: read_file, edit, run_command, get_current_time……
"""

def build_prompt(conversation_history, now):
    return {
        "system": [
            {
                "type": "text",
                "text": STATIC,
                "cache_control": {"type": "ephemeral"},   # ← 静态前缀缓存在此
            },
            {
                "type": "text",
                "text": (
                    "<env>\n"
                    f"today: {now.strftime('%Y-%m-%d')}\n"   # 只到"日"，一天一变
                    f"os: linux\n"
                    "</env>"
                ),
                # 不打断点 → 每次重算，反正只有几十 token
            },
        ],
        "messages": conversation_history,   # 本身就是动态的，无需讨论缓存
    }
```

要点：

- `STATIC` 是稳定前缀，命中 0.1×；
- `<env>` 块极小且动态，重算成本可忽略；
- 时间量化到「日」，进一步降低变化频率；
- 秒级时间需求由 `get_current_time` 工具兜底。
</details>

## 4. 一句话总结

> **"写时间会不会失效缓存"——会，但只从时间出现的位置起向后失效；只要用 cache breakpoint 把「大静态块」和「小动态块」按顺序分开，让静态块当稳定前缀，时间放尾部，再用日期级量化 + 工具兜底，就能在"告诉模型时间"的同时把缓存命中率维持在接近 100%。**

这也解释了为什么 Claude Code、OpenAI Codex CLI 等终端 agent 的系统提示里能看到"当前日期/工作目录"这类信息：它们不是随便塞进去的，而是被刻意放在稳定指令块**之后**的动态环境块里，几乎不损害缓存。

### 🤖 Assistant

# 结论

**对，但"增量"这个词需要澄清——它不是"给 provider 发 diff"，而是"让前缀逐 token 保持不变，只做追加（append-only）"。** 因为 prompt 缓存是**内容寻址 + 最长公共前缀匹配**，它只认"开头是不是和上次一模一样"，并不存在增量合并/打补丁的机制。每次请求你都得把完整 prompt 重发一遍，服务端在后台做前缀去重。

所以 context engineering 里真正的准则不是"增量"，而是：

> **能追加就不原地改；必须改就尽量改在"本来就不稳定的尾部"，别碰稳定前缀。**

---

## 1. 为什么"追加"几乎免费、"原地改"代价巨大

成本不对称（以 Anthropic 为例）：

| 操作 | 缓存效果 | 输入成本 |
|---|---|---|
| 追加内容（前缀不变） | 旧前缀命中 | 读缓存 $0.1\times$，新尾部 $1\times$ |
| 改中间一个字 | 从改动点**向后全部失效** | 大段重算，还可能触发 $1.25\times$ 写缓存 |

这就是核心不对称：

- **改中间 1 个 token = 该 token 之后所有内容全部 miss**（哪怕后面几千 token 都是静态的）。
- **末尾追加 1 个 token = 前面全部命中**，只多算这 1 个 token。

因此"尽量增量/追加而非原地修改"是**绝对正确**的原则。

---

## 2. 但"纯增量"有上限：context window 预算

无限追加会撑爆上下文窗口，所以迟早要 **compaction / summarization / 截断**——而这些都是"修改"，会破坏前缀。这是不可回避的权衡：

- 增量 → 缓存友好，但上下文无限增长，token 成本与延迟上升；
- 压缩 → 省 token，但改写一大段 → 下一次请求大范围 miss。

所以工程上的目标不是"只增量不修改"，而是**"让修改的代价最小化"**。具体有几种做法：

### ① 稳定性排序（stability-ordered assembly）

把 context 块按"变化频率"从低到高排列，最稳的放最前：

```
[系统指令/角色] > [工具定义] > [长期记忆/检索文档] > [滚动摘要] > [近期对话] > [环境块/时间]
  最稳定 ←——————————————————————————————————————————————→ 最易变
```

- 前面的块几乎不动 → 构成稳定缓存前缀；
- 后面的块天然易变 → 反正要重算，改动无额外代价。

### ② 滚动摘要（rolling summary）：只重写摘要块，不碰最近消息

```
[静态系统块]  ← cache breakpoint
[摘要块：对「很久以前」对话的压缩]   ← 偶尔整体重写
[最近 N 轮原始对话]                   ← 只追加
[环境/时间块]
```

- 最近对话只增不改 → 该段前缀稳定；
- 摘要块虽然会被重写，但它和"最近对话"之间隔开了，重写摘要只影响摘要之后的尾部（而尾部本来就在变）。

### ③ 改动集中在"本就不稳定的尾部"

要注入新指令/提醒（system-reminder）时，**追加**到最后一条消息后面，而不是**编辑**开头的 system prompt：

```
# 坏：编辑静态 system prompt → 全盘失效
# 好：追加一个尾部块
messages: [ ...历史..., { role: "user", content: "...<system-reminder>今天改为用 pnpm</system-reminder>" } ]
```

### ④ 改动的"批量化"

如果必须动中间（比如修正早期对话、更新检索文档），把多次小改**合并成一次大改**，比"每次请求都小改"对缓存的伤害更小——因为每次原地改都会触发一次大范围 miss + 写缓存。

---

## 3. 回到上一轮的时间问题：它正好是"最易变块"的代表

时间这类信息应该同时满足三层策略，本质上都是"把变化赶到最不伤害缓存的地方"：

1. **位置**：放尾部动态块，不放进静态前缀；
2. **频率**：量化到"日"甚至更粗，减少变化次数（date 一天才变一次）；
3. **按需**：秒级精度交给 `get_current_time` 工具，prompt 本身不携带高频变化值。

这三条其实是同一个思想的三个维度：**把"变化"从"稳定区域"里赶出去。**

---

## 一句话总结

> 在 context engineering 里，对会变化的信息，原则是**"追加优于改写、改尾部优于改头部、低频优于高频、批量优于零散"**。真正的约束不是"要不要增量"，而是"上下文预算迫使你压缩时，如何把这次改写安排在对缓存伤害最小的位置"。
