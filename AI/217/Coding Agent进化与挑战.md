# Coding Agent进化与挑战

### 🧑‍💻 User

话说，现在的coding agent的核心技术就是23年就有的那套LLM function calling，但是为啥直到25年下半年它才逐渐火起来

---

### 🤖 Assistant

好问题，而且这个问题的答案其实有点反直觉：**火起来的根本不是 function calling，而是 function calling 之外的整个系统在 2023→2025 之间补齐了。**

一句话结论：2023 年你有的是一台发动机（function calling），2025 年你有的是一辆整车 + 高速公路 + 加油站 + 驾校 + 口碑。**function calling 是必要条件，远非充分条件。**

下面拆开说。

---

### 1. Function calling 只是最表层的东西

严格来说，coding agent 的核心技术不是"function calling"（那只是模型输出一个 JSON 结构去调 API），而是**agentic loop**：

> 任务分解 → 工具调用 → 观察输出 → 判断对错 → 纠错 → 继续 → …直到完成

2023 年这个循环**只存在于 demo 里**。当年各种 agent 项目（AutoGPT、BabyAGI）演示时惊艳全场，一上真实仓库就跑飞——因为循环的每一环都不可靠。

### 2. 真正的分水岭：模型被"为代理而训练"了

这是最容易被忽略的一点：

| | 2023 | 2024末–2025 |
|---|---|---|
| 模型 | 通用模型 + 临时接的工具调用 API（bolt-on） | **原生 agentic 模型** |
| 训练方式 | 以"回答问题"为目标 | 直接用 coding agent 的运行轨迹做强化学习训练 |
| 行为特点 | 调一次工具还行，多步就迷路、不自查 | 会自查、会复盘、长任务不跑偏 |

Claude Code、GPT Codex 背后的模型，是**拿着 agent 自己产生的数据再去训练的**（SWE-bench 这类 benchmark 成了训练目标）。所以 2025 年你用的"function calling"和 2023 年的已经不是同一个东西——它被专门打磨成了"干活的工具"，而不是"聊天的附加功能"。

### 3. 可靠性的非线性门槛（数学上）

<details>
<summary>为什么"单步 95% 正确"和"单步 99.5% 正确"是两个世界（点击展开）</summary>

假设一个任务需要 $n$ 步，单步成功率 $p$，总成功率是 $p^n$：

- $p = 0.95$，$n = 20$：$0.95^{20} \approx 36\%$——演示能过，生产必翻车
- $p = 0.995$，$n = 20$：$0.995^{20} \approx 90\%$——真正可用

</details>

也就是说，**每步可靠性从 95% 提到 99.5%，总成功率翻了 2.5 倍**。2023→2025 模型走的正是这段路——而这段路只有靠第 2 点的专项训练才走得完。

### 4. 成本降了一个数量级以上，agent 才烧得起

agent 循环的 token 消耗是单次对话的 **10–100 倍**（要反复读写文件、报错、重试）。2023 年 GPT-4 的价格根本付不起这种"试错成本"。到 2024–2025 年，DeepSeek、Gemini 2.5 把推理成本打下来几个数量级，蒸馏让小模型也能跑 agent——**"让 AI 随便折腾"第一次变得便宜**。经济账不过关，技术再好也火不起来。

### 5. 上下文窗口：从"能调工具"到"装得下整个仓库"

这一点经常被低估。function calling 2023 年就能让 agent 调 grep、读文件，**但模型装不下整个代码库**。而 agent 最难的一环恰恰是：在几千个文件里，判断"下一步该看哪个文件"。

200K → 1M 的上下文窗口 + 代码索引/embedding 的成熟，才让"把项目塞进上下文再决策"成为现实。**上下文管理对 coding agent 的贡献，可能不亚于 function calling 本身。**

### 6. 生态标准化：MCP 是临门一脚

- 2024 年 11 月 Anthropic 发布 **MCP（Model Context Protocol）**，工具接入从"每个产品自己造轮子"变成统一标准；
- 沙箱执行（E2B、Daytona 等）、IDE 集成、权限控制陆续成熟。

2023 年"接工具"是每个 agent 项目的痛点；2025 年"接工具"变成一个插拔协议。

### 7. 产品范式 + 信任飞轮

- 2023 年的范式是 **Copilot（补全）/ Cursor（编辑）**——人机协作，AI 只做一步；
- 2025 年 Claude Code 开创了**委托式**交互：Plan mode（先给方案）+ Diff review（逐行审改）+ 权限控制。用户第一次敢把"整个任务"交给 AI，是因为有安全和透明机制兜底。

然后就是飞轮：Claude Code 口碑爆发 → Google Jules、OpenAI Codex、Amazon Kiro、GitHub Copilot Agent 全面跟进 → 2025 下半年集中爆发。**产品验证 + 巨头入场 + 模型降价，三件事在同一个半年里撞上了。**

---

### 总结：一张表看清 2023 vs 2025

| 维度 | 2023 | 2025 |
|---|---|---|
| 模型 | 通用模型 + 工具调用附加功能 | 为 agentic 任务专项训练的模型 |
| 单步可靠性 | 95% 左右 | 99.5%+ |
| 推理成本 | 贵到烧不起循环 | 便宜到可以随便试错 |
| 上下文 | 32K–128K，装不下仓库 | 200K–1M，装得下项目 |
| 工具生态 | 各家自造轮子 | MCP 统一标准 |
| 交互范式 | 补全/编辑（人做决策） | 委托式（AI 做决策，人做审核） |
| 产品 | 实验室 demo | Claude Code / Codex / Jules / Cursor 等成熟产品 |

所以，与其说"核心技术早就有了只是没火"，不如说：**function calling 在 2023 年只是个钥匙胚子，2025 年它被锻造成了钥匙、配上了门、装了锁、还教了人怎么用。** 火的是那整个系统，不是那把钥匙。

### 🤖 Assistant

你这个框架很对，我先把它补全成"三层问题"，再来逐层拆解 effort：

- **第 1 层：格式**——输出合法 JSON/schema。你说的没错，这是最简单的一层，**纯工程问题**（约束采样、语法校验），2024 年就已经被 vLLM/xgrammar/outlines 这类工具解决到 99.9% 了。
- **第 2 层：语义选择**——根据上下文选对工具、填对参数。这是**模型问题**，只能靠构建场景化的后训练管线。真功夫都在这里。
- **第 3 层：长程可靠性**——单次调用对没用，连续几十次调用都要对（$p^{n}$ 的组合失效）。这一层靠的是 agent 架构 + 后训练长轨迹 + 推理系统的上下文管理。

下面按你点的五个角度，外加一个跨层视角，逐一展开。

---

## 1. Post-training：天花板所在，也是唯一的"语义约束"手段

你说"最难的是根据语境选对工具+填对参数，只能靠后训练"——这就是整个行业的核心共识。具体 effort 分 SFT 和 RL 两段：

### SFT：造数据，专打"选择困难"

- **混淆生成（disambiguation）**：故意造出语义重叠的工具对（比如一个 `edit_file` 一个 `apply_patch`），强迫模型学会读 description 区分。这是"选对工具"能力的直接来源。
- **参数落地（grounding）**：从自然语言中抽取参数值——"把 foo.py 第 3 行改成 `x`" → `{file_path: "foo.py", start_line: 3, new_content: "x"}`，包括单位换算、类型转换、缺省值补齐。这是"填对参数"能力的直接来源。
- **批量/并行调用**：一个意图拆成多次独立调用。
- **负样本：不该调就不调**。没有足够信息时应该反问用户，而不是瞎调一个工具。防止"工具狂魔"行为。
- **错误恢复数据**：工具返回 error 后，模型如何改参数重试、换工具、或降级。
- **schema 扰动（schema randomization）**：训练时随机改写参数名、描述措辞、调整工具顺序——强迫模型靠**语义理解**而非记忆，这样推理时遇到**从未见过的工具**（新 MCP server）也能零样本用对。这是工具泛化的关键，常被忽略。

### RL：把"执行反馈"变成奖励信号

- **结果奖励**：任务最终完成度（测试是否通过、验证器打分）。
- **过程奖励**：单步 tool call 是否正确（LLM-as-judge 或沙箱执行验证），解决长程的 credit assignment。
- **反模式惩罚**：幻觉工具名/参数名、死循环（步数惩罚）、过早终止。Claude Code、GPT Codex 背后都是这套，而且用**线上生产轨迹**做持续后训练——这就是数据飞轮：产品产生轨迹 → 轨迹变成训练数据 → 模型变强 → 产品更可用。

---

## 2. Chat template：训练与推理的"契约"

这层最容易被低估，但它是**训练管线的输入格式**，任何偏差都直接掉点：

- **专用 token**：`<|tool_call|>`、tool 角色、tool result 段的特殊 token——让 tokenizer/模型把"工具调用"当成一个有边界的、可约束的生成区域。
- **工具定义入 prompt 的方式**：系统提示里塞 JSON schema 的做法、XML 风格（Anthropic `<tool_use>`）vs JSON 风格（OpenAI）vs natural-language tool use（Anthropic 模型原生偏好）。**训练用什么格式，推理必须一字不差**——生产环境常见事故就是上线时偷偷加了一行 system prompt，掉 3~5 个点。
- **工具数量与顺序**：一次性塞 50 个工具 = 注意力被稀释；工具排序靠前、描述精简、去重字段都会影响选择准确率。这促使 agent 层做 **tool pruning**（见第 4 节）。
- **推理前置**：在 tool call 之前插入思考段（extended thinking / CoT），模型先想"该调什么、参数从哪来"再生成调用，对第 2 层问题提升巨大，模板得为此留出独立区域。
- Anthropic 明确训练模型"用自然语言描述工具目标、生成结构化调用"（不是简单逼它输出 JSON），这是"模板即训练的一部分"的极端体现。

---

## 3. Inference system：解决第 1 层，顺带兜底第 2 层、支撑第 3 层

### 约束解码（你提到的 strict mode / 引导解码）

- **原理**：把 JSON schema / 工具的输入语法编译成 FSM，每次解码时 mask 掉不合法 token（xgrammar、outlines、llama.cpp GBNF、vLLM/SGLang structured outputs）。
- **收益**：语法零错误、不会输出多余 key；对 enum 类参数还能在解码时硬约束到合法取值（这其实已经半个迈进了第 2 层）；省掉两轮"解析失败重试"。
- **边界（呼应你的观点）**：语法约束纠正不了**语义**——它能保证 `file_path` 是字符串，但保证不了这个路径存在；它能保证调的是合法工具名，但保证不了选的是**对的**工具。所以它只覆盖那 10% 的格式问题，剩下 90% 的 effort 必须给后训练。

### 验证层

- 解码之外再加一道 **schema 校验 + 语义校验**（路径存在吗、行号在界内吗、参数值非空吗），不合法就触发 agent 层的修正循环。

### 长程支撑

- **速度**：agent = 大量往返，prefill 复用、prefix caching、投机解码直接决定可用性。
- **长上下文**：持续增长的对话需要 KV cache 管理 + 上下文压缩（把旧轮次摘要化）——这层不做好，长程任务跑到一半上下文就爆了。
- Agent 会在推理系统外执行工具（沙箱），再把结果 append 回对话继续生成——推理系统要支持"调用 → 执行 → 续写"无重复 prefill 的循环架构。

---

## 4. Terminal agent（产品/架构层）：第 2、3 层的软件化兜底

这一层的 effort 最"软"但效果最直接：

- **工具设计本身就是一种约束**：边界清晰、参数少、命名语义化、description 写明"何时用/何时不用+示例"。**工具 API 设计得差，再好的模型也填不对参数**——很多"选错工具"其实是产品层工具划分不合理的锅。
- **Tool pruning（工具裁剪）**：不把全部工具塞进模板，而是先检索/预筛出"当前任务相关"的 3~10 个工具再交给模型。这是把第 2 层问题从"50 选 1"降维成"5 选 1"，实测收益远大于解码层任何 trick。
- **上下文管理**：代码库索引（embedding/BM25）只喂相关文件片段，维护 scratchpad，把"该读哪个文件"这个最难的长程决策交给检索而不是模型记忆。
- **恢复循环**：解析失败→让模型修正；执行失败→带回错误信息让模型换参数/换工具；步数上限与死循环检测。
- **子代理分解（sub-agent）**：长任务拆给多个子 agent，各自持有受限上下文，父 agent 编排——这是对抗 $p^n$ 组合失效的主要架构手段。
- **自验证**：改完跑测试、看 diff、replan——把"长程不跑偏"从模型能力问题变成产品流程问题。
- **数据回灌**：agent 的 trace 日志 → eval → 后训练数据源，这层是飞轮的起点。

---

## 5. MCP：生态标准化，把"散装工具"变成"统一协议"

MCP 解决的不是模型能力，而是**异构性的成本**：

- **统一 schema 与调用语义**：每个工具暴露 `inputSchema`（JSON schema），响应统一为 `content` / `structuredContent` / `isError` 信封——模型侧、agent 侧、后训练侧都用同一套格式，**消除 per-integration 的模板漂移**（这直接喂给第 2 节的"训练/推理一致性"）。
- **动态发现（`tools/list`）**：agent 运行时可枚举工具清单，为 tool pruning 提供标准接口。
- **标准化错误语义（`isError`）**：让 agent 明确区分"工具失败"与"返回了数据"——这是恢复循环成立的前提。
- **structuredContent**：工具结果以结构化 JSON 返回，便于模型精确 grounding 参数（而不是从格式化文本里猜）。
- **生态位**：一个协议接 N 个 server，后训练可以直接拿海量真实 MCP server 做多样性数据，零样本泛化能力就是这么喂出来的。
- 它**不解决**的问题也该说清：工具爆炸（工具越多越容易选错）、描述质量参差（描述烂=调用烂）、工具结果里的 prompt injection（不可信输入）、跨 server 的长程状态。这些都是 agent 层的活。

## 6. 一张表：每层 effort 对应哪类失败

| 失败类型 | 典型例子 | 主战场 |
|---|---|---|
| 格式/语法 | JSON 非法、key 拼错、多余字段 | **推理系统**（约束解码）+ 验证层 |
| 语义选择 | 用错工具、参数值错、该调不调 | **后训练**（SFT 混淆数据/RL）+ chat template + 工具设计 |
| 上下文缺失 | 不知道该读哪个文件 | **agent 层**（检索 + tool pruning + 压缩） |
| 执行失败不恢复 | 工具报错后死磕同一参数 | **agent 恢复循环** + 后训练错误恢复数据 |
| 长程失效 | 上下文爆炸、中途跑偏、死循环 | **agent 架构**（子代理/检查点）+ 后训练长轨迹 + 推理缓存 |
| 生态接入 | 工具接入难、格式不一 | **MCP** 标准化 |

---

## 结论：effort 的正确分配才是关键

把你原来的二分补成三分之后，各层的"性价比"差异就显出来了：

> **约束解码**便宜，但只吃掉 5~10% 的格式失败；**post-training** 贵，但决定 90% 的语义上限；**agent 架构**决定长程可靠性；**MCP** 决定生态广度；**chat template** 决定前四者的稳定性。

真正成熟的产品（Claude Code / Codex），不是在某一个层疯狂加码，而是**用 eval 循环（SWE-bench、terminal-bench 这类长程 bench）度量失败分布，再把 effort 按分布去分配**——解码层做到"语法绝对不失败"就收手，把大头预算烧在后训练的场景化数据上。这也正是为什么 2025 年的模型厂商都开始公开讲"我们用了多少 agentic traces 做后训练"——因为大家兜了一圈才发现：**工程手段能解决形式，只有训练能解决语义。**
