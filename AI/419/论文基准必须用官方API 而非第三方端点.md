# 为什么论文 baseline 必须走官方 API 或合规 router

一句话概括:**论文比较的对象是"某个具体模型",而不是"某个产品"。** 官方端点(OpenAI/Anthropic 第一方,或 OpenRouter、Azure OpenAI、AWS Bedrock、Vertex AI 这类可追溯的转发/托管)能让你**确知、冻结并公开**你到底测了什么;coding plan 和第三方中转点做不到这一点——它们在模型前面插了一层你看不见也控制不了的东西。

下面拆成三层理由:**测量效度**、**可复现性**、**合规与可信度**。

---

## 一、测量效度:你测的可能根本不是那个模型

这是学术上最致命的。论文的结论必须是"模型 A 比模型 B 强 $\Delta$",但如果端点本身引入了混淆变量,你测到的是 **wrapper + 模型** 的混合物。

| 混淆层 | 官方 API | coding plan | 第三方中转 |
|---|---|---|---|
| 模型版本 | 可用带日期的快照 ID 钉死 | 后端随时静默换/切档 | 常为别名、滚动更新 |
| 权重量化 | 厂商公布的精度 | 未知,可能 4/8-bit | 未知,常是量化/蒸馏 |
| system prompt | 你指定,或明确为空 | 被产品注入("you are a coding assistant…") | 被注入或改写 |
| 工具/agent 循环 | 无(除非你显式加 tools) | 自动带检索、工具调用、多轮 replan | 有的带缓存/重写 |
| 拒绝层/护栏 | 厂商策略,可观察 | 产品策略叠一层 | 未知中间层 |
| 采样默认值 | `temperature`/`top_p` 可设可报 | 常被产品固定 | 常被端点覆盖 |
| 上下文/截断 | 明确 token 上限 | 配额、缓存、压缩策略不同 | 可能悄悄截断 |

任何一行差异都会让"模型能力差"变成"wrapper 差"。而且这些差异**方向不可预测**:coding plan 的脚手架可能让它在代码任务上虚高,也可能因为压缩上下文而虚低。审稿人一旦问"你怎么知道差异来自模型",你无法回答。

---

## 二、可复现性:别人复现不了,作者自己下周也复现不了

学术结果的底线是**可重跑**。coding plan 的中转后端可能在两周内换模型、改系统提示、调采样默认值,而这一切**不对外公告**。于是:

- 你报告的是"2024 年 11 月某个匿名后端",不是"`claude-3-5-sonnet-20241022`"。
- 复现实验时结果漂移,你无法归因。
- 审稿人要求提供 artifact / 复现脚本,你拿不出稳定的 endpoint 契约。

官方端点的价值正在于**可钉版本 + 可钉日期**:论文里写清模型 ID、采集日期、解码参数,任何人都能在一台机器上对齐(即使厂商后来下线快照,也有据可查)。

---

## 三、合规与可信度:科研不端与法律风险

1. **违反 ToS。** 订阅制 coding plan(Codex/Copilot/Claude Code/Cursor/Windsurf 等)通常**明确禁止**把订阅额度当作通用 API 做批量程序化调用或转售;抓取 ChatGPT/Claude 网页 UI 同样违规。用违规途径产出的数据发论文,属于研究伦理问题,轻则被要求重做,重则撤稿。
2. **第三方中转的合法来源不明。** 很多"中转/镜像"站是逆向代理、共享账号甚至盗用密钥,数据和密钥都可能被记录、转卖。用它做 benchmark 等于把论文建立在不可审计的基础上。
3. **数据去向不可控。** 你送进去的 benchmark prompt(尤其私有/未公开测试集)可能被记录、用于训练,既泄露数据,又**污染未来的评测**(下次别人测同一模型时,题已经进了训练集)。
4. **审计与成本不可核。** 官方 API 有 token 账单,可核对、可写进论文;订阅制是包月,实际用量和计费不透明,你无法报告"消耗多少 token、多少钱"。

---

## 那哪些"非第一方"是可以的?

关键不是"第一方 vs 第三方",而是**是否满足四个条件:版本可钉、行为透明、术语合规、服务方可审计**。

<details>
<summary><b>可以接受 / 需谨慎 / 不可接受 的分档</b></summary>

**✅ 推荐**
- 第一方官方 API:`api.openai.com`、`api.anthropic.com`,使用带日期的快照模型 ID。

**🟡 通常可以,但要在论文里注明**
- **云托管方**:Azure OpenAI、AWS Bedrock、GCP Vertex AI。模型由厂商或其授权伙伴按官方版本服务,可钉版本;但**版本可能滞后于第一方**,需在 limitations 里说明。
- **合规 router(OpenRouter 等)**:合法聚合,但底层可能跨多个上游 provider,个别上游用**量化权重**。必须**锁定 provider / 指定具体上游**并记录,否则版本不可控。

**❌ 不接受**
- 订阅制 coding plan / 网页 UI(ChatGPT Plus、Claude.ai、Copilot、Cursor、Codex CLI 等)——agentic 包装 + 静默换模型 + ToS 限制。
- 第三方中转、镜像、逆向代理、共享密钥端点——版本不可知、合规存疑、数据风险高。

</details>

---

## 论文里该报告什么(审稿人会查)

- 精确模型 ID(带日期快照),如 `gpt-4o-2024-08-06`、`claude-3-5-sonnet-20241022`;
- 端点类型(第一方 / 云托管 / router)与**具体上游 provider**;
- 数据采集日期区间(应对多周评测中的版本漂移);
- 解码参数:`temperature`、`top_p`、`max_tokens`、system prompt 是否为空;
- 是否启用工具、检索、缓存;
- 成本或 token 用量(可选但加分)。

<details>
<summary><b>为什么 coding plan 做 dev 实验没问题</b></summary>

探索阶段、快速验证 idea、看趋势,coding plan 和 router 都很方便,成本低、上手快。问题只出在**发表级结论**上:一旦要写进论文作为 claim,就必须换成可钉版本、可复现、合规的端点,并最好用官方端点抽一个子集做 cross-check,证明 wrapper 没改变结论方向。

</details>

---

## 小结

| 维度 | 官方 API / 合规 router | coding plan / 第三方端点 |
|---|---|---|
| 知道在测哪个模型版本 | ✅ | ❌ |
| 别人能复现 | ✅ | ❌ |
| 无隐藏 system prompt / agent 包装 | ✅ | ❌ |
| 合规、可审计 | ✅ | ❌ |
| 数据不被截留/污染 | ✅ | ❌ |

核心不是"官方就一定好",而是**发表的比较必须让读者能回答:你测的是什么、怎么测的、别人怎么重来一遍**。coding plan 和来路不明的中转恰恰在这三问上全部失守。
