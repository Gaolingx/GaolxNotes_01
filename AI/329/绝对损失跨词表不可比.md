# 大词表 vs 小词表：预训练初期 loss 的区别

先说结论：**初期 loss 的绝对数值不可直接比较**，大词表天然更高。真正有意义的差异要分「绝对 loss」「归一化 loss」「学习动态」三个层面看。

---

## 一、最直接的差异：初始 loss 差一个 $\ln V$

输出层是 $V$ 类的 softmax，随机初始化时每个 token 概率约为 $1/V$，因此初始交叉熵：

$$
\mathcal{L}_0 \approx \ln V
$$

| 词表大小 $V$ | 随机基线 $\ln V$ |
|---|---|
| 32k | $\approx 10.4$ |
| 50k | $\approx 10.8$ |
| 100k | $\approx 11.5$ |
| 250k | $\approx 12.4$ |

所以**大词表模型的 loss 曲线整体被抬高**了一段（差不多的平移量 $\ln(V_{\text{大}}/V_{\text{小}})$），PPL $=e^{\mathcal{L}}$ 同理。看到的「loss 降不下去」往往只是这个基线差异，不代表学得更差。

---

## 二、可比的指标：按字节归一化（BPB）

大词表把文本压得更「密」——同样一段文字，大词表切出的 token 数更少，每个 token 携带的信息更多。要公平比较必须除以**每 token 的字节数**：

$$
\text{Bits/Byte} = \frac{\mathcal{L}_{\text{nats}} / \ln 2}{\text{bytes per token}}
$$

于是出现一个反直觉现象：**随机基线在 BPB 意义下，大词表反而更低**。

- 大词表：$\frac{12.4 / 0.693}{6\ \text{bytes/token}} \approx 2.98$ bits/byte
- 小词表：$\frac{10.4 / 0.693}{4.5\ \text{bytes/token}} \approx 3.33$ bits/byte

> 笔记：自然语言的真实熵大约在 $1$ bits/byte 量级，是所有 tokenizer 共同的收敛下界。所以**看「每字节」时两者的终点相近，差别主要体现在中早期的下降路径和效率上**。

---

## 三、学习动态的差异（初期真正值得关注的部分）

<details>
<summary><b>1. 初期主要在学习 unigram 频率分布</b></summary>

训练最早期 loss 从 $\ln V$ 快速下坠，这一大段下降几乎全是**拟合 token 的一元频率**（把概率质量按词频重新分配）。

- 小词表：token 更少、更常见 → 每个 token 被见到的次数更多 → **每条 token 的一元分布收敛更快、更稳**。
- 大词表：词表越大、长尾越重 → 高频 token 学得快，但罕见 token 的分布估计得很慢，早期曲线可能出现「前期陡、后期拖尾」或轻微抖动。

</details>

<details>
<summary><b>2. 参数分配与数据效率</b></summary>

- 大词表：embedding + LM head 参数量大（小模型里可能占大头），每个 token 分到的梯度更新更少，尤其稀有 token 训练不足。
- 小词表：同样的参数量更多留给 Transformer 主体（注意力/FFN），但序列更长，**每字节的算力利用率**可能下降，浪费上下文窗口。
- 存在一个最优词表大小：太小 → 序列过长、上下文浪费；太大 → embedding 主导、稀有 token 欠训练、数据效率变差。

</details>

<details>
<summary><b>3. 稳定性和优化副作用</b></summary>

- 更大的 softmax 分母（partition function）需要更久才估准，早期可能出现更明显的不稳定/尖峰。
- 大词表常见对策：LM head 权重与 embedding 绑定（tied）、logit 缩放、输出层 bias 特殊初始化、z-loss 等，都能改善初期行为。
- 由于各 token 频率极度不均，大词表的有效学习率/梯度噪声在长尾 token 上更明显。

</details>

---

## 四、一句话总结

| 视角 | 大词表 | 小词表 |
|---|---|---|
| 初始/绝对 per-token loss | 更高（$\ln V$ 更大） | 更低 |
| PPL（直接比） | 更高 | 更低 |
| Bits/byte（公平比） | 起点甚至更低、路径高效 | 终点相近 |
| 一元频率收敛 | 慢、长尾拖尾 | 快、更稳 |
| 数据效率 | 词表过大时下降 | 词表过小时序列变长、效率下降 |

**实践建议**：跨不同词表的模型做 loss 对比时，**一律用 bits-per-byte（或 per-character），不要用 per-token loss / PPL**，否则大小词表的差异会让你得出相反的错误结论。

# 为什么绝对 loss 不能跨 tokenizer 比较

一句话核心：**交叉熵 loss 的单位是「每 token」，而 token 不是文本的天然单位，它的「大小」由 tokenizer 任意决定。** 用一个任意的分母去比较平均值，本身就没有意义。

---

## 一、loss 的定义就写在「每 token」上

对一段文本 $x$，切成 token 序列 $t_1,\dots,t_N$，它的交叉熵是：

$$
\mathcal{L} = -\frac{1}{N}\sum_{i=1}^{N}\log p(t_i \mid t_{<i})
$$

注意两件事：

1. 单位是 **nats / token**（或 bits / token）。
2. 分母 $N$ 是 **这个 tokenizer 切出来的 token 数**。

同一段文本，换个 tokenizer，$N$ 就变了，$p(t_i\mid t_{<i})$ 的粒度也变了。分子分母同时被 tokenizer 改写，得到的平均值自然没法对齐。

> 打个比方：比较「每包多少钱」时，一包是 1 个还是 12 个，价格数字完全不同。这里的「一包」就是 token。

---

## 二、只有「总数」是可比的，平均到 token 就被扭曲

真正代表「编码这段文本需要多少信息」的量是**总负对数似然**：

$$
\text{Total NLL} = N \cdot \mathcal{L}
$$

设同一段文本：

- 小词表切出 $N_s$ 个 token，平均 loss $\mathcal{L}_s$
- 大词表切出 $N_l$ 个 token，平均 loss $\mathcal{L}_l$（$N_l < N_s$）

两者总 NLL 是可以比的：

$$
N_s \mathcal{L}_s \;\approx\; N_l \mathcal{L}_l
$$

于是平均 loss 的换算关系大致是：

$$
\mathcal{L}_l \;\approx\; \mathcal{L}_s \cdot \frac{N_s}{N_l}
$$

**只要大词表把 token 数压缩到一半（$N_l = N_s/2$），即便建模质量完全一样，$\mathcal{L}_l \approx 2\mathcal{L}_s$——看起来「差一倍」，实际是同一水平。**

---

## 三、连「起点」都不一样：$\ln V$ 的平移

随机初始化时 loss $\approx \ln V$。词表越大，起点越高：

$$
\Delta \mathcal{L}_0 = \ln V_{\text{大}} - \ln V_{\text{小}}
$$

所以大小词表的 loss 曲线从一开始就错开一截，这个差距和模型好坏无关，纯属词表规模。PPL $=e^{\mathcal{L}}$ 更糟，是指数放大。

---

## 四、最著名的陷阱：字符级模型「吊打」一切

早期字符级 LM 报告 PPL 低到 1.x，看起来碾压词级模型。原因很简单：

- 字符级 tokenizer 把一句话切成几十个 token，每个 token 极好预测 → 平均每 token loss 很低、PPL 很低。
- 但它其实是个**更差的模型**，只是分母被切得极碎。

反过来，激进的 BPE 词表因为 token 少、每个 token 信息量大，per-token loss 天然偏高，会被误判为「更差」。

**这类比较完全是尺子被换了，不是模型变了。**

---

## 五、为什么不能只做一个「固定缩放」修正

有人会想：那我乘个 token/byte 常数不就行了？不严谨，因为：

<details>
<summary><b>展开原因</b></summary>

- loss 里**纠缠了两件事**：① 每个 token 携带多少信息（编码粒度）；② 模型把这段信息预测得多好（建模质量）。换 tokenizer 同时改变两者，无法用一个常数拆开。
- 条件结构变了：不同 tokenizer 下模型要建模的条件分布本身不同（子词边界不同、共享了不同统计规律）。
- 长尾/词频分布随词表变化，稀有 token 比例不同，训练难度不同。

</details>

---

## 六、应该用什么指标

| 指标 | 公式 / 说明 | 是否跨 tokenizer 可比 |
|---|---|---|
| per-token loss (nats) | $\mathcal{L}$ | ❌ |
| Perplexity | $e^{\mathcal{L}}$ | ❌（更糟） |
| **Bits per byte (BPB)** | $\dfrac{\mathcal{L}_{\text{nats}}}{\ln 2 \cdot \text{bytes}}$ | ✅ 标准做法 |
| Bits per character (BPC) | 按字符归一 | ✅（单语种内） |
| 固定测试集上的总 NLL | $N\mathcal{L}$ | ✅ |
| 压缩率 | bytes / token 综合 | ✅ |

BPB 的本质：用**文本的天然不变单位——字节**当分母。因为总 NLL 对同一段文本是近似不变的：

$$
\text{BPB} = \frac{\text{Total NLL}}{\ln 2 \cdot B} = \frac{N\mathcal{L}}{\ln 2 \cdot B}
$$

$N$ 和 $\mathcal{L}$ 里的 tokenizer 依赖恰好被 $\text{tokens/byte}$ 抵消掉，得到的才是真正可比的量。

> 小提示：跨语言/跨书写系统时，字节定义仍依赖 UTF-8 编码（中文一字约 3 字节），所以 BPB 在纯跨语言场景也需谨慎，但在「同一语料、不同 tokenizer」的比较中是最可靠的。

---

## 七、总结

1. loss 是 **per-token** 平均，token 的大小由 tokenizer 任意决定 → 分母不可比。
2. 只有 **总 NLL** 或 **归一到字节/字符** 的量代表真实的「编码这段文本需要多少比特」。
3. $\ln V$ 的起点平移 + token 数变化，双重扭曲了 per-token loss 和 PPL。
4. 换 tokenizer 比 loss 时，**一律用 BPB**，否则会得出正好相反的结论。

## 🤖 Assistant

# 能否解释「同 backbone 大词表看似收敛更差」？

**能解释一部分，但不能全解释。** 要严格拆成两层：

- **口径假象（测量问题）**：per-token loss / PPL 天生被抬高 → 看起来「更差」，这部分确实由 tokenizer 不可比造成。
- **真实效应（确实更差）**：训练预算核算、参数分配、长尾欠训练、优化敏感性 → 这部分换成 BPB 也还在，是真问题。

只看 loss 数字会把两者混在一起，所以必须先分开。

---

## 一、属于「假象」的部分

大词表模型即使建模质量完全相同，per-token loss 也会更高：

$$
\mathcal{L} \approx \ln V - \Delta,\qquad \text{PPL} = e^{\mathcal{L}}
$$

- 起点平移 $\ln V$；
- token 数变少 $\Rightarrow$ 平均每 token 信息量变大 $\Rightarrow$ loss 被进一步抬高；
- 曲线整体像被「压住」，收敛看起来更慢、更差。

**如果把它换算成 BPB，这一层差异会大幅消失。** 如果只看 per-token loss 就下「大词表更差」的结论，基本是被尺子骗了。

> 换句话说：单看 loss/PPL，大词表「显得差」是**必然**的，与模型好坏无关。

---

## 二、属于「真实」的部分

即使换成 BPB，大词表仍可能真的更差，原因如下。

<details>
<summary><b>1. 训练预算的「单位」变了（最容易踩坑）</b></summary>

同一份语料 $B$ 字节：

- 小词表：$N_s = r_s B$ 个 token（$r$ = tokens/byte，较大）
- 大词表：$N_l = r_l B$ 个 token（$r_l < r_s$，更少）

于是「训练量」怎么算，结论完全不同：

| 固定量 | 大词表实际看到的 | 效果 |
|---|---|---|
| 固定 **epoch / 固定语料** | token 数更少 | 更新步数少 → 像「没训够」 |
| 固定 **token 预算** | 字节数更多 | 反而占优 |
| 固定 **FLOPs** | 见第 4 点 | 复杂 |

所以很多「大词表收敛差」其实是**固定了 epoch 或固定了 token 数**，导致大词表有效训练量不足，是调度口径问题，不单纯是测量问题。

</details>

<details>
<summary><b>2. 参数分配被挤占</b></summary>

「同 backbone」有两种理解，结论相反：

- **backbone 不变、只加词表** → 总参变大，embedding + LM head 膨胀，**这些参数需要更多数据才训得好**，小语料下反而拖累。
- **总参固定** → 大词表挤占空间，**backbone 被缩小**，容量下降，真的更弱。

无论哪种，大词表对「数据量」的需求都更高。

</details>

<details>
<summary><b>3. 长尾 token 欠训练</b></summary>

大词表长尾更重，罕见 token 在初期几乎拿不到足够梯度：

- 它们的分布估计差 → 拉高平均 loss；
- 初始化时这些行基本是噪声 → 早期更抖；
- 单看 per-token loss 时，长尾的坏表现会放大「收敛差」的观感。

</details>

<details>
<summary><b>4. 固定 FLOPs 下的算力分配</b></summary>

算力 $\approx \mathcal{O}(\text{params} \times \text{tokens})$。大词表参数量更大（巨大 embedding/softmax 矩阵），固定算力就得减 token，**每 token 有效算力花在了更大的 softmax 上**，body 分到的相对变少。

</details>

<details>
<summary><b>5. 初始化 / 学习率 / 优化敏感</b></summary>

- 输出层类别数变化会改变 logit 尺度与初始方差，**标准 init 未必适配**；
- loss 绝对尺度变大，warmup、LR、weight decay、z-loss 等若不重调，会表现为「不稳/收敛慢」；
- tied embedding 下，词表变大使共享矩阵更难优化。

这些是**调参问题**，不是不可弥补的本质缺陷。

</details>

<details>
<summary><b>6. 词表大小与数据规模不匹配（本质原因）</b></summary>

经验上**最优词表随数据量/算力增长**（大致 $V^\* \sim D^{\gamma}$ 量级）。数据不够大时硬塞大词表，就是**真实的次优**，不是测量假象——这也是为什么小数据集上大词表确实更差。

</details>

---

## 三、怎么判断到底是「假象」还是「真差」

按顺序做这几步即可定位：

| 检查 | 若结果为… | 结论 |
|---|---|---|
| 换算 **BPB** 再比 | 差距消失 | 纯口径假象 |
| BPB 仍更差 | — | 真实差异，继续 |
| 对齐 **训练字节数/FLOPs** | 差距缩小 | 预算口径问题 |
| 对齐 **总参数量** | 差距缩小 | 参数分配问题 |
| 单独看**长尾 token 的 loss** | 明显更高 | 欠训练 |
| 重调 **LR/warmup/init** | 差距缩小 | 优化敏感性 |
| 加数据后重测 | 大词表反超 | 词表-数据不匹配 |

**判据**：先转 BPB → 再对齐预算 → 再对齐参数 → 最后看长尾和调参。走完还差，才是真差。

---

## 四、结论

1. **「看似」更差**，很大程度是 per-token loss / PPL 不可比造成的（$\ln V$ + token 数变化）→ **假象**。
2. 但换成 BPB、对齐预算和参数后往往**还剩下真实差距**，主要来自：训练量口径、embedding 数据效率、长尾欠训练、算力分配、优化敏感性，以及**词表与数据规模的匹配**。
3. 所以：**不能只用 per-token loss 断定「大词表更差」**；也不能假设「只要换成 BPB 就没事」。
4. 实践上：报告 BPB + 对齐字节/FLOPs 预算 + 重调 LR/init，通常能把大部分「收敛更差」消掉；消不掉的部分，才是需要靠加数据或调词表规模来解决的真问题。

## 🤖 Assistant

# 既然大词表更贵、loss 还更高，为什么 SOTA 还在冲 100k+？

因为你的两个前提**在大模型尺度上恰好都不太成立**：

- 「增加计算量」——overhead 占比其实很小，而且**按文本量算，大词表常常反而更省算力**；
- 「loss 更高」——那是 per-token 口径的假象，换成 BPB（bits/byte）通常是**更好**的。

再加上序列变短、多语言覆盖、scaling law 等收益，SOTA 选大词表是理性的。逐个拆。

---

## 一、先纠正前提

### 1. embedding/softmax 的开销占比其实很小

每 token 前向 FLOPs 大致：

$$
\text{body} \approx 2 N_{\text{body}},\qquad \text{head} \approx 2 V d
$$

head 相对 body 的占比：

$$
\frac{V d}{N_{\text{body}}}
$$

- 7B、$d=4096$、$V=128\text{k}$：$Vd \approx 0.5\text{B}$，$N_{\text{body}}\approx 6.5\text{B}$ → overhead 约 **8%**。
- 反过来，1B 小模型里 embedding 可能占 30%+。

**模型越大，大词表的相对开销越小。** SOTA 都是大模型，所以这个「贵」几乎可以忽略。

### 2. 「按文本量算」反而可能更省

固定一段文本 $B$ 字节：

| 组件 | 总计算量 | 词表变大、序列变短后 |
|---|---|---|
| Attention | $\propto L^2 d$ | $L \downarrow \Rightarrow$ **平方级下降** |
| FFN | $\propto L d^2$ | 线性下降 |
| Head | $\propto L V d$ | $L \downarrow 、V \uparrow$，**近似不变** |

如果词表增大让压缩率提升、token 数减少（$L\downarrow$），那么**attention 和 FFN 省下来的比 head 多花的更多** → 同一段文本总计算量**下降**。

> 所以「大词表增加计算量」只在「固定 token 数/上下文长度」的口径下成立；按字节、尤其长上下文场景，大词表往往是净赚。

### 3. loss 更高是口径问题

per-token loss 被 $\ln V$ 抬高，但真实指标 BPB 通常更优（前几轮已论证）。

---

## 二、大词表在 SOTA 尺度上的真实收益

<details>
<summary><b>1. 序列变短的连锁收益（最被低估）</b></summary>

同样一段文字，大词表用更少 token 表示：

- **同样上下文窗口覆盖更多字符/字节** → 长程建模更强；
- **attention 是 $O(L^2)$**，序列减半 → attention 计算降到 1/4；
- **KV cache 更小** → 同显存可放更长上下文/更大 batch；
- **自回归解码步数更少** → 生成同样长度的文本**延迟更低**（推理是逐 token 串行的，步数是硬约束）。

生成延迟对部署模型是命脉，这一条经常直接决定 tokenizer 选型。

</details>

<details>
<summary><b>2. 固定 token 预算下看到更多字节（数据效率）</b></summary>

训练常按 token 数计预算。$r$ = tokens/byte，看到的字节数 $= \text{tokens}/r$：

- 大词表 $r$ 小 → **同样 300B token 预算，喂进更多真实文本**。

也就是说，训练阶段「每 token 更贵」，但**每 token 携带的信息/覆盖的文本更多**，单位字节的收益未必差。

</details>

<details>
<summary><b>3. 多语言 / 多脚本 / 代码，硬性要求大词表</b></summary>

SOTA 全是多语言的。拉丁字母外（中/日/韩/阿拉伯/西里尔…）+ 代码，如果词表太小：

- 非拉丁文字会退化到 byte fallback，**fertility（每词 token 数）爆炸** → 序列被拉长数倍 → 又贵又差；
- 代码标识符、数字、符号也切得很碎。

**覆盖几十种语言+代码，100k 是入门门槛，200k+ 不稀奇。** 这是 SOTA 大词表最直接的驱动力。

</details>

<details>
<summary><b>4. Scaling law：最优词表随算力/数据增长</b></summary>

近年研究（如 *Scaling Laws with Vocabulary*, 2024）给出最优词表随数据/算力呈幂律增长：

$$
V^\* \propto D^{\gamma}\ (\text{或}\ C^{\gamma}),\quad \gamma>0
$$

结论：**算力/数据越大，最优词表越大**，大规模训练下最优点可达 200k 量级甚至更高。SOTA 在万亿 token、巨量算力下训练，最优词表自然是大词表——这不是跟风，是 scaling law 的推论。

</details>

<details>
<summary><b>5. 一次性成本，终身摊销</b></summary>

tokenizer 选型只在训练前定一次，却同时影响：

- 预训练成本
- 所有下游微调
- **部署后的每一次推理**（延迟、吞吐、显存）

一个线上模型的生命周期推理成本远超训练成本，所以「训练时多花一点」换「推理时每 token 生成更快」，是极划算的投资。

</details>

---

## 三、什么时候小词表才更优（边界条件）

大词表并非万能，这些情况下小词表更对：

| 场景 | 原因 |
|---|---|
| 小模型 / 小数据 | embedding 占比高、参数吃数据、长尾训不动 |
| 纯英语、有限算力 | 大词表的收益（多语言/压缩）用不上 |
| tokenizer 与语料不匹配 | 大量 token 几乎不出现，纯浪费 |
| 对字符级鲁棒性敏感（拼写/算术） | 大词表可能损害字符级能力 |
| 固定 token 数、非长上下文比较 | head overhead 相对突出 |

> 核心判断：**最优词表 = 数据量、算力、语言/领域覆盖、推理成本四者的函数。** SOTA 处在大数据、大算力、多语言、重推理的角落，所以选大词表；你的场景不同，最优值就不同。

## 五、一句话总结

1. 大词表的**算力开销**在 SOTA 大模型上占比小，且按文本量算常**净省**（序列变短）。
2. 「loss 更高」是 per-token 假象，BPB 通常**更好**。
3. 真正驱动力：**短序列的多重收益 + 多语言/代码覆盖 + 最优词表随算力增长的 scaling law + 推理成本的一次性摊销**。
4. 小模型/小数据该用小词表——两者不矛盾，只是**最优词表本就随资源单调增长**。
