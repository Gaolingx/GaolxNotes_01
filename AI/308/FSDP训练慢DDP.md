# FSDP训练慢DDP

### 🧑‍💻 User

fsdp的fwd阶段到底gather了哪些东西？

---

### 🤖 Assistant

在 FSDP（Fully Sharded Data Parallel）的前向传播（forward）阶段，核心操作是**参数的 all-gather**。具体来说，它会收集当前正在执行 forward 的那一层（`FSDP module`）的所有**参数（Parameters）**，并临时组装成完整的参数用于计算。

### 详细说明 FSDP Forward 阶段 Gather 的内容

FSDP 的基本思想是将模型参数、梯度和优化器状态分片到不同的 GPU 上。在前向传播时，为了能够进行正常的矩阵乘法等运算，需要把分片的参数重新拼凑完整。

#### 1. Gather 的具体对象
- **参数张量**：这是唯一被 gather 的内容。当程序执行到被 `FSDP` 包裹的某个 `nn.Module` 时，触发该模块的 pre-forward hook。此时，系统会通过 all-gather 操作，从所有 GPU 上收集该层参数的各个分片，并在当前 GPU 上重建该层的**完整参数张量**。
- **注意：不 Gather 激活值或优化器状态**。激活值是上一层的输出，已经在当前 GPU 上了；优化器状态只在反向传播和更新阶段使用。

#### 2. Gather 的触发时机（按层级别）
FSDP 是按模块层级进行包裹的。假设你有一个包含多层 Transformer Block 的模型，并且每个 Block 都被单独包成了一个 `FSDP` unit：
- 当模型执行到第 $i$ 个 Block 的 forward 函数时，才触发该 Block 参数的 all-gather。
- 在该 Block 的 forward 计算完成后（触发 post-forward hook），为了避免显存占用过高，FSDP 会立即**丢弃/释放**刚刚 gather 来的完整参数，只保留该 Block 原本的参数分片。

#### 3. 内存与通信的权衡
- **如果整个模型只包一层 FSDP**（即整个模型作为一个 `FSDP` unit）：会在 forward 开始时一次性 gather 整个模型的全部参数，这会导致极高的峰值显存（等同于不用 FSDP 时的显存），但只通信一次。
- **如果把每一层分别包成 FSDP**：每次只 gather 当前层的参数，峰值显存大幅降低，但通信频率增加。
- **PyTorch 推荐的做法**：采用递归 FSDP 包裹，平衡显存和通信开销。

<details>
<summary><b>补充：仅 Gather 参数为何能省显存？（点击展开）</b></summary>

在标准的分布式训练中，显存主要被四部分占用：
1. **模型参数**：例如 FP32 下占 $4 \times N$ 字节（$N$ 为参数量）。
2. **梯度**：与参数同等大小，占 $4 \times N$ 字节。
3. **优化器状态**：例如 Adam 需保存动量和方差，占 $8 \times N$ 字节。
4. **激活值**：与 batch size 和隐藏层维度相关。

FSDP 的核心优势在于，它把 1、2、3 项全部切分到了每张卡上。如果有 $K$ 张卡，每张卡上原本这三项的常驻显存变为原来的 $1/K$。

在前向阶段，虽然我们必须 Gather 出完整的参数（临时恢复了 $1 \times N$ 的显存），但这仅限当前计算的那一层。计算完立刻释放。这就确保了**前向阶段的峰值显存取决于单层参数大小，而非整个模型的参数大小**，从而能够训练比单卡显存大得多的模型。
</details>

<details>
<summary><b>底层源码视角：FSDP Forward 到底调用了什么？（点击展开）</b></summary>

在 PyTorch 的 `FSDP` 实现中，前向传播的 gather 主要由以下机制驱动：

1. **`_pre_forward` hook**:
   当触发该层的 forward 时，hook 被调用。
   底层会调用类似 `_fsdp_param.ext_module.all_gather(...)` 的方法。
   通信域中使用 `torch.distributed.all_gather` 将各个 rank 上的 `_flat_param` 拼接成完整的 `unsharded_flat_param`。

2. **将完整参数注入 Module**:
   Gather 完成后，FSDP 会将当前的 `nn.Module` 的 `_flat_param` 指向新分配好的完整参数内存，使得原本的 `layer.weight` 等操作可以直接使用完整的权重。

3. **`_post_forward` hook**:
   该层的前向计算（如 `F.linear(x, weight, bias)`）执行完毕。
   hook 介入，将 `_flat_param` 重新指向回自己原本的分片，并释放完整参数占用的显存。

</details>

### 🧑‍💻 User

为什么fsdp的训练速度比ddp慢很多，尤其是全参而不是peft？

---

### 🤖 Assistant

FSDP 训练速度比 DDP 慢，尤其是在全参数微调（Full Fine-tuning）而非 PEFT（如 LoRA）时，主要原因是 **FSDP 在训练过程中引入了大量的显存搬运和额外通信开销**，以换取能够训练超大模型的能力。

DDP 的核心逻辑是“数据并行”，每张卡上都有完整的模型副本，前向和反向完全独立，只在反向传播结束时通过 `AllReduce` 同步梯度。而 FSDP 是“全分片数据并行”，每张卡只保留模型的一部分。为了完成计算，FSDP 必须在不同的阶段“临时借用”其他卡的数据。

具体来说，FSDP 比 DDP 慢的原因可以归结为以下几个核心维度：

### 1. 额外的通信量与层级差异

| 阶段 | DDP (全参) | FSDP (全参) | 开销对比 |
| :--- | :--- | :--- | :--- |
| **Forward** | 无通信 | `All-Gather` 收集当前层完整参数 | **FSDP 远大于 DDP** |
| **Backward** | 无通信 | `All-Gather` 重新收集参数 + `Reduce-Scatter` 分发梯度 | **FSDP 远大于 DDP** |
| **梯度同步** | `AllReduce` 同步所有梯度 | 包含在反向的 `Reduce-Scatter` 中 | 总通信量 FSDP 仍大于 DDP |

* **DDP 的通信量**：反向传播时一次 `AllReduce`，通信量大致为 $2 \times P$（$P$ 为模型参数量大小）。
* **FSDP 的通信量**：
  * 前向：每层都需 `All-Gather`，总通信量约为 $1 \times P$。
  * 反向：需重新 `All-Gather` 参数，再 `Reduce-Scatter` 梯度，总通信量约为 $3 \times P$。
* **结论**：全参数微调下，FSDP 的总通信量显著高于 DDP，且通信被拆散在每一层的计算前后，容易受网络延迟影响。

### 2. 前向阶段必须 Gather 全参（上一问的核心）

在 DDP 中，前向传播直接读取本地显存的权重进行矩阵乘法（$Y = XW$），**没有任何等待时间**。

在 FSDP 全参微调中，每一层在 forward 时：
1. 发起 `All-Gather` 等待其他所有卡发送参数分片。
2. 在本地拼接成完整的 $W$。
3. 执行计算 $Y = XW$。
4. 立刻释放拼接的 $W$ 以节省显存。

这意味着 FSDP 的前向传播被网络通信严重阻塞，而这在 DDP 中是完全不存在的开销。全参数微调时，由于所有参数都参与了计算，这种 Gather 不可避免。

<details>
<summary><b>为什么 PEFT (如 LoRA) 在 FSDP 下比全参快很多？（点击展开）</b></summary>

在 PEFT（如 LoRA）场景下，大部分参数是被冻结的，只有少量 Adapter 参数参与训练。如果配合 FSDP：
1. **冻结参数不被分片/Gather**：通常我们将基础大模型设为 `freeze` 状态，不需要计算梯度，也无需 FSDP 分片其权重。基础模型常驻显存（如果单卡装得下），或者使用 CPU offload。
2. **只有 LoRA 参数走 FSDP 流程**：LoRA 参数量极小（通常只占总参数的 $0.1\% \sim 1\%$）。因此在前向和反向阶段，FSDP 的 `All-Gather` 和 `Reduce-Scatter` 只针对这极少量的参数进行。
3. **减少计算与通信瓶颈**：通信量减少了成百上千倍，自然感觉不到 FSDP 带来的慢速问题。这就是为什么用户感知“全参微调时 FSDP 慢得明显，而跑 LoRA 时感受不深”。
</details>

---

### 3. 显存分配与释放 的频繁开销

FSDP 为了保证显存不爆，采用了类似“用完就扔”的机制：
* **前向阶段**：Gather 完整参数 -> 计算 -> 丢弃（Free）。
* **反向阶段**：再次 Gather 完整参数 -> 计算梯度 -> 丢弃（Free）。

这种模式带来了两个严重的性能损耗：
1. **显存碎片化**：频繁地申请和释放大块显存会导致显存碎片严重，后续申请大张量时可能失败或耗时增加。
2. **CUDA Kernel 调用开销**：创建、拼接、释放大张量需要频繁调用显存管理 API 和相应的 CUDA Kernel，每个微小操作都有 Host-to-Device 的指令延迟。

DDP 因为参数从头到尾都在显存里不动，完全没有这种动态分配释放的开销。

### 4. 反向传播的重计算与通信重叠困难

* **DDP 的通信覆盖**：DDP 在反向传播时，计算完一层的梯度，立刻和其他卡进行该层的梯度 `AllReduce`。因为每张卡的模型结构一样，梯度生成顺序一样，通信可以和下一层的反向计算完美重叠，几乎不抢占时间。
* **FSDP 的串行依赖**：FSDP 在反向计算某层前，**必须先等该层的 `All-Gather` 完成**。没有参数就无法求导。这就导致反向阶段的计算和通信难以完美重叠，出现了大量“卡等网络”的闲置时间。

### 5. 优化器步骤的解包与重打包

在 FSDP 中，梯度和优化器状态都是分片保存的。虽然这节省了显存，但在每一步 `optimizer.step()` 前后，FSDP 需要做大量的张量重塑操作。全参数微调下，所有分片都需要处理，这比 DDP 单纯读取本地梯度的开销要大。

<details>
<summary><b>底层视角：FSDP 反向传播的具体流程（点击展开）</b></summary>

为什么 FSDP 反向通信难以和计算重叠？我们看反向传播时单层的执行顺序：

```text
[反向传播第 i 层开始]
1. 触发 _pre_backward_hook
2. All-Gather: 拉取该层完整的参数 W_i  <--- 必须等待网络通信完成
3. 计算梯度: dW_i = dY_i * X_i^T     <--- 计算依赖上一步的 W_i
4. Reduce-Scatter: 将 dW_i 分发到各卡  <--- 通信，可能部分重叠下一层
5. Free: 释放完整的 W_i 和部分梯度
[反向传播第 i 层结束]
```
由于步骤 2 必须在步骤 3 前完成，且 All-Gather 引入的是高风险的延迟，所以反向阶段的 FSDP 常常表现为 GPU 利用率波动剧烈（因为一直在通信和计算之间来回切换，无法流水线化）。
</details>

### 总结对比

| 影响因素 | DDP | FSDP (全参微调) | 速度差异原因 |
| :--- | :--- | :--- | :--- |
| **前向通信** | 无 | 每层 All-Gather 参数 | FSDP 引入了阻塞计算的网络延迟 |
| **反向通信** | 一次性 AllReduce | 每层 All-Gather + Reduce-Scatter | FSDP 通信总量更大且碎裂，难以重叠 |
| **显存调度** | 静态分配 | 动态分配与释放 | FSDP 有 CUDA 内存分配开销及显存碎片化 |
| **参数驻留** | 全常驻显存 | 按需借还 | DDP 可以优化访存局部性，FSDP 频繁拷贝 |

**核心结论**：FSDP 用“时间”换“空间”。在单卡显存装得下整个模型及优化器状态时，DDP 绝对是效率之王；但当模型参数量超过单卡显存（如 7B 模型 FP32 需约 28GB 参数+梯度+ 56GB 优化器状态，单卡 80GB 也非常紧凑），FSDP 就成为必须的选择，而它慢是架构决定的必然代价。
