# Liger Kernel不适用于模型生成加速

### 🧑‍💻 User

为什么liger kernel不能加速llms model.generate，包括decode stage，但可以加速train时候的fwd？

---

### 🤖 Assistant

我们来剖析一下 Liger Kernel 为什么在训练时能加速前向传播（fwd），但在 LLM 的 `model.generate()`（尤其是逐 token 生成的 decode 阶段）却几乎“失灵”。

---

## 1. Liger Kernel 的加速原理

Liger Kernel 的核心思路是 **算子融合（Kernel Fusion）**：将多个简单的 PyTorch 操作（如 `RMSNorm`、`SiLU`、`RoPE`、`Linear + CrossEntropy` 等）合并成**一个** CUDA 核。其收益主要来自：

- **减少中间张量的显存读写**
  原本计算 $A = \text{SiLU}(W_1 x)$，然后 $B = W_2 A$，需要将 $A$ 写入 HBM 再从 HBM 读回。融合后，$A$ 仅保留在寄存器或共享内存中，大幅节省内存带宽。

- **减少 kernel launch 开销**
  每个 CUDA kernel 的启动都有固定延迟，融合后一次启动完成多个计算。

在**训练**场景中，这些优化非常有效，因为：
- **大批量、长序列**：batch size × sequence length 通常很大（例如 4M tokens），中间激活张量（如 hidden state）尺寸巨大，此时**激活带宽**成为瓶颈，融合能直接削减瓶颈。
- **需要保存中间结果用于反向传播**：融合核可以在反向传播时重算中间值，从而减少训练时 HBM 占用（即节省显存），这反过来允许使用更大的 batch，间接提升吞吐。

---

## 2. 推理（Model.generate）时的计算特征

LLM 的自回归生成包含两个阶段，都与训练的前向传播有本质区别：

<details>
<summary><b>Prefill 阶段（输入序列的首次编码）</b></summary>

- 输入是完整的 prompt，序列长度较长（例如 512 或 4096）。
- 此时计算模式接近训练时的前向传播，**Liger Kernel 在此阶段实际上有可能带来一定加速**。
- 不过由于不需要反向传播，激活内存的节省优势消失（本来也不成为瓶颈），而单纯的前向速度提升取决于模型规模与实现细节。
</details>

<details>
<summary><b>Decode 阶段（逐 token 生成）</b></summary>

这是生成过程的主体，也是瓶颈所在。其特征为：
- **输入尺寸极小**：每次仅生成 **1 个 token**，hidden state 的形状是 `(batch_size, 1, hidden_dim)`，甚至更小。
- **权重读取绝对主导**：每个生成步骤都必须完整扫描一遍模型的所有权重（数十 GB），而计算量（矩阵乘、Norm 等）与权重大小相比几乎是 $O(\text{hidden}^2)$ 对 $O(\text{hidden}^2)$，但输入维度 $1$ 导致**算术强度**（FLOP/Byte）极低，运行在**内存带宽瓶颈区**。
- **KV cache 的读写**：每次还要读取和更新历史键值对，进一步加重内存带宽压力。

</details>

## 3. 为什么 Liger Kernel 无法加速 Decode 阶段？

### 3.1 瓶颈转移：从“激活带宽”变成“权重带宽”

- **训练时**（大批量长序列）：可并行处理的 token 数极多，隐藏状态张量非常大，中间结果的读写是痛点。融合核通过消除这些中间张量，直击瓶颈，效果明显。
- **Decode 时**（小批量序列长1）：中间激活张量尺寸极小（`[bs, 1, hidden]`），读写的绝对量远小于模型权重的加载。此时 **80% 以上的时间都花在把权重从 HBM 搬到芯片上**。
  融合核再怎么减少那点激活的读写，也**改不动权重带宽这个主要矛盾**。

### 3.2 并行度不足，内核效率暴跌

- 融合核通常针对**大张量**设计，以利用 GPU 的数千个线程，隐藏内存延迟。
- 当 `seq_len = 1` 时，一个融合核内部可并行的元素数会骤降（例如原本一次处理 `N × d` 个元素，现在只剩 `1 × d`），导致 **GPU 占用率（Occupancy）极低**，甚至线程空转等待数据。
- 此时，融合核的额外逻辑（如寄存器读取、重计算步）带来的开销可能会超过它节省的启动开销，反而比直接调用 cuBLAS / 原生 PyTorch 更慢。

### 3.3 融合算子覆盖不全，生成流程未完全适配

- 许多 Liger Kernel 优化的是 “Linear + CrossEntropy”、“LayerNorm + Dropout” 等**训练专用**组合。`model.generate()` 根本不调用 CrossEntropy，Dropout 也被关闭，这些融合自然无法生效。
- 即使像 `RMSNorm`、`SwiGLU` 等模型层被替换了融合实现，**Decode 特有的操作**（如高效的增量 Attention、KV cache 管理、PagedAttention 等）才是真正的性能瓶颈，而 Liger 并未提供这些推理专用内核的替代实现。
- 此外，部分 `generate()` 实现可能绕过常规的 `forward()`，直接调用底层模块，导致融合层根本没被用上（取决于具体封装方式）。

### 3.4 与训练时“加速前向”的本质差异

- 训练时 Liger 的加速，除了纯前向速度提升，更重要的是通过减少中间保存来**释放显存**，从而允许更大的微批次（micro batch），提升 GPU 利用率。这属于**系统层面的吞吐加速**。
- 推理解码则是**单个请求的延迟**问题，没有“扩大 batch”这种间接收益途径，且单次步进延迟极度敏感，任何微小的启动抖动都会被放大。

---

## 总结

| 维度          | 训练前向 (fwd)                             | 生成解码 (decode)                           |
|---------------|--------------------------------------------|---------------------------------------------|
| **瓶颈来源**  | 中间激活的内存带宽 / kernel launch         | 模型权重加载 + KV cache 内存带宽             |
| **并行规模**  | 大批量 × 长序列，几千～百万 tokens          | 通常 batch=1, seq_len=1，并行度极小          |
| **融合收益**  | 直接削减瓶颈，释放显存允许更大 batch        | 不触及主要瓶颈，内核利用率低，可能负优化     |
| **使用场景**  | 计算密集/内存密集混合，算子融合价值高       | 极致内存带宽受限，融合对延迟无益甚至有害     |

因此，Liger Kernel 可以高效加速训练时的前向传播，但在 LLM 的解码式生成（尤其是逐 token 的 decode 阶段）中，由于算力负载、瓶颈性质与并行形态的彻底改变，**无法再提供可观的加速**。
