# 评估 Pretrain → Midtrain → SFT 后的模型是否需要 DPO

这是一个很实际的问题。核心思路是：**DPO 解决的是"偏好对齐"，而不是"能力提升"**。所以评估的起点是先搞清楚你的模型当前缺的是能力还是偏好，再决定是否值得引入 DPO。

---

## 一、先明确 DPO 解决什么、不解决什么

| 维度 | DPO 擅长 | DPO 不擅长 |
|------|---------|-----------|
| 输出风格/语气/长度控制 | ✅ 让回答更简洁、更符合人设 | ❌ 无法教会模型它不会的新知识 |
| 格式遵循 | ✅ 纠正格式错误、乱加前缀 | ❌ 无法解决能力性错误（如数学算错） |
| 安全/拒答边界 | ✅ 减少有害输出、纠正过度拒答 | ❌ 无法弥补 midtrain 领域知识的不足 |
| 帮助性/相关性 | ✅ 减少答非所问 | ❌ 无法替代缺失的 SFT 数据覆盖 |

**判断的第一性问题：你观察到的问题，是"模型不会"（能力），还是"模型会但做得不合意"（偏好）？**
- 前者 → 回补 midtrain/SFT 数据，DPO 帮不上忙。
- 后者 → DPO 是合适的工具。

---

## 二、五维评估框架

### 1. 任务/业务性质

- **客观可验证任务**（数学、代码、结构化抽取）：如果有 ground-truth 可判对错，优先考虑 **RLVR / 可验证奖励的强化学习**，DPO 收益有限。
- **主观偏好任务**（写作、对话、摘要、客服话术）：天然适合 DPO，因为它学的正是"人更喜欢哪个回答"。
- **混合场景**（如代码生成 + 注释风格）：DPO 可用于风格层，但能力层仍需 SFT。

### 2. SFT 后评测诊断（最关键）

在 SFT 结束后，做一轮系统化诊断，看是否存在以下**"偏好型缺陷"**：

| 症状 | 是否适合 DPO |
|------|-------------|
| 回答啰嗦、冗余、过度解释 | ✅ 典型偏好问题 |
| 格式不遵循（漏字段、乱用 markdown） | ✅ |
| 语气不一致（该正式时口语化） | ✅ |
| 过度拒答 / 该拒答不拒答 | ✅ |
| 谄媚附和用户错误前提 | ✅ |
| 安全红队测试不过 | ✅（但需配合安全 SFT 数据） |
| 知识性错误、幻觉 | ❌ 回补 midtrain/SFT |
| 逻辑推理错误 | ❌ 能力问题 |
| 长尾任务完全不会 | ❌ 数据覆盖问题 |

**做法**：抽 200–500 条真实业务样本，用 GPT-4 或人工做 pairwise 打分，统计 SFT 模型与基线的 win rate。

### 3. 偏好数据可得性

DPO 的效果高度依赖偏好对（chosen vs rejected）的质量。评估：

- 能否构造**高质量、差异明显**的偏好对？（chosen 和 rejected 的差距太小，DPO 学不到东西）
- 数据规模是否够？（通常几万到几十万条效果好；几千条只能做微调式改善）
- rejected 来源是否多样？（模型自身采样、人工改写、强模型生成等，来源单一容易过拟合）

如果手里没有偏好数据，标注成本又高，DPO 的"省一个 reward model"的优势就大打折扣。

### 4. 成本收益

- DPO 相比 PPO/RLHF 的**计算成本低很多**（单阶段 SFT 式训练，无需独立 reward model 和在线采样）。
- 主要成本在**偏好数据标注**。
- 如果业务对"风格/安全/格式"要求高，且已有数据，DPO 是性价比最高的对齐手段之一。

### 5. 小规模 Ablation 实验（最终判据）

理论分析再充分，不如一次小实验：

1. 用 5k–20k 条偏好对，在 SFT 模型上跑一版 DPO。
2. 用同一批评测集对比 **SFT vs SFT+DPO** 的 win rate / 指标。
3. 同时观察是否出现**能力退化**（DPO 可能略微损害多样性和某些 benchmark 分数，需要权衡）。

**决策规则**：
- win rate 显著提升（如 +3~5 个百分点以上）且无明显能力退化 → 做 DPO。
- 提升微弱 → 说明当前瓶颈不是偏好，回补数据或换方法。
- 出现明显能力退化 → 调低 DPO 的 beta（正则强度）、加 SFT 数据混合训练，或放弃 DPO。

---

## 三、建议的评测指标组合

| 层级 | 指标/方法 | 用途 |
|------|----------|------|
| 通用能力 | MMLU / 自有领域 benchmark | 防止 DPO 造成能力退化 |
| 偏好对齐 | MT-Bench、AlpacaEval、Arena-Hard | 衡量帮助性/风格 |
| 业务指标 | 真实任务的 GPT-4-as-judge 或人工 win rate | 最终业务相关性 |
| 安全 | 红队测试、安全 benchmark | 检查拒答边界 |
| 格式/风格 | 规则化检查（字段完整率、长度分布） | 针对性验证 |

---

## 四、决策 Checklist（可快速过一遍）

- [ ] 业务中有**主观偏好类**任务？（否则考虑 RLVR）
- [ ] SFT 模型存在**偏好型缺陷**（风格/格式/安全/冗余）而非能力缺陷？
- [ ] 能拿到**高质量偏好对数据**（差异明显、规模够、来源多样）？
- [ ] 预算能覆盖**数据标注 + 一轮 DPO 训练**？
- [ ] 已用**小规模实验**验证 DPO 有正收益且无显著退化？

若前四条满足、最后一条验证通过 → 值得做 DPO。

---

## 五、几个常见误区

1. **"SFT 效果不好就上 DPO"** —— 如果 SFT 本身数据质量差、覆盖不足，DPO 只会放大问题。先把 SFT 做到位。
2. **"DPO 能替代 SFT"** —— DPO 是在 SFT 基础上做偏好微调，不能跳过 SFT 直接做（除非用强基线初始化）。
3. **"DPO 数据越多越好"** —— 低质量偏好对（噪声大、margin 小）反而会损害模型，质量优先于数量。
4. **忽视能力退化监控** —— DPO 可能让模型在格式上更"乖"，但牺牲了多样性和部分推理能力，需要全程对比 benchmark。

---

**一句话总结**：先诊断 SFT 模型的缺陷是"能力型"还是"偏好型"；若是偏好型、有高质量偏好数据，就做一轮小规模 DPO 实验，用 win rate + 能力退化两个指标决定是否全量推进。
