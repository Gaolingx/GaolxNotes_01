# A100跑DS报错

### 🧑‍💻 User

如何解决a100*8运行deepseek v4flash不支持deepgemm和flashmla的问题，目前使用vllm/vllm-openai:deepseekv4-cu129该模型时，初始化失败，并出现以下错误：RuntimeError: Assertion error (.../deepgemm-src/csrc/apis/hyperconnection.hpp:56): Unsupported architecture，即使使用 --enforce-eager 参数，这种情况仍然会发生，因此它似乎与 DeepGEMM / HyperConnection 内核有关，而不是与 torch.compile 有关。

---

### 🤖 Assistant

## 问题根因分析

您遇到的错误 `hyperconnection.hpp:56: Unsupported architecture` 的根本原因是 **DeepGEMM 和 FlashMLA 均仅支持 SM90 (Hopper/H100/H800) 和 SM100 (Blackwell/B200) 架构**，而 A100 是 **SM80 (Ampere) 架构**，不在支持范围内。

根据 DeepGEMM 官方 README 的明确要求：

> - **NVIDIA SM90 or SM100 architecture GPU**

FlashMLA 同样：
> - **SM90 / SM100** (See the support matrix)

您使用 `--enforce-eager` 无效的原因是：该错误发生在 **内核调度/编译阶段**（DeepGEMM JIT 编译时检测到不支持的架构直接 assert 失败），与 `torch.compile` 无关。

具体触发路径是 vLLM 中的一个 **dispatch bug**：`mhc_pre_broadcast_tilelang` 无条件调用了 DeepGEMM 的 `tf32_hc_prenorm_gemm`，而其兄弟路径都做了 `is_deep_gemm_supported()` 守卫并回退到 tilelang fallback，唯独 broadcast 变体遗漏了守卫。此问题已有修复 PR [#50645](https://github.com/vllm-project/vllm/pull/50645)。

---

## 解决方案

### 方案一：使用社区分支（推荐，立即可用 ✅）

目前最成熟的两个分支：

**A. `haosdent/vllm` — `dsv4-flash-a100` 分支**

已验证在 8×A100 上运行 `DeepSeek-V4-Flash-0731`：
- 85.6 tok/s 单流 decode
- 170 tok/s 配合 DSpark spec decode
- ~1.2k tok/s 聚合吞吐
- 支持 1M `max_model_len`

```bash
git clone https://github.com/haosdent/vllm.git
cd vllm
git checkout dsv4-flash-a100
pip install -e .

# 启动命令（已验证可用）
vllm serve deepseek-ai/DeepSeek-V4-Flash-0731 \
  --trust-remote-code \
  --kv-cache-dtype fp8 \
  --block-size 256 \
  --tensor-parallel-size 8 \
  --no-enable-flashinfer-autotune \
  --tokenizer-mode deepseek_v4 \
  --tool-call-parser deepseek_v4 \
  --enable-auto-tool-choice \
  --reasoning-parser deepseek_v4
```

> ⚠️ 注意：0731 版本用 DSpark 替代了传统 MTP，如需 speculative decode 应使用：`--speculative-config '{"method":"dspark","num_speculative_tokens":4}'`

**B. `Lasimeri/vllm-dsv4-ampere` — 社区 Triton 回退分支**

另一个经过验证的社区分支，提供纯 Triton/PyTorch 回退方案。

### 方案二：手动 Patch 当前 vLLM（部分修复）

如果希望基于当前 vLLM main 分支修复，需要解决 **SM80 上的四个核心阻塞点**：

| # | 阻塞点 | 原因 | 修复思路 |
|---|--------|------|----------|
| 1 | `fp8e4nv` 转换 | SM80 的 Triton 不支持 `fp8e4nv` | 使用手动 e4m3 位操作（RNE 编码器 + bf16 LUT 解码器） |
| 2 | `flash_mla_sparse_fwd` | SM90a/SM100f only | 使用 Triton bf16 sparse-MLA 路径（社区分支已有） |
| 3 | DeepGEMM `fp8_einsum` + MegaMoE | Hopper+ | 使用 bf16 参考路径（`rocm_inv_rope_einsum` 已在 tree 中） |
| 4 | `wo_a` / `is_bmm` Marlin repack | 权重格式不兼容 | 为 `is_bmm` 层排除 Marlin repack |

建议直接使用方案一的社区分支，这些修复已经集成完毕。

### 临时规避（如果只是调试）

```bash
# 禁用 DeepGEMM（但单独使用通常还不够）
export VLLM_USE_DEEP_GEMM=0
```

仅设置这个环境变量不足以解决问题，因为还需要 Triton MLA sparse backend 和 FP8 转换原语——这些在当前 main 分支中均未就绪。
