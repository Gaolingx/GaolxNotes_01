# 内核兼容张量并行

### 🧑‍💻 User

liger kernel是否可以和tensoparallel一起使用？

---

### 🤖 Assistant

Yes, **Liger Kernel can absolutely be used together with Tensor Parallelism (TP)**. The Liger team explicitly designed their kernels to be compatible with common distributed training strategies (FSDP, TP, PP, etc.). However, you need to pay attention to how you shard the tensors – some fused kernels assume certain dimensions are unsharded. Below is a practical guide covering how to combine them and what pitfalls to avoid.

---

## 1. How Tensor Parallelism shards tensors

Tensor Parallelism typically splits linear layers along the **column** dimension (output features) and adds a final all‑reduce or splits along the **row** dimension (input features) after a partial sum. For example:

- Column‑parallel `Linear`: input is replicated, weight is split along output features → each device computes a partial output, then all‑gather/concatenate → final output.
- Row‑parallel `Linear`: input is split along input features, weight is split along input channels → each device computes partial sums, then all‑reduce.

Many layers like `RMSNorm`, `SwiGLU`, `RoPE` are applied **per token** and therefore trivially compatible with TP as long as the sharding is done along the correct axis (e.g., sequence dimension for RoPE, hidden dimension for RMSNorm before column‑parallel linear).

---

## 2. Liger kernels that work seamlessly with TP

Most Liger kernels are direct replacements for standard PyTorch ops that operate token‑wisely – they inherit the sharding behaviour of the underlying `nn.Module`. If the model’s TP sharding logic (e.g., Megatron‑style) works with PyTorch ops, the Liger equivalents will work too.

| Liger Kernel                  | Compatible with TP? | Notes                                                                        |
| ----------------------------- | ------------------- | ---------------------------------------------------------------------------- |
| `LigerRMSNorm`                | ✅ Yes             | Works per token; TP shards the hidden dimension → apply to local slice.      |
| `LigerSwiGLU`                 | ✅ Yes             | Element‑wise + linear fusion; respect the TP splitting of the feed‑forward.  |
| `LigerRoPE`                   | ✅ Yes             | Operates on rotary dims; sequence or head parallel only.                     |
| `LigerLayerNorm`              | ✅ Yes             | Same as RMSNorm.                                                             |
| `LigerCrossEntropyLoss`       | ⚠️ With care      | Loss needs **full logits** unless you all‑reduce logits first (see below).  |
| `LigerFusedLinearCrossEntropy`| ⚠️ With care      | **Requires unsharded logits along vocab**; works if TP doesn’t split vocab.  |

---

## 3. The main gotcha: `FusedLinearCrossEntropyLoss`

This kernel fuses the final linear projection, log‑softmax, and cross‑entropy loss into a single Triton kernel for speed. Softmax requires a global maximum and sum over **all logits**. If Tensor Parallelism splits the vocabulary dimension (e.g., column‑parallel output layer), each device only holds a chunk of the logits. Performing softmax locally gives incorrect gradients.

### Solutions

1. **Don’t shard the output logits.**
   Keep the final vocabulary projection unsharded (i.e., use pure data parallelism or sequence parallelism for that layer). This is the simplest approach.

2. **Use sequence parallelism (SP) instead of vocab‑sharding.**
   SP shards the sequence dimension across devices but keeps the full vocabulary on each device. In this layout, `FusedLinearCrossEntropyLoss` works perfectly because every device sees the complete set of logits for its batch chunk.

3. **All‑reduce logits before loss.**
   If you must use vocab‑parallel TP, gather the logits across devices, apply the fused loss on the full logits, then let autograd handle the backward all‑reduce automatically. This loses some memory savings but keeps the fused kernel’s speed.

```python
# Example: all-gather before fused loss in a vocab-parallel setup
logits = model.output_layer(hidden)          # [seq, vocab // tp_size]
full_logits = torch.cat(AllGather(logits), dim=-1)  # [seq, vocab]

loss = liger_kernel.transformers.LigerFusedLinearCrossEntropyLoss()(
    hidden,       # you may need to compute loss from hidden, but here it expects logits → use separate cross entropy
    target
)
# Or use the fused kernel that accepts hidden + weight; if weight is gathered, kernel will compute full logits.
# Some implementations accept a gathered weight tensor for fp32 compute.
```

Many Liger users combine TP with Sequence Parallelism (the 2D parallelism used in Megatron‑LM) precisely to avoid this issue.

---

## 4. Practical integration with Hugging Face Transformers + DeepSpeed/Megatron

- **Hugging Face x TP**: When you use `device_map="auto"` or `TensorParallel` with `transformers`, the model is sharded. You can safely apply Liger’s monkey‑patch (`liger_kernel.transformers.monkey_patch.apply_liger_kernel_to_llama()`) and the patched modules will obey the TP sharding.
- **Megatron‑LM style**: Liger kernels are designed to be plug‑and‑play inside Megatron’s layers. Replace `ColumnParallelLinear` + `RowParallelLinear` with Liger‑fused counterparts (if available) or keep the TP layout unchanged and just use Liger’s loss/norm/activation kernels without splitting the loss across vocab.
- **DeepSpeed TP (inference)**: Liger kernels are not specifically optimised for DeepSpeed inference, but they work if you manually apply the patch before TP splitting.

## Summary

- ✅ Most element‑wise / per‑token Liger kernels work out‑of‑the‑box with TP.
- ⚠️ Loss‑fused kernels (especially `FusedLinearCrossEntropyLoss`) need the **full vocabulary** to correctly compute softmax; use sequence‑parallel or avoid sharding the output layer.
- 💡 Combine TP with Sequence Parallelism to maximise compatibility and performance.
