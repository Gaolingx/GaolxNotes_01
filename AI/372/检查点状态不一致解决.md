# 检查点状态不一致解决

### 🧑‍💻 User

千卡大模型训练，分布式ckpt恢复检查点因为状态不一致报错是很常见的问题吗，怎么解决？

---

### 🤖 Assistant

这是个非常典型且“高频”的分布式训练痛点——尤其在千卡规模下。可以明确回答：**是的，非常常见，几乎是每个大模型团队从单机几百卡扩展到千卡、万卡过程中的必经之坑。**

根本原因在于：千卡训练通常采用多种并行策略（张量并行 TP、流水线并行 PP、数据并行 DP、序列并行等）的混合并行，且往往搭配 **异步保存（async checkpointing）** 来降低 I/O 阻塞。恢复时容易出现 **优化器状态、模型权重、学习率调度器状态、随机数状态（RNG state）、数据加载状态** 之间的不一致。

---

### 为什么千卡规模更容易出现状态不一致？

1. **多并行状态的耦合**
   - TP 切分的权重/优化器状态，恢复时必须与 TP group 拓扑一致。
   - PP 的 micro-batch 调度状态、通信缓冲区状态不易完整保存。
   - 如果训练中断后，重启时 DP 的 rank 顺序、world size 哪怕有微小变化（例如坏节点替换后重新分配 rank），就会导致旧 checkpoint 无法直接加载。

2. **异步 checkpoint 导致的“快照不同步”**
   - 主流的异步保存方案（如 Megatron 的 `async_save`、FSDP 的 `SHARDED_STATE_DICT` 配合独立进程）会让各 rank 的 checkpoint 文件在物理时间上有微小偏差。如果在保存过程中恰好发生故障，部分 rank 写入了新 state，部分还是旧 state，恢复时必然不一致。

3. **元数据与分片文件的不匹配**
   - 分布式 checkpoint 通常包含一个全局元数据文件（记录 world size、分片映射、step 等）和大量分片文件。若元数据与分片内容版本不一致（例如恢复了旧的元数据，但分片已被新保存覆盖），加载时会因 shape、dtype 或并行切分方式不匹配而报错。

4. **优化器状态与模型参数的错位**
   - Adam 优化器的 `exp_avg`、`exp_avg_sq` 等状态与参数一一对应。如果因并行配置变化导致参数在恢复后做了重分布（reshard），但优化器状态未相应调整，就会直接报 shape mismatch 或出现数值发散。

---

### 怎么解决？——分层级的工业级实践

以下是从**预防→检测→恢复**全流程的解决方案，按重要性排序：

#### 1. 使用支持“分布式弹性恢复”的训练框架
不要重复造轮子。千卡训练首选框架已内置解决大量一致性问题：

- **Megatron-LM**：原生支持 `--ckpt-format torch_dist`（分布式 checkpoint 格式），配合 `--use-dist-ckpt`，在保存时会按 TP/PP/DP 结构切分并记录各 rank 的 ownership，允许在相同拓扑或按规则重排后恢复。
- **DeepSpeed**：ZeRO 的 checkpoint 本身就是按照 DP 分片的，只要 DP world size 不变，恢复天然一致。其 `universal checkpoint` 功能更允许在 DP world size 变化时加载和重新分片。
- **PyTorch 原生 DTensor / FSDP**：从 PT 2.1 开始，FSDP 支持 `SHARDED_STATE_DICT` 和 `DTensor` 的分布式 checkpoint。搭配 `torch.distributed.checkpoint`，通过 `LoadPlanner` / `SavePlanner` 自动处理重分片和特性一致性，是目前趋势。

**策略**：优先让你的训练代码使用上述框架的**官方分布式 checkpoint 格式**，而非自己拼装文件。

#### 2. 严格对等化保存与恢复的 topology（拓扑一致性）
恢复时的并行拓扑必须与保存时**完全一致**或满足特定的可推导变换：

- **记录拓扑元数据**：在 checkpoint 中保存完整的并行配置信息（TP size、PP size、DP size、sequence_parallel 是否开启），以及各 rank 对应的 GPU 的 hostname/node_id。
- 恢复时**校验拓扑**：脚本应检测当前实际的 world_size、rank 布局、节点数是否与元数据匹配。不匹配则抛出明确错误，而不是静默加载错误数据。
- 对于无法完全一致的情况（如节点故障），使用框架支持的**重切分恢复**（resharding），如 Megatron 的 `--ckpt-fully-parallel-load` 并结合重排工具，或 DeepSpeed 的 `universal checkpoint`。

#### 3. 实现原子性的 checkpoint 保存（防撕裂）
异步保存时尤其要保证“要么全写，要么全不写”的原子性：

- **主流做法**：所有 rank 将数据先写入临时目录（如 `ckpt_step1000.tmp/`），全部写完后，由 rank 0（或外部协调进程）执行一次原子 `mv` 或 `rename` 将目录改为最终名。恢复脚本只加载已原子化完成的目录（没有 `.tmp` 后缀）。
- **Metadata 后写**：全局元数据文件在最后写入，并作为“成功保存”的标志。恢复时若发现元数据缺失或不完整，应退回到上一个完整 checkpoint。
- **硬件层面**：如果使用分布式文件系统（如 Lustre、GPFS），需确保文件系统同步（`fsync` 后写元数据）。框架如 Megatron 中的 `torch_dist` 格式会管理此过程。

#### 4. 恢复时进行一致性校验（Checksum / Verification）
- **显式校验**：保存时计算模型权重的 checksum（如 SHA256 前 N 个字节、或累加和 sum），写入元数据。恢复加载完成后，在所有 rank 上计算一遍 checksum 并做 all_reduce 对比。任何不一致立即终止，防止“挂羊头卖狗肉”的坏模型继续训练。
- **数据加载校验**：对于数据加载器状态（sequence offset, batch epoch 等），优先让 dataloader 支持 deterministic 恢复（例如基于全局 step 而非内部迭代器状态重建），并在恢复后校验 consumed_samples 或 token count 是否一致。

#### 5. 全量保存 vs 增量保存，并维护安全回退点
- **定期全量保存**：异步保存虽然快，但一致性风险更高。关键里程碑（如每 5000 step）做一次**同步的全量 checkpoint**，即所有 rank 阻塞直到保存完成。这个全量点就是极可靠的回退点。
- **维护有效链**：保留最近的 3-5 个完整 checkpoint，遇到不一致报错时，脚本自动回退到上一个验证过的 checkpoint。不要只有一个可覆盖的文件。

#### 6. 运维与流程规范
- **故障后重启检查**：手动或半自动流程中，不要直接 `resume`。先运行一个**离线校验脚本**：加载 checkpoint，在不初始化完整训练的情况下，测试性地执行一步 forward/backward（或用 hook 检查优化器状态），确认 loss 正常、无 NaN 后再正式重启。
- **固定 GPU 绑定**：千卡训练中，尽量固定“逻辑 rank”到“物理 GPU”的映射（通过 rank 文件或框架的 rank_mapping），避免因为节点重启造成 DP 的 rank 顺序打乱而导致参数加载错位。

---

### 一句话总结
千卡分布式 checkpoint 的状态不一致是**可以通过工程化手段系统避免的**。关键在于：**使用框架提供的分布式弹性 checkpoint 格式、保持拓扑一致、实现原子化保存、恢复后自动校验。** 做好这四点，状态不一致的问题可以下降一个数量级，即使发生也能“早发现、快回退”。

---

### 🧑‍💻 User

pytorch lightning/fabric有没有针对这类问题针对性处理？

---

### 🤖 Assistant

是的，**PyTorch Lightning 和其底层引擎 Fabric 在近两年的版本中，已经专门针对分布式 checkpoint 的易错点做了很多针对性的内置处理**。虽然它不像 Megatron-LM 那样原生封装 TP/PP，但对于大规模数据并行+FSDP/DeepSpeed 训练场景，它的处理已经相当成熟。

下面梳理它具体解决了哪些问题，以及需要注意的局限：

---

### 1. 原生支持“分布式弹性 checkpoint”（解决拓扑一致性问题）

这是最关键的一点。

- **Lightning 2.x + Fabric** 直接使用 PyTorch 官方的 `torch.distributed.checkpoint`（简称 DCP）来保存/加载模型，底层是 `DTensor` 的分片表示。
- 在 **FSDP** 或 **DeepSpeed** 策略下，checkpoint 不再是一个拼接好的完整 `state_dict`，而是保存每个 rank 负责的 **Sharded State Dict**。
- **恢复时支持 world size 变化**：Fabric 的 `load()` 内部会调用 `DCP` 的 `LoadPlanner`，自动将旧的切分方案映射到新的拓扑上（resharding）。也就是说：
  - 保存时是 256 张卡 DP=256，恢复时可以换成 128 张卡或 512 张卡。
  - 只要并行策略类型（FSDP/DeepSpeed）一样，就能自动重分布，**不再要求拓扑严格一致**。

这直接根治了“因为节点更换、扩缩容导致 rank 数量/布局变化而报错”的经典问题。

### 2. 原子性保存 & 异步快照一致性

Lightning 的 `ModelCheckpoint` 长久以来都遵循 **“先写临时文件，再原子 rename”** 的逻辑，防止因为保存中断而产生半个损坏的 checkpoint。

在分布式场景下：

- 所有 rank 都把自己的分片写入同一个 checkpoint 目录下的专用文件。
- 写完后由 `rank 0`（或由 `torch.distributed.checkpoint` 的内部机制）在全部 rank 完成写入后，再做一次统一的提交（写入元数据 `.metadata`）。
- 恢复脚本检查元数据是否存在且完整，否则回退到上一个合法 checkpoint。这基本解决了“部分 rank 写成功、部分 rank 写失败”的撕裂状态。

如果你使用 Fabric 的 `fabric.save()` / `fabric.load()`，这些原子性和一致性逻辑都是框架帮你做的，不需要手动借助 `.tmp` 目录。

### 3. 优化器状态、学习率调度器、随机数状态的全量保存

Lightning/Fabric 默认会把 **模型权重、优化器、学习率调度器、TrainingState（epoch/step 等）** 全部打包保存，而不是只保存模型。

- 恢复时通过 `fabric.load()` 自行恢复全部组件的状态，保证训练续点后优化器动量、学习率衰减曲线等完全连续。
- 随机数状态（RNG state）则需要你显式地在每个 rank 保存/恢复，Lightning 的 `seed_everything` 并不自动包含这部分。但你可以把 `torch.get_rng_state()` 等放在 `state` 字典里一并处理，Fabric 不会丢失它们。

### 4. 内置的“加载后验证”能力（Incremental 但不强制）

Lightning 没有在加载后强制计算 checksum，但提供了一些辅助：

- 有一个 `validate_checkpoint()` 方法（某些版本中）可以检查 checkpoint 的结构是否和当前模型兼容。
- 你可以在 `on_load_checkpoint()` 回调中轻松注入自定义的校验逻辑（比如计算权重的全秩和，然后做 `all_reduce` 比较），框架会在所有 rank 上执行该回调，确保同步。
- `Fabric` 的调试模式（`fabric = Fabric(..., loggers=..., ...)` ）可以在恢复后立即跑一个梯度检验或损失检查，不会有额外负担。

---

### 局限 & 需要注意的“千卡深坑”

尽管 Lightning/Fabric 已经处理了很多通用问题，但在**千卡、混合 TP/PP 的高级并行**场景下，仍有一些它不擅长的地方：

1. **张量并行（TP）/ 流水线并行（PP）支持有限**
   Fabric 的策略目前主要覆盖 DDP、FSDP、DeepSpeed（ZeRO），不原生构建 Transformer 层的 MP（如 Megatron 的 Tensor Parallel）。如果你的千卡训练使用了手写的 TP（例如用 `torch.distributed.tensor.parallel` 或 Megatron-style），Fabric 无法自动管理这些切分状态。这时 checkpoint 的不一致风险依然存在，需要你按 Megatron 的方式额外处理。

2. **数据加载器状态的确定性恢复**
   Fabric 保存的是“训练步骤数、epoch”等宏观状态，但**没有保存 DataLoader 的内部迭代偏移量**。如果你在恢复时希望精确接续被打断的 `next(iterator)`，就需要自己包装一个可恢复的 DataLoader（例如基于全局 step 重建数据顺序，而不是依赖内部状态）。否则同一 batch 可能被重复学习或跳过，虽然不报错，但训练会微妙地偏移。

3. **异步 I/O 下的严格校验**
   DCP 的异步保存虽然快，但物理磁盘上可能存在缓存。如果你使用自定义的异步 save 逻辑（绕过 Fabric 的默认保存），仍然可能遇到不一致。建议直接使用 `fabric.save()`，它的实现已经考虑了各 rank 的同步点。

4. **没有自动的“安全回退链”**
   Lightning 会保留 `last.ckpt` 或按 `every_n_train_steps` 生成的多个文件，但**不会自动在检测到损坏时回退**。你需要自己编写一个轻量脚本：加载 checkpoint → 跑一步 dummy forward → 检查 loss 正常，再正式提交训练任务。这依然是工业界千卡训练的常规操作。

---

### 实践建议（结合 Lightning/Fabric）

如果你用 Lightning/Fabric 管理千卡 FSDP/DeepSpeed 训练，可以按下面的方式最大程度避免状态不一致：

- **启用分布式 checkpoint 格式**（例如 `Fabric(strategy="fsdp", ...)` 时设置 `state_dict_type="sharded"`），自动获得弹性恢复能力。
- **确保只使用 `fabric.save()`/`fabric.load()`**，不要混用自己写的 `torch.save`/`load`。
- **在 `on_load_checkpoint()` 回调中增加校验**：计算权重前 N 个元素的 CRC 并 all_reduce，任何不一致直接抛异常。
- **隔一定步数做一次同步全量保存**（`fabric.barrier()` 后调用 `fabric.save()`），作为稳定锚点。
- **恢复后务必跑一两个 step 的“试跑”**：用很小的数据验证 loss 无 NaN、优化器 step 正确，再正式开始记录日志。

总的来说，**Lightning/Fabric 已经把分布式 checkpoint 的不一致风险降低了一个量级，尤其解决了拓扑变化和原子保存这两大难题**。但对于极致的千卡级自定义并行，你仍然需要结合底层库（Megatron/DeepSpeed）的特定机制，并在流程上增加验证环节。
