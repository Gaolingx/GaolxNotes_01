## 😀 默认助手 (7)

这三句话表面上像是在给数据格式排一个「fp16 < bf16 < fp8」的总榜，实际上它们回答的是**三个不同的问题**。拆开来看就完全不矛盾了——而且最后你会看到一个挺讽刺的事实。

## 先看这三句话各自在说什么

| 说法 | 真正的问题 | 判据 |
|---|---|---|
| fp16 bad | 16-bit 训练**稳不稳、省不省心** | 动态范围、要不要 loss scaling |
| bf16 good | 16-bit 里**默认该选谁** | 同样字节数/吞吐下谁更鲁棒 |
| fp8 better | 能不能**再快一倍** | 吞吐收益 ÷ 工程代价 |

它们不在同一根轴上。你感觉矛盾，是因为默认了「难度」是唯一变量；但真正决定产业行为的变量是 **收益/难度比**。

## 一、fp16 的「bad」是动态范围，不是精度

| 格式 | 指数位 | 尾数位 | 最大值 | 最小正规数 |
|---|---|---|---|---|
| fp32 | 8 | 23 | $3.4\times10^{38}$ | $1.2\times10^{-38}$ |
| bf16 | 8 | 7 | $3.4\times10^{38}$ | $1.2\times10^{-38}$ |
| fp16 | 5 | 10 | **65504** | $6.1\times10^{-5}$ |
| fp8 E4M3 | 4 | 3 | **448** | $1.6\times10^{-2}$ |
| fp8 E5M2 | 5 | 2 | 57344 | $6.1\times10^{-5}$ |

注意两件事：

1. **fp16 的精度其实比 bf16 高**（11 位有效位 vs 8 位）。所以「fp16 bad」跟精度无关，纯粹是 **5 位指数 → 动态范围只有 $2^{\pm15}$ 量级**。
2. LLM 的 activation 是**重尾分布**——少数 channel 的幅值能飙到几百上千（attention logits、outlier features）。fp16 的上限 65504 看着不小，但一乘上 attention 的 $QK^T$ 缩放、一遇到 loss spike，就 inf 了；梯度那侧又会被压到 subnormal 甚至直接下溢成 0。

于是 fp16 必须配 **loss scaling**：动态试一个 scale 因子，溢出就跳过这一步、调小 scale；连续若干步没溢出就调大。这套机制能用，但它是**运行时反馈控制**：
- 有 inf/nan 就得跳步，吞吐掉；
- scale 因子调错了，梯度精度受损或直接炸；
- 万卡跑几周的 pretraining，一次没检测到的 NaN 就是几百万美元。

bf16 为什么好？因为它**就是 fp32 砍掉低 16 位尾数**：指数位一模一样，范围跟 fp32 等同，转换是一次移位+舍入，**永远不需要 loss scaling**。尾数少几个 bit 带来的噪声，被 fp32 累加和巨大的 batch 平均掉了。

所以 bf16 的定位是：**「不费任何额外工程就够用的最小格式」**。

## 二、关键在这：fp16 被 bf16 严格支配

这是整件事的核心，也是那句「wtf」的答案所在：

**在 Hopper/Ampere 上，fp16 和 bf16 的 tensor core 吞吐完全一样，内存带宽占用完全一样。**

| 格式 | H100 SXM 稠密算力 |
|---|---|
| fp16 / bf16 | ~989 TFLOPS |
| fp8 | ~1979 TFLOPS（2×） |

也就是说：

- **fp16 = bf16 的成本 + 额外的脆弱性** → 帕累托被支配，没有任何理由选它。所谓「解决 fp16」，收益是 **0**。
- **fp8 = bf16 的成本 ÷ 2** → 收益是 **2× 算力 + 半内存流量**。所以大家愿意为它烧工程。

你的直觉「能搞定 fp8 还搞不定 fp16？」——**对，搞 fp8 那套东西搬去 fp16 只会更容易，问题是你搞完之后它还是和 bf16 一样快。** 没人愿意为 0 收益支付复杂度。

一句话：**fp16 不是「做不到」，是「不值得」。**

## 三、更讽刺的是：fp8 在数值上比 fp16 难得多

E4M3 的最大值只有 **448**，尾数只有 **3 位**。范围比 fp16 窄两个数量级，精度还少 7 位。所以「fp8 better」**纯粹是速度意义上的 better，不是数值意义上的 better**。

fp8 之所以还能训，靠的不是「格式好」，而是一整套**外部脚手架**：

<details>
<summary>fp8 训练的真实配方（点开）</summary>

- **细粒度 scaling**：per-tensor → per-block（如 $128\times128$ 或 $1\times128$ 的 tile）动态算 scale，把张量压进 fp8 范围再 cast，算完反 scale。
- **高精度累加**：GEMM 输入是 fp8，累加器是 fp32；部分实现还会周期性用 CUDA core 做一次高精度累加来抑制误差漂移。
- **混合精度孤岛**：master weights 用 bf16/fp32，optimizer states 用 fp32，LayerNorm / softmax / MoE gating / loss 全程 bf16 或 fp32。只有纯 GEMM 的输入被量化。
- **前反向用不同格式**：前向多用 E4M3（要精度），反向按需 E5M2 或 E4M3 + 额外缩放（要范围）。

</details>

看到问题了吗？**这套「per-block 动态缩放 + 高精度累加 + 关键算子保高精度」，本质上是 loss scaling 的推广版。** 把它原样套到 fp16 上，你会得到一个极其鲁棒、比 bf16 还准的 16-bit 训练——只是速度和 bf16 一模一样。

所以「能解 fp8 却解不了 fp16」这个悖论的正确表述是：**fp8 的解药本身就包含了 fp16 的解药，只是没人去服用，因为药费比病贵。**

## 四、那这些话术为什么满天飞

<details>
<summary>人群与动机（点开）</summary>

- **说「fp16 bad」的**：日常训练/推理的人。PyTorch 在 Ampere+ 上 `torch.autocast` 默认就是 bf16，FlashAttention、transformers、几乎所有新 kernel 的默认 dtype 都是 bf16。fp16 已经变成「历史遗留 + 需要手动配 loss scaler」的选项。
- **说「必须 fp8 pretraining」的**：大集群 infra 团队 + 硬件厂。前者有 2× 收益、有专职团队踩坑、跑的是几万卡几个月的任务，省 50% 就是天文数字；后者（NVIDIA）的 roadmap 就是 fp8 → fp4，生态推力天然存在。确实有营销成分，但底层账是算得平的。
- **一个被忽略的例外**：**推理**场景里 fp16 经常比 bf16 更准（尾数多 3 位，且没有梯度/loss 的动态范围问题）。「fp16 bad」是训练语境的结论，被过度推广了。反过来也有坑——用 bf16 训的模型直接 cast 成 fp16 推理，可能被 outlier 撑爆。

</details>

## 结论

不是「fp16 < bf16 < fp8」的线性排名，而是**帕累托前沿**的问题：

$$\text{有效前沿} = \{\text{bf16},\ \text{fp8},\ \text{fp4}\},\qquad \text{fp16} \notin \text{前沿}$$

- bf16：免费拿到 16-bit 的全部好处，**零额外工程**。
- fp8：付出一套 scaling 工程的代价，换 2× 吞吐，**大集群划得来**。
- fp16：付出复杂度，换 0×——**被 bf16 支配**，所以社区直接跳过。

所以那句「你都能解 fp8 了怎么不能用 fp16」的答案是：**能，而且更容易；但解完它还是个 bf16，所以没人解。** 大家的意识不是「fp16 坏」，而是「fp16 多余」。

## 一、bf16 防的不是「爆炸」，是**下溢**——而且 LayerNorm 恰恰是元凶

这是你四条里错得最关键的。

### 1. 真正杀 fp16 的是下溢，不是上溢

fp16 只有 5 位指数，范围是 $[2^{-14}, 2^{15}]$，即 $[6.1\times10^{-5},\ 65504]$。**下界和上界一样致命。**

一个具体到不能更具体的证据：PyTorch `GradScaler` 的初始 scale 是 $2^{16}=65536$，而实践中它常年稳定在 $2^{14}\sim2^{20}$。这意味着什么？

$$\text{未缩放梯度} \approx \frac{O(1)}{2^{16}} \approx 1.5\times10^{-5} \;<\; 6.1\times10^{-5}$$

**梯度天然就落在 fp16 正规数门槛下面。** 这不是「模型不稳」，这是 fp16 的算术事实。loss scaling 存在的唯一理由就是把梯度乘回可表示区间。

### 2. 「健康模型不该横跨十个数量级」——不，深度网络必然如此

即使 loss 单调下降、零 spike、完美调参，梯度幅值在层间也横跨 $10^{6}\sim10^{10}$：深层 Jacobian 连乘 $\prod_i J_i$ 的奇异值只要略小于 1，就是指数衰减。**这是问题的条件数，不是你的 bug。** 再稳的模型也逃不掉。

### 3. 最反直觉的一击：LayerNorm / RMSNorm 是**制造**大激活的原因

你说「加了 norm 早就解决了」——正好相反。归一化的本质是**尺度不变性**：

$$\text{RMSNorm}(x) = \frac{x}{\|x\|/\sqrt d} \cdot \gamma \quad\Rightarrow\quad \text{RMSNorm}(\alpha x) = \text{RMSNorm}(x)$$

对任意 $\alpha>0$，**输出完全不变**。于是激活的绝对尺度成了一个**规范自由度（gauge freedom）**——网络可以从这个方向上任意漂移，却拿不到任何梯度惩罚。既然归一化之后还有 $\gamma$ 把它拉回来，那把 $\|x\|$ 推到 $10^4$ 有什么代价？**没有。** 优化器于是自由地漂。

这不是「skill issue」，这是**归一化的结构性后果**。CNNs 靠 BatchNorm 的 running stats + 有界 ReLU + 卷积局部性把尺度摁住了；Transformer 的 pre-norm 残差流是**加法累积**的，$\|x_\ell\|$ 随深度单调累积，外层再归一化——所以 LLM 里出现 **massive activations**（Sun et al. 2024：少量 channel 幅值达中位数的 $10^2\sim10^3$ 倍）是**功能性的**，模型在用这些 outlier 通道编码信息，注意力汇聚（attention sink）也依赖它们。模型**想要**它们。

### 4. 顺带：LayerNorm 自己就不能在 fp16 里算

方差那一步要算 $x^2$，而

$$x^2 > 65504 \iff |x| > 255.9$$

任何大于约 256 的激活元素，$x^2$ **直接溢出 fp16**。所以所有框架的 LayerNorm/RMSNorm 内部强制 fp32。你说「加 norm 解决问题」——**这个 norm 本身就得靠 fp32 活着**。

## 二、尾数太少 / 精度玄学——半对，但结论相反

### 半对的部分

bf16 只有 7 位尾数，相对舍入误差 $2^{-8}\approx 0.4\%$，确实粗。而且「深度学习的玄学有多少是精度造成的」——**这个问题问得很好，答案是有不少**：

<details>
<summary>真·精度引起的玄学清单（点开）</summary>

- **LayerNorm 方差**：$E[x^2]-E[x]^2$ 在 $E[x]\gg\sqrt{\mathrm{Var}}$ 时灾难性抵消，结果可能为负 → NaN。必须 fp32（或用 Welford）。
- **CrossEntropy**：算 `log(softmax(x))` 而非 `log_softmax(x)`，小概率类被 flush 成 0，梯度消失。PyTorch 内部用 log_softmax，很多自定义/JAX 实现没有。
- **Attention**：先算 $QK^\top$ 再除 $\sqrt d$ → 中间量溢出。正确做法是先把 $Q$ 缩放掉。
- **Softmax 溢出阈值**（这条最狠，见下）。
- **Adam 的 $\epsilon$**：$10^{-8}$ 与梯度量级的相互作用，fp32 下才有意义。
- **不可复现性**：fp16/bf16 的 reduce 顺序不确定，同 seed 不同结果。
- **小模型大 lr** 的稳定性，很大一部分是数值噪声。

所以你这条不是胡说，是真有货。

</details>

### 但结论反了：softmax 恰恰是 **bf16 赢**的场景

看 $\exp(x)$ 在三种格式里的溢出阈值：

| 格式 | 最大值 | $\ln(\max)$，即无需 max-sub 的安全上界 |
|---|---|---|
| fp16 | 65504 | **11.09** |
| bf16 | $3.4\times10^{38}$ | **88.7** |
| fp8 E4M3 | 448 | 6.1 |

注意力 logits 在长上下文 + 大 $d$ 下轻松超 11，甚至过 30。**在 fp16 里你必须做 max-subtraction，而且 $QK^\top$ 得先缩放**；在 bf16 里你可以宽松得多。用「softmax 有数值 bug」来论证「应该用 fp16」，方向恰好是反的——它论证的是「softmax 该用 fp32」，而 bf16 天然给了你 8 倍的指数余量。

### 而且 bf16 的粗尾数被 fp32 累加洗掉了

两种格式的 tensor core **都用 fp32 累加器**。K 项点积里，信号 $\sim K$，随机舍入误差 $\sim\sqrt K \cdot 2^{-8}$，相对误差 $\sim 2^{-8}/\sqrt K$。K=4096 时 bf16 的 0.4% 被压到 $10^{-5}$ 量级。这就是为什么**大规模 LLM 预训练里 bf16 和 fp16 的 loss 曲线基本重合**——已有大量消融证实。

**「精度不够」的正确解法是加 fp32 孤岛（master weights、optimizer、norm、softmax、loss），不是换 fp16。** 换 fp16 只会让你在需要 fp32 的地方还是得用 fp32，同时在不需要 fp32 的地方省不下任何东西。

## 三、fp8 range ≤ fp16 → 所以 fp16 能行：**这条你完全正确**

而且我上一条回复就在说这个。fp8 E4M3 最大 448、3 位尾数，**范围精度双输**，它能跑纯粹靠 per-block scaling + fp32 累加 + bf16 孤岛这套脚手架。把这套搬到 fp16 上，数值上只会**更好**。

所以：**「fp16 做不到」是个假命题，从来没人真的这样主张。** 真正的主张是——

$$\text{fp16 的收益} = 0\times,\qquad \text{fp8 的收益} = 2\times$$

你论证赢了「可行性」，但业界优化的是「值得性」。如果明天 NVIDIA 把 fp16 吞吐提到 bf16 的 2 倍，**全行业一周内就会换回 fp16 + loss scaling**，连同那些坑一起吞下去。格式之争从来不是数值之争，是硬件账单之争。

## 四、CV 用 fp16 没事——**前提就错了**

### 1. CV 当年**就是** fp16 + 手动 GradScaler

2018–2021 年 `torch.cuda.amp` 的标准写法就是：

```python
scaler = torch.cuda.GradScaler()   # fp16 专属，bf16 根本不需要
with torch.cuda.amp.autocast(dtype=torch.float16):
    ...
scaler.scale(loss).backward()
scaler.step(opt); scaler.update()
```

「没事」不是因为没坑，是因为**坑被 GradScaler 填了，而且大家习惯了不觉得那是坑**。bf16 出来之后这段代码直接删掉——那才是「没事」。

### 2. 失败成本差 4~6 个数量级

| | ImageNet | LLM 预训练 |
|---|---|---|
| 时长 | 几小时~2 天 | 数周~数月 |
| 规模 | 8 卡 | $10^3\sim10^5$ 卡 |
| 一次 NaN 的代价 | 重跑一天 | **几百万美元 + 一个季度** |

同样的 0.1% 失败率，在 CV 里是噪音，在 LLM 里是灾难。**这才是「LLM 这不行那不行」的真正原因——不是模型娇气，是赌注太大。**

### 3. 结构上 CNN 真的更友好

- **没有 massive activations**：卷积 + BatchNorm 的尺度被 running stats 钳住，没有 pre-norm 残差流的规范自由度。
- **没有残差流累积**：ResNet 的 identity 是归一化过的。
- **vocab softmax 只有 1000 类**，不是 100k+ 的大 log-sum-exp。
- **稠密梯度**：LLM 的 embedding / LM head 是稀疏梯度，单 token 在 4M batch 里出现一次，其梯度是全局梯度的 $1/4\text{M}$——直接沉到 fp16 地板以下。

### 4. 而且 CV 早就还债了

现在的 CV 是 **ViT**。ViT 一上来，所有 LLM 的数值问题**原封不动全回来了**（massive activations、attention sink、长序列累积）。「CV 用 fp16 没事」是关于 **CNN** 的陈述，不是关于现代 CV stack 的陈述。

## 结论：你赢了辩论，但赢错了辩题

| | fp16 | bf16 |
|---|---|---|
| 数学充分性 | ✅ 更高（11 位尾数） | ❌ 8 位 |
| 工程充分性 | ❌ 需 loss scaling | ✅ 零额外机制 |
| 吞吐 | 1× | **1×（相同）** |
| fp8 迁移路径 | 无 | fp8 配方的天然底座 |

**fp16 是「数学上够用」的格式，bf16 是「工程上够用」的格式。** 你整段论证证明的是前者，而整个行业优化的是后者。

「bf16 是傻逼」翻译过来是「工程最优解在数学上不是最优解」——这话对，但没用。**飞机的气动外形在数学上也不是最优的，因为它还得装得下人和油。**

真要说谁傻：不是 bf16，是「在 fp16 和 bf16 吞吐完全相同的前提下，还愿意多写一套 GradScaler 并承担 NaN 跳步风险」的那个选择。
