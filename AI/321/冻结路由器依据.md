## 一、核心依据：router drift 会破坏 off-policy 修正

PPO/GRPO 这类 RL 依赖重要性采样（IS）来修正 off-policy：

$$ w_{i,t}(\theta) = \frac{\pi_\theta(y_{i,t}\mid x, y_{i,\lt t})}{\pi_{\theta_{\text{old}}}(y_{i,t}\mid x, y_{i,\lt t})} = \exp\big(\log\pi_\theta - \log\pi_{\theta_{\text{old}}}\big) $$

这个式子的前提是：分子分母是**同一套计算图**，参数只是小幅变化，所以比值接近 1。

但 MoE 的 token 到专家的映射是**离散的**：

$$ g_t = \mathrm{Softmax}\big(\mathrm{TopK}(W_r\, h_t)\big) $$

只要 $W_r$ 一动，TopK 选中的专家集合就可能整体翻转。此时 $\log\pi_\theta$ 与 $\log\pi_{\theta_{\text{old}}}$ 的差里，混进了"换了完全不同的一组专家"带来的**跳变**，而不是平滑扰动。于是：

- $w_{i,t}$ 被顶到很大 → 大量 token 触发 clipping → 梯度信号被 clip 主导（GSPO 论文 Fig.2 专门统计了被 clip 的 token 比例）；
- 结合 RLVR 的**序列级奖励**却配 **token 级比值**，方差被进一步放大；
- 最终表现为 **reward collapse / 训练发散**（突发骤降 + KL 与梯度范数异常）。

GSPO 论文（Qwen，`arXiv:2507.18071` §5.3）给了一个非常硬的量化证据：在 48 层的 `Qwen3-30B-A3B-Base` 上，**每做一次 RL 梯度更新，同一个 rollout 样本约有 10% 的激活专家与 old policy 不同**。他们原话是：这种 expert-activation volatility "can prevent RL training from converging properly"。

而冻结 router（或做 routing replay）的作用就是——**让 token→专家映射在 $\pi_{\theta_{\text{old}}}$ 和 $\pi_\theta$ 之间保持一致**，从结构上消除 router drift，使 IS 比值重新只反映专家权重的平滑变化，trust region 假设重新成立。

<details>
<summary><b>二、三种"冻结/对齐"做法的实测对比（RSPO 论文附录 D，含失败细节）</b></summary>

微软的 RSPO 论文 *Towards Stable and Effective RL for Mixture-of-Experts*（`arXiv:2510.23027`）把 router 不稳定性作为主线，并**直接做了"冻结 router"的消融**，在附录 D 对比了三种"显式约束 router 动态"的方案（Qwen2.5-MoE / Countdown 小规模诊断）：

| 方案 | 做法 | 结果 |
|---|---|---|
| **(i) Freezing the router** | 整个 RL 期间 $\phi$ 固定，只更新其余参数 | 按构造消除 drift；但**假设预训练路由已对齐 RL 目标**，实际"reduces the model's ability to adapt expert allocation to the evolving policy updates"，**限制性能上限** |
| **(ii) Logit replay** | 更新时用缓存的 old router logits 计算概率 | 专家选择与权重都对齐 old policy；但**梯度传不到 router**，等于禁止 router 学习 |
| **(iii) Index replay** | 只缓存 old TopK 专家索引，强制当前策略路由到这些 index | 保留 old 路由支撑、允许有限梯度，但**限制探索**，仍可能不稳定 |

论文结论："none of the rigid approaches consistently improves stability or final performance"——即冻结能稳，但**不是最优**；他们还指出 replay 类方法要缓存全层全 token 的路由轨迹，显存/通信开销可观。他们转而提出软方案 RSPO：用 old 激活专家算一个 per-token "router-shift ratio"，加 stop-gradient 与下界，再对 IS 比值做重标定。

**这段消融正是你说的那个 trick 的直接出处**：冻结确实是业界早就在用的"刚性稳定器"，论文把它当作 baseline 来批判。
</details>

<details>
<summary><b>三、为什么说"冻结"其实是"稳"而不是"优"（边界条件）</b></summary>

三个方向可以印证它不是必须，而且各有代价：

1. **GSPO 的立场**：它用**序列级** likelihood ratio $s_i(\theta)=\big(\pi_\theta(y_i|x)/\pi_{\theta_{\text{old}}}(y_i|x)\big)^{1/|y_i|}$，对单个 token 的似然不敏感。因为 MoE "always maintains its language modeling capability"，序列似然不会剧烈波动，所以能**在不用 Routing Replay 的前提下**稳定收敛。原文明确说这"obviates the need for complex workarounds like Routing Replay"。
2. **RSPO 的立场**：用软重标定保留 router 自适应性，效果优于硬冻结。
3. **反向证据**：MoE-GRPO（`arXiv:2603.24984`, CVPR 2026）反过来把**专家选择建模成序列决策、用 GRPO 去训练 router**，还专门加 modality-aware router guidance 来保稳定。说明 router 是"可以训的"，只是需要额外稳定机制。

所以准确表述是：**冻结 router 是解决 router-drift 导致发散的一种充分但偏保守的手段**；它能稳，但会牺牲"让专家分配随 RL 目标演化"的能力。
</details>

<details>
<summary><b>四、另外两条常被引用的支撑理由</b></summary>

- **防止路由塌缩 / 负载失衡**：预训练靠 auxiliary load-balancing loss 或 DeepSeek-V3 那种 aux-loss-free 的 bias 项来维持负载均衡。RL 目标是任务奖励，**不含负载均衡项**，且奖励信号噪声大，梯度容易把大量 token 推到少数专家（hot expert 迁移）。有系统工作如 ReLibra（`arXiv:2605.08639`）指出 RL 下 "hot experts can shift frequently across micro-batches"，冻结路由可避免把预训练辛苦建立的路由结构冲垮。
- **参考策略/KL 一致性**：KL 正则和 reference model 都是围绕 SFT 策略定义的。若路由在训练中漂移，KL 惩罚衡量的对象也随之漂移，惩罚项的意义被削弱；冻结路由让"参考分布"在路由层面保持稳定。
- **离散动作空间过大**：把路由当作策略的一部分，等价于一个组合型 bandit，动作空间随层数×TopK 爆炸，用序列级稀疏奖励去优化它本就样本效率极低。

</details>

## 五、实务建议（如果你想用这个 trick）

1. **想要最低风险的稳定**：可以冻结 router，同时**继续训练 expert 的 MLP 权重**（"冻结路由、不冻结专家"是常见折中，模型仍能适配）。
2. **更现代的替代**：优先考虑从算法层面消除敏感度——GSPO 的序列级比值，或 RSPO 的 router-shift 软重标定；这样既稳又保留自适应。
3. **若坚持训练 router**：务必保留负载均衡机制（aux loss 或 bias 校正），并监控上面那两个诊断量：**expert-activation 翻转率**与**被 clip 的 token 比例**，任一异常上升基本就是崩溃前兆。
4. **不要迷信"必须冻结"**：它是经验性稳定器，效果依模型/任务而定，RSPO 的消融已说明硬冻结会压性能上限。

**关键文献**：GSPO（Qwen，`arXiv:2507.18071`，给出 10% 专家翻转的量化证据 + Routing Replay 讨论）、RSPO（MSRA，`arXiv:2510.23027`，直接消融"冻结 router"）、MoE-GRPO（`arXiv:2603.24984`，反例：可训 router）。

## 一、先分清：RL 冻结 router 的理由，本质不是"bs 小"

上一轮说过，RL 冻结 router 的根因是**重要性采样（IS）比值的合法性**：

$$ w_{i,t}=\exp\big(\log\pi_\theta-\log\pi_{\theta_{\text{old}}}\big) $$

当 TopK 专家集合在 old/new 之间翻转时，这个比值里混进了"换了专家"的离散跳变，导致方差爆炸。这跟 batch size 是**两个独立的失效通道**。RL 的 micro-batch 小只是**加剧**了稳定性问题（见下文 ForeMoE），不是冻结的理由本身。

**所以"SFT 不冻结是因为 bs 大"这个因果是错位的。** 真正的原因是：

> **SFT / midtrain 根本没有 IS 比值。** 它是标准的交叉熵：每一 step 都是对固定标签做一次全新的前向/反向，$\log\pi_\theta$ 不需要和任何 old policy 对齐。路由翻转在这里只是"这一步更新了另一批专家"，只要负载均衡，就没有结构性危害。

因此**"SFT/midtrain 默认不冻结 router"是对的，而且是绝大多数 recipe 的现状**——DeepSeek/R1 的 midtrain、Qwen 的 SFT 阶段，router 都是参与的。只有在你做**小数据 + 跨域适应（PEFT / 领域微调）**时，才会出于"保留预训练专家分工、防遗忘"的目的去冻 router，那是另一个动机，不是稳定性。

## 二、那"bs 够大"到底有没有道理？——有，但它是二阶因素

<details>
<summary><b>展开：SFT/midtrain 里 router 的真实风险，以及 batch size 作用在哪一环</b></summary>

SFT 阶段 router 的失效模式和大 batch 的收益，主要在这三条通道：

**1. 负载均衡统计的方差（batch size 在这里最直接）**

无论用 aux load-balancing loss 还是 DeepSeek-V3 那种 aux-loss-free 的 bias 校正，均衡信号都来自当前窗口内每个专家的 token 占比：

$$ \hat f_i=\frac{1}{N}\sum_{t=1}^{N}\mathbb{1}\!\left[i\in\text{TopK}(x_t)\right],\qquad \mathrm{Var}(\hat f_i)\propto \frac{f_i(1-f_i)}{N} $$

**噪声 $\propto 1/\sqrt{N}$，$N$ 是均衡统计窗口内的 token 数。** $N$ 小的时候，均衡项本身就是一个高方差估计，bias 校正会来回过冲，router 在两个专家之间反复横跳。

这一条有很硬的实证。ForeMoE（`arXiv:2606.11867`）在 RL post-training 里观察到：**"step-level load 是稳的，但 micro-step 处理的极小 batch 会造成 severe, high-frequency load fluctuations"**——这正说明瓶颈是"均衡统计窗口太小"。

**2. 路由波动（routing fluctuation）**

StableMoE（ACL 2022，`arXiv:2204.08396`）把这个问题命名得很清楚：同一个输入的目标专家会随训练变化，但推理时只激活一个，所以"same input updates different experts but only one is finally used"，直接**损害样本效率**。他们的解法正是"先学一个均衡且内聚的路由，再 freeze 住"。小 batch 的高方差梯度会让 TopK 频繁翻转，放大这个现象；大 token-batch 平滑梯度，减少路由抖动。

**3. 数据覆盖度**

大 global batch（配合好的数据混合）在一个 step 内看到更多域的 token，router 学到的是全局均衡的路由；小 batch 且数据同质时，router 会塌到当前 mini-batch 的主导专家上。

</details>

## 三、为什么"bs 够大"仍不是正确答案

<details>
<summary><b>展开：batch size 的三个"不够"，以及真正该调的旋钮</b></summary>

**（1）这里的 "bs" 是 token 数，而且要看均衡统计的窗口，不是序列数。** 关键是 `tokens per balancing window`。如果你的实现是**逐 micro-batch** 算 aux loss，那么 gradient accumulation 把 global batch 撑大**并不解决**每个 micro-batch 内的负载波动——你得上全局 batch 级均衡，或者用 bias 型均衡。很多人"把 global batch 提到 4M token 但 router 还是抖"，就是踩了这个坑。

**（2）大 batch 不是充分条件——甚至在某些场景是反的。** SFT 的失败往往来自"数据太窄/太少"，而不是 batch 太小：单域几千条数据，batch 再大 router 也会塌。反过来，R&Q（`arXiv:2602.19938`）在推理侧发现 "load imbalance persists and **worsens with larger batch sizes**"——大 batch 会把负载偏斜暴露得更充分。训练侧虽然不完全同理，但足以说明 batch size 不是单调的万能药。

**（3）真正"承重"的旋钮是这几个，batch 只是配角：**

| 旋钮 | 作用 |
|---|---|
| **保留均衡目标**（aux loss / bias 校正） | 没有它，SFT 一定漂向 hot expert。但注意 aux loss 本身引入噪声梯度（COLM 2026 那篇 `arXiv:2604.23036` 明确吐槽 SFT 的 router "fragile"，DenseMixer/ESFT 的 aux loss "introduce noisy gradients that often degrade performance"） |
| **aux-loss-free bias 均衡**（DeepSeek-V3 风格） | 把均衡从梯度里剥离，绕开"噪声梯度"问题 |
| **router 单独的小 LR / router z-loss** | 直接抑制路由抖动与 logit 爆炸 |
| **数据多样性 / 混合** | 比 batch size 更根本 |
| **Expert-Choice Routing**（`arXiv:2202.09368`） | 让专家选 token，**按构造**保证负载均衡，从根上不需要调 batch |

**（4）冻结本身是一个"光谱"而非开关。** HyperRouter（`arXiv:2312.07035`）总结得很到位：**"fixing the routers" 能缓解专家同质化坍缩，但代价是"随机/次优路由策略"和训练效率损失**。所以更准确的图景是：
$$\text{冻结 router} \leftrightarrow \text{固定路由} \leftrightarrow \text{软约束/重标定} \leftrightarrow \text{完全可训 router}$$
——你选哪一档，取决于数据量、域差距和算力，而不是"RL vs SFT"这个标签。

</details>

## 四、可操作的分档建议

| 阶段 | router | batch 建议 |
|---|---|---|
| **Midtrain / 继续预训练** | **照常训练**（这本来就是预训练目标的延伸） | token-batch 尽量大；保留原均衡机制；不需要 batch-size warmup 之外的额外处理 |
| **大规模、多域 SFT** | **照常训练**，默认不冻 | 保证 `tokens per 均衡窗口` 足够大；若 micro-batch 受限，做**全局 batch 级**均衡或 bias 型均衡 |
| **小数据 / 单域 SFT、领域适配** | 可**冻 router**（保留预训练分工、防遗忘），或用极小 LR + z-loss | batch 帮不上忙，别指望靠调 batch 救 |
| **RL post-training** | 冻结 / routing replay / RSPO 软重标定（见上一轮） | micro-batch 小是常态，靠算法层（序列级比值 GSPO、routing replay）而非 batch 解决 |

**一句话回答你**：SFT/midtrain 不冻结 router 是对的，但依据不是"bs 大"，而是**没有 IS 比值这一层**；bs（准确说是均衡统计窗口内的 token 数）确实能压低负载波动与路由抖动，是有效的一阶稳定手段，但**既非必要也非充分**——真正的承重件是"保留/改造均衡目标 + router 的正则，以及数据多样性"。如果 micro-batch 被显存卡死，光堆 gradient accumulation 可能修不了 router 抖动，这时候要么改用全局/ bias 型均衡，要么换 Expert-Choice Routing。

**关键文献**：StableMoE（`2204.08396`，冻路由的经典依据）、HyperRouter（`2312.07035`，"fix router" 的利弊总结）、COLM 2026 长尾专家保留（`2604.23036`，SFT router 脆弱 + aux loss 噪声梯度）、ForeMoE（`2606.11867`，小 micro-batch → 负载高频波动）、Expert-Choice Routing（`2202.09368`）。
