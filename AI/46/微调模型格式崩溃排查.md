# 微调模型格式崩溃排查

## 🧑‍💻 User

请教各位大佬的训练经验。我现在在微调Qwen3VL用于检测Grounding语义，主要是用来检测生成幻觉的。有两批sft数据 输出文本是坐标与label，其中一批是box标注粗略，输出文本 比较短，另外一批精细标注，输出文本较长。但是精细标注的数据训练后，输出就崩溃了，60%以上json输出格式不闭合或者反复重复。这种情况应该怎么避免呢

## 😀 默认助手 (7)

## 先说判断：你这 60% 大概率不是“训崩了”，而是“长度或模板层面的系统性 bug”

“两批数据一短一长，长的崩”+“60% 不闭合”这种高度规律的比例，几乎不会是模型能力不够，而是**有某个环节在长输出上必然失败**。先花 10 分钟做三个隔离实验，再谈调参，否则容易在错误的方向上改数据。

### 三个隔离实验（按这个顺序做）

1. **把 `max_new_tokens` 直接开到 4096，关掉所有 repetition penalty，贪心解码**再跑一遍精细数据。
   60% 不闭合这个词太像“被生成长度截断”了——精细标注的 box 数量多，输出 token 数是粗标注的好几倍，如果你推理脚本的 `max_new_tokens` 是照粗标注调的（比如 256/512），长样本必然“不闭合”，而且看起来就像模型不会收尾。**这是我最怀疑的一条。**
2. **在 held-out 集上按输出长度分桶统计“可解析率”**（比如按 box 数量分 1–5 / 6–15 / 16+ 三桶）。
   - 只有长桶崩 → 截断/长度/位置泛化问题；
   - 短桶也崩 → chat template / 特殊 token / 格式不一致问题；
   - 全崩且表现为“越训越崩” → 过拟合或 LR 问题。
3. **用训练集样本做 teacher forcing 评测**（给 GT 前缀，逐 token 算损失，找第一个“模型不认为该这么写”的位置）。如果连 teacher forcing 下 GT 的闭合括号概率都极低，说明这不是生成问题，是**训练数据或标签本身有截断/格式不一致**。

<details>
<summary><b>同时一定要查的两个数据硬指标（最容易忽略）</b></summary>

- **截断率**：统计精细数据里 `len(tokenize(prompt+response)) > max_length` 的样本占比。如果有，务必**整条丢弃，不要左截断也不要右截断**——右截断会让模型学到“JSON 写一半就停”。
- **GT 自身合法率**：用 `json.loads` 过一遍两批数据的 label，看非法比例、`x1>x2`、坐标越界、坐标格式（浮点/整数、几位小数、是否相对坐标）是否统一。粗标注和精标注如果**坐标归一化方式不同**（一个 0–1000、一个绝对像素），模型会同时学两套映射，长序列下必然漂移。

</details>

## 最可能的 5 个原因（按概率排序）

| # | 原因 | 特征 | 修法 |
|---|---|---|---|
| 1 | 推理 `max_new_tokens` 不足 / 训练 `max_length` 截断 | 只有长样本崩；teacher forcing 正常 | 提高上限；超长样本整条丢弃 |
| 2 | 用了 sample packing 但 attention 隔离有 bug | 输出“跨样本续写”、莫名重复、不闭合 | 先关掉 packing 验证 |
| 3 | train / infer 的 chat template 或 assistant 起止 token 不一致 | 开头就发散、不会收尾 | 用 `apply_chat_template(..., add_generation_prompt=True)` 严格对齐 |
| 4 | 学习率对长输出 SFT 偏大 | 首个 epoch 正常，后面格式退化 | 降 LR、按 ckpt 监控格式合法率 |
| 5 | 坐标 tokenization / 长尾 label | 重复出现在某个数字或某个 label 上 | 坐标离散化 + 收敛 label 词表 |

## 数据侧：优先换掉 JSON

这是我最想给你的一条建议。**JSON 用来做 grounding 输出本身就很脆**：闭合括号是长距离依赖，box 数到几十个时模型需要“数括号”，任何一处 token 概率抖动都会导致整条不可解析；而且重复的 `"`, `,`, `{` 天然容易诱发重复循环。

### 方案 A（首选）：用 Qwen3-VL 原生 grounding 格式

Qwen3-VL 的底座本来就见过 grounding 数据，格式token（形如 `<|object_ref_start|>label<|object_ref_end|><|box_start|>(x1,y1),(x2,y2)<|box_end|>`，以你 tokenizer 里的实际 special token 为准）在预训练里就有强先验。用它做输出：

- 每个对象是一个**独立的、长度固定的短单元**，没有跨对象的嵌套闭合依赖；
- 天然带“单元结束”信号，几乎不会出现“写到一半停不下来”；
- 你还可以顺带保留底座的 grounding 能力，避免灾难性遗忘。

如果你的下游需要 JSON，**在推理后处理时再包一层 JSON**，而不是让模型直接生成 JSON。

### 方案 B：如果必须 JSON，就把它“压平”

- 单行、无空格、**固定 key 顺序**、坐标固定整数位（0–1000 量化，统一 `%d`）；
- 强制每个样本用同一套 canonical serializer 生成（不要在 A/B 两批里用两种 dumps 参数）；
- 去掉所有可选字段，能用数组就别用嵌套对象；
- 在结尾加一个不可混淆的终止标记（例如 `</detection>`），让“收尾”变成一个单 token 决策，而不是“数够括号”。

### 其他数据动作

- **控制单样本 box 数量**：精细标注如果动辄 50–100 个框，随机下采样到 20–30 个。长列表对生成和评测都是负担，收益很低。
- **长度课程**：先只用粗标注训，格式锁死后再以低 LR 混入精细数据（比如 1:1 → 1:2），不要一开始就把长样本全灌进去。长样本在 token-level loss 里会**主导梯度**，直接改变输出长度分布的先验。
- **混入少量“格式锚点”样本**：同 schema 的短样本，专门维持格式先验。
- **label 词表收敛**：精细标注的长尾类别如果每个只出现几次，模型对 label 字符串本身不确定，容易在 label 处开始重复。合并同义类别、丢弃低频类。
- **去重**：GT 里如果有重复 box/label，模型会学着重复输出。

## 训练侧

- **先关 packing**，确认崩溃消失再考虑加回来。packing 的跨样本污染是“不闭合 + 重复”的经典元凶。
- **降低 LR**：LoRA 建议 5e-5 ~ 1e-4，full FT 建议 ≤ 1e-5。格式类任务对 LR 比语义任务敏感得多。
- **只对 assistant 段算 loss**，且保证 **EOS 在 loss 里**（很多崩溃是最后那个 EOS 被 mask 掉了，模型永远学不会停）。
- **冻结 vision tower**，只训 LLM（或只 LoRA LLM）。视觉侧扰动会连带改变语言侧的输出分布。
- **加 5–10% 通用 replay 数据**，防止底座原有的 JSON / 结构化输出能力被覆盖。
- **每个 checkpoint 都评测格式合法率**，不要只训到最后一个 epoch。格式崩溃常常出现在过拟合的后期，**最好的 ckpt 往往在前 1–2 个 epoch**。
- 按长度分桶做 batch（同桶内 padding 少），避免长样本被大量 padding 稀释。

---

## 推理侧兜底（生产上建议加，但别用来掩盖训练问题）

- **语法约束解码**：vLLM / XGrammar / outlines 按 JSON Schema 或自定义文法约束，从结构上消灭“不闭合”。对检测类任务成本极低，收益巨大。
- repetition penalty 只给 **1.02–1.05**，**不要**用 `no_repeat_ngram_size`——grounding 里坐标数字重复是合法的，ngram 惩罚会破坏正常输出。
- `max_new_tokens` 按“最大 box 数 × 每 box token 数 × 1.5”来设。

---

## 建议的监控指标（每 ckpt 都记）

- `json_parse_rate`（或格式合法率）
- 按输出长度分桶的 `parse_rate`
- `avg_output_len`（如果突然变长/变短，是崩溃前兆）
- 按 box 数量的召回率、label 准确率、IoU@0.5
- **首个错误 token 位置的分布**（teacher forcing），这个最能定位是格式问题还是内容问题
