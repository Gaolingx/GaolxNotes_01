## 一、整体思路：冻结两端的"桥接器"范式

这个项目的核心思想并非原创，而是借鉴自 **Baseten 的 `GLM-5.2-Vision-NVFP4`** 方法论：

> **冻结文本主干 + 冻结视觉塔 + 仅训练一个紧凑的投影器（Projector）**

| 组件 | 来源 | 状态 | 规模 |
|------|------|------|------|
| 文本主干 | `deepseek-ai/DeepSeek-V4-Flash-0731`（经 `MJPansa` NVFP4 量化） | 冻结，48 shards | ~175 GB |
| 视觉塔 | `moonshotai/Kimi-K2.6` 的 **MoonViT** | 冻结，329 BF16 张量 | 833 MB |
| 投影器 | WebBrain 自训 **PatchMerger** | 训练，6 BF16 张量 | **仅 40,119,040 参数（~80 MB）** |
| 路由桥 | WebBrain 自研 | 检入仓库 | 64-ID 调色板 |

**关键洞察**：仅需训练约 4000 万参数的投影器，就能把两个独立训练的大模型"焊接"在一起——这是参数高效到极致的多模态扩展方案。

## 二、技术实现细节

### 2.1 数据流：图像如何变成 DeepSeek 的 token

整个前向数据流如下（来自 `config.json` 的 `vision_config` 与模型卡说明）：

```
原始图像
  │
  ▼  Kimi K2.6 processor: resize / normalize / patchify
  │   patch_size=14, pos_emb 64×64×4 (divided_fixed)
  ▼
MoonViT 视觉塔 (27层, hidden=1152, 16头)  ── 输出 1152 维特征
  │
  ▼  PatchMerger 投影器
  │
  │   LayerNorm
  │      ↓
  │   2×2 patch merge  (merge_kernel_size=[2,2], merge_type=sd2_tpool)
  │      ↓
  │   Linear(4608 → 4608)        ← 注意是 4608 = 1152×4 (合并后)
  │      ↓
  │   GELU
  │      ↓
  │   Linear(4608 → 4096)        ← 对齐 DeepSeek 的 hidden_size=4096
  │
  ▼  4096 维图像 embedding，注入 DeepSeek 的 embedding 序列
```

**为什么是 4608？** MoonViT 输出 1152 维，2×2 patch merge 后每组合并 4 个 patch → $1152 \times 4 = 4608$。这与 Kimi 原版 PatchMerger 的形状完全一致，说明投影器沿用了 Kimi 的结构设计，只是最后一层输出维度从 Kimi 的语言模型隐藏维改成了 DeepSeek 的 **4096**。

### 2.2 最关键的创新：MoE 路由桥（Routing Bridge）

这是该项目相对 Baseten 方案的**核心增量**，也是嫁接到 DeepSeek 上独有的难点。

**问题背景**：DeepSeek V4 Flash 是一个 **MoE 模型**：
- 256 个路由专家（`n_routed_experts=256`）
- 每 token 选 top-6 专家（`num_experts_per_tok=6`）
- 路由由 token 的 embedding 经 hash/gate 决定

普通文本 token 有自己的 `token_id`，路由器会自然给出专家分配。但**图像 token 是凭空插入的**——它们没有对应的词表 ID，DeepSeek 的路由器不知道该把它们送到哪些专家。

**WebBrain 的解法**（见 `config.json` → `deepseek_vision.routing_policy = "palette_cycle"`）：

1. 预先选定一个 **64-ID 调色板**（`routing_palette`），是从词表中挑出的 64 个真实 token ID（如 `0, 1, 2, 8, 9, 10, 12, 74, 81, 110, ...`）。
2. 对图像位置，按顺序**循环复用**这 64 个 ID 作为路由依据（"palette_cycle"）。
3. 文本 token 的路由 ID **完全保留**，不受影响。
4. 路由替换**只在 prefill/extend 阶段生效**，decode 阶段保持原生行为。

> 直白地说：图像 token "借" 64 个真实文本 token 的身份去走 MoE 路由，且借用是确定性的（位置 $i$ 借调色板中第 $i \bmod 64$ 个 ID）。这样既不破坏 DeepSeek 的 hash 路由逻辑，又让图像 embedding 能被合理地分发到专家网络。

### 2.3 配置层面的嫁接痕迹

对比 `config.json` 可以清楚看到"嫁接"的痕迹：


### 2.4 文件级的"零侵入"嫁接

从 `VISION_ADAPTER_MANIFEST.json` 可见嫁接的极简性：

- 48 个文本 shard **字节级未改动**（`tensor_files_modified: false`）
- 仅**新增**两个 safetensors 文件：`vision_tower.safetensors` + `mm_projector.safetensors`
- 仅**增强**（而非改写）`config.json` 和 `model.safetensors.index.json`，把 335 个视觉/投影器张量名追加进索引
- `conversion-receipt.json` 完整保留，证明 0731 的 DSpark/MTP 张量和量化元数据原封不动

> 这种"叠加层"（overlay）式发布意味着：去掉两个新文件、还原 config，就立刻回到纯文本 DS。可逆性极强。

## 三、推理侧集成：为何需要魔改 SGLang

模型卡和部署文档明确指出：**这不是 stock SGLang 或 stock Transformers 的多模态架构**，需要：

1. **Pin 特定 SGLang commit**：`fdebc938f7f4d16fe6b9f55dcd9a767cf0899ea1`
2. **加载外部 model/processor 包**：仓库内 `sglang_ext/` 目录
3. **打源码补丁**：修改多模态 embedding 注入逻辑，但**不改** DeepSeek V4 的 attention 和 routing 行为

SGLang 扩展做的事（来自部署文档）：

| 步骤 | 说明 |
|------|------|
| 1. 识别 `<image>` 标记 | 当前仅支持**一个**字面 `<image>` 标记 |
| 2. 调用 Kimi K2.6 processor | resize / normalize / patchify |
| 3. 加载 MoonViT 塔 | 通过 SGLang 原生 MoonViT 模块 |
| 4. 加载 PatchMerger | 输出 4096 维 DS embedding |
| 5. 路由 ID 替换 | 文本路由保留，图像位置循环 64-ID 调色板 |
| 6. 仅 prefill 阶段替换 | decode 生命周期行为保持原生 |

**硬件定位**：明确面向 **NVIDIA Blackwell**（`KERNEL_PROFILE=blackwell-native`，用 `flashinfer_trtllm` 的 FP4 dense 和 MoE 路由后端）。NVFP4 是 Blackwell 原生支持的四比特浮点格式。

## 四、训练侧推断（仓库未公开训练代码，但可从结构反推）

基于 Baseten 范式 + 本仓库的"路由感知"（routing-aware）描述，可推断训练流程大致是：

1. **冻结** DeepSeek 文本主干（包括所有 MoE 专家、attention、MTP）
2. **冻结** MoonViT 视觉塔
3. **仅训练** PatchMerger 的 6 个张量（40M 参数）
4. 训练目标是让图像 embedding 在 DeepSeek 的隐藏空间中"可读"——即让 DS 的 attention 和 MoE 能像处理文本 token 一样处理图像 token
5. "routing-aware" 暗示训练时已经考虑了 palette_cycle 的路由分配，让投影器学会在给定路由下产出对 DS 友好的 embedding

由于只训 40M 参数，**所需算力和数据量远小于从头训练多模态模型**——这是该方法能在社区级别复现的关键。

## 六、方法学价值与可复用性

### 6.1 这套范式的可推广性

这套"冻结两端 + 训投影器 + 路由桥"的配方**高度可复用**：

```
任意文本 LLM  +  任意视觉编码器  +  PatchMerger 投影器  +  (MoE 模型才需要的) 路由桥
```

- 对**稠密 LLM**（如 GLM、Llama）：只需投影器，无需路由桥（Baseten 的 GLM-5.2-Vision 即此情况）
- 对 **MoE LLM**（如 DeepSeek V4、Mixtral）：需额外设计路由桥，本项目给出的 `palette_cycle` 是一种简洁解法

### 6.2 相比"从头训多模态"的优势

| 维度 | 从头训 VLM | 本嫁接方案 |
|------|-----------|-----------|
| 训练参数量 | 数十亿~数百亿 | **40M** |
| 所需数据 | 海量图文对 | 中等规模图文对 |
| 文本能力 | 易退化 | **完全保留**（主干冻结） |
| 视觉特征质量 | 取决于训练 | **继承 Kimi SOTA 视觉塔** |
| 工程复杂度 | 高 | 中（主要在推理侧集成） |
| 可逆性 | 无 | **强**（叠加层式） |

### 6.3 巧妙之处

1. **借身份走路由**：用真实文本 token ID 给图像 token 当"路由护照"，绕过了 MoE 路由器对未知 token 的处理难题——这是最聪明的一步。
2. **零侵入文本权重**：48 个 shard 字节级不变，意味着 DeepSeek 团队后续发布新版本时，只需重新镜像 + 叠加视觉层即可升级，无需重训投影器（维度不变的前提下）。
3. **维度对齐的极简性**：投影器最终只需把 1152 维 → 4096 维，本质上是一个低秩线性映射 + 非线性，参数极少。

## 七、一句话总结

> WebBrain 把 **Kimi K2.6 的 MoonViT 视觉塔**（冻结）通过一个仅 **40M 参数的 PatchMerger 投影器**（自训）接到 **DeepSeek V4 Flash 0731**（冻结的 NVFP4 量化文本主干）上；针对 DeepSeek 的 MoE 架构，设计了一个 **64-ID 调色板循环路由桥**，让图像 token 借用真实文本 token 的路由身份通过专家网络；推理侧通过**魔改 SGLang**（pin 特定 commit + 源码补丁）实现多模态 embedding 注入，文本权重字节级零改动。整个方案参数高效、可逆、可复用，是"冻结两端训桥接器"范式在 MoE 模型上的首个公开实践。

# 关于"仅需少量平行数据"的辨析

你的直觉方向正确，但需要修正一个关键误解：**参数少 ≠ 数据少**。下面逐层拆解。

---

## 一、"平行数据"的准确定义

这里需要的不是翻译意义上的"平行语料"，而是**多模态对齐数据**：

| 数据类型 | 形式 | 作用 |
|----------|------|------|
| 图像-描述对 | `(image, caption)` | 让投影器学会把视觉特征"翻译"进 DeepSeek 的语义空间 |
| 图像-指令对 | `(image, question, answer)` | 让模型学会**利用**视觉信息完成推理、问答等任务 |

---

## 二、为什么"40M 参数 → 少量数据"的直觉是**部分正确**的

✅ 正确的部分：

- 投影器只有 6 层、40M 参数，**容量有限**，无法靠记忆大量样例来拟合——它必须学到通用的映射模式
- 两端都是冻结的 SOTA 模型：MoonViT 已能提取高质量视觉特征，DeepSeek 已具备强语言推理能力——投影器只需"接线"，不需"补能力"
- 因此数据的**下限**确实比从头训 VLM 低一个数量级

---

## 三、为什么"只需很少量数据"是**不完全正确**的

❌ 被忽略的三个关键因素：

### 3.1 两个独立训练的空间之间存在"语义鸿沟"

MoonViT 是与 **Kimi 的语言模型**协同训练的，它的输出特征天然适配 Kimi 的隐藏空间。现在要把它"嫁接"到 DeepSeek 上——两者的：

- **隐藏维不同**：Kimi LM 的 hidden_size ≠ 4096
- **attention pattern 不同**：Kimi 和 DeepSeek 的注意力分布、层间信息流不同
- **词表语义分布不同**：DeepSeek 的 embedding 空间有自己的几何结构

投影器必须学习一个**跨空间翻译**，这不是简单的线性映射能解决的——所以 PatchMerger 设计了 `LayerNorm → 2×2 merge → Linear → GELU → Linear` 的非线性结构。

### 3.2 两阶段训练，数据需求不同

这类嫁接方案的训练通常分两个阶段，数据需求差异很大：

```
阶段一：对齐预训练（Alignment Pretraining）
  │  数据：大规模图像-描述对（如 CC3M, LAION 子集）
  │  目标：让图像 embedding 在 DS 空间中"可读"
  │  数据量：通常需要 50万 ~ 100万 条
  │  学习率：较大
  │
  ▼
阶段二：指令微调（Instruction Tuning）
  │  数据：图像-问答/指令对（如 LLaVA-Instruct, ShareGPT4V）
  │  目标：让模型学会"用"视觉信息做推理
  │  数据量：通常需要 10万 ~ 50万 条
  │  学习率：较小
  │
  ▼
最终：模型能看图回答问题
```

### 3.3 MoE 路由桥增加了隐含约束

这是本方案独有的复杂性。投影器不仅要"翻译"特征，还要让翻译结果在**palette_cycle 路由**下表现良好：

- 图像位置 $i$ 的 embedding 会被送到第 $(i \bmod 64)$ 个调色板 ID 对应的专家
- 不同专家擅长处理不同语义内容
- 投影器必须学会：**在特定位置产出的 embedding，要匹配该位置将被路由到的专家的能力**

这意味着训练数据需要**足够多样**，覆盖各种图像位置 × 专家组合，否则某些调色板位置会"欠训练"。这不是数据"量"的问题，而是数据**覆盖度**的问题。

## 四、实际数据量估算

对比几种方案的典型数据量：

| 方案 | 训练参数量 | 训练数据量 | 说明 |
|------|-----------|-----------|------|
| 从头训 VLM（如 LLaVA-1.5） | ~7B+ | ~120万条 | 视觉塔 + LLM 都要训 |
| Baseten GLM-Vision（稠密 LLM） | ~40M | 估 50~100万条 | 两阶段，对齐+指令 |
| **WebBrain DS-V4-Vision（MoE LLM）** | **~40M** | **估 50~100万条 + 路由覆盖增强** | 额外需保证调色板覆盖 |
| 仅做"能看图说话"的最小可用版 | ~40M | ~5~10万条 | 仅阶段一，能力很弱 |

> 注意：这些是估算值。WebBrain 仓库**未公开训练数据和训练代码**，以上基于同类项目（LLaVA、Baseten）的经验推断。

## 五、核心结论

```
"只需很少量平行数据" → 部分正确，但需要修正为：

参数少  →  训练算力需求低  →  单卡/小集群可完成
                                    ↓
但语义鸿沟 + 两阶段需求 + MoE 路由覆盖  →  数据量仍需 50~100万条级别
                                    ↓
                            数据的"质量和多样性"
                            比数据量更关键
```

**一句话**：这个方案省的是**算力**（40M 参数 vs 7B+），不是**数据**。它仍然需要数十万到百万级的多模态对齐数据，只是这些数据的获取成本远低于从头训练 VLM 所需的海量预训练数据。真正的优势在于：**用消费级或小规模学术算力，就能完成原本需要工业级集群才能做的多模态扩展**。

# 关于"翻译成文本 token"的辨析

你的直觉抓住了**核心意图**（确实是在做某种"翻译"），但在**机制层面**有一个重要误解需要纠正。

---

## 一、关键区分：连续向量 vs 离散 token

你说的"图片 token"和"文本 token"其实是**两种本质不同的东西**：

| | 文本 token | MoonViT 输出的"图片 token" |
|--|-----------|--------------------------|
| 本质 | **离散整数 ID**（如 `token_id=1234`） | **连续浮点向量**（1152 维浮点数组） |
| 来源 | 词表查表 | 卷积/注意力层输出的特征图 |
| 举例 | `"猫"` → `8639` | 一张图 → `[[0.12, -0.47, 0.03, ...], ...]` |

MoonViT 输出的**不是离散 token**，而是一组连续特征向量——你可以理解为"图像被切碎成很多小 patch，每个 patch 变成一个高维浮点向量"。

---

## 二、投影器真正做的事：空间映射，而非符号翻译

投影器的输入输出都是**连续向量**，它不涉及任何离散 token：

```
MoonViT 输出          投影器                  DeepSeek 的 embedding 序列
                        
[0.12, -0.47, ...]    LayerNorm               [0.31, 0.08, ...]  ← "今天" 的 embedding
[0.55,  0.21, ...]    2×2 merge               [0.12, -0.47, ...] ← 图像 patch 1 (投影后)
[0.03,  0.89, ...]    Linear+GELU+Linear      [0.55,  0.21, ...] ← 图像 patch 2 (投影后)
[... 1152维 ...]      ─────────────→          [... 4096维 ...]   ← "的" 的 embedding
                      输出 4096 维向量          [... 4096维 ...]   ← "天气" 的 embedding
```

投影器做的事是：

$$\text{视觉特征向量} \in \mathbb{R}^{1152} \xrightarrow{\text{投影器}} \text{语言空间向量} \in \mathbb{R}^{4096}$$

它把视觉特征**映射到** DeepSeek 的隐藏空间，让 DeepSeek 的 attention 机制能像处理文本 embedding 一样"看到"这些向量。

**它没有把图片"变成文字"**——模型从头到尾都不知道这张图叫"猫"，它只是拿到一组能被 attention 机制处理的向量。

## 三、一个更准确的类比

~~"把英文翻译成中文"~~（符号到符号的翻译）

✅ **"把一张乐谱从五线谱转写成钢琴能弹奏的琴键序列"**

- 转写器不负责"理解"音乐——它只负责格式转换
- 真正"听懂"音乐的是钢琴本身（DeepSeek 的 attention 和 MoE）

或者用更技术的类比：

## 四、那"翻译"到底发生在哪里？

```
图像 ──MoonViT──→ 视觉特征(1152维)

                      ▼
```

# 投影层结构与训练机制：你的理解基本正确，但有几个关键细节需要修正

---

## 一、结构修正：维度变换的完整链条

你写的 `image(dim2) -> x(n,4608) -> x(n,4096)` 方向对，但漏掉了最关键的一步——**2×2 patch merge**。完整的维度流是：

```
MoonViT 输出:  (N, 1152)        ← N 个 patch，每个 1152 维
                    │
                    ▼
              2×2 Patch Merge
              把相邻 4 个 patch 拼接
                    │
                    ▼
              (N/4, 4608)        ← 4 个 patch 合成 1 个 token，4608 = 1152×4
                    │
                    ▼
              Linear(4608 → 4608)
                    │
                    ▼
                 GELU
                    │
                    ▼
              Linear(4608 → 4096)
                    │
                    ▼
              (N/4, 4096)        ← 最终注入 DeepSeek 的图像 token
```

**关键点**：4608 → 4096 不只是"压缩维度"，它前面还有一步 **4 合 1 的 patch merge**。所以从总信息量看：

| 阶段 | 形状 | 总数据量 |
|------|------|---------|
| MoonViT 输出 | $(N, 1152)$ | $1152N$ |
| Patch Merge 后 | $(N/4, 4608)$ | $1152N$（拼接，未压缩） |
| 最终输出 | $(N/4, 4096)$ | $1024N$（**确实压缩了 ~11%**） |

> 真正的"压缩"发生在两个地方：① patch merge 把 4 个 token 合成 1 个（token 数减少 4 倍）；② 4608→4096 的线性层做了一点点降维。

---

## 二、为什么 4608 → 4096 的降维不会丢太多信息？

这是你问题的核心。三个原因：

### 2.1 相邻 patch 之间存在大量冗余

2×2 merge 把空间上相邻的 4 个 patch 拼在一起。但自然图像中，**相邻区域往往语义高度相关**（比如一片蓝天中的 4 个相邻 patch 几乎一样）。4608 维向量里存在大量线性相关的冗余维度，用 4096 维就能几乎无损表示。

> 类比：4 张几乎相同的照片拼在一起，你不需要存 4 份，存 1 份 + 3 个微小差异就够了。

### 2.2 4096 维是 DeepSeek 的"原生语言"

DeepSeek 的所有 attention、FFN、MoE 都是为 4096 维设计的。如果你硬塞进去一个 4608 维向量，DeepSeek 的每一层都没法处理。所以**必须**降到 4096——这不是"能不能压缩"的问题，是"必须对齐"的问题。

### 2.3 Linear 层本身就在做信息选择

`Linear(4608 → 4096)` 的权重矩阵 $W \in \mathbb{R}^{4096 \times 4608}$ 本质上是一个**学习到的投影**。训练过程中，这个矩阵会自动学会：

- 哪些维度的信息对 DeepSeek 有用 → 保留
- 哪些是冗余 → 抑制

这不是随机丢掉 512 维，而是**有方向性地筛选**。

---

## 三、训练机制：你的理解基本正确，但需要补充梯度流向

你说：

> "训练时投影层不断调整自己的参数，让转换出来的向量能被 transformer backbone 正确关联到正确的文字描述上就能完成对齐就能压低 loss"

✅ **方向完全正确**。但完整的机制是这样的：

### 3.1 训练时的前向传播

```
图像 ──MoonViT(冻结)──→ 视觉特征(1152维)
                            │
                            ▼
                      投影层(可训练)
                            │
                            ▼
                     图像 embedding(4096维)
                            │
                            ▼
          ┌─────────────────────────────────┐
          │  [图像emb] + [文本emb: "一只猫"]  │  ← 拼接成序列
          │         DeepSeek(冻结)           │
          │    next token prediction         │
          └─────────────────────────────────┘
                            │
                            ▼
                       预测概率分布
                            │
                            ▼
              loss = CrossEntropy(预测, 真实下一个token)
```

### 3.2 反向传播：梯度只流到投影层

```
loss
  │  反向传播
  ▼
DeepSeek 的 attention/FFN 层  ←─── 梯度经过，但参数冻结，不更新
  │
  ▼
图像 embedding (4096维)  ←─── 梯度传到这里！
  │
  ▼
投影层的 Linear/GELU  ←─── 梯度传到这里！参数更新 ✅
  │
  ▼
MoonViT 输出 (1152维)  ←─── 梯度到这里被截断（MoonViT 冻结）
```

**关键**：DeepSeek 虽然参数冻结，但**梯度仍然要穿过它**回传到投影层。这是"冻结"与"停止梯度"的区别：

- **冻结**：参数不更新，但梯度可以流过（用于计算上游梯度）
- **停止梯度 (detach)**：梯度完全截断

这里 MoonViT 和 DeepSeek 都是**冻结但不断梯度**，只有 MoonViT 的参数不更新——梯度流到 MoonViT 的输入层就自然停止了（没有更上游的可训练参数）。

### 3.3 训练目标的精确表述

你说的"关联到正确的文字描述"更准确的表述是：

$$\mathcal{L} = -\sum_{t=1}^{T} \log P_{\text{DeepSeek}}(w_t \mid w_{<t}, \mathbf{v})$$

其中：
- $w_t$ 是第 $t$ 个文本 token
- $\mathbf{v}$ 是投影后的图像 embedding
- $P_{\text{DeepSeek}}$ 是 DeepSeek 给出的条件概率

**投影层的任务**：调整参数，使得 $\mathbf{v}$ 能让 DeepSeek 在预测 $w_t$ 时给出高概率。

---

## 四、对齐的本质：不是"记住图片"，而是"让图片可被读取"

一个容易误解的点：训练目标并不是让投影器"记住"图片内容，而是让它把图片编码成 **DeepSeek 能用的方式**。

考虑两种极端情况：

| 投影器行为 | 结果 |
|-----------|------|
| 把所有图像都投影成固定向量 | DeepSeek 无法区分不同图片，loss 高 |
| 把图像投影成 DeepSeek 空间中"猫"附近的向量 | DeepSeek 能正确预测"猫"，loss 低 |

训练就是在推动投影器从第一种行为走向第二种。**"对齐"的本质是**：

> 让语义相似的图像和文本，在 DeepSeek 的隐藏空间中**几何上靠近**；语义不同的，**几何上远离**。

这不是"翻译"，而是**让两种模态共享同一个语义空间**。

## 一、两种范式的架构对比

### 1.1 后接投影器（如 WebBrain DS-V4-Vision）

```
┌─────────────┐     ┌──────────┐     ┌─────────────────────┐
│  ViT (冻结)  │ ──→ │ Projector│ ──→ │   LLM (冻结)         │
│  独立训练    │     │ (可训练)  │     │   独立训练            │
│  与LM无关    │     │ 40M参数   │     │   不感知视觉          │
└─────────────┘     └──────────┘     └─────────────────────┘
     输入端              桥接层              输出端
```

- 视觉编码器和语言模型**各自独立训练**，在训练时完全不知道彼此存在
- 桥接层是事后"焊接"上去的，信息只能单向流动
- LLM 内部所有层都不感知"视觉"这个概念

### 1.2 原生多模态（如 Gemini、GPT-4o）

```
┌──────────────────────────────────────────────────┐
│              统一 Transformer 主干                 │
│                                                  │
│  [img_tok_1] [img_tok_2] ... [txt_tok_1] [txt_tok_2] ...
│     │            │              │           │
│     ▼            ▼              ▼           ▼
│  ┌────────────────────────────────────────────┐  │
│  │     每一层 attention 都同时处理            │  │
│  │     图像 token 和 文本 token               │  │
│  │     (从第一层到最后一层)                    │  │
│  └────────────────────────────────────────────┘  │
│                                                  │
│  从预训练阶段就联合训练，所有参数共同优化          │
└──────────────────────────────────────────────────┘
```

- 从**预训练第一天**开始，图像和文本就是**混合序列**一起喂给模型
- 没有独立的"视觉塔"和"语言塔"之分——所有模态共享同一个 transformer
- 每一层的 self-attention 都在做跨模态交互

## 二、训练范式的本质差异

### 2.1 数据组织方式

| | 后接投影器 | 原生多模态 |
|--|----------|-----------|
| 预训练数据 | 纯文本（LLM 独立预训练） | **图文交织序列**（interleaved image-text） |
| 对齐训练 | 事后用图文对微调投影器 | 不需要单独对齐——预训练就在一起 |
| 指令微调 | 仅投影器学习 | 全模型学习跨模态指令遵循 |

**原生多模态的预训练数据长这样**：

```
<token> 一只 <img>猫咪坐在<img> 窗台上 <token> 阳光照射进来 <img> 形成了 <token> 斑驳的光影
```

图像 token 和文本 token **自然交织**在同一个序列里，模型从一开始就在学"图中的猫"和"文字的猫"之间的关联。

### 2.2 参数更新范围

| | 后接投影器 | 原生多模态 |
|--|----------|-----------|
| 预训练阶段 | LLM 和 ViT 各自独立训练 | **所有参数联合训练** |
| 对齐阶段 | 仅 40M 投影器参数 | 不需要单独对齐阶段 |
| 指令微调 | 仅投影器（或少量 LoRA） | **全模型参与** |
| 总可训练参数（对齐阶段） | ~40M | ~数十B |

这是最根本的差异：**原生方案在训练时让所有层都"见过"图像**，而投影器方案只有桥接层见过。

## 三、能力鸿沟：具体差异

### 3.1 深层跨模态推理

**原生多模态能做的**：

```
问：图中这个人拿的工具适合拧什么类型的螺丝？
```

模型在第 1 层就能让"工具"的文本 token 去关注图像 token 的形状特征，到第 20 层已经完成了"形状→功能"的推理链，到第 40 层生成了精准回答。**每一层都在做跨模态推理**。

**投影器方案的局限**：

图像 token 在第 0 层被注入后，就**不再有新的视觉信息进入**。DeepSeek 的深层在做推理时，只能反复"咀嚼"那 4096 维的固定向量。如果第 5 层需要"重新看一眼图像的某个细节"——做不到，图像信息已经被压缩成了固定 embedding，没有"回看"机制。

> 类比：原生多模态像**开着摄像头实时操作**；投影器方案像**看了一眼照片后闭眼回答**。

### 3.2 细粒度视觉理解

| 任务 | 原生多模态 | 投影器方案 |
|------|-----------|-----------|
| "图中红色汽车的车牌号" | ✅ 能聚焦到极小区域 | ❌ patch merge 后细节大量丢失 |
| "这张表格第三行第二列的值" | ✅ 能精确空间定位 | ⚠️ 2×2 merge 后空间分辨率 ×¼ |
| "这个分子的化学结构式" | ✅ 像素级理解 | ❌ patch merge 严重破坏精细结构 |

**关键瓶颈**：投影器方案的 2×2 patch merge 把 4 个 token 合成 1 个，空间分辨率直接降低 4 倍。而原生多模态可以设计成**不合并 patch**，或者在更高分辨率下处理图像。

### 3.3 多图推理与空间关系

```
问：图A中的物体能放到图B的容器里吗？
```

| | 原生多模态 | 投影器方案 |
|--|----------|-----------|
| 多图处理 | ✅ 预训练见过多图交织 | ❌ WebBrain 明确限制仅 1 张图 |
| 图间关系 | ✅ attention 天然处理跨图关系 | ❌ 多图 token 混在一起，路由桥混乱 |
| 空间推理 | ✅ 保持完整空间布局 | ⚠️ patch merge 破坏空间结构 |

### 3.4 视频理解

| | 原生多模态 | 投影器方案 |
|--|----------|-----------|
| 时序建模 | ✅ 预训练含视频数据，能建模时间 | ❌ 架构上没有时序模块 |
| 帧间推理 | ✅ attention 跨帧交互 | ❌ 无法处理多帧 |

## 五、投影器方案的优势（并非全无优点）

公平地说，投影器方案也有独特优势：

| 优势 | 说明 |
|------|------|
| **成本极低** | 40M 参数 vs 数十B 联合训练 |
| **文本能力零退化** | LLM 冻结，原有能力完整保留 |
| **可逆性** | 去掉投影器就回到纯文本模型 |
| **模块化** | 可随时换更好的 ViT 或更好的 LLM |
| **快速迭代** | 新 LLM 发布后，几天就能重新训练投影器 |

原生多模态如果联合训练时数据配比不好，**文本能力可能反而退化**——这是工业界做原生多模态时最头疼的问题之一。

---

## 六、GPT-4o / Gemini 的具体做法（已知信息推断）

基于 OpenAI 和 Google 公开的技术报告和论文：

### 6.1 GPT-4o

- **单一神经网络**处理所有模态（文本、图像、音频）
- 预训练数据包含**原生交织的多模态序列**
- 不存在独立的"视觉编码器→投影器→语言模型"管线
- 音频也是直接 tokenize 后进入同一序列

### 6.2 Gemini

- 从头训练的**原生多模态模型**
- 使用 **Interleaved Image-Text 预训练**：图文在同一个序列中自然交替
- 支持高达 **原生分辨率**的图像输入（不做 patch merge，或用更灵活的分块策略）
- 视觉理解能力在预训练阶段就已建立，不需要事后对齐

### 6.3 对比总结

```
原生多模态的信息流：
  图像 ─→ tokenize ─→ [img_tok] [txt_tok] [img_tok] [txt_tok] ...
                         │           │           │           │
                         ▼           ▼           ▼           ▼
                    ┌─────────────────────────────────────┐
                    │    每一层 attention 自由交互          │
                    │    跨模态信息在深层反复融合            │
                    └─────────────────────────────────────┘
                         │
                         ▼
                      输出

投影器方案的信息流：
  图像 ─→ ViT ─→ 投影 ─→ [img_emb] ──→ 冻结LLM ──→ 输出
                            │
                     一次性注入，无法回看
                     深层只能反复"咀嚼"固定向量
```

## 七、一句话总结

> **原生多模态**像一个人**同时用眼和脑**看世界——视觉信息在每一层神经网络中都与语言深度融合，能做细粒度定位、多图推理、深层跨模态推理。
>
> **投影器方案**像一个**天生的盲人获得了导盲犬**——导盲犬（ViT+投影器）看一眼世界后给出一次性的压缩描述，盲人（冻结的 LLM）用自己强大的语言推理能力去理解这个描述。能做基本的看图说话，但在需要**反复观察、细节聚焦、深层视觉推理**的任务上存在结构性天花板。
>
> 但投影器方案的成本优势是压倒性的：40M 参数 + 几天训练 vs 数十B 参数 + 数月联合训练。**它不是原生多模态的替代品，而是"预算有限时的最优解"**。
