# FlashMLA 矩阵吸收 vs. 展开解压成 MHA

## 一句话结论

**矩阵吸收**利用矩阵乘法的**结合律** $((A\times B)\times C = A\times(B\times C))$，把「先把压缩的 latent 解压回 K/V、再算注意力」重排成「把上投影矩阵吸收进 Q/O，直接在 latent 空间算注意力」。这样 Decode 时 KV Cache 只需存低维潜向量与位置 key，无需物化每个 head 的完整 K/V —— 显存带宽开销可降到 **约 1/57**，且**数学上完全等价、无损**。

而「**展开 + 解压成 MHA**」（业内常称 Non-Absorbed / CacheDecompressed）是另一条路径：每步把 $c_t$ 上投影还原成 $K,V$（甚至把完整 K/V 写进 Cache），再跑标准 MHA。它数学等价，但**既不省显存也不省带宽**。

---

## 1. 前置：MLA 到底压缩了什么

MLA（Multi-head Latent Attention，DeepSeek-V2/V3）对 KV 做**低秩联合压缩**：

$$\underbrace{c_j}_{1\times r} = \underbrace{h_j}_{1\times d}\,W^{DKV},\qquad r = 512 \ll d = 7168$$

推理时 **Cache 只存 $c_j$**，需要用的时候再上投影还原：

$$k_{j,i}^C = c_j W_i^{UK},\qquad v_{j,i} = c_j W_i^{UV}$$

这里 $c_j$ 是所有 head **共享**的「共同底稿」。问题在于：如果只缓存 $c_j$ 却每步都重新上投影，Decode（每步只生成 1 个 token）就要对全部历史 token 做大 GEMM 解压，把本该极轻的操作拖慢。

---

## 2. 矩阵吸收是什么

<details>
<summary><b>K 侧吸收（Attention Score）——把 $W^{UK}$ 移到 Q</b></summary>

当前 query 与历史 key 的分数：

$$s_{i,j}^C = q_i^C (k_{j,i}^C)^\top = q_i^C (c_j W_i^{UK})^\top = q_i^C (W_i^{UK})^\top c_j^\top$$

由结合律：

$$s_{i,j}^C = \underbrace{\big(q_i^C (W_i^{UK})^\top\big)}_{\hat q_i \in \mathbb{R}^{1\times r}}\, c_j^\top = \hat q_i\, c_j^\top$$

即：**把 $W^{UK}$ 吸收到 Q 侧**，得到吸收后的 query $\hat q_i$，之后直接和 Cache 里的潜向量 $c_j$ 做点积，历史 token 不再被逐头展开成 K。

（若 Q 本身无中间非线性，理论上可进一步预合并权重 $\widehat W^{QC}_i = W_i^{QC}(W_i^{UK})^\top$。）

</details>

<details>
<summary><b>V 侧吸收（Output）——先在 latent 空间加权再展开</b></summary>

头输出：

$$o_i = \sum_{j} a_{i,j} v_{j,i} = \sum_j a_{i,j}\, c_j W_i^{UV} = \Big(\sum_j a_{i,j} c_j\Big) W_i^{UV} = z_i W_i^{UV}$$

先在潜空间求加权和 $z_i = \sum_j a_{i,j}c_j$，**只对当前聚合结果**展开一次。再和输出投影合并：

$$u = \sum_i o_i W_i^O = \sum_i z_i \underbrace{(W_i^{UV} W_i^O)}_{B_i}$$

即 $W^{UV}$ 可被 $W^O$ 吸收，也可在运行时用重新排序（einsum 重排）避免生成 $[L, H, d_v]$ 的大中间张量。

</details>

<details>
<summary><b>RoPE 无法吸收 → 吸收「分离」</b></summary>

RoPE 是**位置相关**变换（每个 token 的旋转矩阵 $R(\text{pos})$ 不同），而吸收要求 $W$ 是**位置无关**的固定权重，所以带 RoPE 的 K 无法用结合律挪到 Q 侧。

解决方法是把 Key 拆成两部分：

$$K = [\,K_{nope},\; K_{rope}\,],\qquad K_{nope}=c_tW^{UK}\ (\text{可吸收}),\quad K_{rope}=\text{RoPE}(k_{pe})\ (\text{不可吸收})$$

分数分两路算再相加（Move Elision，省掉拼接/广播）：

$$\text{score} = \underbrace{\hat q_{nope}\, c_t^\top}_{\text{吸收部分}} + \underbrace{q_{rope}\,\text{RoPE}(k_{pe})^\top}_{\text{RoPE 部分}}$$

因此 Cache 里只存两个东西：**latent $c_t$（512 维）+ 位置 key $k_{rope}$（64 维）= 576 维/token**。

</details>

## 3. 「展开 + 解压成 MHA」是什么

这是**非吸收**路径，有两种典型形态：

| 形态 | Cache 内容 | Decode 行为 |
|---|---|---|
| **CD**（CacheDecompressed，官方 HF 实现） | 完整、已加 RoPE 的逐头 K/V（$128\times128\times2$） | 直接跑标准 MHA，但 Cache 巨大 |
| **CC**（CacheCompressed，非吸收） | 共享 latent $c_t$ | 每步把 $c_t$ 上投影、扩展到 num_heads 还原 K/V 再跑 MHA |

两者数学等价，但都不省显存/带宽——CD 显存爆、CC 带宽爆（把本该压缩的收益又还原回去了）。

## 4. 好处对比：矩阵吸收 vs 展开成 MHA

以 DeepSeek-V3 配置（$d_c=512$, $H=128$, $d_h=128$, rope=64）为例：

| 指标 | 展开解压成 MHA（Non-Absorbed） | 矩阵吸收（Absorbed） | 收益 |
|---|---|---|---|
| **每 token KV 读取量** | $128\times128\times2 = 32{,}768$ 维 | $512+64 = 576$ 维 | **~57×** ↓ |
| **KV Cache 容量** | 逐 head 独立 K/V | 仅共享 latent + 位置 key | 同显存可装更长上下文 / 更大 batch |
| **Decode FLOPs** | 随上下文长度 $t$ 线性增长（解压开销大） | 低，且与 $t$ 的线性项被大幅削减 | Decode 更快 |
| **计算强度 / Arithmetic Intensity** | 低（单 token 利用率差） | ~2× 提升，更接近计算瓶颈 | GPU 利用率高 |
| **等效行为** | 标准 MHA（多头独立 KV） | 等效 **MQA**（共享单潜头） | 可复用成熟 MQA kernel |
| **模型效果** | 无损 | 无损（纯结合律等价） | 完全等价 |
| **推荐场景** | **Prefill / Chunked Prefill**（大 batch GEMM 效率高） | **Decode / 投机采样**（省带宽） | 动态切换 |

**核心好处归纳：**

1. **KV Cache 显存暴降 ~57×** —— 只缓存 512 维 latent + 64 维位置 key，而非逐头完整 K/V。
2. **显存带宽暴降** —— Decode 本质是 memory-bound，每步要读全部 KV Cache；读取量降 57× 直接决定长上下文下的吞吐/延迟。
3. **Decode FLOPs 显著降低** —— 避免了每步对全部 $L$ 个历史 token 做大上投影。wkq 的推导显示：非吸收版 FLOPs 与吸收版之差约为 $16678912\,t - 16777216$（$t$ 为缓存长度），随 $t$ 增大迅速为正。
4. **计算强度提高** —— 在 $d_c=512$ 维做注意力，数据复用率高，越接近计算瓶颈。
5. **工程可复用** —— 吸收后等价 MQA，可直接套用高度优化的 MLA/MQA kernel（FlashMLA 就是干这个的），并配合 chunked prefill。
6. **无损** —— 是线性代数重排，不是新训练算法，不改变注意力权重（低精度舍入顺序可能使 bit 级结果不同）。

## 5. 代价与权衡（为什么不能「无脑吸收」）

<details>
<summary><b>展开看看代价项</b></summary>

1. **Prefill 阶段吸收反而更慢**：seq_len 大时，解压 KV 的开销被大 GEMM 摊薄，Non-Absorbed 的大 batch GEMM 更能打满 Tensor Core。
2. **预合并权重会膨胀**：$\widehat W^{UQ}=W^{UQ^\top}W^{UK}$ 形状为 $(h,q,k)$，元素数约是 $W^{UQ}+W^{UK}$ 的 3 倍；因此**实践中不真正预合并**，而是运行时先算 $q_{nope}$ 再乘 $(W^{UK})^\top$（即代码里的「顺序 2」），WKQ 的分析证明它比「提前吸收」更省。
3. **RoPE 分离的开销**：需要 nope/rope 两路 score 分开算再相加，增加 kernel 复杂度。
4. **需要专用 kernel**：这也是 FlashMLA 存在的意义。

</details>

## 6. 工程实践：Prefill / Decode 动态切换

实际推理系统（SGLang / vLLM）按当前阶段选路径：

- **新 token 数 $x \ge$ 阈值（≈64）** → 用 **Non-Absorbed（展开成 MHA）**，先解压再 FlashAttention，大 GEMM 高效，适合 Prefill / Chunked Prefill。
- **$x = 1$（Decode）** → 用 **Absorbed（矩阵吸收）**，直接 $\hat q \times c_t^\top$，读量降 57×，带宽压力极小。

阈值典型值约 $x=64$，与 FlashMLA 的 `page_size=64` 对齐。**FlashMLA** 正是把这套「吸收式 MLA」做成 CUDA kernel 的成果：它让压缩后的注意力**不必重新展开**也能高效执行，dense MLA decode 在 H800 上可达 3000 GB/s（memory-bound）/ 660 TFLOPS（compute-bound）。

---

## 7. 常见误区

- ❌ 吸收是新的训练算法 → ✅ 只是推理期的线性代数重排，函数等价。
- ❌ 既然只缓存 latent，K/V 就不存在了 → ✅ K/V 仍会在计算中「按需」产生，只是不再逐头物化进 Cache。
- ❌ 「吸收」= 减少 FLOPs → ✅ 相对**完整 K/V Cache** 基线，它主要省**显存容量与读取流量**；省 FLOPs 只相对「缓存 latent 却每步重新解压」这条假想基线而言。

# FlashMLA 的内核组织：为什么不能直接复用 FlashAttention

## 核心结论先讲清楚

FlashAttention 的 `S = QKᵀ → softmax → O = PV`（严格说是 **2 个 GEMM + 1 个 softmax**）假设了一个**对称 MHA/GQA 格局**：$h_k = h_v$、$d_k \approx d_v$ 且都很小（64–256）、K 与 V 是两块不同的张量、输出宽度就是 $d_v$。

而 **MLA Decode 走的是「吸收（absorb）」路线**，吸收之后它**变形为 MQA**：$h_q = 128$、$h_{kv} = 1$、`head_dim_k = 576`、`head_dim_v = 512`，而且**K 与 V 是同一块潜向量矩阵 $C$**。这打破了 FA 的全部布局假设，所以只能**另写内核**。

> 一个容易被忽略但关键的事实：**MLA 本身可以写成标准 MHA 并用 FlashAttention 跑**——这正是 FlashMLA 的 **prefill** 内核（support matrix 里标明 Dense Prefill = **MHA 模式**，`head_dim_k=192`、`head_dim_v=128`）。所以问题不是「MLA 能不能用 FA」，而是**decode 阶段为了让 HBM 带宽最小化，主动选择了 absorb→MQA 的形态**，而这个形态天然对不上 FA 的内核骨架。

---

## 1. 两条数学等价、但计算形态截然不同的路线

| | Naive / 展开（MHA 模式） | Absorb / 吸收（MQA 模式） |
|---|---|---|
| Cache 里存 | 每 head 的完整 K/V | 共享潜向量 $C$（512）+ RoPE key（64） |
| 「K」形状 | $h_q$ 个 head，每头 $d_k=192$ | **1** 个 head，$d_k=576$ |
| 「V」形状 | $h_q$ 个 head，每头 $d_v=128$ | **1** 个 head，$d_v=512$ |
| 每步额外 GEMM | 无（就是标准注意力） | **Q 侧吸收前 GEMM + O 侧投影后 GEMM** |
| 适配内核 | FlashAttention（可直接用） | FlashMLA 专用内核 |
| 用在 | **Prefill / 训练** | **Decode** |

FlashMLA 的 README 用一张 support matrix 把这件事说得非常直白：
- `Dense Decoding` → **MQA mode**（`head_dim_k=576`, `head_dim_v=512`）
- `Dense Prefill` → **MHA mode**（`head_dim_k=192`, `head_dim_v=128`）

所以「把三个 GEMM 原样替换」在**训练/prefill**里其实成立（naive==MHA==FA）；**只有 decode 不成立**。

---

## 2. Absorb 形态为什么对不上 FA 内核 —— 7 个不匹配点

<details>
<summary><b>(1) 算子降级为 MQA，且 K=V=C（同一块内存用两次）</b></summary>

吸收后 $K,V$ 都退化成一个共享潜向量：

$$S = Q\,C^{\top},\qquad O = P\,C$$

注意这里 **PV 的右操作数就是 QK 的左操作数 $C$ 本身**（DeepSeek 在博客里明确写：*"in MLA, K and V are the same with different names"*）。FA 的内核假设你加载**两块不同**的 K、V，并分别放在 SMEM 的两块 buffer 里；这里只需加载**一块** $C$，被两个 GEMM 复用——load 一次、用两次，SMEM 预算、流水线、寄存器分配全部要改。

而且**头维度暴涨**：$d_k$ 从 192 变 576，$d_v$ 从 128 变 512。FA 的 tile 尺寸、`qk_scale`、SMEM 布局都是围绕小 head_dim 调的。

</details>

<details>
<summary><b>(2) 多出一次「Q 吸收」前置 GEMM</b></summary>

喂给内核的 q **不是原始 q**，而是先做过吸收的：

$$\hat q_{nope} = q_{nope}\,W^{UK}\quad (128 \to 512,\ \text{per head})$$

再和 RoPE 部分拼接成 576 维：

$$\hat q = [\,\hat q_{nope}\ (512),\ q_{rope}\ (64)\,]$$

这是一次 `[h_q, 128] × [h_q, 128, 512]` 的**逐头小 GEMM**，因为 $s_q$ 极小（1–2）所以很便宜，但它是 FA 里根本不存在的算子。（V4 更进一步，用 fused-norm-rope-attn-rope-cast 内核把 Q-norm / Q-RoPE / 核心注意力 / O-RoPE / cast-to-fp8 全融了。）

</details>

<details>
<summary><b>(3) 多出一次「输出低秩投影」后置 GEMM</b></summary>

标准注意力算完 $O$ 就结束了；但这里 $PC$ 得到的是 **512 维潜向量** $z$，还要再过 $W^{UV}$（512→128/head），再并入 $W^O$：

$$o_i = z_i\,W^{UV}_i,\qquad u = \sum_i z_i\,(W^{UV}_i W^O_i)$$

这是 FA 没有的第 4 个 GEMM，且是**逐头不同权重的 batched GEMM**，属于内核 epilogue。FA 的 epilogue 只做 softmax-normalize + 写回，不能容纳它。

</details>

<details>
<summary><b>(4) 寄存器压力 → 无法照搬 FA-3 的 ping-pong</b></summary>

这是新内核设计中最硬的一条约束：

- 输出 tile $64\times512$，fp32 → $64\times512 = 32{,}768$ 个 32-bit 寄存器；
- 一个 SM 只有 $65{,}536$ 个 32-bit 寄存器；

→ **一个 SM 只能容纳一个输出矩阵**。而 FlashAttention-3 的 ping-pong（两个 warpgroup 各持一半输出、交替占用 Tensor Core 与 CUDA Core）**需要两个输出矩阵**。既然放不下，FA-3 的调度**无法直接移植**。

</details>

<details>
<summary><b>(5) 它是 compute-bound，不是 memory-bound</b></summary>

直觉上 decode 应该是 memory-bound，但博客做了理论推导：FLOPs/byte

$$\frac{2h_q s_q s_k(d_k+d_v)}{2 s_k d_k} \approx 2 h_q s_q$$

H800 节流后实际峰值 ~865 TFLOPS / 3.35 TB/s，阈值 $\frac12\cdot\frac{865}{3.35}\approx128$。DeepSeek 的在线推理**decode 实例不做张量并行**，故 $h_q = 128$，$h_q s_q \ge 128$ ⇒ **compute-bound**。

这意味着设计目标完全反转：FA-decode 追求省带宽（访存打满即可），FlashMLA-decode 必须**把 Tensor Core 喂饱**，并让 CUDA Core（softmax/反量化）与 TC（GEMM）重叠。

</details>

<details>
<summary><b>(6) RoPE 无法吸收 → 两段 QK + Move Elision</b></summary>

$576 = 512 + 64$ 的切分导致 QK 是**两个 GEMM 相加**：

$$S = \underbrace{\hat q_{nope}\,C_{nope}^{\top}}_{512\text{-dim 可吸收}} + \underbrace{q_{rope}\,\text{RoPE}(k_{pe})^{\top}}_{64\text{-dim 不可吸收}}$$

FA 只做一次 QK。这里要么 concat 再算（浪费），要么两路算完相加（DeepSeek-V2 的 **Move Elision**）——内核必须显式支持。

</details>

<details>
<summary><b>(7) FP8 KV cache 引入「反量化瓶颈」</b></summary>

这是 FP8 版专用内核才有的问题：H800 **无法直接把 `float8_e4m3` cast 到 `bfloat16`**，必须

```
fp8 → half → float32 → bfloat16 → ×scale
```

博客的时钟周期分析：每个 token 的 MMA 只需约 **34 cycles**，而反量化要

$$\Big(\tfrac{1}{64}+\tfrac{1}{64}+\tfrac{1}{16}+\tfrac{1}{256}\Big)\times512 \approx 50\ \text{cycles}$$

→ 内核变成 **dequantization-bound**，Tensor Core 反而闲置。FA 的 fp8 路径没有这个结构。

</details>

## 3. $C$ tile 是怎么组织的

**KV Cache 就是潜向量矩阵 $C \in \mathbb{R}^{s_k \times 576}$**（V3/V3.1/V3.2），分页固定 **page_size = 64**。

- 每个 K/V tile 是 $64\times576$。
- **细粒度 TMA→GEMM 流水**：不是一次性搬一个 $64\times576$，而是拆成 **9 个 $64\times64$ 的 TMA copy**（$576 = 9\times64$）。**每完成一个 copy，对应那一段的 QK GEMM 就能开始**，从而把访存延迟藏起来。
- **Cache hint**：TMA copy 用 `cute::TMA::CacheHintSm90::EVICT_FIRST`，提升 L2 命中率。
- 因为 $K=V=C$，这块 tile **只加载一次**，两个 GEMM 共用——这是吸收路线在 SMEM 上的红利。

**FP8 变体**下每 token 的 $C$ 布局（共 **656 bytes**）：

| 区段 | 内容 | 字节 |
|---|---|---|
| 前 512 维（nope） | 512 × `float8_e4m3`（1×128 tile 量化） | 512 |
| 该 512 维的 scale | 4 × `float32` | 16 |
| 后 64 维（RoPE） | 64 × `bfloat16`，**不量化**（对精度敏感） | 128 |

内核里的处理：先**把 512 个 fp8 反量化成 bf16**，与 64 个 bf16 RoPE 拼接，再用 **bf16 MMA** 计算（输入 bf16、累加 fp32）——即「**FP8 只做存储，矩阵乘用 bf16**」。

## 4. Q absorption 在流水线里的位置

吸收把「$128$ 头 × $128$ 维的 K」变成「$128$ 头 × **共享的** $512$ 维」，本质是**把 MHA 的访存问题改造成 MQA 的算力问题**：

$$\underbrace{q_{nope}W^{UK}}_{\text{前置小 GEMM}}\ \to\ \hat q\in\mathbb{R}^{h_q\times512},\qquad \hat q \,\|\, q_{rope}\ \to\ \mathbb{R}^{h_q\times576}$$

- **前置 GEMM**（$h_q\times128 \times 128\times512$）因 $s_q$ 小，开销可忽略；
- **后置 GEMM**（$W^{UV}$，并可并入 $W^O$）放在 kernel epilogue；
- 中间的核心内核于是看到的是一个**干净的 MQA 问题**：$(h_q\times576)\times(1\times576)$ 的 QK，再加 $(h_q\times s_k)\times(s_k\times512)$ 的 PV。

这也解释了为什么它 compute-bound：head_dim 从 128 涨到 576/512，**每个字节的 KV 被复用了 128 次**（$h_q$ 个头共享），算术强度 $2h_q s_q$ 直接顶满。

## 5. Online softmax + 「seesaw」调度

### 标准部分
沿用 FlashAttention 的 streaming 逻辑：维护 running max $m$ 与 running sum，每个 block 做 rescale。$C$ 的每一列同时充当 K 和 V。

### 创新部分：单个输出矩阵上做 ping-pong
如前所述，$64\times512$ fp32 输出吃掉 $32{,}768$ 个寄存器，SM 放不下第二份，**FA-3 的双输出 ping-pong 不可用**。DeepSeek 的办法是：

- 把输出**竖切**成 $O_L, O_R$（各 $64\times256$），分属两个 warpgroup；
- 每次取**两个 KV block**（$K_0,K_1,V_0,V_1$，且 $V$ 也竖切为 $V_{0L},V_{0R},V_{1L},V_{1R}$）；
- 交错执行 12 步，让两个 warpgroup 的 **CUDA Core（softmax）与 Tensor Core（GEMM）天然错峰**：

```text
0. 维护共享 running max m 与 oL, oR
1. [wg0] p0 = q·K0ᵀ / qk_scale
2. [wg1] p1 = q·K1ᵀ / qk_scale
3. [wg0] mp0=max(p0); m_new0=max(m,mp0); scale0=exp(m_new0-m); m=m_new0
4. [wg0] p0 = exp(p0 - m_new0)
5. [wg0] oL = oL·scale0 + p0·V0L
6. [wg1] mp1=max(p1); m_new1=max(m,mp1); scale1=exp(m_new1-m); m=m_new1
7. [wg1] p1 = exp(p1 - m_new1)
8. [wg1] oR = oR·(scale0·scale1) + p1·V1R
9. [wg0] p0 = p0·scale1
10.[wg1] oR = oR + p0·V0R
11.[wg0] oL = oL·scale1 + p1·V1L
```

原理：当 wg0 在 CUDA Core 上算 `max/exp`（第 3、4 步）时，wg1 的 Tensor Core 在跑 `q·K1ᵀ`（第 2、6 步），反之亦然——**用一个输出矩阵就实现了双 warpgroup 的 TC/CUDA-core 交错**。DeepSeek 把它称作 **"seesaw"（跷跷板）调度**，数学上等价于 FA 的 online softmax。

配合 **TMA 的 `EVICT_FIRST`** 和「数据用完即发下一个 TMA」的时序，做到 **访存与计算重叠**。实测达到（节流后峰值的）**80% Tensor Core 利用率**和 **3 TB/s** 带宽。

## 6. FP8/BF16 Tensor Core 流水线组织

dense decode 用 bf16；FP8 KV cache 出现在 **sparse decoding（DSA, V3.2）**。流水线大致是：

```text
[Producer / TMA]  9×64×64 async copy  →  SMEM（EVICT_FIRST）
        │
[CUDA Core]       反量化 fp8→bf16（+scale），RoPE 段直接 bf16
        │
[SMEM]            C = [512 bf16 | 64 bf16]  (K=V)
        │
[Tensor Core]     WGMMA bf16×bf16→fp32：  QKᵀ  (576-dim, 两段相加)
        │
[seesaw warpgroups]  online softmax  ↔  PV (512-dim) 交错
        │
[epilogue]        ×W^{UV}/W^O，写回
```

因为 **反量化（~50 cyc）比 MMA（~34 cyc）还慢**，DeepSeek 又发明了 **"crossover"**：

- 以 **cluster = 2 个 CTA** 启动，每 CTA 负责同一 token 的 **64 个 query head**；
- 每 CTA 只 **load + 反量化一半** KV；
- 用 Hopper 的 **Distributed Shared Memory (DSM)**，通过 `st.async` 把反量化结果**写进同 cluster 另一个 CTA 的 SMEM**；
- 用 **cluster transaction barrier** 同步；交换后每个 CTA 都拿到**完整**的 bf16 K/V，再跑 MMA。

**每个 CTA 只需反量化一半 KV**，直接消掉一半反量化开销：FP8 sparse decode 从 **250 → 410 TFLOPS**（topk=2048；topk=32768 时可达 460）。

## 7. 全局 Schedule 与工程细节

- **Split-KV + Combine**：decode 只有 $s_q\in\{1,2\}$ 个 query，但 KV 很长，故把 KV 维切分到多 SM（`splitkv_mla`），再跑一个 `combine` kernel 合并（处理 lse / 输出缩放）。
- **Programmatic Dependent Launch (PDL)**：让 `combine` 在 `splitkv_mla` 尾部**重叠启动**，隐藏 kernel launch 与 tail 开销。
- **Tile Scheduler**：把 (request, block) 作业均衡地分给各 SM，避免长尾（`get_mla_metadata` 一次算好，循环内 `flash_mla_with_kcache` 复用）。
- 有趣的数据点：新 seesaw 内核在 **memory-bound** 场景比旧的 ping-pong buffer 版**略慢 ~2%**，但在 **compute-bound** 下从 580 提到 **660 TFLOPS**——换来的是正确的瓶颈方向。

## 8. 一句话回答「为什么能跑得快」

> **不是把 FA 换掉，而是先通过矩阵吸收把 decode 的算子从「MHA/带宽受限」改造成「MQA/算力受限」，然后针对这个新形态重做整套调度：单输出矩阵的 seesaw 双 warpgroup 交错、9 段 TMA→GEMM 细粒度流水、K=V=C 的 load-once-use-twice、FP8 存储+bf16 MMA+DSM crossover 反量化、以及 split-KV/combine 的 PDL 重叠。**
