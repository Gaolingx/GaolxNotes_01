## 判据重述:一个"状态机"就是一个生命周期持有者

- 两个生命周期**融合** → 需要同步;分布在两个节点/进程 → 需要**远程同步**。
- 耦合有两个直接代价,正是你点名的两条:
 - **回滚**:回滚 $A$ 必须连带回滚 $B$,且必须协调(分布式事务感)。
 - **空泡**:等待同步/互等期间被钉住的资源。论文里空泡有三种物理形态——**内存**(长寿命沙箱 + 保留状态)、**核内执行资源**(SMT sibling)、**镜像/存储**(被物化却不使用的数据)。
- 于是"持有者是谁"直接决定:要维护几个状态机、跨边界是**同步事务**还是**软状态/单向信号**。

DSec 全部设计收敛成一句话:**每个对象只有一个所有者,所有者尽量下推到离资源最近处,其余组件无状态;跨边界只留可容忍陈旧的视图或单向信号,绝不引入跨实例协商。** 回滚于是变成局部动作,空泡于是可被单边排空。

<details>
<summary><b>A. 控制平面:把所有权"编码"进名字,而不是"同步"进状态</b></summary>

**A1 最干净的一次下推:沙箱 ID 内编码 owning edge,apiserver 无状态。**
如果放置结果存在某个中心状态机里,"沙箱 X 在哪"就成了需要同步、需要回滚的全局状态。DSec 把归属**在出生瞬间冻进 ID**,apiserver 只查表转发。结果:路由路径上需要远程同步的状态机数 = $0$,apiserver 崩溃**无物可回滚**。这是全文你那条判据的标准范例。

**A2 placement / watcher 无持久化状态。**
放置视图是**允许陈旧的软状态**,watcher 重启后重新探测即可重建;真正的资源真值在 edge(本地准入,最后一票否决权)。这是刻意**拒绝两阶段提交**:若让 placement 权威化,placement↔edge 就得协商,placement 失败就要去对账本地资源(远程回滚)。把最终权威交给离资源最近的 edge,回滚范围收敛到单节点。

**A3 本地视图叠加 in-flight,不跨实例协调。**
每个 placement 实例把自己的"尚未被 watcher 快照反映的近期放置"叠加上去。代价是各实例互相看不见对方的 in-flight(可能的过载空泡),但换来零跨实例同步;兜底落在 edge 准入。这是用"本地近似"主动放弃全局精确——一个刻意的、有界的空泡。

**A4 IaC 全量重置 = 最便宜的回滚。**
定期从零重建所有控制面服务,要求"不依赖累积的人工状态"。无状态 ⇒ 回滚退化为"删掉重建"。这本质上是把回滚成本从"反向补偿"变成"幂等重放"。

</details>

<details>
<summary><b>B. 环境与镜像:把生命周期的粒度切开</b></summary>

**B1 base / workspace / toolkit 三层各自持有生命周期。**
单体镜像把三者的生命周期**焊死**:升 $m$ 个 base 要重建 $O(m\cdot N)$ 个 workspace 组合。解耦后只重建改动层,$O(m)$。EROFS mount vs tar 解包更能说明问题:**解包是把内容的生命周期"复制"进每个沙箱**(每沙箱各持一份,总盘写量 $5.5\times$);mount 让层留在平台手里(不可变、共享、引用计数),沙箱只拿到一层薄的可写 upper。论文特意讨论 overlayfs 的 **merge/append** 语义而非 bind-mount 的 replace——用你的话说,层生命周期必须**合并进命名空间**,而不是替换掉命名空间里原有的生命周期。

**B2 按访问模式切分读/写/元数据的生命周期。**
3FS 大顺序 I/O 强、小随机 I/O 弱,于是:写(不规则、小)**留在本地**(节点自持);读(按需、批量)去远端;元数据(小读)**预取本地**。eager pull 的错误在于:它把**整张镜像的生命周期先拉进沙箱**才允许启动——既造物化空泡(只用 4.2%–13.3% 的数据却写全量,完成时间 $1.7\times$),又造 straggler。on-demand 让镜像生命周期留在 3FS,沙箱只"借" working set。

**B3 (pack_diff) 把"会话生命周期"固化成构件,并必须在 build→run 交界处**截断**它。**
agent 可 checkpoint 沙箱为增量磁盘快照、再 restore 成新环境:运行时生命周期被 reify 成可复用构件。但 build 与 run 复用同一套基础设施,所以必须**显式切断生命周期**(builder/runtime 分账号、打包前清空可写层里的残留答案),否则 building 阶段的私有状态会漏进 running 阶段。这是"同一基础设施上两条生命周期交界处的卫生问题"。

</details>

<details>
<summary><b>C. 资源的空泡,在物理层长什么样</b></summary>

**C1 重复的页缓存 = 同一数据被 $N$ 个生命周期持有。**
microVM 里镜像数据 host 缓存一次、每个 guest 再缓存一次,$N$ 份彼此独立、彼此不感知。virtio-pmem+DAX 让这份 page cache **只由 host 持有** → 峰值内存 $-40.2\%$。这不是"优化",是**消除一个生命周期归属错误**。

**C2 guest 空闲页的空泡,需要 guest 自己吐出来。**
host 无法回收 guest 拥有的页;必须由 guest 通过 balloon free-page reporting 上报。默认按 order-9(2 MiB)上报,而冷文件页是**散落**的,凑不满高阶块 → 报不出去(典型碎片空泡)。DAMON 先用采样识别冷页、经内核回收路径把散页**聚拢**成高阶块,balloon 才能上报 → 时间积分内存 $-21.2\%$。注意跨边界协议是**异步单向报告**,不是 host 同步 poke guest——这条边界上不允许同步。

**C3 CPU 空泡 = SMT sibling;分配单元被提升到"核"。**
SCHED_IDLE 单独只改善 $3.4\%$,因为 LS 线程仍与 BE 共享物理核的 sibling 执行资源。core scheduling 把"核"作为 QoS 生命周期的分配单元 → 干扰 $45.2\%\to17.3\%$。残余来自 turbo/LLC/带宽——**这些资源调度器根本"持有"不了**,所以论文明确不再做带宽隔离。

</details>

<details>
<summary><b>D. RL 协同:全篇重心,生命周期归属的胜负手(展开)</b></summary>

**D1 拆开 agent loop 与训练器:状态机数 3→1。**
旧结构里三个状态机堆叠:GPU 训练器(可抢占)、agent loop(跑在训练 pod 内)、沙箱(在 DSec)。
- 训练器被抢占 → agent loop 生命周期死,而沙箱生命周期活着 → **两个状态机分叉**。
- 分叉就必须**对账**:靠 command log 把训练框架恢复的 rollout 状态与沙箱执行状态对齐,并对已完成操作走"记录结果而非重放",以免非幂等命令产生重复副作用——这正是分布式事务的味道。

V4.1 把 rollout 移到 DSec:**worker container + agent sandbox 共同持有完整 rollout 状态,作为唯一真源**,且都跑在可抢占池之外。于是 GPU 作业被抢占**碰不到** rollout 状态机,边界从"回滚/重放"退化成"重连"。**需要远程同步的状态机从 3 个降到 0 个**,回滚逻辑直接从 RL 框架里删掉。

**D2 pause/resume:把"谁持有状态"与"谁占用内存"拆开。**
抢占不可避免,沙箱状态必须活到 rollout 结束,于是训练暂停期间大量空闲沙箱钉着内存(纯空泡)。机制上:
- **逻辑生命周期**归 DSec → **保留**;
- **物理内存** → **释放**;
- RL 框架只持有"要不要暂停"的**决策**,不持有机制;后续任何请求**透明恢复**,调用方无需知道。

容器 vs microVM 的两种切法值得注意:容器冻结进程树 + swap + memory.reclaim(保活进程,MADV_WILLNEED 预取恢复);microVM 快照后**杀掉 Firecracker 进程**再重建恢复。前者回滚粒度是"活进程",后者把活状态**序列化成构件**——生命周期从"活的"转成"存的"。

**D3 TTL:回收的所有者必须是平台,而非用户。**
一个任务能瞬间起 32K 沙箱,不可能保证它逐个显式 stop。把回收权做成平台的**租约(TTL)**,就得到一个**不依赖对方存活、无需协商**的单边生命周期。被丢弃的会话不能永久占资源——这是 abandonment 场景下的默认回滚。

</details>

<details>
<summary><b>E. 边界与善后:哪些生命周期系统"持有不了"</b></summary>

**E1 隔离强度 = "状态机数量"旋钮。**
FnCall(无 aether/chronus、预创建容器复用、每次调用后 best-effort 清理,几乎无状态)→ container → microVM → full VM。边界越细,故障回滚越局部(一个内核崩了不拖垮整机),但**同节点密度越低、空泡越多**。论文的 user isolation 是**明说用密度换 blast radius**。Table 1 那张后端适配表,实质就是"生命周期所有权 vs 隔离"的权衡表。

**E2 agent 越界 = 逃出边界的回滚。**
`XFS_IOC_SWAPEXT` 打坏 XFS 元数据并触发文件系统 shutdown;`grep /proc/kpagecgroup` 触发内核 bug 崩内核;`yes` 的无界输出被 chronus 落盘到几十 GB。AppArmor 管文件/套接字(即便 root 也受控),eBPF 管网络白名单——本质是**把 fault 的生命周期钉在边界内**;`yes` 那条则说明**输出必须有界**,否则单条命令就能造出无界资源足迹。论文诚实承认:对抗性 agent 的生命周期**无法被完全持有**,访问控制只覆盖 reward hacking 的一部分,内核 bug 类破坏不在其内。

</details>

## 综合对照

| 子系统 | 生命周期持有者 | 需远程同步的状态机 | 回滚成本 | 空泡处理 |
|---|---|---|---|---|
| 路由/接入 | 无(归属编码进 ID) | $0$ | 无状态,无物可回滚 | — |
| placement/watcher | 软状态,可重建 | $0$(容忍陈旧) | 重启即恢复 | edge 准入兜底 |
| 环境层 base/ws/toolkit | 平台各持一份,不可变 | 无 | 只重建改动层 $O(m)$ | 不物化 ⇒ 无复制写 |
| 镜像数据 | 3FS 持数据,node 持元数据 | 按需拉取 | 无需整镜像 | 只用 working set(4%–13%) |
| microVM 页缓存 | host 持单份 | 无 | — | DAX 消重复 $-40.2\%$ |
| guest 空闲页 | guest 持,异步上报 | 单向 | — | DAMON 聚拢→balloon 释放 $-21.2\%$ |
| CPU 核 | 核为分配单元 | 无 | — | core sched 填 SMT 空泡 |
| rollout | DSec(worker+sandbox 唯一真源) | 无 | 重连而非重放 | pause 释内存、存状态 |
| 训练 | GPU pod,可抢占 | 与 rollout 解耦 | — | 抢占即让位 |

## 收束

把 DSec 当成一条判据的展开,最值得记住的三点:

1. **"沙箱 ID 内编码 edge" = 把归属冻进名字**,是消除路由侧全局状态机的最省手段;凡是能被编码进标识符的归属,都不应该被同步进中心状态。
2. **可容忍陈旧的软状态 + 离资源最近的硬权威(edge 准入)**,替代了两阶段提交;跨边界要么容忍陈旧,要么单向异步(balloon 上报 / pause 信号),**从不双向协商**。这样才能让回滚局部化。
3. **pause/resume 是全文最深的拆分**:它证明"逻辑生命周期的所有"与"物理资源的所有"可以分离——**状态留、内存走**。这一步同时解决了"错误回滚要不要丢掉长 rollout"和"训练挂起时的内存空泡"两个看似对立的问题,是本论文对"生命周期由谁持有"最本质的贡献。

反过来说,凡是这套模型失效的地方(内核 bug、无界输出、turbo/LLC 残余干扰),都恰好是**平台无法持有其生命周期**的对象——这也从反面印证了你的判据。

## 结论先说:方向成立,归因错位

"DSec 能跑 DSH 也能跑别的 agent"——**这个结论论文是支持的**。但把它归因于"训练过程和 Agent 解耦"不准确;真正让它成立的机制是另一根正交设计轴。你那句"生命周期由谁持有"恰好能把这层混淆切开。

---

## 一、论文里其实有**两根**解耦轴,别混成一根

| 解耦轴 | 被切开的两个生命周期 | 出处 | 目的 |
|---|---|---|---|
| **垂直(时间维)** | rollout 生命周期 $\perp$ trainer 生命周期 | §6.2 | 训练器被抢占不拖死 rollout |
| **水平(种类维)** | scaffold 生命周期 $\perp$ 平台控制生命周期 | §6.2 worker | 换 DSH / OpenCode / 多agent harness |

你说的那句"训练与 Agent 解耦"只对应**第一根**(而且被解耦的是"训练器 vs rollout",不是"平台 vs agent")。真正支撑"能换 agent"的是**第二根**。

## 二、支撑你结论的原文(这一根)

**① 生态前提(§1):**
> "a growing ecosystem of agent tools and orchestration harnesses, such as DeepSeek Harness (DSH), **OpenCode**, and **multi-agent training harnesses**."

**② 关键机制的原文(§6.2)——这句话你直接可以拿来当证据:**
> "...separate it into two components: an **agent sandbox, which hosts the scaffold (e.g., DeepSeek Harness) and its tools**, and a **worker container**, which manages the sandbox and provides a **scaffold-agnostic control layer** for the rollout."

`scaffold-agnostic control layer` 是全文唯一一次把"agent 无关性"写成明确设计目标 —— 而它是 **worker container** 的属性,不是"训练解耦"的属性。

**③ DSH 被归到了可替换的那一层(§5.1):**
> "...one or more frequently updated **toolkits (e.g., the DeepSeek Harness)**."(生产周内平台服务了 103 个 toolkit)

也就是说:**DSH 同时以"toolkit"和"scaffold"两种身份出现**。它被装进"环境三层(base / workspace / **toolkit**)"里可独立版本化的那一层——这才是"可换"的物理位置。

## 三、用你的判据重演一遍:为什么必须这样切

假设 **scaffold 自己持有 rollout 状态**:
- 换 DSH → OpenCode,等于**换掉一个状态机**;
- 上一轮讲的恢复路径(command-log 对账、非幂等命令的"记录结果而非重放")全部要针对新 scaffold 重写;
- 水平方向的回滚能力直接归零。

DSec 的做法是:**把"rollout 控制生命周期"从 scaffold 手里拿走,交给 scaffold-agnostic 的 worker**,由 `worker + agent sandbox` 共同持有 rollout 状态并作**单一真源**;scaffold 只保留"沙箱内的执行生命周期"。于是:

$$ \text{可替换性} = \text{边界清晰的副产品} $$

而**不是**"训练解耦"的副产品。这跟你上一轮那个最深的拆分(**pause/resume:状态留、内存走**)是同一招的第二次出现——**把"谁持有"与"谁执行"分开**。DSec 在这里切了三次:

- worker = 持有**控制**生命周期(scaffold-agnostic)
- agent sandbox = 持有**隔离/执行**生命周期(scaffold 无关)
- scaffold/toolkit = 持有**内容**生命周期(可替换,如 DSH)
- 训练器 = 持有 **GPU** 生命周期(可抢占)

## 四、但严格说,你的推断要打四条补丁

1. **实证缺位**:§8 明说 "*the framework integration in [§6] is outside the evaluation scope*"。整篇评测只测了镜像/内存/CPU/分层,**跨 scaffold 的通用性没有任何量化证据**,它是架构声明,不是实测。
2. **能力 ≠ 事实**:生产数据(3M 沙箱/天)几乎全是自家 DSH 流量。"能用其他 agent 数据"是可替换性**能力**陈述,论文没给你"已经在用别家 agent 数据"的证据。
3. **残留的 agent-specific 耦合没被切**:§6.4/6.5 的访问控制、网络白名单、reward verifier,以及 §6.1 的环境构造,都可能是 scaffold/task 相关的。换 scaffold 时这些是否要重写,论文回避了。
4. **co-design 是双向刃**:§6 标题就是 "Co-design with **the** RL framework"——训练侧集成是**框架特定**的;只有 scaffold 侧被显式做成 agnostic。所以"平台对 agent 中立"成立,"平台对训练框架中立"并不成立。

## 五、如果你想把推断升级成能站住的版本

> "DSec 把 **rollout 控制**从 **scaffold** 和 **trainer** 双向剥离:对 trainer 剥离的是**时间生命周期**(可抢占不再中断 rollout);对 scaffold 剥离的是**控制生命周期**(以 worker 的 scaffold-agnostic 层为合同边界)。因此只要一个 agent 能以 toolkit/scaffold 形式装入沙箱并遵守该控制合同,它的数据就能进同一套 rollout 流水线——DSH、OpenCode、多 agent harness 都属此类。"

这样表述:结论不变,归因从"训练解耦"改成"**双重剥离 + scaffold-agnostic 控制合同**",并且诚实标注了"架构支持但未实证"。你原来的推断**成立,只是少了一个中间变量**。
