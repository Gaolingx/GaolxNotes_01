# 帧同步 状态同步 确定性 需求 差异 说明

## 🧑‍💻 User

帧同步话可能需要你手搓一个确定性物理引擎在server实时跑，状态同步为什么不一定

---
## 😀 默认助手 (7)

# 核心一句话

**确定性是"多台独立机器必须算出同一个结果"时才需要的东西。帧同步把这个需求强加给了所有人（客户端 + 可能的服务器），状态同步只有一个权威模拟器在算，别人只负责"看"，所以不需要确定性。**

---

## 一、帧同步为什么把你逼到手搓确定性物理引擎

### 1. 帧同步的本质：服务器只转发输入

帧同步（lockstep / deterministic lockstep）里，服务器**默认根本不算物理**。它做的事只有：

- 收集每个客户端本帧的输入（按键、指令、目标点）
- 盖上帧号，按帧广播给所有人
- 保证大家拿到**同一组输入、同一顺序、同一帧号**

物理、碰撞、伤害结算、寻路……全都在**各个客户端本地各算一遍**。

### 2. 于是"相同输入 → 相同结果"成了硬约束

因为没人广播结果，客户端之间没有任何"对答案"的机制。只要 A 的机器算出"这一炮打中"，B 的机器算出"这一炮擦过"，两个人看到的世界就永久分叉了 —— 而且**没有任何东西能把它们拉回来**。

这要求的是**比特级一致**（bit-exact），不是"数值上差不多"。数学上就是把模拟写成纯函数：

$$
S_{t+1} = f(S_t,\; u_t), \qquad f \text{ 在所有机器上必须完全等价}
$$

### 3. 浮点数天生不满足这个条件

同一段 `float` 代码在不同环境可能给出不同低位结果，来源包括：

| 来源 | 例子 |
|---|---|
| 指令集 | x87 80 位扩展精度 vs SSE 32/64 位 |
| 融合乘加 | FMA 合并 `a*b+c` 改变舍入 |
| 编译器优化 | `-ffast-math`、重结合、自动向量化 |
| 数学库 | `sin/cos/sqrt/pow` 各平台实现不同 |
| 求值顺序 | 遍历容器顺序、多线程归约顺序 |
| 随机数 | RNG 实现、种子策略、调用次序 |
| 碰撞求解 | 接触点排序不稳定、迭代收敛顺序 |

所以帧同步工程上的标准解法就是你说的"手搓"：**定点数（fixed-point）数学库**、固定步长积分、确定性排序的碰撞宽相/窄相、确定性 RNG、禁止 `-ffast-math`、固定编译工具链、单线程或确定性并行归约。

### 4. 那"服务器实时跑一份"是为什么？

纯帧同步服务器确实不用跑。但一旦你加上下面任何一条，服务器就**必须能重建同一个世界**：

- **中途加入 / 断线重连**：新客户端要追上当前世界，服务器得给出一个"可信的当前状态"
- **观战 / 回放 / 录像**：需要确定性重演
- **服务器校验 / 反作弊 / 裁决**：服务器拿输入历史重算一遍，和客户端上报的结果比对
- **权威判定**：谁赢了、这局有效无效，不能由客户端说了算

而"重建同一个世界"只有在服务器跑**同一份确定性实现**时才成立。于是服务器也必须：同样的定点数学、同样的碰撞顺序、同样的 RNG 消耗节奏 —— 这就是"手搓确定性物理引擎在服务器实时跑"的由来。注意它通常不是重新发明力学，而是**重新发明数值与调度**：把不确定的东西全部铲掉。

## 二、状态同步为什么"不一定"需要

### 1. 因为权威模拟只有一份

状态同步（state sync / snapshot + delta）里，服务器**就是唯一那个模拟器**。它跑普通物理（PhysX、Havok、Rapier、自研 float 版本都行），然后把状态或增量广播出去：

- 位置、朝向、血量、动画状态
- 或者只发变化的 delta
- 客户端**插值 + 外推 + 渲染**，它不负责"判定"

确定性之所以被需要，是因为要让两台机器收敛到同一结果。这里只有**一台**机器产生结果，其他机器是结果的**消费者**。没有对比对象，就没有分叉问题 —— 也就没有确定性需求。

### 2. 客户端的误差不需要"对上"，只需要"好看"

状态同步里客户端算错了怎么办？服务器下一帧的权威状态直接覆盖它。误差 $\varepsilon$ 只要在**视觉可接受范围内**、能被插值和平滑吸收即可：

$$
\text{视觉误差} \le \text{可容忍阈值}, \qquad \text{而帧同步要求} \; \varepsilon = 0
$$

这是一个**连续容忍**的要求，而不是**离散精确**的要求。差别巨大。

### 3. 商业引擎直接用就行

这是最直观的后果：状态同步项目里你可以直接抱 PhysX / Havok，甚至不用管跨平台一致性；帧同步项目里用这些库几乎是自找麻烦（除非它明确提供确定性模式）。

## 三、对比一览

| 维度 | 帧同步 | 状态同步 |
|---|---|---|
| 权威模拟在哪 | 各客户端（可能 + 服务器校验） | 服务器独此一份 |
| 需要确定性 | **必须，比特级** | 不必须 |
| 服务器跑物理 | 默认不跑；校验/重连时才跑同一份 | 一直在跑，普通物理即可 |
| 带宽 | 极小（只发输入） | 较大（状态/delta） |
| 服务器 CPU | 低（转发）／校验时高 | 高，随实体数 × tick 率增长 |
| 反作弊 | 难（完整状态在客户端） | 容易 |
| 重连/观战 | 难，需要确定性重建 | 天然支持，发个快照就行 |
| 可承载规模 | 极大（RTS/大规模单位） | 受服务器算力限制 |
| 延迟耦合 | 强，受最慢的玩家拖累 | 弱，各自插值 |

<details>
<summary><b>一些容易混淆的边界情况（点开）</b></summary>

**1. 状态同步也有"局部确定性"需求**
客户端预测（client-side prediction）要求客户端能**重演自己角色的移动**，才能做回滚调和（reconciliation）。但这是：
- 只针对本地玩家可控实体
- 客户端和服务器跑**同一份代码**
- 不一致时由服务器覆盖修正

这是"局部一致 + 允许纠错"，不是"全局比特级确定"。性质完全不同。

**2. 回滚网络码（GGPO / rollback netcode）是中间态**
它需要确定性，但只在客户端之间，而且是"同一平台 / 同一构建"级别即可。跨平台联机会立刻暴露浮点问题 —— 这也解释了为什么很多格斗游戏跨平台时会踩坑。

**3. 状态同步不是"免费"的**
它只是把确定性成本换成了**带宽 + 服务器算力 + 预测复杂度**。实体多、tick 高的时候，服务器成本会非常难看。

**4. 两者可以混血**
- 帧同步项目里常加**服务器权威校验**：平时转发，争议时重算
- 状态同步项目里也可能主动上**定点数**：不是为了跨机一致，而是为了让服务器模拟不同机器/不同时间跑出可复现的结果，方便复盘和自动化测试

**5. "实时跑"不一定是真实时**
帧同步的服务器校验完全可以**离线批量重算**（存完整输入历史，事后从头快进），或者低优先级异步跑。真正要求"和客户端同帧率实时推进"的，是**在线仲裁**那种场景。多数校验是"事后算账"。

</details>

## 四、一句话判断标准

> 问自己：**这个模拟结果，会由几台机器独立产生？**

- 只有服务器一台 → 状态同步，**不需要确定性**，普通物理引擎即可
- 客户端各自产生、且必须互相吻合 → 帧同步，**需要确定性**，该手搓就得手搓

所以"状态同步为什么不一定"的答案可以压缩成：**因为确定性是解决"多机分歧"的工具，而状态同步在设计上就把分歧消灭了 —— 只有一个人说了算。**
