## 😀 默认助手 (7)

# Agent = Model + Harness：一个 Harness Meta-Framework 的设计稿

先把我对这个式子的理解摆出来，因为它决定了框架的第一性对象。

`Model` 是**随机过程**：给定上下文，采样出一个 token 序列。`Harness` 是**把这个随机过程约束成可靠系统的全部确定性工程**——它决定模型每一步看到什么、能做什么、做完之后世界如何变化、以及事后我们如何相信它确实做了。

所以我认为 harness 的本质不是「编排（orchestration）」，而是**约束、投影与回放**。而「meta」的意义在于：它不该交付 *一个* agent，而该交付 **agent 的空间 + 组合代数 + 可观测的约束系统**。

---

## 一、三条公理

设计任何 meta framework，最重要的动作是选对**不变量（fixed points）**。我把它们压到三条：

**公理 1：日志即真相（Log is the source of truth）。**
一切皆事件，且只追加。内存里的任何状态都必须能从事件日志重建。这条公理一旦立住，回放、时间旅行、分支调试、评测、审计就全部是**免费推论**，而不是后期补丁。

**公理 2：上下文是被编译的产物，不是字符串拼接。**
「模型此刻看到了什么」必须是一等、可序列化、可 diff、可解释的 artifact。它由日志 + 外部资源，经一次**带预算约束的编译过程**生成。

**公理 3：控制是中间件，不是状态机。**
框架应优先暴露可组合的拦截器，环绕两个原语（模型调用、工具调用），而不是逼用户去画一张图。图不可组合、难版本化、难测试；中间件可以。

> 一句话：**Event 是事实，Effect 是请求，Context 是编译结果，Control 是函子。**

---

## 二、分层架构

| 层 | 职责 | 关键抽象 | 是否可替换 |
|---|---|---|---|
| L0 原语 | 定义宇宙 | `Event` / `Effect` / `Model` / `Tool` | 冻结 |
| L1 内核 | 推进轨迹 | `reducer` / `executor` / loop controller | 极少替换 |
| L2 上下文编译器 | 决定模型看到什么 | `Project` / `Slice` / `Budget` / `Render` | 高频替换 |
| L3 控制面 | 决定怎么走 | `aroundModel` / `aroundTool` / `aroundTurn` | 高频替换 |
| L4 能力面 | 决定能做什么 | `Capability` = schema + handler + policy + cost | 高频替换 |
| L5 状态与记忆 | 决定记得什么 | `Scratchpad` / `Session` / `DurableMemory` | 可替换 |
| L6 安全与权限 | 决定允许什么 | Capability token / 审批闸口 / 沙箱后端 | 必须可替换 |
| L7 观测与评测 | 决定如何相信 | `replay` / `fork` / `assertOnTrajectory` | 冻结接口 |

关键判断：**L2 才是差异化战场**。绝大多数 harness 框架把 90% 精力花在 L3（编排）和 L4（工具）上，然后把 L2 写成一坨 `messages.push(...)`。但真正决定 agent 质量的，恰恰是「每一步塞进 context window 的那几千 token 是怎么选出来的」。

## 三、L0/L1：内核长什么样

```ts
// 事件是已发生的事实，Effect 是尚未发生的请求 —— 这个分离是幂等、审批、重放的基础
type Event =
  | { t: 'message';  role: Role; content: Content }
  | { t: 'tool_call'; id: string; name: string; args: unknown }
  | { t: 'tool_result'; id: string; ok: boolean; value: unknown }
  | { t: 'decision';  reason: string }          // "我为什么再跑一轮"
  | { t: 'checkpoint'; label: string }
  | { t: 'budget';    kind: 'tokens'|'cost'|'turns'; delta: number }
  | { t: 'interrupt'; reason: 'approval'|'budget'|'policy' }

type Effect =
  | { e: 'call_model'; ctx: CompiledContext }
  | { e: 'invoke_tool'; name: string; args: unknown; token?: CapabilityToken }
  | { e: 'ask_human';  question: string }
  | { e: 'halt';       reason: string }

// 内核只有两个纯函数 + 一个循环
declare function reduce(state: State, ev: Event): State
declare function step(state: State, model: Model): Effect[]
```

内核刻意做小：**它不理解「agent」，只理解轨迹如何推进。** 所有聪明的东西都在 L2–L6 的插件里。

## 四、L2：上下文编译器（我最想赌的一层）

传统写法是「把历史消息全塞进去」。我想要的是一套**声明式投影语言**：

```ts
const ctx = compile(trajectory, {
  system: persona,                              // 不变量
  pins: ['task_spec', 'current_plan'],          // 永不淘汰
  slices: [
    recent({ last: 12, roles: ['user','assistant'] }),
    retrieve({ query: '$lastUserTurn', topK: 8, from: 'durable' }),
    fold({ over: 'all', strategy: 'hierarchical', targetRatio: 0.3 }),
  ],
  budget: { tokens: 32_000, reserve: 2_000 },
  render: 'anthropic-xml' // 或 'openai-md' / 'tool-native'
})
```

三个设计点：

1. **Provenance 是必须的。** 每个 slice 都能回答「这段内容为什么在这里、来自哪个事件」。这是调试长程 agent 唯一的抓手。
2. **预算是约束求解，不是截断。** 超预算时按优先级 / 相关性 / 新鲜度做淘汰，而非从中间砍一刀：
   $$ \max_{\text{keep}} \sum_i \text{value}(s_i) \quad \text{s.t.} \sum_i \text{cost}(s_i) \le B - \text{reserve} $$
3. **Compaction 是一等策略。** 历史折叠（hierarchical folding）应该可插拔、可对账——折叠后的摘要必须能追溯到被折叠的原始事件。

> 我的立场：**上下文编译器做得好，等于免费涨一个模型档位。**

## 五、L3–L4：控制面与能力面

控制面用洋葱模型，两个环绕点足够表达绝大多数模式：

```ts
harness.use(
  retry({ on: Timeout, max: 3 }),
  reflect({ when: 'tool_result.ok === false', rounds: 1 }),
  planThenExecute({ planFormat: 'checklist' }),
  budgetGuard({ tokens: 200_000, costUSD: 5 }),
  approvalGate({ when: cap => cap.write && cap.scope === 'prod' }),
)
```

「多 agent」不是新原语，而是 `aroundTool` 里把「工具调用」换成「子 harness 调用」——**sub-agent 就是一个被中间件装饰的、有独立预算和独立日志的 tool。** 这样拓扑组合就对上层透明了。

能力面（Tool）我坚持四件套：

```ts
type Capability = {
  schema: JSONSchema          // 模型看的
  handler: (args, ctx) => Promise<Result>
  policy: Policy              // 权限、限流、审批
  cost: CostModel             // 预估 token/延迟/金钱，供 L2 预算使用
}
```

**MCP 是一等公民**（外部能力走标准协议），但我倾向于同时提供 **code-as-action**：让模型写一小段代码去调用能力，而不是逐条 JSON tool call。对多步、可组合的任务，这能显著压缩轨迹长度和轮数。

## 六、L5–L7：记忆、安全、可观测

<details>
<summary><b>L5 状态与记忆：三层，且带写入策略</b></summary>

- **Scratchpad**：单轮内推理草稿，可丢弃。
- **Session state**：任务级结构化状态（计划、已确认事实、待办）。**结构化优于自然语言历史**——这是长程任务不漂移的关键。
- **Durable memory**：跨会话。它有两个必须显式设计的策略：*写入策略*（何时记、记什么、去重）与 *检索策略*（何时读、topK、重排）。

底层用 append-only log + compaction（tombstone / rollup）避免无界增长；记忆是**项目**，不是**存储**。
</details>

<details>
<summary><b>L6 安全与权限：capability-based，而非 allow-list</b></summary>

- 权限用**可传递的 capability token** 表达（谁、对什么、在什么范围、多久），而不是全局白名单。子 agent 只能继承能力的**子集**，天然满足最小权限。
- **审批闸口是 Effect 的一种**：`ask_human` 可暂停轨迹、序列化、恢复。人机协作因此不是特例分支。
- **沙箱是可替换后端**（本地进程 / 容器 / 微虚拟机 / 远程）。核心逻辑不感知隔离方式。
</details>

**L7 是公理 1 的红利，几乎零额外成本：**

```ts
replay(log)                  // 确定性重放
fork(log, atStep = 7)        // 从第 7 步分叉，试另一条路
assertOnTrajectory(log, t => // 评测 = 对轨迹的断言
  t.toolCalls.every(c => c.args.path.startsWith(workspace)) &&
  t.totalCost < 1.0)
```

**离线评测与在线监控因此使用同一套语义。** 这是我拒绝「先做功能，可观测以后再补」的根本原因。

## 七、Meta 的地方：变体点即配置

真正让它「meta」的，是把所有变化点显式化为一个 **Harness Spec**：

```yaml
profile: coding-agent
topology:   { kind: orchestrator, maxDepth: 2 }
context:    { slices: [...], budget: 64000, compaction: hierarchical }
capabilities: [fs, git, shell, mcp:*]
memory:     { durable: sqlite, writePolicy: on-checkpoint }
policy:     { fs: workspace-only, shell: sandboxed, prod-write: approve }
budgets:    { tokens: 500k, costUSD: 20, wallclock: 30m }
observability: { trace: otlp, replay: true, snapshotEvery: 5 }
```

运行时解释这份 spec，同时每个字段都支持 **代码逃生舱**（`context: (traj) => ...`）。声明式负责 80% 的常规配置，代码负责剩下 20% 的怪需求——**但两者共享同一套原语**。

## 八、我拒绝做的（同样定义了框架）

| 反模式 | 理由 |
|---|---|
| 把 State Graph 当主抽象 | 图不可组合、不可 diff、不可测试；中间件代数可以 |
| 隐式 prompt 拼接 | 无法解释、无法回放上下文 |
| 单厂商 / 单模型耦合 | render 层必须可切换；能力探测要运行时化 |
| 可观测事后补丁 | 破坏公理 1，回放/评测全部失效 |
| 把「记忆」做成黑盒向量库 | 没有写入策略的记忆等于噪声累积 |
| 用轮数而非预算做终止条件 | 真实约束是 token / 成本 / 墙钟 |

## 九、落地顺序（如果明天开工）

1. **先做内核 + Event Log + replay。** 哪怕只有一个 echo 工具，只要能重放。
2. 再做 **上下文编译器**（这是护城河，别外包给 prompt 字符串）。
3. 上 **中间件控制面** 和 **capability + policy**。
4. 最后才是多 agent 拓扑、记忆、UI。

顺序不可逆：**可回放性必须在第一天存在，否则它永远补不上。**

## 十、开放问题（我还没想清楚的）

- **上下文压缩的理论**：多长的轨迹折叠成多短的摘要，信息损失可度量吗？我怀疑需要类似率失真的框架，但目前只有启发式。
- **不确定性下的一致性**：重放时模型输出会变（温度、版本漂移）。「重放」应重放 *模型采样结果*（记录 seed/logprob 或直接缓存）还是 *决策*？我倾向前者，但那让 log 变大。
- **跨 agent 的统一语义**：子 agent 的预算、权限、日志如何与父轨迹合并成一条可审计的线？继承容易，**归因（attribution）难**。
- **context 编译器的可评测性**：我们如何知道「这版切片策略」比上一版好？需要一套针对上下文的消融实验协议。

**总结成一句设计宣言：**

> 不要在 harness 框架里造「智能体」，要造一整套让智能体的**随机性变得可约束、可解释、可回放、可组合**的系统——Truth 是日志，Product 是上下文，Control 是中间件，Safety 是能力，而 Meta 是把这些变化点诚实暴露出来的代数。

你这个观察很准，而且我觉得它指向的不是「用词不严谨」，而是一个**真实的层混淆（layer confusion）**。我先把那个流行的定义拆开，因为它内部就是矛盾的。

## 一、「自己拿主意的模型」为什么是个范畴错误

流行说法是：**agent = 自己拿主意的模型，harness = 外面的脚手架。**

问题在于——「拿主意」这个动作，拆开来看，需要下面这一整套东西才能成立：

| 「决策」的必要条件 | 谁来提供 |
|---|---|
| 动作空间（有哪些「下一步」是可表达的） | harness |
| 状态表示（此刻世界是什么样） | harness（context compiler） |
| 意图→动作的接地（把 token 解析成一个 tool call） | harness |
| 副作用执行（真的改变世界） | harness |
| 终止条件（什么时候叫「做完了」） | harness |
| 失败恢复、重试、回滚 | harness |

这六项**没有一项**来自模型。模型的输出只是词表上的一个分布 $p(\text{token} \mid \text{context})$。它做的不是「拿主意」，而是**打分**。真正「拿主意」——即提交一次状态转移——这个动作发生在 loop 里。

用形式化说：harness 定义一个 MDP $(S, A, \delta)$，模型只提供策略 $\pi_\theta(s)$。所谓「模型自己决定」，精确含义是：

$$\arg\max_{a \in A} \; \pi_\theta(a \mid s)$$

注意 $A$ 和 $s$ 都是 harness 给的。**模型永远只能在一个别人替它画好的集合里排序。**

所以你那句「误以为模型不靠脚手架也能自己决定下一步」，我认为是对的，而且是关键：**去掉脚手架之后，根本不存在「下一步」这个东西，只有一次补全（completion）。** 补全不是一步。把 text 变成 world-change 的那一跃，100% 是脚手架干的。

> 结论：**Agency 不是模型的属性，是 loop 的属性。** 「会拿主意的模型」是一个观察者视角，不是一个本体。

## 二、agent / harness 其实是**视角对偶**，不是两种东西

我觉得这个混淆有个很干净的解法：

- **从外面看**，一个在追求目标的东西，我们叫它 **agent**。
- **把它拆开看**，它是 模型 + 一段程序；那段程序，我们叫 **harness**。
- **再往上抬一层**，整个 agent 对它的父级来说，就只是一个被调用的 **tool**。

同一个对象，不同缩放级别，三个名字。所以大家分不清是正常的——**它们本来就是重叠的**。那句话想命名的其实是「一次组合里的两个角色」，而不是「两类实体」。

这也解释了「harness」这个词义的漂移：

<details>
<summary><b>为什么 harness 的含义会越变越大</b></summary>

最初 harness 来自 test harness——纯粹的**外部观测/驱动装置**，它不参与「智能」，只负责夹住被测对象。

后来大家做 agent 时发现：真正要写、要调、要负责的那部分，**就是**那套脚手架。模型是买的，脚手架是自己写的。于是 harness 从「外部观测装置」变成了「agent 里你亲手 authored 的那部分」。

但「agent」从外面看又涵盖整体。于是两个词开始互相吞噬。大家于是回头去找那条界线，就找到了「谁拿主意」这条——但它不成立，因为拿主意本身也要脚手架。

</details>

我更愿意用一对**工程上**可判定的词，而不是本体论词：

- **agent** = 一个*正在运行的实例*（有状态、有生命周期、可能不可复现）。
- **harness** = 生成它的那段*可复用的程序*。

类比：**进程 vs 内核 / 实例 vs 类**。前者是你观察到的行为，后者是你能版本化、能测试、能 review 的东西。

## 三、模型变强，harness 会变小吗？——不会，它只是**往上移**

这是第二个常见幻觉：模型越来越会规划、会用工具，harness 迟早会被「吃掉」。

我的判断是：**harness 的复杂度跟部署严肃度成正比，跟模型能力几乎无关。**

- 模型变强 → 你开始接**更难的任务** → 更难的任务需要更多治理（权限、审计、成本、合规）。
- 模型变强 → 一些「笨」的中间件（解析、格式修复、简单规划）变冗余 → 但这些是 harness 里**最不值钱**的一层。
- 同时新长出来的东西：子 agent 拓扑、跨会话记忆、审批闸口、预算编排——都在更高层。

类比很直接：**CPU 快了 1000 倍，操作系统没有消失。** 变的只是 user/kernel 接口的位置。ISA 边界在移动，OS 在变胖。

所以真实图景是一条**移动的均衡**：模型吸收下层，harness 长出上层。净复杂度大致守恒甚至上升。

## 四、那为什么还需要一套统一的 meta framework

前提摆清之后再回答这个,答案就不是「少写代码」。**少写代码是个副产品，不是价值。** 真正的价值有四条，按重要性排：

**1. 可复现性 —— 这是让随机系统变得可工程化的唯一路径。**
Agent 是有状态 + 随机的。没有统一 runtime，就没有同一条轨迹语义，你既不能重放也不能 A/B。统一框架**最主要的出口不是 API 好不好用，而是 eval 能不能复用**。这一条是地基，其他三条都建在它上面。

**2. 模型可移植性 —— 穿越能力跑步机。**
模型每几个月换一代。如果把逻辑和某个模型的怪癖缠在一起，每次升级都要重写。框架的作用是把**策略（模型）和程序（harness）解耦**，让换模型变成改配置。这在当下是 ROI 最高的一条。

**3. 治理 —— 把「我们希望」变成「我们能证明」。**
权限、PII、审批、成本上限，你想要**一个地方**强制，而不是 N 份各写各的。集中策略是「可审计」和「碰运气」的分界线。

**4. 组合与知识沉淀。**
retry / context / budget / permission 这些原语，每个团队都重造一遍。更贵的是那些**踩坑得来的隐性知识**（上下文怎么压、tool schema 怎么写、错误信息怎么给），框架把它编码一次，而不是每个项目重新悟一遍。

再加一条最「meta」的：一旦语义统一，同一份 spec 就能编译到不同后端（本地 / 云 / 批处理）——这就是 Terraform 之于 IaC 的东西。

## 五、诚实的反面：什么时候**不该**建这个框架

<details>
<summary><b>反方论证（我认为相当强）</b></summary>

- 框架会**僵化**。你今天建的框架会固化今天的假设（JSON tool call、单 agent loop）。下一个模型能力出现时，抽象层反而挡路。
- 目前**最好的 agent 往往是手写的 loop**。前沿移动太快，跟得上的抽象还没成型。
- 过度抽象会杀死探索空间。

所以我的结论不是「一定要有」，而是：**框架的合法性，取决于它是否遵守细腰原则（thin waist）**——冻结的内核极小，其余全部热插拔，处处留代码逃生舱。内核要小到「新模型能力出现时不需要重写框架」，恰恰是框架价值的来源。

</details>

## 六、把话收回来

- 「agent 是拿主意的模型，harness 是脚手架」——这句话把**视角**当成了**本体**。拿主意需要脚手架，所以不存在「裸的决策者」。
- 更耐用的区分是：**agent 是运行中的实例，harness 是可复用的程序**；或者更彻底一点——**agent 是 harness 从外面看的样子，harness 是 agent 从里面看的样子。**
- 统一 meta framework 的价值不在这句话的哪个版本，而在于：它让**随机、有状态、多变的模型**，变成**可信、可复现、可治理、可换**的系统组件。

一句话：**框架的价值，正是它不去假装自己是那个「拿主意的东西」——它只做所有 agent 脚下那块不动的地板。**
