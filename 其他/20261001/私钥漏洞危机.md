# 锐评：当 384 位私钥的实际取值是 $d=4$

先说结论：这件事的荒诞程度，完全不需要靠“阿三”来加戏；用国别去解释，反而会低估它，因为**换成任何国家的 CA，只要跑同一段坏脚本，结果一模一样**。这是 WebPKI 的世界级笑话，不是某国的土特产。

## 一、事实骨架（先对齐）

| 项 | 内容 |
|---|---|
| 当事方 | eMudhra / emSign（印度 CA，Mozilla、Microsoft、Apple、Chrome 四大根证书库均在列） |
| 受影响 | 8 张中间 CA：6 张 TLS（DV、OV、EV，G3B、G3C）+ **2 张代码签名**（EM OV CS CA - G3B、G3C） |
| 密钥类型 | **P-384 ECC** |
| 密钥取值 | $d \in \{4, 56, 66, 115, 155, 156, 230, 237\}$ |
| 生成时间 | 2025 年 4 月（一说 4 月 30 日）的 key ceremony |
| 披露 | 2026-10-17 20:06 UTC 提交 Mozilla；署名研究者 Wayne 用**每把私钥各签一句** “we have a problem — Wayne” 作为证据（能签名即证明持有私钥，不必交出私钥，只信数学） |
| 复现 | Scott Helme 在笔记本上从公开证书里恢复出私钥，**< 1 秒** |
| 撤销理由 | CCADB 记录为 `cACompromise` |
| 应急 | Chrome CRLSet 约 1 小时 40 分、Mozilla OneCRL 约 2 小时 53 分完成云端阻断；Apple、Microsoft 数日内跟进；Firefox 158.0.1、ESR 153.5.1、115.43.1 与 NSS 3.131.1 直接移除根证书；Go 发布 1.27.3、1.26.10，把 8 个 SPKI 的 SHA-256 硬编码进 `crypto/x509`；certifi 2026.10.18 一度一刀切，10.20 回滚；webpki-roots 1.0.10 更新 |
| 根因（eMudhra 口径） | 生成仪式中 “wrap 与 unwrap” 环节缺陷，额外产生了第二套弱密钥，且弱的那套被写进了证书 |

> 说明：以上综合自 The Register 报道的转述、Mozilla 侧行动与多家中文技术媒体；eMudhra 官方口径为“流程缺陷、非入侵、根密钥未受影响、这 8 张中间 CA 未签发过终端证书”。**最后这一条是自证，不是他证**——CT 日志能证明“公开渠道没被滥用”，证明不了“没人私下用过”。

## 二、难绷点逐个数

<details>
<summary><b>难绷 1：384 位 → 1 字节，安全强度掉了 184 bit</b></summary>

P-384 标称安全强度约 $\approx 192$ bit。而这 8 个 $d$ **全部小于 256**：

$$0x04,\ 0x38,\ 0x42,\ 0x73,\ 0x9B,\ 0x9C,\ 0xE6,\ 0xED$$

即 $\log_2(255) \approx 7.99$ bit 的密钥空间。攻击者枚举的期望次数从

$$2^{383} \quad \longrightarrow \quad 2^{7}$$

难度下降了 $2^{376}$ 倍。这个数字大到什么程度？宇宙原子数约 $10^{80} \approx 2^{266}$。也就是说，**“猜中正确私钥”这件事，比数清宇宙原子还难 $2^{110}$ 倍；而现在它比“手机解锁手势画错一次重画”还简单。**

更尴尬的是数字 $4$：验证它只需要算一次 $4G$ 看看等不等于公钥 $Q$——两次点倍加，微秒级。它不是“被破解”，它是**根本不用破解**。
</details>

<details>
<summary><b>难绷 2：八个值全都装得进一个字节，这不是“弱随机”，是缓冲区错位</b></summary>

如果只是糟糕的 RNG，你看到的值应该是“48 字节里有一半是零”“时间戳打头”“全 0xFF”这类图案。但 $4, 56, 66, 115, 155, 156, 230, 237$ 是**八个均匀分布在 $[0,255]$ 的字节**。

这不是熵不足，这是**字段取错了**：某个长度为 48 字节的标量缓冲区，最后只有 1 个字节（甚至 1 个字节里的某段）真正落进了 $d$ 里。工程上最常见的几种翻车姿势：

- 把 DER 里的 `INTEGER` 当定长 `OCTET STRING` 读，小整数编码只有 1 字节（`02 01 04`），于是“读出 1 字节”；
- 把 key blob 的**长度字段、CKA_ID、句柄号、迭代计数器**当成了标量；
- HSM 的 wrap/unwrap 之后重新导入时，解析器把“包装头”当“密钥体”，而包装头里恰好有个 1 字节 tag（`04` 是 OCTET STRING 的 tag 号！**$d=4$ 很可能是 tag 字节被当成了密钥值**）。

第三点是我最怀疑的：`0x04` 是 ASN.1 `OCTET STRING` 的 tag。一个把 tag 当 payload 读的解析器，第一条输出必然是 **4**。而 eMudhra 自己的说法正是 “wrap 与 unwrap 环节”出了问题——**方向对得上**。（此为技术推断，非官方结论。）

也就是说，真正的 bug 不是密码学，是**一个指针偏移**。而这个指针偏移一路走过了：HSM、双人控制、见证人、录像、脚本审计、WebTrust 审计、根证书入库、CT 日志——**全部通过，无人报警**。
</details>

<details>
<summary><b>难绷 3：公钥长得完美无缺，全世界校验器都在“验签成功”</b></summary>

这是最要命的一点：$Q = dG$ 在数学上是**完全合法的 P-384 点**。证书里没有 length 字段、没有 flag 字段告诉你 “d 只有 8 bit”。

- 浏览器验证链：公钥编码合法 ✅ 签名有效 ✅ 有效期 ✅ CT ✅
- `openssl verify`：PASS
- 所有 lint、所有 zlint、所有 BR 合规检查：PASS（BR 里没有一条要求“验证私钥的熵”）
- 唯一的检测手段：**假设 $d$ 很小，去枚举。**

于是出现了极为讽刺的局面：**整个生态有上万个校验器在检查“签名对不对”，却没有一个校验器检查“私钥配不配”。** 信任模型的假设是“私钥由 HSM 生成”，而审计审的是“流程合规”，不是“数学正确”。这就是安全工程里最古老的笑话：**门锁是 FIPS 140-3 Level 3 的，钥匙挂在门把手上。**
</details>

<details>
<summary><b>难绷 4：躺了 18 个月，而发现只需 1 秒</b></summary>

2025 年 4 月生成 → 2026 年 10 月被发现。这 18 个月里：

- 攻击者（有动机、有资源）没发现？
- 也没人发现？
- **一台笔记本、一个 `for d in range(1, 1000)` 循环、0.9 秒。**

这说明一个残酷事实：**“没被利用”从来不等于“难被利用”，往往只等于“没人去看”。** 而 CT 日志本来就是为了让“有人去看”成为可能——这次它确实起了作用，但它是**事后**起作用，且靠的是一个研究员的好奇心，不是任何自动化监控。整个行业在 CT 上投了天文数字的基础设施，却没人写个脚本对新增中间 CA 做“小标量穷举”。

成本：**一个周末的脚本**。
</details>

<details>
<summary><b>难绷 5：真正的次生灾害不在浏览器，在后端</b></summary>

浏览器的表现是教科书级的：Mozilla 2 小时 53 分完成 OneCRL 推送，Chrome 1 小时 40 分推 CRLSet，用户无感、无需重启。

然后后端的技术栈暴露了真正的脆弱状态：

| 生态 | 现实 |
|---|---|
| Go | 没有运行时吊销通道 → 把 8 个 SPKI 哈希**硬编码**进 `crypto/x509`。防住了，但**存量静态编译镜像不重编就永远在挨打** |
| Python `certifi` | 10.18 版一刀切移除根证书，误伤大量无关合法业务，10.20 紧急回滚 |
| Rust `webpki-roots` | 发版了，但“不发版就无效” |
| macOS 自带 `curl` | 据开发者实测，封锁生效数日后**仍然信任**这些证书，测试域名访问“成功”——这个“成功”就是最坏的结果 |

结论：**我们在上层架构里铺了零信任、mTLS、SPIFFE，底层却依赖一份 `ca-certificates.crt` 静态文件，而且默认不查 CRL/OCSP**（因为性能、隐私、可用性，早就默认关了）。CRL 与 OCSP 这两套“在线吊销契约”事实上已经名存实亡，唯一真正生效吊销的通道是浏览器厂商的**私有推送管道**。生态的分裂，比那个 $d=4$ 更值得写进教科书。
</details>

<details>
<summary><b>难绷 6：还包括两张代码签名 CA</b></summary>

媒体都把焦点放在 HTTPS 上，但 8 张里有 **2 张是 `EM OV CS CA`**——代码签名。

- TLS 中间 CA 失守 = 可以 MITM 任意站点（但需要网络位置）
- **代码签名 CA 失守 = 可以给恶意软件盖上“可信发布者”的章，绕过 SmartScreen/签名校验，且不需要网络位置**

后者在供应链攻击语境下价值高一个量级。而且代码签名证书在很多体系里**没有 CT 那样的强制公开日志**，一旦被滥用，“是否发生过”很可能永远无法证实。这才是 eMudhra 那句“未签发任何终端证书”最该被追问的部分。
</details>

## 三、谁该被骂，谁其实值得表扬

| 对象 | 评价 |
|---|---|
| eMudhra 的密钥生成脚本 | **问题源头**。一个 off-by-one 级别的 bug，跳过了所有物理与流程控制。 |
| eMudhra 的 QC / 仪式验收 | **第二责任人**。“生成后检查 $d \ge 2^{380}$ 且 $dG=Q$”是一行代码，没人写。 |
| eMudhra 的披露姿态 | 中性偏好。把原因讲成“wrap/unwrap 缺陷、非入侵、根密钥无恙”，至少方向可查；但也明显在把事情控制到“全球 TLS 业务”这个小范围内，把印度 DSC/eSign 主业务切开以防受影响。（业务上无可指摘，公关上很熟练。） |
| Mozilla / Chrome | **本次真正的英雄**。OneCRL、CRLSet 数小时静默生效，这是“可远程撤销”架构的胜利。 |
| Scott Helme / Wayne | 一个签名自证、一个公开复现，方法论干净利落：不公开私钥、只公开签名与验证方式，各方无需互信。 |
| NIST / BR / zlint 全行业规范 | **被点名批评**。十几年了，没有一条要求“验证 CA 私钥的取值范围”。 |
| 后端语言与基础镜像生态 | 挨骂但冤枉：它们本来就没有下发通道，问题在于“我们假装 CRL/OCSP 还在工作”。 |

## 四、这事的真正教训（可执行版）

**给 CA / 任何做签名服务的人**

1. 上线前 key lint：$d \in [2^{n-1}, 2^n)$，且 $dG = Q$，且 48 字节定长。三行代码，能防住本次 100% 的事故。
2. 熵不是“我以为有”，是“我测出来有”。NIST SP 800-90B 的评估不是为了合规，是为了抓到这种 1 字节的事。
3. 仪式录像与双人见证，防的是“人作恶”，防不了“脚本算错”。**流程合规 ≠ 数学正确**，这两个是正交的。

**给开发者**

4. 不要相信“系统根证书更新了”。用 Go/Rust 静态编译的镜像、IoT 固件、容器基础层，**必须重编重发**才算修完。
5. 去测。客户端**拒绝连接**才是合格；返回 200 说明你还在信任一个把私钥当玩具的 CA。
6. 关键业务别把信任压在单一 CA 上；证书固定、双 CA 备份、CAA、CT 监控，都是事后恢复能力的组成部分。

**给看客**

7. HTTPS 的小锁只证明“链路经某张证书加密过”，不证明“对面是你以为的那家公司”，更不证明“签发这张证书的机构私钥是 $d=4$”。**把锁当安全认证，是这次事件最大的智商税。**

## 五、一句话收尾

> 一个把熵当儿戏的 `unwrap`，让价值亿级的审计流程、FIPS 认证的 HSM、四大浏览器的信任库，全部为一行指针偏移背书了 18 个月；最后是浏览器的私有推送管道在 3 小时内救了场，而整个后端生态还在等下一次发版。

**打分：脚本 0 分，HSM 无辜，审计体系 3 分，Mozilla 的 OneCRL 95 分，$d=4$ 本身 100 分——它大概是密码学史上最诚实的数字，因为它连假装随机的兴趣都没有。**

（顺带一提：如果你在为这类事件做预案，最该写进 runbook 的那条不是“如何撤证书”，而是“**如何在一小时内找出所有静态编译的二进制**”。这条能做到的公司，其实没几家。）
