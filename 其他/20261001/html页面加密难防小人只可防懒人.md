## 😀 默认助手 (7)

## 一句话结论

**HTML 页面加密的本质只是"提高门槛"，不是"保证安全"。它能防住 90% 的普通用户和伸手党，但防不住任何一个下了决心的开发者——尤其是"小人"。**

---

## 为什么原理上就防不住

浏览器要**渲染**你的页面，就必须**看懂**你的页面。而渲染发生在用户的机器上。

所以无论你怎么加密，最终发到客户端的必然包含三样东西：

```
密文(HTML/CSS/JS) + 解密逻辑(JS/WASM) + 解密密钥
```

密钥和解密逻辑都在用户手里，那这就不是加密，只是**混淆（obfuscation）**。

最典型的就是网上那些"HTML 加密工具"，生成一个输入密码才能看的页面——密码哈希或密钥就硬编码在文件里，打开源码或断点一看就没了。

## 关键判断：你要防的是哪种"小人"？

| 对手 | 前端加密有用吗 |
|---|---|
| 隔壁公司行政，想复制你的文案 | ✅ 完全足够 |
| 普通用户，想拿走图片/文字 | ✅ 基本够用 |
| 半吊子爬虫 / 培训班学员 | ⚠️ 提高成本，能耗掉他几小时到几天 |
| 熟练前端 / 逆向工程师 | ❌ 基本无效 |
| 铁了心要扒你的人（"小人"本义） | ❌ 完全无效，只是让他多花点时间 |

## 那什么才"有意义"？

**把安全边界从"客户端"挪到"服务端"。** 这是唯一真正的分界线。

按你的目标选：

- **保护数据本身** → 不要把敏感数据放进 HTML/JS。接口鉴权、按用户下发、签名、限流、短时效 token。页面里根本不存在的东西，谁也拿不走。
- **保护核心算法/逻辑** → 挪到服务端当 API；实在不行，前端只留 UI。指望 JS 混淆保护算法是自欺欺人。
- **防止内容被爬（价格、电话号、榜单）** → 字体映射、图片切片、Canvas 渲染，配合**个性化水印**（可追溯到具体账号）。
- **保护"版权感"/防抄袭** → 混淆 + 服务条款 + 水印追溯 + 必要时走法律，比技术手段实在。

> 水印和"账号绑定"才是真正的威慑：**防的不是获取，是滥用。** 你扒走了，我能知道是谁扒的，这就够了。

## 别忽略的成本

前端加密是**有代价**的，而且大多数时候代价大于收益：

- **性能**：解密 + 混淆代码拖慢首屏
- **SEO**：JS 解密后才渲染的内容，搜索引擎基本不收录
- **可访问性**：屏幕阅读器、复制粘贴、翻译插件全废
- **可维护性**：混淆后的线上 bug 几乎无法调试
- **误伤真实用户**：禁用右键、检测 DevTools，恶心到的往往是正常用户，小人一点感觉没有

---

## 建议

1. **默认心态**：前端加密 = 给门加个挂锁，防顺手牵羊，不防撬锁的人。接受这一点，心态就对了。
2. **先问威胁模型**：到底是谁、为什么要拿、拿了会造成多大损失？答案通常会让"加密"这个需求直接缩小一大半。
3. **能做服务端就做服务端**，这是性价比最高的一步。
4. **要做前端保护**，就上**混淆 + 关键数据非文本渲染 + 水印追溯**的组合拳，别用"禁用右键"这种既没用又讨人嫌的手段。
5. **别忘了法律和授权条款** ——技术防不住的地方，合同和追溯能兜底。

**一句话：加密防不了小人，但能筛掉懒人；真正防小人的是"数据压根不在前端"和"拿了能查到你"。**
