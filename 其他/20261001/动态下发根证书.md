# CA 动态下发与动态注册/吊销根证书

## 一句话回答

**“CA 动态下发”就是：把信任锚（根证书 / 中间证书）从“烧进系统镜像或浏览器二进制”改成“像推送配置一样，由一条带外可信通道远程下发、按签名校验、运行时生效”。** 要做到不更新系统或浏览器就动态注册、吊销 CA 根证书，必须依赖**已经存在的动态通道**（Windows Update / Chrome 组件更新 / MDM / 组策略 / 企业策略）——或者**给你自己的应用自带一套信任存储**。

---

## 0. 先区分两个容易混淆的概念

| 说法 | 含义 | 本回答是否覆盖 |
|---|---|---|
| **CA 证书动态下发**（trust anchor distribution） | 把根/中间证书**分发到设备的信任存储**，并支持远程吊销 | ✅ 主线 |
| CA 动态**签发** | SCEP / EST / ACME / CMP 在线给设备签证书 | 简要提及 |

你问的“注册/吊销 **根证书**”明确属于第一种。

---

## 1. 为什么必须“动态”

传统信任存储的根本矛盾：

- 根证书有效期 10–25 年，但**私钥泄露、CA 违规、司法强制**随时可能发生；
- 全球约 150+ 个受信根，任何一次移除都要“等下一个 OS/浏览器版本” → 响应时间以**月**计；
- 企业私有 CA 更是无法预装进公有系统镜像。

于是现代实现都把信任存储拆成 **「极小的引导信任锚（bootstrap）」+「可远程更新的信任数据」** 两层。

---

## 2. 通用架构：任何“动态下发”系统都长这样

```
┌──────────────────────────────────────────────┐
│ 1. 根信任锚（不可变，出厂预置）                 │
│    - 1~3 个长期密钥 / 一个签名校验公钥           │
│    - 只在“信任根轮换”时才变（TUF root rotation）│
└───────────────┬──────────────────────────────┘
                │ 验证
┌───────────────▼──────────────────────────────┐
│ 2. 签名元数据仓库（版本化快照）                 │
│    add[] / remove[] / 约束(名称约束、EKU)      │
│    generation 单调递增、expires、threshold 签名 │
└───────────────┬──────────────────────────────┘
                │ HTTPS 拉取（CDN，可被缓存/镜像）
┌───────────────▼──────────────────────────────┐
│ 3. 客户端 applier（系统组件 / 浏览器组件 / Agent）│
│    验签 → 防回滚 → 原子应用 → 落盘 + 审计日志    │
└───────────────┬──────────────────────────────┘
                │
┌───────────────▼──────────────────────────────┐
│ 4. 生效：证书链验证时实时查信任存储             │
└──────────────────────────────────────────────┘
```

**四个安全要件（缺一个就会变成后门）：**

1. **签名而非仅 TLS**：元数据必须用离线密钥签名，TLS 只防窃听不防供应商作恶；
2. **防回滚**：`generation` 单调递增 + 本地持久化最高值，否则攻击者重放旧清单即可“复活”已吊销根；
3. **离线/门限签名**：签名密钥放 HSM，$m\text{-of-}n$ 门限 + 双人复核；
4. **作用域约束**：下发的根尽量带 name constraints / EKU 限制，限制“一个根签全世界”的风险。

## 3. 各平台现成机制（可直接用，无需改代码）

| 平台 | 动态通道 | 注册根 | 吊销根 | 备注 |
|---|---|---|---|---|
| **Windows** | 自动根证书更新（Windows Update CTL） | ✅ 自动/GP/MDM | ✅ Disallowed CTL | 根由微软审核收录 |
| **Chrome/Chromium** | Component Updater | ✅ 企业策略 | ⚠️ CRLSet 主要覆盖中间/叶 | Chrome 有自己的 Root Store |
| **Firefox** | Remote Settings / 应用更新 | ✅ 企业策略 + 系统根 | ✅ OneCRL / CRLite | 根存储随版本发布 |
| **macOS / iOS** | MDM 描述文件 / 软件更新 | ✅ 描述文件 | ✅ MDM 移除 | 受监督设备可控性强 |
| **Java** | 自管 `cacerts` | ✅ keytool | ✅ keytool | 完全可脚本化 |
| **Linux** | `update-ca-certificates` / `trust` | ✅ | ✅ | 发行版包管理 |
| **Android** | 系统分区 + 近年 Mainline 化 | ⚠️ | ⚠️ | 用户 CA 仅 debug 信任 |

<details>
<summary><b>Windows：自动根证书更新 + 禁止列表（详细）</b></summary>

**1) 自动根证书更新（Automatic Root Certificates Update）**

Windows 不预装全部根，而是按需从 Windows Update 拉取 **CTL（Certificate Trust List）**：

```
http://ctldl.windowsupdate.com/msdownload/update/v3/static/trustedr/en/authrootstl.cab      # 受信任根
http://ctldl.windowsupdate.com/msdownload/update/v3/static/trustedr/en/disallowedcertstl.cab # 禁止列表
```

本地缓存为 `.stl` 文件（`authroot.stl` / `disallowedcert.stl`），随 CTL 版本号增量更新。**这就是最典型的“CA 动态下发”**——设备不发版也能获得新根、拒绝旧根。

**2) 企业注册根（三种方式）**

```powershell
# 单机
certutil -addstore -f root C:\pki\corp-root.cer

# 域内批量：组策略
# 计算机配置 → Windows 设置 → 安全设置 → 公钥策略 → 受信任的根证书颁发机构 → 导入

# Intune / MDM：Trusted Certificate profile（.cer / .p7b）
```

**3) 企业吊销根（把根拉黑）**

```powershell
certutil -addstore -f Disallowed C:\pki\bad-root.cer
certutil -delstore root <Thumbprint>
```

- `Disallowed` 存储优先级高于 `Root`，是**唯一可靠的“根级吊销”手段**；
- 可通过 GPO（公钥策略 → 不受信任的证书）、Intune、或 `certutil -delteststore` 批量下发；
- 注意：**微软的自动更新不会自动删除你手工装进去的根**（第三方根不受 CTL 管理），必须自己推删除。

**4) 关闭自动更新（隔离环境常见）**

计算机配置 → 管理模板 → 系统 → Internet 通信管理 → Internet 通信设置 → **关闭自动根证书更新**

</details>

<details>
<summary><b>Chrome / Chromium：自带根存储 + 组件更新</b></summary>

Chrome 从 2021 年起在 Windows/macOS/Linux/ChromeOS/Android 上使用**自己的 Chrome Root Store**，不再完全依赖系统根，因此：

- **根存储更新走 Component Updater**：不需要用户升级 Chrome 主版本，后台组件即可更新信任数据；
- **CRLSets** 同样通过组件更新下发，可以在数小时内吊销**中间 CA**；
- 同时仍会尊重 **用户/企业手工安装的根**（OS 用户存储 + 策略）。

**企业注册根（策略 `CACertificates`）**

Windows 注册表形式：
```
HKLM\SOFTWARE\Policies\Google\Chrome\CACertificates\1
  Data  = <Base64 编码的 DER>
  File  = corp-root.cer        # 二选一
```
macOS 用 `com.google.Chrome` 的 `CACertificates` 数组；Linux 用 `/etc/opt/chrome/policies/managed/*.json`：

```json
{
  "CACertificates": [
    { "File": "/etc/pki/corp-root.pem" }
  ]
}
```

**限制**：Chrome 没有“企业策略吊销根”的能力，`CACertificates` 只增不减；真正吊销根要靠 **Root Store 程序移除 + 组件更新**。

</details>

<details>
<summary><b>Firefox：Remote Settings + OneCRL + CRLite</b></summary>

- **信任根**：随 Firefox 版本发布（`certdata.txt`），**这是硬更新**，无法纯远程加根；
- **例外**：`security.enterprise_roots.enabled = true` 会合并系统根存储（Windows/macOS）；
- **吊销**：**OneCRL** 通过 Remote Settings（HTTPS + 签名清单）下发，可在**分钟级**吊销中间 CA；**CRLite** 用 Bloom filter 覆盖全量叶证书吊销状态；
- **企业策略**：

```json
{
  "policies": {
    "Certificates": {
      "ImportEnterpriseRoots": true,
      "Install": ["/etc/pki/corp-root.pem"]
    }
  }
}
```
`policies.json` 放在 `distribution/`（Windows/macOS）或 `/etc/firefox/policies/`（Linux）。

- 手工 NSS 操作：
```bash
certutil -A -n "Corp Root" -t "C,," -i corp-root.pem -d sql:$HOME/.pki/nssdb
certutil -D -n "Corp Root" -d sql:$HOME/.pki/nssdb
```

</details>

<details>
<summary><b>macOS / iOS：MDM 描述文件是标准通道</b></summary>

```xml
<key>PayloadType</key>      <string>com.apple.security.root</string>
<key>PayloadIdentifier</key><string>com.corp.rootca</string>
<key>PayloadContent</key>    <data>MIIB...（DER 的 Base64）</data>
```

- 通过 MDM **安装 = 注册**，**移除 profile = 吊销**，秒级生效；
- **受监督设备（Supervised）** 才能强制不可移除、并配合 `com.apple.security.TLS` 策略；
- 用户手动加的根在“钥匙串访问 → 系统根证书 → 信任设置”里，属于用户可控范围，企业管不到。

</details>

<details>
<summary><b>Java / Android / Linux：完全可编排</b></summary>

```bash
# Java：可脚本化增删，cacerts 就是你的“动态信任存储”
keytool -importcert -noprompt -alias corp-root -file corp-root.pem \
        -keystore $JAVA_HOME/lib/security/cacerts -storepass changeit
keytool -delete -alias old-root -keystore $JAVA_HOME/lib/security/cacerts -storepass changeit

# Linux（Debian 系）
cp corp-root.crt /usr/local/share/ca-certificates/ && update-ca-certificates
rm /usr/local/share/ca-certificates/corp-root.crt && update-ca-certificates --fresh
```

Android 7+ 起，用户安装的 CA 默认**不被 App 信任**（除非 `network_security_config` 显式声明），所以 App 侧要自己控制信任集。

</details>

## 4. 吊销：必须分层，根级吊销最难

| 层级 | 最佳手段 | 生效速度 | 现实约束 |
|---|---|---|---|
| **叶证书** | OCSP / CRL / **CRLite** / 短有效期（7–90 天） | 分钟~小时 | 软失败（soft-fail）普遍，不可靠 |
| **中间 CA** | CRLSet（Chrome）/ **OneCRL**（Firefox）/ OCSP | 小时级 | 效果较好 |
| **根 CA** | Disallowed CTL（Win）/ MDM 移除 / Root Store 程序移除 + 组件更新 | **天~月** | 无全球统一实时根吊销机制 |

> **核心结论：根证书的“秒级吊销”在公有生态里不存在。**
> 工程上的正确做法是**缩短链路**：让业务证书挂在“短命中间 CA”下（如 90 天轮换），把吊销压力从“根”下沉到“中间/叶”，根只在极端事件时做慢速移除。

**替代/补充手段：**

- **Certificate Transparency**：监控是否有人给你签发未授权证书（`crt.sh`、Google CT 监控）；
- **OCSP must-staple / 短周期证书**：让吊销不依赖客户端联网；
- **DANE / 证书固定（pinning）**：App 侧固定 SPKI 哈希，绕开公有信任体系；
- **CAA 记录**：限制哪些 CA 可为你的域签发。

## 5. 自建“动态下发”系统：可落地的蓝图

<details>
<summary><b>数据模型与签名清单（TUF 风格）</b></summary>

```json
{
  "_type": "trust-anchor-bundle",
  "generation": 42,
  "expires": "2026-03-01T00:00:00Z",
  "anchors": [
    {
      "id": "corp-root-2024",
      "action": "add",
      "der_b64": "MIIB...",
      "spki_sha256": "9f2c...",
      "not_after": "2034-01-01T00:00:00Z",
      "constraints": {
        "name_constraints": "corp.example",
        "eku": ["serverAuth"]
      },
      "activate_after": "2026-01-10T00:00:00Z",
      "retire_after":    "2027-01-10T00:00:00Z"
    }
  ],
  "revoked": [
    { "spki_sha256": "a1b2...", "reason": "keyCompromise", "effective": "2026-01-05T00:00:00Z" }
  ],
  "min_agent_version": "3.2.0",
  "signatures": [
    { "keyid": "ta-admin-1", "sig": "base64..." },
    { "keyid": "ta-admin-2", "sig": "base64..." }
  ]
}
```

**设计要点**：

- `activate_after` / `retire_after` 实现**平滑轮换**（重叠期双根共存）；
- `generation` 单调递增，客户端持久化 `last_seen_generation`，**拒绝 ≤ 本地值**的清单；
- `constraints` 让每个根的能力边界清晰，避免一次性把整个域的信任交出去；
- `min_agent_version` 用于淘汰有漏洞的旧客户端逻辑。

</details>

<details>
<summary><b>客户端应用流程（伪代码）</b></summary>

```python
def apply_bundle(local_store, manifest_bytes, sig_keys):
    m = parse(manifest_bytes)

    # 1. 门限验签（2-of-3）
    if count_valid_sigs(m, sig_keys) < 2:
        raise Reject("signature threshold not met")

    # 2. 防回滚
    if m.generation <= local_store.last_generation:
        raise Reject("rollback detected")

    # 3. 过期检查
    if now() > m.expires:
        raise Reject("manifest expired")

    # 4. 原子应用：先写临时区，校验通过再切换
    staging = local_store.derive_staging()
    for a in m.anchors:
        if a.action == "add" and now() >= a.activate_after:
            staging.add(verify_and_parse(a.der_b64), a.constraints)
    for r in m.revoked:
        staging.remove_by_spki(r.spki_sha256)

    # 5. 一致性兜底：不能把信任集清空
    if staging.count() == 0:
        raise Reject("refuse to empty trust store")

    local_store.commit(staging, generation=m.generation)
    audit_log(m.generation, m.signatures)
```

**运维侧要求**：

| 项目 | 做法 |
|---|---|
| 签名密钥 | HSM / 云 KMS，离线，$2\text{-of-}3$ 门限 |
| 发布流程 | 变更单 → 双人复核 → 金丝雀环境 → 全量 |
| 分发 | CDN + 强 ETag + 短 TTL，保留 N 个历史版本 |
| 回滚 | `generation` 只能前进；回滚=发一个更高 generation 的“反向清单” |
| 可观测 | 客户端上报 `applied_generation`、失败原因；断网设备可查 |
| 极端兜底 | 保留“安全模式”：只用出厂引导根 + 人工干预 |

</details>

## 6. 诚实说明能力边界

| 目标 | 是否可行 | 说明 |
|---|---|---|
| 不升级 OS，给 Windows/macOS 加企业根 | ✅ | GPO / MDM / Intune |
| 不升级 OS，**吊销**企业根 | ✅ | Disallowed 存储 / 移除 profile |
| 不升级 Chrome，给 Chrome 加企业根 | ✅ | 企业策略 `CACertificates` |
| 不升级 Chrome，**吊销**根 | ❌ | 只能靠 Root Store 程序移除 + 组件更新 |
| 不升级 Firefox，加/删根 | ⚠️ | 加可以（策略/系统根），删根基本要发版 |
| 不升级**任何**组件，纯远程改浏览器信任集 | ❌ | 除非你控制该浏览器（自研/内嵌） |

**如果目标设备没有上述任何动态通道**，唯一的技术路径是：

1. **绕过系统/浏览器信任体系**——自己的 App 自带信任存储：
   ```go
   pool := x509.NewCertPool()
   pool.AddCert(corpRoot)                 // 从签名清单加载
   tls.Config{RootCAs: pool}
   ```
   Java：自定义 `X509TrustManager`；Python：`certifi` 换成自管 bundle；curl：`--cacert`。
2. **自带浏览器内核**（CEF / WebView）并在应用层接管证书校验；
3. **中间代理 + 应用层 pinning**（注意：这是合法的 MITM，必须有授权和审计）。

## 7. 最小可行落地清单

1. **确认目标平台的动态通道是否开启**（`certutil -verifyCTL authroot` / `chrome://components` 看 Root Store 版本 / `about:policies` 看 Firefox 策略）。
2. **根证书生命周期设计**：有效期 ≤ 10 年、**预备根**（pre-root）提前 1 年下发、重叠期 ≥ 90 天。
3. **优先 MDM / GPO / 企业策略**，不要手工敲 `certutil`——手工操作不可审计、不可回收。
4. **把“吊销根”做成预案**：提前验证一次 Disallowed / MDM 移除流程，别等出事再试。
5. **下沉吊销压力**：业务证书挂短命中间 CA，用 CRLSet/OneCRL/CRLite 覆盖中间层。
6. **接入 CT 监控**（`crt.sh` 告警 + CAA 记录）。
7. **自建下发系统时**：离线 HSM 签名、门限、`generation` 防回滚、原子切换、审计日志、双人复核——**这五条缺一不可**，否则你造的就是一个合法的中间人攻击平台。

---

### 一句话总结

**“CA 动态下发”= 引导信任锚 + 签名清单 + 带外通道 + 运行时应用**；注册容易（GPO/MDM/策略都能秒级加根），**吊销根才是真正的难题**——公有生态里没有实时根吊销，正确姿势是“缩短证书链 + 下沉吊销到中间层 + 预演移除流程”。
