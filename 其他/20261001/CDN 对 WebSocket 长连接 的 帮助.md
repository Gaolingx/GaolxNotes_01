# CDN 对 WebSocket 长连接 的 帮助

## 🧑‍💻 User

cdn是不是对ws长连接帮助非常小

---
## 😀 默认助手 (7)

## 一句话结论

**“帮助非常小”这个判断，一半对、一半错。**

- 如果你看的是 CDN 最核心的价值——**缓存卸载**——那对 WebSocket 的帮助是 **0**（WS 帧根本不可缓存）。
- 但 CDN 还有另外四个价值：**边缘终结/连接卸载、就近接入降 RTT、骨干网优化、DDoS/WAF 防护**。这四个对 WS **是实打实有用的**，尤其是握手阶段和大规模连接扇入场景。

所以更准确的说法是：**CDN 对 WS 的帮助从“省带宽”转移到了“省握手 + 省连接 + 保质量”，而省带宽这部分确实是零。**

---

## 拆开看：CDN 的五种价值对 WS 的有效性

| CDN 的能力 | 对静态资源 | 对 WebSocket | 说明 |
|---|---|---|---|
| 缓存 / 回源卸载 | ★★★★★ | **无** | WS 是双向字节流，逐帧透传，没有 cache key 可谈 |
| 边缘终结 TCP/TLS | ★★ | ★★★★ | 握手在离用户最近的 PoP 完成，首帧时延大幅下降 |
| 连接聚合（边缘→回源用长连接池） | — | ★★★ | 百万客户端 → 回源只需几十/几百条池化连接 |
| 就近接入 + 专线骨干 | ★★ | ★★★ | 不缩短物理距离，但改善长肥管道上的丢包/抖动 |
| 安全（DDoS/WAF/限速/证书） | ★★★ | ★★★★ | 长连接更容易被打，边缘清洗价值高 |

**一句话：CDN 的商业模型建立在“可缓存 + 无状态请求”之上，而 WS 两个都不满足，所以它的最大卖点失效了。**

---

## 算一笔握手的账（这里 CDN 帮助最大）

一次直连回源的 WS 建连，大约要花 **3 个 RTT** 才收到第一帧：

$$
T_{\text{direct}} \approx 1\,\text{RTT}_\text{TCP} + 1\,\text{RTT}_\text{TLS1.3} + 1\,\text{RTT}_\text{upgrade} = 3\,\text{RTT}
$$

走 CDN 时，前面三个 RTT 全部发生在 **客户端 ↔ 边缘**（RTT 很小），而边缘 ↔ 回源可以用**预先建好的池化连接**，接近 0 RTT：

$$
T_{\text{edge}} \approx 3\,\text{RTT}_{\text{edge}} + \varepsilon
$$

代入实际数字：用户到源站 $150\,\text{ms}$，用户到边缘 $15\,\text{ms}$：

- 直连首帧：$3 \times 150 = 450\,\text{ms}$
- 经 CDN 首帧：$3 \times 15 \approx 45\,\text{ms}$
- **差距约 10 倍。**

如果你的业务是**频繁重连、短会话、或 App 冷启动要立刻收到推送**，这 10 倍就是体感差异，CDN 帮助**巨大**。

---

## 但到了稳态，CDN 甚至可能更慢

握手完成后，每条消息的路径变成：

```
客户端 ──(短肥管道)──> 边缘 PoP ──(长肥管道)──> 源站
```

而直连是：

```
客户端 ───────────(长肥管道)───────────> 源站
```

**CDN 并没有缩短你和源站的物理距离**，只是把脆弱的那一截截短、把长途那一段换到质量更好的专线骨干上。结果通常是：

- **单条消息时延**：基本持平，有时略差（多一跳）
- **抖动 / P99 / 丢包**：明显改善 ← 这才是真正的收益
- **带宽成本**：按字节计费，**一点没省**，某些厂商 WS 流量单价还更高

所以“CDN 对 WS 没用”这个直觉，其实来自**稳态阶段**的观察，而稳态确实是它最不占优势的地方。

---

<details>
<summary><b>实操避坑清单（点开）</b></summary>

1. **空闲超时**：很多边缘节点对空闲 WS 有自己的 idle timeout（几十秒到几分钟），必须靠应用层心跳（ping/pong）打点保活，否则会被静默断开。**这是最常见的坑**。
2. **连接最长存活时间**：部分厂商会对单条 WS 连接设上限（例如数小时到 24 小时），到点强制断，必须实现**带抖动的自动重连**。
3. **PoP 维护/发布导致断连**：边缘节点滚动重启会清掉连接，客户端要能把“被动断开”和“业务错误”区分开。
4. **缓冲（buffering）**：某些代理会为了吞吐做缓冲，破坏实时性；要确认是**透传**而非缓冲模式。
5. **HTTP/3（QUIC）**：部分厂商支持 WS over HTTP/3，换网/弱网下更稳；但 WS 传统上跑在 TCP 上，QUIC 是 UDP，需要厂商在边缘做终结转换，**不是所有 CDN 都支持**。
6. **计费**：确认 WS 的带宽和连接数是否单独计价，很多坑在账单上。
7. **可观测性**：长连接在日志/APM 里往往是“一条不结束的请求”，传统指标会失真，需要单独埋点。

</details>

---

## 什么情况下 CDN 对 WS 帮助很大

- 客户端数量巨大、单连接流量小（IoT、在线状态、移动端推送）→ **连接聚合 + 边缘终结**收益极大
- 用户离源站远、跨洲/跨国 → **骨干网优化**收益明显
- 频繁重连或短会话为主 → **握手加速**收益极大
- 容易被打 → **边缘防护**几乎是刚需
- 用**边缘计算**（Workers + Durable Objects、Fastly Compute、Deno Deploy 等）直接把 WS **终结在边缘**，源站根本看不到这些连接 → 这是 CDN 对 WS 最强的一种用法

## 什么情况下几乎没用

- 单一区域、用户和源站已经同城 → 没什么可优化的
- 追求**极低单帧时延**（游戏状态同步、协同编辑）→ 多一跳是真伤害
- 主要成本是**带宽** → CDN 一分钱不省，还可能更贵
- 连接数很小、会话很长很稳定 → 卸载和聚合都没意义

---

## 如果目标是“大规模实时推送”，比起 CDN 更该考虑

- **边缘有状态计算**（Cloudflare Durable Objects 这类）——真正让 CDN 从“管道”变成“服务器”
- **专用 Pub/Sub 服务**：Ably、Pusher、PubNub、AWS IoT Core、EMQX Cloud 等，它们本身就跑在多边缘节点上
- **SSE + HTTP/2/3**：单向推送场景下，CDN 对 SSE 的友好度远高于 WS，因为它是普通 HTTP 语义，能吃到多路复用和缓存体系
- **协议选型**：如果只需要服务端推、不需要客户端双向高频发，SSE 往往比 WS 更省心

---

## 总结

> CDN 对 WS **不是没用，而是“用错了地方”**：它帮你省的是**握手、连接数、抖动和安全**，但它最擅长的**缓存和带宽成本**，对 WS 完全帮不上忙。
>
> 判断标准很简单：**你的瓶颈是“建连”还是“传输”？** 是建连 → CDN 帮助很大；是带宽 → CDN 帮助为零。

## 先纠正一个认知：你说的“直连”，其实是“直连 Cloudflare”

这点很关键。你的 WS 已经跑在 **CF Worker** 上了，而 CF Worker 本身就部署在全球边缘节点上——**你已经在用 CDN 了**。所以真正要对比的不是“直连 vs CDN”，而是：

```
方案 A（现状）:  玩家 ──> CF 边缘(Worker 终结 WS) ──> 源站
方案 B（套 Doki）: 玩家 ──> DokiCDN 边缘 ──> CF 边缘(Worker) ──> 源站
```

**方案 B 本质上是把两张边缘网络串起来，多背了一跳。** 它只有在"Doki 到玩家"这段明显优于"CF 到玩家"时才划算。

所以问题就转化成了：**从国内到 CF 边缘，和从国内到 Doki 边缘，哪条路更好？**

<details>
<summary>顺带说清楚：免备案 CDN 的“国内优化”到底是什么</summary>

未备案的 CDN **不可能有真实的国内落地节点**（法律上不允许接入）。DokiCDN 这类所谓"国内优化"，实际是**香港 / 日本 / 新加坡节点 + CN2 GIA / BGP 直连线路**。

这是好事——**只要线路质量够，效果和国内节点差别不大**（HK CN2 到国内电信可以做到 20–40ms）。但你要有正确预期：它不是真国内节点，晚高峰照样会拥堵，而且**抗 DDoS 能力远不如 CF**（CF 有全球最大清洗网络）。

</details>

## 两条路径的对比

| 维度 | A：直连 CF Worker | B：套 DokiCDN |
|---|---|---|
| 国内首帧握手 | CF 给你分到哪个 PoP 看运气（常发美西/圣何塞，晚高峰烂） | HK/JP 优化线路，通常明显更好 |
| 稳态消息延迟 | 少一跳 | **多一跳**（玩家→Doki→CF→源站，三段） |
| 稳定性/抖动 | CF anycast + 自研骨干，很稳 | 看 Doki 的线路和负载，波动更大 |
| WS 支持 | 原生支持，无超时坑 | **❓ 必须实测**，很多免备案 CDN 不支持或会静默断连 |
| 抗 DDoS | 极强 | 弱（可能就是个反代+高防的皮） |
| 真实 IP | `CF-Connecting-IP` 可拿 | 需确认 XFF 链路是否透传，否则全是节点 IP |
| 成本 | 免费额度够用 | 按流量计费，WS 长连接会吃量 |
| 备案 | 不需要 | 不需要 |

## 决定性的三个问题（按优先级）

### 1. DokiCDN 到底支不支持 WS 透传？——这是**唯一的一票否决项**

很多免备案 CDN 的 WS 支持是"**能连，但不稳**"：

- 空闲 60s 被断开
- 连接最长存活 10 分钟 / 1 小时
- 中间有缓冲，实时性被毁
- 单连接限速

**对联网游戏来说，任何一个都是致命的。** 这个必须自己压测，别信客服的"支持"。

### 2. 你的玩家在哪？

如果玩家 **70%+ 在国内** → 方案 B 大概率值得（前提是第 1 条通过）。
如果玩家**主要是海外** → 直接用 CF，Doki 纯属添乱。

### 3. 游戏节奏是快是慢？

- **实时竞技**（FPS / MOBA / 动作）→ 每一跳都是钱，多一跳的伤害实打实，倾向 A
- **回合制 / 休闲 / 卡牌 / 挂机** → 200ms 和 250ms 没有区别，B 的稳定性收益更重要

---

## 我的建议

**别叠两层。这就是我的核心结论。**

如果你的玩家主要在国内，**最优架构不是 `DokiCDN → CF → 源站`，而是让 DokiCDN 直接回源，把 CF 从 WS 链路上摘掉**：

```
玩家 ──> DokiCDN ──> 源站 VPS        ← WS 走这条
玩家 ──> CF Worker                    ← 只做信令/登录/静态资源/海外兜底
```

理由：

- 少一跳，延迟直接省下来
- **CDN 本身就隐藏了源站 IP**，你原本用 Worker 当反代的意义已经被替代了
- CF Worker 的免费额度（请求数）可以省下来给 HTTP 部分
- 出问题时只有一家要排查，不是两家互相甩锅

如果玩家**海内外都有**，就做**分线路解析**：

```
game.example.com     → CF（海外玩家）
cn.game.example.com  → DokiCDN（国内玩家）
```

## 实测清单（别拍脑袋，测了就知道了）

<details>
<summary><b>点开：具体怎么测</b></summary>

**① 多地握手耗时对比（A/B 各测一轮）**

```bash
curl -o /dev/null -s -w \
'dns:%{time_namelookup} conn:%{time_connect} tls:%{time_appconnect} total:%{time_total}\n' \
https://a.example.com/
```

**② WS 真实往返延迟 + 保活测试**

```bash
# 连上后不停发 ping，记录 RTT 分布
websocat -t wss://a.example.com/ws
```

自己写个小脚本更好：连接 → 发 100 次 ping 记录 p50/p95/p99 → 然后**挂着不动 30 分钟**，看会不会被踢。

**③ 多地网络质量**

用 `itdog.cn` / `ping.pe` 对 A、B 两个域名做 **tcping + 路由追踪**，重点看国内三大运营商。

**④ 时间点**

**必须在晚高峰 20:00–23:00 测。** 白天测出来的数据全是自欺欺人，国内线路的差距全在晚高峰暴露。

</details>

## 几个隐藏的坑

<details>
<summary><b>点开：踩了会很痛</b></summary>

1. **CF `*.workers.dev` 在国内基本被污染/阻断**。一定要绑**自定义域名**，并做 **CF 优选 IP**（扫出国内路由好的 anycast IP）。
2. **CF 免费版对国内用户的路由很差**，常发美西。这也是你想套 Doki 的根本原因——**这个判断是对的**。
3. **Cloudflare TOS**：长期把 CF 当纯流量代理跑非 Web 内容（游戏流量）有被限速/警告的风险，Workers 场景一般没事，但心里要有数。
4. **Worker 出站 WS 到源站**也有连接数和时长限制，长连接多了要压测。
5. **真实 IP 链路**：`CF-Connecting-IP` / `X-Forwarded-For` 在 `Doki → CF → 源站` 这条链上很容易断，反作弊和限流会全废。这是叠两层最容易翻车的地方。
6. **CF Worker 的 WS 计费口径**：升级请求算 1 次请求，后续消息是否计入、以及免费版 10 万请求/天的天花板，**上线前务必自己确认**。
7. **排查困难度翻倍**：两层代理，玩家报"掉线"你根本不知道是谁断的。

</details>

---

## 最终结论

> **你的直觉方向是对的**：CF 免费版对国内的路由确实差，套一个国内优化线路的 CDN 是合理思路。
>
> **但架构选错了**：不要 `Doki → CF → 源站` 三层叠，而应该让 **Doki 直接回源，CF 退居二线只管 HTTP/信令**。
>
> **一票否决项**：先花半天把 Doki 的 WS 支持压测清楚——**支持就上，不稳定就别上**，宁可继续用 CF 优选 IP 硬扛。
>
> **如果 Doki 不支持 WS**，退路是：WS 直连 CF（优选 IP），只把 HTTP/资源交给 Doki；或者如果你的推送是单向的，考虑用 **SSE 替代 WS**，CDN 对 SSE 的友好度远高于 WS。
