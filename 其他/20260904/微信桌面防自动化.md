根据我查到的社区与开发者实测报告，微信电脑版（Windows/macOS）确实针对 Computer-Use Agent 做了几类"防御"。核心思路是：**CUA 通常靠三条技术路线，微信就把这三条路都堵了一遍** —— 截屏看屏、无障碍 UI 树读取、模拟键鼠。

## 一、Windows PC 版：主打"隐藏 UI 树 + 反截屏"

### 1. 隐藏 UIAutomation UI 树（最关键的一招）

- 微信从 **4.0 版**开始做多端 UI 框架重构，**4.1.5.16** 起彻底改变了 UIAutomation 暴露策略。
- 旧版微信 3.9.x 会默认暴露完整的 **Control View / Raw View**；新版改成**"按需暴露"**：
 - 默认只暴露 1~2 个根节点，UI 树近乎"清空"；
 - **只有检测到合法无障碍客户端（屏幕阅读器）接入时，才构建完整控件 Provider**。
- 检测方式：通过系统 API 判断是否有引用 `UIAutomationClient.dll` / `UIAutomationTypes.dll` 的客户端附着到微信窗口；命中则判定为"无障碍场景"，放行完整 UI 树。
- **后果**：`Inspect.exe`、`FlaUI`、`pywinauto`、`wxauto` 等基于 UI Automation 的工具全部失效——这正是它们"防"的最典型场景。

### 2. 反截屏（WDA_EXCLUDEFROMCAPTURE）

- 微信窗口在**系统级截图/录屏**时会变黑或被"穿透"。
- 底层用的就是 Windows 的 `SetWindowDisplayAffinity`，标志位 `WDA_EXCLUDEFROMCAPTURE`（Win10 2004+）或 `WDA_MONITOR`。
- **后果**：靠"截图 → 视觉模型识别 → 点击"的 CUA（如 Codex Computer Use、Operator 等）**看不到微信内容**，视觉闭环直接断掉。唯独微信自带的截图功能正常（走的是应用自己的捕获路径）。

### 3. 自绘 + 跨平台框架（让控件"非原生"）

- 4.0.3 后微信放弃 Windows 原生控件，改用**自绘引擎**（本质是一个"宿主窗口画布"，按钮/输入框都是动态绘制）。
- 这既是"UI 树隐藏"的根因，也让基于坐标/控件句柄的传统自动化定位变得困难。

### 4. 行为风控 / 反自动化检测

- 针对模拟键鼠、高频批量操作、多开等有账号级风控（限流、警告、封号），属于"事后"防线。

## 二、macOS 版：主打"发消息即闪退 + 截图失效"

据 2026 年 5 月社区实测（Anthropic Computer Use 操作微信）：

| 操作 | 结果 |
|------|------|
| AI **读取**微信聊天内容 | 可以 |
| AI **发送消息** | 微信**立刻闪退（崩溃）** |
| 全屏截图（针对微信） | 提示**无法保存** |
| 框选截图 | 直接**"穿透"**微信窗口（窗口被当作透明） |
| 微信内置截屏 | 正常 |

即：**读可以、写就崩** + **系统级截图被屏蔽**，疑似反自动化/风控机制（重置录屏权限也无效）。

## 三、一句话总结

微信电脑版的防御可以概括为**"三个断点"**：

1. **断"看"** —— 反截屏（`WDA_EXCLUDEFROMCAPTURE`），让 CUA 截图看不到或变黑；
2. **断"读"** —— UI 树按需暴露，让无障碍/UI 树类工具抓不到控件；
3. **断"写"** —— 检测到自动化写入行为时崩溃/风控，让模拟操作无法落地。

有意思的是，这些"高墙"不是微信独有的——它和银行 App、DRM 软件的反截屏、反无障碍是同一套系统 API 思路，只是首次被大规模用在**对抗 AI Agent** 上。
