# 日常KCTF逆向设计

## 🧑‍💻 User

在non_kctf里面这种正常的逆向过程中，我们怎么保证我们的设计既能保障这种日常逆向，也能在类似KCTF这种高自由度探索的任务里面保持鲁棒性？

---
## 🤖 Assistant

这是一个架构/鲁棒性问题,本质是在问:**如何用一套底座同时支撑"确定性强的日常逆向"和"高自由度探索的 KCTF"**。我按设计原则 → 具体机制 → 保障/评估三层来回答。

> 说明:我查了当前可用的工具(浏览器/抓取/Python/思考等),没有和 `non_kctf`、KCTF 相关的知识库或代码索引,所以下面是通用的架构设计建议,不是对你某个私有仓库的逆向结论。

## 一、先承认:两类任务共享接口,但不能共享策略

不要把二者当成"一个更难的版本",它们是**同一动作空间上、不同搜索空间与反馈密度**的两类分布:

| 维度 | `non_kctf` 日常逆向 | KCTF 高自由度探索 |
|---|---|---|
| 目标 | 明确(定位校验点、提取算法、patch) | 开放(找漏洞/拿 flag/提权) |
| 解路径 | 近似线性、可脚本化 | 树状、需试错与回退 |
| 反馈 | 密集、可机检(输出比对、反汇编一致) | 稀疏、延迟、可能误导 |
| 成本特征 | 低方差、要求可复现 | 高方差、要求预算可控 |
| 主要失败模式 | 工具/解析错误 | 方向性错误、死胡同 |

**核心矛盾:精度/确定性 ↔ 灵活性/探索。** 保证鲁棒性的关键,是让这个矛盾**只暴露在一个可插拔的层里**,而不是弥漫到整个系统。

---

## 二、设计原则:分层,把"自由度"关进策略层

<details>
<summary><b>展开:三层架构与职责边界(点击展开)</b></summary>

**1. Grounding 层(工具原语)——要"死板"**
- 最小、正交、可组合:读写字节、反汇编、反编译、执行、下断点、内存读写、符号求解。
- 契约化:类型化入参、幂等性声明、统一错误分类(`tool_error` / `parse_error` / `timeout` / `wrong_hypothesis`)。
- 这一层在两类任务里**字节级相同**,因此 KCTF 探索不会污染日常逆向的稳定性。

**2. State 层(世界模型)——要"唯一事实来源"**
- 显式、可序列化的状态:假设集、已证/已否命题、提取到的常量、文件/内存快照引用。
- 绝不把关键状态只放在 prompt 里。日常逆向靠它复现,KCTF 靠它回溯。

**3. Policy 层(规划器)——唯一允许"自由"的地方**
- 同一 Action API,挂不同策略:
 - 日常:plan → execute → verify 的**确定性流水线**(可缓存、可重放)。
 - KCTF:beam search / MCTS / 回溯搜索,带价值与成本估计。

这样"保日常"= 把策略钉死;"保 KCTF 鲁棒"= 只改策略,底座不动。

</details>

## 三、六个具体机制(两类任务共享,收益不同)

1. **同构观测接口**:每个动作都返回结构化 `observation + 可验证信号`。日常逆向用它对答案,KCTF 用它当搜索信号(flag 正则命中、crash、输出 diff)。
2. **检查点/快照与回滚**:进程、文件系统、内存的快照-恢复。一套机制同时满足日常逆向的**可复现**和 KCTF 的**分支回溯**。
3. **统一资源治理器(budget/护栏)**:超时、沙箱重置、token/步数上限。日常要稳定,KCTF 要防止 runaway。
4. **分级退化(escalation ladder)**:高层工具失败 → 降级到原语。KCTF 里这是"卡住还能动"的生命线。
5. **可机检的闭环验证**:每步尽量接一个 cheap oracle。反馈密度越低越要**主动造验证信号**,否则探索变猜。
6. **成本模型进价值函数**:让策略显式权衡"多探一层"与"重开沙箱"的代价。

形式化上,策略 $\pi(a \mid s)$ 的搜索目标可写成:

$$
\max_{\pi}\ \mathbb{E}\Big[\mathbb{1}[\text{solve}]\ -\ \lambda\, C(\tau)\Big]
$$

日常逆向里 $\lambda C$ 主导(别乱花钱、要重复),KCTF 里 $\mathbb{1}[\text{solve}]$ 主导且反馈 $V(o)$ 稀疏——**同一个目标函数,不同权重/反馈密度**,这就是"同一底座、不同表现"的来源。

一个可复用的执行环:

```python
while not done(state) and state.budget.left():
    hyp   = state.select_hypothesis()          # 日常:取下一个确定步骤;KCTF:按价值探索
    act   = policy.propose(hyp, state)         # 唯一随任务类型变化的层
    obs   = grounding.dispatch(act)            # 工具原语,行为恒定
    ok    = verify(obs)                        # 闭环验证信号
    if not ok and policy.mode == "explore":
        state.rollback_to(state.last_checkpoint)  # 探索专属
    state.update(hyp, obs, ok)
```

## 四、怎么"保证"鲁棒性——用评估集把两种分布钉住

<details>
<summary><b>展开:回归 + 压力 + 课程 + 指标(点击展开)</b></summary>

- **`non_kctf` 当回归集(CI)**:确定性、便宜、可重放。任何改动先跑它,防止"为了 KCTF 变灵活"而破坏日常。
- **KCTF 当压力/OOD 集**:评测鲁棒性与探索前沿。它不该进 CI 的快速门(方差太大),而应作为定期触发。
- **混合课程/训练配比**:固定比例混合两类任务,避免策略过拟合任一侧——只练日常会变脆,只练 KCTF 会变得不肯走直线。
- **指标要看方差,不只看均值**:成功率、步数/解、token 与成本、**方差**、回滚率、死胡同耗时占比。
- **消融**:关掉回滚、关掉验证信号、关掉预算,分别看两类任务各退化多少——这能直接暴露"哪些机制在替谁兜底"。

一句话:**用 `non_kctf` 保证"不变坏",用 KCTF 保证"不脆";两者是互补的门,而不是二选一。**

</details>

## 五、最容易踩的两个反模式

- **为 KCTF 过度工具化**:到处加探索、随机性和自动分支,导致日常逆向步骤不可复现、成本失控。**探索必须被限制在 Policy 层并受预算约束。**
- **为 `non_kctf` 过度脚本化**:把流程写死成脆弱的 pipeline,一到开放任务就无路可走。**原语要正交、验证信号要显式,策略要可换。**

两者的通用解法都是同一句:**把"确定性"下沉到 Grounding/State,把"自由度"上收到 Policy,用检查点与预算把两者缝在一起。**
