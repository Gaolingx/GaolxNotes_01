# 数据库索引能加快查询

### 🧑‍💻 User

数据库索引为什么能加快查询

---

### 🤖 Assistant

数据库索引之所以能加快查询，本质上是**用空间换时间**——通过维护一个额外的、有序的数据结构，把"逐行扫描"变成"快速定位"。

## 一、类比：书的目录

没有索引时，查询就像在一本没有目录的书里找一个词，只能**从第一页翻到最后一页**（全表扫描）。有了索引，就像先查目录，直接定位到对应页码。

## 二、核心原理：降低时间复杂度

大多数关系型数据库（MySQL 的 InnoDB、PostgreSQL 等）默认使用 **B+ 树**作为索引结构。

| 查询方式 | 时间复杂度 | 100 万行数据的查找次数 |
|---------|-----------|----------------------|
| 全表扫描 | $O(n)$ | 最多 100 万次 |
| B+ 树索引 | $O(\log n)$ | 约 20 次（树高约 3~4 层） |

### 为什么 B+ 树这么高效？

1. **数据有序存放**：索引列的值按顺序排列，支持二分查找。
2. **树很"矮胖"**：每个节点能存几百上千个键值，树的高度通常只有 3~4 层，从根节点到叶子节点只需几次磁盘 IO。
3. **叶子节点是链表**：叶子节点之间用指针串联，所以不仅能精确查找，还能高效支持**范围查询**（如 `BETWEEN`、`>`、`ORDER BY`）。

## 三、具体工作流程对比

以查询 `SELECT * FROM users WHERE id = 1000` 为例：

**无索引（全表扫描）**
```
读取第1行 → 比对 → 不是
读取第2行 → 比对 → 不是
...
读取第1000行 → 命中 ✓（最坏要读完全表）
```

**有索引（B+ 树查找）**
```
根节点：1000 > 500，走右子树
中间节点：1000 > 800，走右子树
叶子节点：命中 1000 所在的页 → 回表取完整行数据 ✓（只需 3~4 次 IO）
```

## 四、其他数据结构

| 结构 | 特点 | 适用场景 |
|------|------|---------|
| **B+ 树** | 平衡、支持范围查询 | 通用默认选择 |
| **哈希索引** | $O(1)$ 精确查找，但不支持范围 | 等值查询（如 Memory 引擎） |
| **位图索引** | 压缩存储，适合低基数 | 数据仓库 |

## 五、索引的代价（为什么不能乱建）

1. **写入变慢**：每次增删改，除了更新表，还要维护索引树（可能引起页分裂、平衡调整）。
2. **占用空间**：索引本身是一份数据副本，占用磁盘和内存。
3. **可能失效**：对索引列做函数运算（如 `WHERE YEAR(date) = 2024`）、前导通配符（`LIKE '%abc'`）、隐式类型转换等，会导致索引失效，退回全表扫描。

## 总结

> 索引把查询从"翻遍整本书"变成了"先查目录再翻页"，用 $O(\log n)$ 代替了 $O(n)$，这是它能大幅提升查询速度的根本原因。代价是额外的存储开销和写入性能损耗，因此要在**读多写少、查询频繁**的列上建索引。
