# EasyTier vs Tailscale：核心区别与选型

**二者定位不同**：Tailscale 是一套**基于身份的企业级零信任组网服务**，开源客户端搭配“官方云控制台”；EasyTier 是一个**纯开源、去中心化的点对点组网（SD-WAN 或内网穿透）工具**，没有控制面，也没有账号体系。因此，“哪个更好”完全取决于你是要**管人**（合规、审计、SSO），还是要**连设备**（要连接通、免费、国内可用）。

---

## 一、最根本的区别：有没有“中心控制面”

| | EasyTier | Tailscale |
|---|---|---|
| 控制面 | **没有**。节点之间通过“网络名+密码”以及公网节点或共享节点互相发现，各自计算路由 | **有**。官方 coordination server 负责分发公钥、下发 ACL、分配 IP、协调 NAT 穿透 |
| 数据面 | 自研 UDP/TCP 协议（Rust 实现），加密可选 AES-128-GCM 或 WireGuard 模式 | WireGuard（用户态 wireguard-go），端到端加密的 P2P 或 DERP 中继 |
| 成员授权 | 一个共享密码（或网络名+密钥），谁拿到谁就能入网 | 每台设备独立密钥和身份（SSO/OIDC/GitHub/Microsoft），可撤销单台设备 |
| 开源程度 | **全部开源**（Apache-2.0，Rust，单二进制） | 客户端开源（BSD-3），**控制服务端闭源**（要自建只能靠第三方 Headscale） |

```text
Tailscale:   设备 ──┐
                   ├─→ 官方控制服务器（选路/公钥/ACL）→ 直连 or DERP 中继
             设备 ──┘

EasyTier:    设备 ←→ 设备 ←→ 设备  （任一台有公网 IP 的机器都能当“共享节点”）
             谁先连上谁就转发，无全局目录
```

## 二、逐项对比

| 维度 | EasyTier | Tailscale |
|---|---|---|
| 上手难度 | 极低，一条命令即可组网；GUI、Web 控制台和中文文档 | 低，但需要注册账号并登录 SSO |
| 成本 | 完全免费，无设备数限制（中继需自备或使用社区共享节点） | 免费版 3 用户/100 设备；超出后按用户或设备付费 |
| 平台 | Win/macOS/Linux/FreeBSD/Android/OpenWrt，可嵌入 ESP32；iOS 支持较弱 | 全平台，包括 iOS/Android 和各类 NAS、容器；客户端体验成熟 |
| NAT 穿透 | UDP 打洞，失败走任意节点中继；支持多路径、自动切换 | STUN/UPnP/PMP 打洞，失败走 DERP 中继（全球节点） |
| ACL | 有静态 ACL 配置（较简易） | 强大的策略文件（tags、grants、SSH 规则），可审计 |
| DNS | 魔法 DNS（功能有限） | MagicDNS，比较好用 |
| 广播/组播 | 游戏联机场景通过 WinIPBroadcast 等配套工具解决局域网发现 | **官方明确不支持**广播/组播 |
| 国内可用性 | 好，可完全自建，无境外依赖 | 一般，控制面和 DERP 在境外，常需自建 Headscale+DERP |
| 特色功能 | KCP/QUIC 代理（抗丢包）、子网代理、网对网、无 TUN 免 root 模式、SOCKS5、端口转发、WireGuard 客户端接入 | Taildrop 传文件、Tailscale SSH、exit node、Serve/Funnel、App Connectors、企业合规（SOC2/HIPAA） |
| 成熟度/支持 | 社区项目（~14k stars），活跃但无商业 SLA | 商业公司产品，企业级支持和安全响应 |
| 典型用户 | 个人、NAS 玩家、游戏联机、国内小团队 | 企业、跨国团队、需要审计合规的组织 |

<details>
<summary><b>EasyTier 的强项（展开）</b></summary>

- **零成本、零账号**：不需要注册，不依赖任何在线服务就能组网（用 `--peers` 直连即可），也可完全离线或内网使用。
- **国内网络友好**：不受境外控制面、中继影响；可自建共享节点，甚至用家里宽带上行做中继。
- **功能实用，偏重实用场景**：KCP 代理专门针对高丢包链路（比如跨境或移动网络）提升体验，这是 Tailscale 没有的。
- **体积小、可嵌入**：单文件，能跑在 OpenWrt 路由器、ESP32 上。
- **完全开源可审计**：Apache-2.0，可自行修改协议或增加功能。

**代价**：没有身份体系（一个密码泄露 = 全网泄露）、没有审计日志、ACL 简陋、没有商业支持、iOS 端不成熟。
</details>

<details>
<summary><b>Tailscale 的强项（展开）</b></summary>

- **身份即边界**：设备绑定用户或标签，离职或设备丢失时可以一键撤销；ACL 能精确到“谁能访问哪台机器的哪个端口”。
- **运维体验和个人可用性好**：MagicDNS、Taildrop、exit node（把流量从家里或公司出去）、Funnel 临时公网暴露、SSH 免密钥登录。
- **企业合规**：SSO/SCIM、审计日志、SOC2/HIPAA/ISO 相关支持。
- **网络质量**：全球 DERP 网络 + 成熟的穿透逻辑，跨国场景通常很稳定。

**代价**：控制面闭源、按人头、设备收费、国内访问不稳定、不支持广播（局域网游戏基本没戏）。
</details>

## 三、我的建议（按场景）

| 你的场景 | 推荐 |
|---|---|
| 个人或家庭：远程访问 NAS、家里电脑，1–10 台设备 | **EasyTier**（免费、无账号、国内稳定）；愿意折腾且在乎体验可以 Tailscale |
| 国内小团队或工作室（<20 人），需要简单组网 | **EasyTier** 自建共享节点，或 **Tailscale + 自建 Headscale** |
| 局域网游戏联机（艾尔登法环、无主之地等） | **EasyTier**，Tailscale 不支持广播，基本不可用 |
| 公司或组织：需要 SSO、审计、按人授权、合规 | **Tailscale**（或同类商业方案），不要用 EasyTier 承担这个职责 |
| 跨境访问或需要稳定中继 | Tailscale（DERP 网络）优于 EasyTier 的公共节点 |
| 高丢包、高延迟链路（4G/卫星/跨境） | **EasyTier** 的 KCP/QUIC 代理 |
| 路由器或嵌入式设备（OpenWrt、ESP32） | **EasyTier** |

## 四、几个需要注意的问题

1. **EasyTier 不能替代 Tailscale 的安全模型**。它的网络安全性约等于“共享 WiFi 密码”：密码一旦外泄，等于对外开放了整个内网。生产环境务必启用 Secure Mode，并配合主机防火墙。
2. **Tailscale 在国内不直接可用**。控制面和 DERP 在境外，常见做法是自建 Headscale 和 DERP 节点，但那已经相当于自己维护一套控制面了。
3. **“去中心化”不等于没有依赖**。EasyTier 的纯 P2P 只在双方都能直连时可行；在对称 NAT 或 CGNAT 下仍然需要一台有公网 IP 的中继（自己的 VPS 或社区共享节点）。EasyTier 官方也提供公共节点，但那属于**他人提供的服务**，不适合传输敏感数据。
4. 如果介于两者之间，还有 **ZeroTier**（有中心但可自建控制器）和 **NetBird**（开源 + 可自建控制面 + WireGuard + ACL，思路最接近“开源的 Tailscale”）。要“像 Tailscale 但全开源可自建”，NetBird 通常比 EasyTier 更合适。
5. 版本和计费信息经常变化，选型前建议再看一眼官网当前价格和平台支持列表（EasyTier 的 iOS/移动端支持在路线图上仍在演进）。

**一句话总结**：想**免费用、自己掌控、国内好连、打游戏**，用 EasyTier；想**管人、要审计、要合规、要省心**，用 Tailscale。二者不是替代关系，很多团队其实会同时用：对内使用 Tailscale 管理员工设备，对外或对客使用 EasyTier 或 ZeroTier 连接临时设备。

# 对“有人声称破解 tailnet”的评估

要评估一个安全声称，不能只看标题，关键是把“破解”这个词拆开——**90% 的“破解 tailnet”新闻，实际都不是攻破了密码学或软件本身，而是拿到了人的凭据**。下面分几层说明，你可以对照看看对方声称属于哪一类。

---

## 一、“破解”的五种含义，可信度差异极大

| 号称破的是什么 | 现实可行性 | 说明 |
|---|---|---|
| ① **破解 WireGuard 加密流量** | **几乎不可能**（除非量子计算真的落地） | Noise IK 握手 + Curve25519/ChaCha20-Poly1305，目前没有可用的攻击。如果有人说“截获了你的 tailnet 流量能解密”，那几乎一定是他先拿到了终端权限或密钥 |
| ② **攻破控制服务器，进而控制所有 tailnet** | 理论攻击面存在，但**做不到解密流量** | 控制面只保存公钥、负责分发 netmap。它无法解密数据，但**可以往你的 netmap 里加入节点**，从而伪造“合法设备”并与你握手，这是真实的信任边界问题，也是 Tailnet Lock 存在的原因 |
| ③ **加入别人的 tailnet（冒名入网）** | **非常容易，而且经常发生** | 这是最常见的情况：auth key 泄露在 GitHub、粘贴进 CI 或 Docker 镜像、从被入侵的机器中提取 `tailscaled.state`，或管理层账号被钓鱼 |
| ④ **利用软件漏洞（RCE、提权、信息泄露）** | 存在真实历史案例，但数量极少 | 官方 GitHub 安全公告至今只列出几条：2022 年 Windows 守护进程 CSRF RCE（严重）和 CSRF 信息泄露、2023 年 FreeBSD 上 Tailscale SSH 的 gid 问题 |
| ⑤ **绕过登录、设备数限制或“共享账号”** | 真的，但**和安全无关** | 自建 Headscale、修改客户端指向伪造控制面，都属于“不用它的服务”，并不等于破了它的安全 |

> 判断参考：官网 security bulletins 上最近一条是**设备元数据泄露**——后加入的设备能看到先加入设备的主机名、系统版本、最后在线时间和公网 IP，但**无法建立连接**，且官方明确“无证据表明被利用”。这类公告看着吓人，实际影响很小。真正的攻击往往根本不需要 CVE。

---

## 二、真实的攻击面在哪里

Tailscale 的威胁模型写得很清楚：**控制服务器不被信任用于保护数据机密性**，但它确实能看到你的网络拓扑、可以下发 ACL、可以给网络加入节点。所以现实中的攻击路径几乎都集中在“身份”和“控制面权限”，而不是协议：

```text
真实入侵路径（按常见度排序）
1. auth key / OAuth client secret 泄露 ──→ 直接入网，无需任何漏洞
2. 节点密钥文件被读取（磁盘/备份/镜像/容器层）──→ 以该设备身份冒充
3. 管理后台账号失陷（无 2FA / 会话被窃）──→ 改 ACL、加节点、开 Funnel
4. ACL 写得太宽（* 或 autogroup:member 全放行）──→ 入网即等于内网全通
5. subnet router 把整个 LAN 暴露给整个 tailnet
6. 自己在 tailnet 里跑的服务有漏洞（Funnel 开到公网）
7. 软件漏洞（少数，见上表④）
```

**特别值得注意的一条**：`tailscaled.state` 这类密钥文件默认不带口令保护，本机上任何能以该用户或 root 身份运行的程序都能读它——这就是为什么 2024 年以来多个信息窃取木马和勒索软件团伙（Sophos、GuidePoint 等都有公开报告）的做法是**在已入侵的主机上安装 Tailscale 或直接读取密钥，把受害者的机器并入攻击者自己的 tailnet**，用于隐蔽维持访问。这类新闻被二次传播时，标题常常变成“Tailscale 被攻破”，实际上是“受害者主机被攻破后，Tailscale 被当成后门通道”。

## 三、“攻破某个 tailnet”新闻的核实清单

遇到这类声称时，建议直接问对方下面五个问题，答不上来基本可以当作流量内容处理：

1. **编号**：有 CVE 或 GHSA 吗？影响哪些版本？哪个版本修复？
2. **前提**：攻击需要什么条件——物理接触、本地管理员、已有凭据、还是纯远程零交互？前提不同，严重性差一个数量级。
3. **对象**：破的是“软件/协议”，还是“某个人的账号”？后者的正确表述是“账号被盗”，不是“tailnet 被破解”。
4. **证据**：有没有可复现步骤、抓包、时间线，以及厂商回应（Tailscale 有明确的漏洞披露流程和安全公告页）。
5. **动机**：发帖人在卖课、卖“破解版”、推竞品，还是纯技术分享？

还有一个中文社区常见套路要提醒：所谓“破解版 Tailscale / 共享 tailnet 账号 / 一键破解面板”，**绝大多数是钓鱼页或捆绑木马**。你装上的那一刻，才是真正被“破解”的时候。

<details>
<summary><b>如果你的 tailnet 可能已被入侵，按这个顺序处置（展开）</b></summary>

1. **看设备列表**：管理后台 Machines / `tailscale status`，逐个核对不认识的主机名、OS、最后在线时间。
2. **查 ACL**：确认没有 `*`、没有过宽的 `autogroup:member`、没有意料外的 tag 授权。
3. **轮换凭据**：撤销可疑设备的 node key、重置 auth key 和 OAuth client secret、作废长期 API token；对管理员账号开 2FA 并检查登录会话。
4. **启用防护**：Tailnet Lock（防止控制面或管理员单点加节点）、device approval、key expiry、审计日志。
5. **清理暴露面**：关掉不需要的 Funnel/Serve，收窄 subnet router 通告的网段，给关键主机加本机防火墙（tailnet 不是内网信任状）。
6. **查泄露**：搜代码仓库和 CI 变量里有没有 `tskey-` 开头的字符串——这是最常见的入网点。
</details>

## 四、结论

- **“破解 tailnet”这个说法本身多半是错的表述**：真正发生的是凭据泄露、终端被控，或者某个管理员账号被钓鱼。这类事件确实存在，且相当普遍，但它们**不是 Tailscale 的漏洞**，换 EasyTier、ZeroTier、NetBird 结果一样——EasyTier 甚至更弱，因为它是“网络名+密码”的共享密钥模型，一旦泄露就没有 per-device 撤销这回事。
- **技术上唯一值得认真讨论的信任风险**，是控制面（或管理员）能向你的网络注入节点。这个风险是设计权衡的产物，Tailscale 的应对是 Tailnet Lock；自建方案（Headscale、NetBird）则是把这份信任转移到你自己身上——**并没有消除，只是换了人承担**。
- **对个人和家用场景**，Tailscale 的实际安全性远高于“被破解”这类传闻所暗示的水平；真正的风险是你自己 —— 密钥写进 dotfile、Funnel 开到公网、ACL 一把梭。
- **对企业**，任何自建或 SaaS 组网工具都要按“身份系统”来治理：SSO + 2FA + 最小权限 + 密钥生命周期 + 审计，这套东西的价值远大于纠结协议实现。

一句话：**密码学没有被破，被破的是钥匙管理**。听到“破解 tailnet”，先问“他拿的是谁的钥匙”。
