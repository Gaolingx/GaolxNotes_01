## 😀 默认助手 (7)

你的三条猜测都成立，但我觉得它们都还不是最根本的原因。真正的决定性因素是：**变更频率高的往脚本层放，变更频率低的往 native 放；而脚本层用什么语言，取决于“谁来写”和“跑在哪”。**

## 1. 不只是 hotfix，还有“编译”这个动作本身

HybridCLR 解决的是“能不能热更”，没解决“改一行要等多久”。

- **C#**：修改 → 编译 → 打包或热更 → 重启进程或重载程序集。
- **Lua**：修改 → 保存 → 编辑器里刷新（很多项目连重启都不用，模块直接重新 `require`）。

策划调整一个技能数值、改一段任务流程，一天要试几十次。累积下来，差几秒和差一分钟就是流程差异。这跟 hotfix 是两件事。

而且 **Unity/IL2CPP 下程序集基本卸载不掉**（`AssemblyLoadContext` 用不了），C# 热更的逻辑“只增不减”，改多了内存只涨不降。Lua 模块可以 `require` 掉、可以 GC。

## 2. 最关键的一条：双端跑同一份代码

这条你没展开，但我认为这是权重最大的。玩法里最贵的 bug 是“客户端算出来和服务端校验不一致”，因为伤害公式、状态机、CD 判定写了两遍。

Lua 让客户端、服务端、甚至离线数值验证工具跑**同一份**战斗/公式/任务状态机。C# 很难做到：客户端是 Unity 的 C#，服务端是另一套运行时，很难让它们共用一份代码。

顺带还有一个很少被提起的好处：**离线 headless 跑模拟战斗**验证数值。不用起引擎、不用起客户端，直接跑 lua 脚本。版本验证的效率差一个量级。

## 3. 脚本层的首要用户是策划，不是程序员

人力结构上，策划、关卡和文案的人数远大于程序。

强类型对程序员是保护，对策划却是障碍。Lua 的 table 和弱类型让“配置即代码”几乎没有额外成本：Excel 导出的表就是 lua table，读取、继承、覆盖、写默认值、写条件表达式全在一套语法里。C# 那边要走 POCO、反序列化，改配置还得同步改类型定义。配置本质是数据，而数据结构和 Lua table 天然对应，这是很实际的理由。

## 4. 沙箱与容错（服务器侧的决定性理由）

- 用 `pcall` 隔离单个玩法脚本的错误，不影响整个进程。C# 里未捕获异常可能直接带走进程，而 try-catch 的边界很难准确划定。
- 服务器要跑“受玩家输入影响”的逻辑，需要限制指令数防止死循环、需要禁止文件 IO，Lua 沙箱是现成的；C# 做不到真正的沙箱。
- 每帧执行预算可以用 debug hook 卡住。

## 5. 用协程写流程确实顺手

任务流程、技能流程、剧情演出，本质都是“跨帧的顺序逻辑”。Lua 的 `coroutine` 手动 `resume`，可以存档、可以打断、可以并行派发、可以做时间轴；C# 的 `async/await` 在帧循环里会给你带来调度器上的麻烦，尤其当要求可序列化、可中断重入的时候。

## 6. 最容易被低估的：生态惯性和迁移成本

`xlua`、`slua`、`UnLua`、`tolua`、`skynet`，再加上配套的 profiler、内存分析、断点调试、热重载。换语言意味着推倒重来。技术选型里有个巨大的惯性项叫“我们组已经会用，工具链已经跑通”。

<details>
<summary>两点需要澄清</summary>

**关于“原神服务端也是 Lua”**：这个说法我没找到权威来源，社区传闻居多。米哈游公开分享里客户端明确是 Unity/C#，服务端技术栈没有定论。拿传闻当论据不太稳。

**“脚本层”是行业共性，选 Lua 是偶然**：网易 Messiah 用 Python，不少 Web 系游戏用 JS/TS。所以真问题不是“为什么用 Lua”，而是“为什么要有脚本层”。Lua 的优势是**嵌入成本低、解释器几百 KB、C API 极其干净**，这些特性让它成了默认答案。
</details>

<details>
<summary>代价也不小（所以现在主流是混合）</summary>

- 弱类型大项目重构噩梦，拼写错误运行期才炸
- 性能问题难定位（谁在每帧 new table）
- 调试体验差
- 与 C# 交互的 GC 边界、引用管理是长期坑
- 代码规模一大，Lua 的工程化能力就吃紧

所以现在的趋势是**按变更频率分层**：核心系统、UI 框架、渲染、网络底层用 C#/C++；玩法、任务、活动、配置相关用 Lua。纯 C# 项目也一大把（欧美、独立游戏居多），说明这更多是组织形态的产物，而不是技术必然。
</details>
