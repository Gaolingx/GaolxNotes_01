# 多线程字典同步方案

## 🧑‍💻 User

uvicorn多线程有什么办法能够解决线程间字典同步的问题吗

---
## 😀 默认助手 (7)

## 先确认场景：这里的“多线程”是哪一种

这决定了方案完全不同，90% 的人会在这里混淆：

| 场景 | 是否共享内存 | 典型触发方式 |
|---|---|---|
| **单进程 + 线程池**（uvicorn 默认） | ✅ 共享同一份 dict | `def` 路由被 Starlette 通过 `anyio.to_thread.run_sync` 丢进线程池（默认 40 线程） |
| **单进程 + 异步**（`async def`） | ✅ 但是单线程事件循环 | 没有线程竞争，只有 `await` 处的协程切换 |
| **多 worker**（`--workers 4`） | ❌ 完全独立的进程 | 每个 worker 有自己的 dict，改了别的进程看不见 |

如果你用的是 `uvicorn app:app --workers 4`，那么**加锁毫无意义**，必须用外部存储。下面按场景给方案。

---

## 关键前提：GIL 不等于线程安全

CPython 下单个 dict 操作（`d[k]=v`、`d.get(k)`、`d.pop(k)`、`d.setdefault(k, v)`）在 C 层是一次调用、持 GIL 完成，**是原子的**；但**复合操作不安全**：

```python
# ❌ 典型竞态：check-then-act
if key not in cache:
    cache[key] = compute()      # 两个线程可能都进来了，compute 跑两遍

# ❌ 遍历时被改
for k, v in cache.items():      # 别的线程 insert/del → RuntimeError
    ...

# ❌ defaultdict 的工厂 + 写入是两步，不是原子的
cache = collections.defaultdict(dict)
cache[k]["x"] = 1               # 可能创建出两个不同的内层 dict
```

> 注：Python 3.13+ 的 free-threading（无 GIL）构建下，连单操作的“原子性”也不该依赖，别把设计建立在 GIL 上。

---

## 方案一：`threading.Lock` 封装（最直接，推荐先用这个）

不要裸存 dict，封装一个只暴露**原子语义**方法的类，并且**永远不要把内部 dict 暴露出去**：

```python
import threading
from typing import Any, Callable

class LockedDict:
    def __init__(self) -> None:
        self._data: dict[str, Any] = {}
        self._lock = threading.RLock()      # RLock：方法互相调用不自杀

    def get(self, key: str, default=None):
        with self._lock:
            return self._data.get(key, default)

    def set(self, key: str, value: Any) -> None:
        with self._lock:
            self._data[key] = value

    def delete(self, key: str) -> None:
        with self._lock:
            self._data.pop(key, None)

    def update(self, key: str, fn: Callable[[Any], Any]):
        """把「读-改-写」作为一个原子操作暴露出来，这是精髓"""
        with self._lock:
            self._data[key] = fn(self._data.get(key))
            return self._data[key]

    def increment(self, key: str, delta: int = 1) -> int:
        with self._lock:
            self._data[key] = self._data.get(key, 0) + delta
            return self._data[key]

    def snapshot(self) -> dict[str, Any]:
        """要遍历就拷一份出来，在锁外面遍历"""
        with self._lock:
            return dict(self._data)
```

FastAPI 里用起来：

```python
from fastapi import FastAPI

app = FastAPI()
counters = LockedDict()

@app.post("/hit/{name}")
def hit(name: str):                      # def → 跑在线程池，多线程并发
    return {"name": name, "count": counters.increment(name)}

@app.get("/stats")
def stats():
    return counters.snapshot()           # 拷贝后返回，安全
```

**要点：**

1. **锁粒度只包住内存操作**，别把 `compute()`、I/O、`time.sleep` 放进临界区。
2. **不要返回内部 dict 引用**，否则调用方一遍历就炸。
3. 避免死锁：多个锁时固定加锁顺序；只在必要时用 `RLock`（有轻微开销，但省心）。

## 方案二：不共享，或换成天生线程安全的结构

| 需求 | 用法 |
|---|---|
| 生产者/消费者 | `queue.Queue`（内部自带锁），别用 list 自己加锁 |
| 每线程独立状态 | `threading.local()`，但注意线程池会复用线程，**不能当请求级状态用** |
| 请求级上下文 | `contextvars.ContextVar`（需要 `copy_context()` 才能跨线程传） |
| 只读缓存 | `functools.lru_cache`（CPython 内部有锁，但**被包裹函数可能被并发重复调用**） |
| 带过期的缓存 | `cachetools.TTLCache` + 自己的 `threading.Lock`（cachetools 本身不加锁） |
| 同步/异步两边都要用的队列 | `janus.Queue` |

## 方案三：从架构上消灭共享（最优解）

如果状态是**可变的、跨请求的**，问一句：能不能不要它？

**1. 改成 `async def` + 单线程事件循环**

uvicorn 每个进程一个 event loop，`async def` 路由全在同一线程跑。只要你在**修改状态的代码段中间不 `await`**，就天然没有竞态，不需要任何锁：

```python
@app.post("/hit/{name}")
async def hit(name: str):
    counters[name] = counters.get(name, 0) + 1   # 中间无 await → 原子
    return {"count": counters[name]}
```

⚠️ 三条红线：

- 一旦这里出现 `await something()`，中间就可能被其它请求插进来 → 要么把 `await` 移到状态修改前后，要么用 `asyncio.Lock`。
- **`threading.Lock` 绝对不能跨 `await` 持有**（会阻塞整个事件循环，甚至死锁）；异步代码里用 `asyncio.Lock`。
- `asyncio.Lock` **只在同一个事件循环内有效**，不能跨线程/跨进程。

**2. Actor 模式：把状态关进一个线程**

用一个专门的线程（或一个 asyncio Task）独占 dict，其它线程通过 `queue.Queue` 发消息、用 `Future` 收结果。所有访问串行化，永不竞态。适合状态复杂、需要审计/顺序保证的场景。

**3. 状态外置（最推荐用于生产）**

会话、计数器、缓存这类东西本就该进 Redis / 数据库，而不是进程内存。见下。

## 方案四：多 worker / 多进程 → 必须外部化

`--workers N` 是 N 个独立进程，要跨进程同步：

```python
# 1) Redis：把原子性交给 Redis
import redis
r = redis.Redis()

r.hincrby("counters", name, 1)          # 原子自增
r.hgetall("counters")                    # 读全量

# 复合逻辑用 Lua 脚本，保证原子
LUA = """
local cur = tonumber(redis.call('HGET', KEYS[1], ARGV[1]) or '0')
cur = cur + tonumber(ARGV[2])
redis.call('HSET', KEYS[1], ARGV[1], cur)
return cur
"""
r.eval(LUA, 1, "counters", name, 1)

# 分布式锁（用于非 Redis 原语能表达的临界区）
with r.lock(f"lock:{name}", timeout=5, blocking_timeout=2):
    ...                                 # 注意：持锁期间别做长耗时操作
```

其它选择：
- `multiprocessing.Manager().dict()` —— 能跨进程，但**每次访问都要 pickle + IPC**，性能很差，只适合低频小数据。
- 数据库事务：`SELECT ... FOR UPDATE` 行锁，或 `UPDATE t SET c = c + 1` 这类单语句原子更新。
- SQLite：`PRAGMA journal_mode=WAL` + `BEGIN IMMEDIATE`。
- 更省事的路子：**让状态无共享**（每个请求自带、或用一致性哈希路由到固定 worker），从根上不要同步。

---

<details>
<summary><b>常见坑速查（点开）</b></summary>

- **加锁了还是不生效**：锁对象被重新赋值了，或者在不同模块里各建了一个 `Lock()`。锁必须跟着数据走——把数据和锁封在同一个类/单例里。
- **`if k not in d: d[k] = ...` 加了锁吗？** 两行都要在同一把锁里，拆开就白加。
- **`defaultdict` 看似并发安全，实际上会重复创建内层对象**，别在并发路径用它。
- **`dict.setdefault` 是原子的**，可以放心用它做“不存在才插入”；`dict.get` + 判断则不行。
- **`copy.deepcopy(d)` 不是原子的**——遍历过程中被改照样报错，得先 `snapshot()`。
- **只在 `def` 路由里才需要 `threading.Lock`**；`async def` 里用 `threading.Lock` 反而会卡住事件循环。
- **线程池大小**：Starlette 默认 `anyio` limiter 是 40 个线程。并发量高时锁竞争会明显拖慢吞吐 —— 这本身就是“该换方案”的信号。
- **GIL 不是锁**：它能保证单字节码不被打断，保不住你的业务逻辑不被打断。
</details>

## 选型建议

1. **能无状态就无状态**，状态进 Redis/DB → 问题消失。
2. **数据量小、单进程、并发中等** → `LockedDict` 方案一，当天就能上线。
3. **想彻底避开锁** → 全链路改 `async def`，状态修改段内不 `await`；需要互斥再上 `asyncio.Lock`。
4. **已经上了 `--workers`** → 直接跳到方案四，加线程锁是浪费时间。
5. **状态复杂 / 需要顺序与审计** → Actor 模式（单线程独占 + 队列）。

| # | 口径 | 精确化 |

## 回答 #3：可以，但要先分清"状态"和"事件"

挂中间件之前，先回答一个问题：**你要的是"大家看到同一份数据"，还是"某件事发生了，通知别人"？**

| 诉求 | 该用什么 | 典型例子 |
|---|---|---|
| 同一份数据，多进程读写 | **KV / Redis** | 计数器、限流、会话、任务进度、分布式锁、缓存 |
| 事件发生，异步解耦，可多消费者 | **MQ** | 下单后发短信/发邮件/建索引/写数仓 |
| 事件要**可靠投递 + 可重放 + 顺序** | **MQ（Kafka 类）** | 订单流水、CDC、审计 |
| 只是跨进程互斥 | **KV 的 `SET NX`** | 定时任务防重、单例扫描 |
| 强一致 + 事务 | **数据库**（不是 KV 不是 MQ） | 账户余额、库存扣减 |

**最常见的错误**：拿 MQ 当共享内存用（发个请求消息、等个响应消息回来做 RPC），或者拿 Redis 当数据库用（指望它做资金账本）。前者是性能灾难，后者是一致性灾难。

## 方案 A：KV（Redis）—— 首选，覆盖 80% 场景

### A1. 能原子就别加锁

Redis 单命令天然原子，**先找原语，不要先想锁**：

```python
import redis.asyncio as redis          # 口径 1：必须用 async 客户端，别用同步版阻塞 event loop

r = redis.Redis(host="127.0.0.1", port=6379, decode_responses=True)

@app.post("/hit/{name}")
async def hit(name: str):
    n = await r.incr(f"counter:{name}")       # 原子自增，替换掉 dict 的读-改-写
    return {"name": name, "count": n}

@app.post("/session/{sid}")
async def set_session(sid: str, payload: dict):
    await r.hset(f"sess:{sid}", mapping=payload)
    await r.expire(f"sess:{sid}", 1800)       # 顺手解决 dict 时代的内存泄漏

@app.get("/session/{sid}")
async def get_session(sid: str):
    return await r.hgetall(f"sess:{sid}") or {}
```

### A2. 复合逻辑 → Lua（跨 key 组合时注意 hash slot）

```lua
-- KEYS[1]=计数key  ARGV[1]=上限  返回 -1 表示超限
local cur = tonumber(redis.call('GET', KEYS[1]) or '0')
if cur >= tonumber(ARGV[1]) then return -1 end
return redis.call('INCR', KEYS[1])
```

```python
HIT_LUA = """ ... 上面那段 ... """
n = await r.eval(HIT_LUA, 1, f"counter:{name}", 100)
```

> Redis Cluster 下 Lua 涉及的 key **必须同 slot**，用 hash tag 强制：`{order:123}:lock`、`{order:123}:state`。

### A3. 真的需要跨进程互斥 → `SET NX PX` + Lua 释放

```python
import uuid

async def acquire(key: str, ttl_ms: int = 5000) -> str | None:
    token = uuid.uuid4().hex
    ok = await r.set(f"lock:{key}", token, nx=True, px=ttl_ms)
    return token if ok else None

RELEASE_LUA = """
if redis.call('GET', KEYS[1]) == ARGV[1] then return redis.call('DEL', KEYS[1]) end
return 0
"""
async def release(key: str, token: str) -> None:
    await r.eval(RELEASE_LUA, 1, f"lock:{key}", token)   # 校验 token，防止误删别人的锁
```

⚠️ 分布式锁的坑不小：**长 GC 停顿 / 网络分区**会破坏互斥性，Redlock 至今有争议。真正要"严格互斥"（比如财务扣款）请用**数据库行锁/乐观锁**，或带 **fencing token** 的方案；Redis 锁适合"防重复触发"这种宽松场景。

### A4. 性能：别让每个请求都打一次网络

| 手段 | 效果 |
|---|---|
| 本地 L1 缓存（`cachetools.TTLCache`）+ Redis L2 | 大幅降 RTT |
| Redis **pub/sub 广播失效** → 各 worker 清本地缓存 | L1 一致性 |
| Pipeline / `mget` 批量 | 降往返次数 |
| 直接走 Redis Cluster / 就近部署（同 AZ） | 降 RTT |

## 方案 B：MQ —— 只在"事件"语义成立时才用

### 什么时候真的需要 MQ

- 一次请求要触发 **N 个下游动作**，且允许异步
- 需要**多消费者**各自独立消费（搜索索引、风控、数仓）
- 需要**削峰**、**重放**、**消费进度管理**
- 需要**跨服务解耦**，生产者不该知道消费者是谁

选型速查：

| MQ | 适合 |
|---|---|
| Redis Streams | 已用 Redis，要轻量消费组，不想引入新组件 |
| RabbitMQ | 路由灵活（exchange/routing key）、任务队列、延迟队列 |
| Kafka | 高吞吐、可重放、分区有序、日志/CDC/数仓入湖 |
| NATS JetStream | 轻量、低延迟、云原生 |
| SQS/SNS | 全托管、运维成本最低、语义简单 |

### 两个绕不过去的工程问题

**① 双写不一致 → 用 Transactional Outbox**

```python
# ❌ 先写库再发消息：中间崩了 = 消息丢了 / 消息发了库没提交
await db.execute(...)
await producer.send(...)

# ✅ 同一事务写业务表 + outbox 表，另一个 relay 进程轮询 outbox 投递
async with db.transaction():
    await db.execute(insert_order_sql)
    await db.execute(insert_outbox_sql, topic="order.created", payload=...)
# 独立 relay 任务：SELECT ... FROM outbox WHERE sent=false ORDER BY id LIMIT 100
#                → publish → 标记 sent（至少一次，所以消费端必须幂等）
```

**② 至少一次投递 → 消费端必须幂等**

用业务唯一键做幂等（`INSERT ... ON CONFLICT DO NOTHING`、`SETNX processed:{msg_id}`），不要指望 MQ 帮你做到 exactly-once。

```python
async def handle(msg):
    if not await r.set(f"idem:{msg.id}", 1, nx=True, ex=86400):
        return                      # 已处理过，直接 ack
    await do_business(msg)
```

## 方案 C：组合拳（生产上最常见）

```
写路径:  DB（真相源，事务保证）
   └─ outbox ──relay──▶  MQ  ──▶  各消费者
                         └──▶  更新 Redis 读模型（缓存/计数/排行）

读路径:  请求 ──▶ 本地 L1 ──▶ Redis ──▶ DB
```

- **DB** 管正确性（唯一真相源）
- **Redis** 管读性能和跨进程共享状态
- **MQ** 管变更传播和异步解耦
- 各 worker 仍然是**无状态**的 —— 这是能水平扩容的前提

---

<details>
<summary><b>外部化之后的工程注意事项（点开，容易被忽略但会出事）</b></summary>

- **口径 1 的硬约束**：一定要用 `redis.asyncio` / `aiokafka` / `aio-pika` / `aioboto3`。同步客户端在 `async def` 里会阻塞整个 event loop，等于把整个 worker 卡死 —— 这比原来的字典竞争严重得多。
- **外部依赖成了新的单点**：必须设 `socket_timeout` / `connect_timeout`、连接池上限、熔断降级。Redis 挂了不能让全站 500，要有本地兜底或快速失败。
- **重试要带退避 + 抖动**，且只重试幂等操作。重试风暴能把自己的 KV 打挂。
- **Redis 内存策略**：`maxmemory-policy` 要显式设置（缓存放 `allkeys-lru`，状态类绝不能 `allkeys-lru` 否则会被淘汰掉）。持久化（AOF/RDB）决定你能不能容忍丢数据。
- **大 key / 热 key**：单个 hash 存几十万字段、或某个 `counter:hot` 被所有请求打 —— 前者用分片，后者用本地批量聚合（如每 100ms 汇总一次再 `INCRBY`）。
- **可观测性**：`redis` 命令耗时、MQ 消费 lag、outbox 积压量，这三个指标必须上监控，否则积压了你不知道。
- **别在 `async def` 里用 `threading.Lock`**，也**别在持锁期间 `await`**；外部化之后你基本不再需要进程内锁了。
</details>

## 一句话结论

**同意口径 1、2、3。** 在新口径下，"线程间字典同步"这个命题不成立——multi-worker 是多进程，进程间没有共享内存。所以：

- 要**共享状态** → KV（Redis），优先用原子命令/Lua，其次才用锁；
- 要**传播事件** → MQ，配 Outbox + 消费幂等；
- 要**强一致账务** → 数据库事务，两者都别硬套；
- 无论哪种，**worker 保持无状态**，客户端一律用 async 版，且把超时/重试/降级/监控当成方案的一部分而不是后续优化。
