锐评一下deepseek super agent

## 😀 默认助手 (7)

## 一句话：这不是“DeepSeek 出了个超级智能体”，而是一份**把“人的注意力”写成系统约束的 RFC，并顺手附带了一个 0.1.0 的参考实现**

> 它在 10 月 31 日晚由 DeepSeek Harness 团队发布的长文《Super-agent 设计探索：迈向更自主的 Agent 系统》和 MIT 仓库 `deepseek-ai/dsh-superagent-prototype` 中给出。README 第一句自己写着：*Research prototype for reference only, **not an official DeepSeek product***。

所以“锐评”的第一刀，其实应该先划在**传播层**上。

---

### 一、先纠正三处被传播带偏的说法

| 流传的说法 | 实际是什么 |
|---|---|
| “DeepSeek 发布新模型或新 Agent 产品” | 不是模型。它是一个 TypeScript 写的 DSH（DeepSeek Harness）bundle，模型由你在 profile 里配置，`engines.dsh: ^0.2.1-alpha.2` |
| “对标 Claude Code” | 错位。Claude Code 解决“一个人怎么和 Agent 一起写代码”；它解决“一个 Agent 怎么长期待在团队里而不变成噪音” |
| “AI 开始给 AI 派活、无人 @ 也主动干活” | 默认 `observe`（只记录不执行）、白名单为空则什么都不做、必须由白名单成员**新发评论** @ 它 |

从 Bloomberg 的一条推文，到中文圈“超级智能体来了”，中间经过了三层放大。技术含量最高的那部分——3.8 倍 token 和消融实验——恰好是传播中最先被删掉的部分。

---

### 二、值得给的分：真正的新意不在 Router/Worker

Router/Worker、orchestrator-worker、supervisor 模式这些词并不新，Anthropic、OpenAI 都写过类似东西。**这个词本身只值 3 分。**

真正把分挣回来的是这几处：

**1. 它用能力边界代替自我克制。**
Router 只调度不执行，甚至**可以不配 Bash 工具**。这一点很关键：很多“主 Agent 别自己干活”的设计靠提示词约束，而它直接拿掉工具。**能力边界比自我克制可靠**——这是全文最漂亮的一行设计。

**2. 它承认 Agent 之间互相通信是负担。**
Worker 之间没有点对点通信，靠“Thread 订阅的多对多可见性”让撞车的两个 Worker 自己看见对方在干什么、自己解决冲突。这个取舍很克制：多 Agent 系统常见的情况是加消息总线，而它做的是**减少通信通道、增加共享状态**。

**3. 它把代价写在明面上。**
$2323\text{万} \div 605\text{万} \approx 3.8$ 倍读缓存 token，消融实验里去掉直通后 Router 决策 $+30\%$、token $+37\%$（2323 万 → 3177 万），**而完成时间几乎不变**。这条“花 37% 的钱买 0% 的时间”的负结果，它没有藏。

**4. `docs/000-philosophy.md` 那句设计原则，比代码值钱。**
“Take as little human attention as possible, and give as much value as possible.” 一个细节：SETUP.md 被写成了**给 Agent 执行的规格**（一次只问一个问题、不在聊天里索要密钥），而不是给人读的说明书。这个元设计比架构图有意思。

### 三、该扣的分：四个地方说不通

<details>
<summary><b>刀口一：3.8 倍的账没人替你算完（点击展开）</b></summary>

这 3.8 倍的本质是**用钱买 p95**：把“被新消息反复打断”的长尾（29.5 分钟）砍到 15.7 分钟。

- 对个人开发者：你的钱比时间便宜，这买卖**不划算**。
- 对团队：注意力更贵，可能划算。

但它从头到尾**没给“人时 / 元”的换算**，也没给最该给的三个数：**打扰率、误报率、Watchdog 命中率**。

也就是说——**它宣称优化的那个量（人的注意力），恰恰是唯一没有被测量的量。** 一套说“我只在你必须行动时才说话”的系统，却不报告它到底说了多少次废话。这是这份工作最大的软肋，也是唯一一个“补一版实验就能救回来”的软肋。
</details>

<details>
<summary><b>刀口二：29.5 分钟的 baseline 有点“稻草人”（点击展开）</b></summary>

那个被广泛引用的 p95 29.5 分钟，前提是：中性提示下，模型 **5 次运行一次都没有主动调用 Subagent**，所有活都挤在主会话里干。

可作者自己也写了：换成明确鼓励委派的提示词后，5 次里 4 次委派了。

那么这组对比真正证明的不是“单 Session 架构有天花板”，而是“**单 Session + 不会用工具的提示词有天花板**”。用提示词工程没做到位的系统当 baseline 去论证架构优越性，说服力是要打折的。

再加上：合成负载、约 300 条消息里只有约 20 条真工作请求、编码那一步被换成**空转的假工具**、每种方案只跑 5 次。结论的正确表述是“**双层架构比单会话更能扛并发**”，而不是“你上线能省一半时间”。拿 47% 去说“效率翻倍”的，都是过度解读。
</details>

<details>
<summary><b>刀口三：最要命的一条——省下你的注意力，交出去你的机器（点击展开）</b></summary>

文档原话：Router 和 Worker 两个 preset 都以 `danger-full-access` 运行在**操作者的 OS 用户**下，Worker **能按路径执行程序、能读 operator 的 home 目录**，且执行无审批提示（approval-free）。

缓解措施全部在**部署层**：用一个只放 agent 凭据的独立 OS 账号或 VM。那个 `gh-agent` 包装脚本让它**默认**用 agent 凭据，**不是隔离**。

于是形成一个很锋利的结构：

> 它的立论是“尽可能少占用人的注意力”，而它的默认权限模型是“把整台机器的注意力全交出去”。

对研究原型，这是合理选择（把责任明确下推给部署者）。但如果这套思路**被产品化**，它就是把“Agent 时代的权限模型”这个真问题又往后推了一格。

外加那个绕不开的注入面：它要读 Issue 正文和评论来干活，**被它读到的文字都可能被当成指令**。一个“主动”的 Agent，意味着“被注入后主动干活”。
</details>

<details>
<summary><b>刀口四：蓝图和原型不是一回事，而且它自己说了（点击展开）</b></summary>

文章里讲的这些，**README 里没有**：Thread 订阅直通、投机执行、云端存算分离、BYOM。属于“设计方向”，未在原型实现。异步 `start()/stop()` 在 DSH 里已实现但**默认未开启**。

原型实际能干的事窄得多：**一个 `github.com` 仓库**（不支持 GHES）、轮询 notifications 一分钟一次、可选飞书、要一个**专用 GitHub 用户账号**（不能是 GitHub App）、每个 Ticket 一个独立 session + git worktree、回原对话开 PR、本地面板 `127.0.0.1:3082`。

而且 README 自己写：*much of the engineering done by coding agents*，与内部版、与文章描述**不完全一致**，可能有 bug、风格不一致。

——用 Agent 写的一份 Agent 架构参考实现，很元，很诚实，但它和“能跑的效率方案”之间差着一个量级。v0.1.0、依赖 rc 版 DSH、跑错一次 `dsh superagent --from-default-profile` 就会覆盖并删掉你的 `cordis.patch.yml`。2800 颗星里，读到第 8 个 docs 的人大概不到 1%。
</details>

---

### 四、还有一层没人提的：它把组织能力当成了模型能力

“该不该管这件事”，最终落在**“团队把提示词里的规则写得多清楚”**上。

这等于说：**主动性的上限 = 你团队流程的清晰度**。

而真实的研发上下文散在会议、私聊、线上事故、深夜那通电话里。它的 Source 只有 GitHub 和飞书——覆盖的全是“**已经被写下来的那部分工作**”。

所以我的定性是：**它更像一个“on-call 值班 Agent”，而不是“超级智能体”**。这不是贬低。值班 Agent 是个真实且有价值的形态，只是别用“超级”这个词去卖它。

### 五、谁该碰、谁别碰

| 你是谁 | 建议 |
|---|---|
| 想立刻提效的个人开发者 | **别装。** 你的瓶颈不是会话数，是判断力 |
| 团队平台工程 / 在造 Agent 产品 | **必读 `docs/000`–`008`。** 抄“Router 无 Bash”的能力边界，抄那套默认值，比抄代码有用一万倍 |
| 要做多 Agent 通信设计的人 | 把两句话记进设计文档：**订阅可见性 > 点对点消息**；**多 Agent 的收益本质是调度收益，不是智能收益** |
| 真想跑起来 | 单独 GitHub 账号 + 单独 OS 用户或 VM；白名单只放自己；`observe` 起步；auto-merge 别开；注意**编辑 Issue 正文 @ 它收不到，必须新发评论** |
| 想拿它做生产 | 它自己说了不建议。信它 |

---

### 收尾

**这份东西最像的不是产品，是一份 RFC。它的价值全在默认值里——“白名单为空就什么都不做”“主动工作先只记录”“只在人必须行动时说话”“Router 不配 Bash”——而不在 Router/Worker 这两个词里。**

**它的风险，也全在默认值里。**

一句话版本：**DeepSeek 交出的不是“更强的 Agent”，而是“一次关于 Agent 该占人多少注意力的、难得诚实的自问自答”。** 至于那个自问自答的答案对不对——它缺的那组数据（打扰率、误报率），比你缺的那个 PR 更难补。
