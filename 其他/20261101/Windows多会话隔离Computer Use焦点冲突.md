## 你的直觉是对的：但真正隔离的是会话，3389 本身并不负责隔离

先确认你判断对的地方：Windows 的多用户隔离**单位是 logon session，而非窗口**。每个 session 拥有独立的一套：

- 窗口站（`WinSta0`）+ 独立 desktop 对象
- 独立的**输入队列**（raw input thread）——焦点、光标、键盘注入都在本会话内部
- 独立的剪贴板、DWM 合成器、屏幕分辨率/DPI
- 独立的 `SendInput` / UI Automation 作用域

所以 GPT Computer Use 那个窗口抢焦点这件事，在另一个 session 里**物理上不可能发生**——它的 `SetForegroundWindow` 只能影响自己的输入队列。这一点你判断得完全准确：单会话内无论怎么调整（虚拟桌面、`WS_EX_NOACTIVATE`、最小化）都只是绕开问题，只有换 session 才是根本解决。

补充一个关键约束，后面会反复用到：**CU agent 必须运行在目标会话内部**。`SendInput`、UI Automation、截屏都是 per-session 的，隔着会话是操作不到的。所以必须考虑如何让 agent 在那个会话里启动（`PsExec -i <sid>`，或 service 里 `WTSQueryUserToken` + `CreateProcessAsUser`）。

## 关于给客户端版打补丁这条路，我不建议走，也不会给出具体步骤

原因有三个，而且第三个最实际：

1. **这属于绕过授权，不属于技术障碍**。客户端 SKU 的单会话限制写在 `termsrv.dll` 的策略检查里，Win7 时代确实一直是改字节码绕过，RDPWrap 后来用 hook 的方式做到了同样的事。技术可行不等于可以随意使用——这属于规避微软的许可控制，我不会提供具体 patch 步骤。
2. **维护成本高**。RDPWrap 上游早已停更，靠社区 fork 更新 `rdpwrap.ini`；每次累积更新（尤其 24H2 那类大版本）都可能失效，然后你会遇到"登录后另一个会话被踢掉"这种典型故障——对自动化来说是非常坏的失败模式：不崩溃，但会静默抢占会话。
3. **即使成功了，它也没解决你真正的痛点**。你真正需要处理的是"agent 的窗口不能干扰人"+"人能随时接管"，并非"省一台机器"。如果只沿这条思路走，你会在 DPI 变化、断开重连、截图黑屏上投入的时间，比直接开一台虚拟机多得多。

<details>
<summary>如果你还是想评估现有补丁方案的可靠性（仅说明，不提供操作）</summary>

判断一个方案是否值得用的三个信号：

- 是否 hook `termsrv.dll` 的 `CSessionArbitrationHelper` / 会话计数检查，还是直接改文件字节（后者每次更新必挂）
- 是否有针对你当前 build 号（`winver` 里的完整 build，如 `22631.4890`）的 ini 条目；没有条目就是必然失败
- 是否能随时干净卸载（`RDPWrap.ini` + 服务移除），否则系统更新后可能与远程桌面服务冲突

如果三条里有任意一条不满足，就把它当作不可用于生产的方案。
</details>

## 更值得考虑的四个方案（按推荐度）

| 方案 | 多会话 | 授权 | 隔离强度 | 适合你的场景 |
|---|---|---|---|---|
| **Hyper-V 虚拟机，每 agent 一台** | 天然 | Win11 Pro 自带 Hyper-V；guest 需自己的授权/评估版 | 整个 OS + 磁盘 | ★ 最推荐 |
| **Windows Server + RDS** | 原生支持 | 评估版 180 天；正式需 RDS CAL | 会话级（你原本想要的） | 想复刻"3389 体验" |
| **Windows 11 企业版多会话（AVD）** | 原生 | 云上正规授权 | 会话级 | 已有 Azure |
| 客户端版打补丁 | 勉强 | 违反许可 | 会话级 | 不建议 |

**为什么我最推荐 VM 而不是多会话**：会话隔离共享同一个内核、同一个磁盘、同一份用户配置和注册表。CU agent 到处点、乱装东西、改环境变量、把注册表改坏——这些全会泄漏到你的人机会话里（同用户的 profile 甚至直接共享）。VM 给你的是**快照回滚**，这对 computer use 是决定性优势：agent 一次点错，30 秒回到干净状态。多会话给不了这个。

Hyper-V 也顺便解决了"人在旁边看"的问题：VM 连上去是 RDP（Enhanced Session），你随时接管，agent 断开也不影响它继续跑。

<details>
<summary>Windows Server 方案的几个实操要点（如果你要走"原生多会话"这条路）</summary>

- Server 默认允许 **2 个并发会话用于管理**（不需 RDS CAL），超过就要 RDS 授权；评估期有 120 天 grace，做开发验证够了。这正好覆盖"1 个人 + 1 个 agent"。
- 会话数确认：`query session` / `quser`，能看到 `console` 和 `rdp-tcp#N`。
- 让 agent 跑在指定会话：`psexec -i <sessionID> -d <agent.exe>`，或用计划任务绑定到该用户登录触发。
- **固定分辨率**：会话重连会改分辨率，agent 记录的坐标全部失效。用 `.rdp` 文件里固定 `desktopwidth/desktopheight`，并关掉动态分辨率。
- **别让会话注销**：注销 = 桌面销毁，agent 进程一起死。断开会话（disconnect）是保留的，但要用 `tscon` 或组策略确保不自动注销。
</details>

## 在一台机器上的临时缓解手段（无法从根本上解决）

- **虚拟桌面（`Win+Ctrl+D`）没用**。Win10 以后，跨虚拟桌面调 `SetForegroundWindow` 会直接把桌面切过去——这恰好就是 CU agent 那种行为，所以它反而会加剧问题。
- **独立的 desktop 对象 + `SwitchDesktop`**（Sysinternals `Desktops.exe` 就是这个原理）能在单会话内做出多个互不见的桌面，非活动桌面上的窗口不抢活动桌面的焦点。但同一时刻只有一个可见，agent 的截屏拿不到自己的画面——只能退化成逐窗口 `PrintWindow`，对 GPU 渲染的内容（浏览器、Electron）不可靠。
- **Session 0 服务桌面**：把 agent 塞进 session 0 的不可见 desktop，理论上完全不打扰人。但 session 0 没有 DWM、没有显示驱动、GPU 加速基本不可用，现代浏览器/Electron 应用在这种环境下渲染和截屏都会出问题。属于"看起来很美"的坑。

## 动手前需要知道的主要问题（CU + 远程会话）

1. **截图黑屏**：会话断开或处于无显示状态时，硬件加速的桌面复制（DXGI Duplication）和某些情况下的 GDI `BitBlt` 会返回全黑。这是 CU 类工具在 RDP 里最常见的翻车点，远早于"多用户限制"暴露出来。
2. **断连时的 UI 行为**：部分应用在会话断连后会暂停动画/渲染循环，依赖"等动画结束"的 agent 会一直等下去。
3. **DPI 与缩放**：会话的 DPI 与人机会话不同时，坐标换算全错。要么两边统一，要么 agent 端做 DPI-aware 换算。
4. **剪贴板**：只在会话内有效，跨 agent 传数据要走文件或网络，别指望剪贴板。

---

## 结论

你的方向是对的——**要的是"独立桌面"，3389 只是实现它的其中一条路径，而且是最脏的一条**。同样的目标，Hyper-V 虚拟机或者 Server + RDS 都能以合法且可维护的方式拿到，还额外解决了"agent 玩坏了怎么办"这个你用会话隔离根本没解决的问题。真正应该投入精力去解决的，是截图可靠性、坐标稳定性、会话内启动 agent 这三件事——这三件事无论走哪条路都躲不掉。
