## 结论：这个梗大概率成立，但这是硬件限制，不是你的品味问题

2080 Ti（**sm_75 / Turing**）在很多现代推理框架眼里已经是“上一代、不再重点支持”的架构。它缺的东西恰好是现代推理栈最依赖的那几项，所以“折腾一圈回来还是 llama.cpp”不是玄学，而是 compute capability 写死的。

但也不是没有第二选择：**ExLlamaV2 + EXL2** 是靠 Turing 仅存的那点优势（INT4 Tensor Core）跑赢 llama.cpp 的方案。

---

## 一、Turing 把你挡在门外的那些特性

| 特性 | 2080 Ti | 后果 |
|---|---|---|
| BF16 | ❌ | 只能 FP16 计算，部分 kernel 与量化格式直接不可用 |
| FP8 | ❌ | FP8 权重、FP8 KV cache 可以放弃 |
| FlashAttention 2 | ❌（官方要求 sm80+） | vLLM、SGLang 的主要路径没有了 |
| FlashAttention 3 | ❌（Hopper） | — |
| Marlin、GPTQ-Marlin INT4 | ❌（sm80+） | vLLM 的 4bit 高速路径没有了 |
| FlashInfer | ❌ | **SGLang 基本跑不起来** |
| TensorRT-LLM | ❌ | 新版已不支持 sm75 |
| **INT4、INT8 Tensor Core** | ✅ | Turing 是首款带 INT4 TC 的消费卡，**EXL2 因此受益** |
| FP16 TC ~107 TFLOPS | ✅ | prefill 阶段完全够用 |
| **显存带宽 616 GB/s** | — | 这才是你 decode 速度的天花板 |

> decode 的物理上限就是 $616\ \text{GB/s} \div \text{权重体积}$；llama.cpp 实测能到 70–85%，再乘一下，你就有速度预期了。

## 二、方案选型

| 方案 | 评级 | 评价 |
|---|---|---|
| **llama.cpp / llama-server** | ⭐ 首选 | GGUF 生态最全，新架构、MoE 跟进最快，Turing 被当作一等公民对待 |
| **ExLlamaV2 + TabbyAPI 或 text-generation-webui** | ⭐ dense 模型时速度最优 | EXL2 真的会调用 INT4 TC，在同样模型和 bpw 下通常比 llama.cpp 快 20–50%；但 MoE、新架构支持滞后 |
| Ollama / LM Studio | ✅ 省事 | 底层就是 llama.cpp，只是参数控制少 |
| ik_llama.cpp | 🔧 适合折腾 | MoE 和 CPU offload 优化更激进，IQ 量化种类多 |
| vLLM | ⚠️ 能跑但很难受 | 只能退回 xformers 后端，新版对 sm75 越来越不友好；只有确实需要并发批处理才值得 |
| SGLang | ❌ | FlashInfer 需要 sm80+ |
| TensorRT-LLM | ❌ | 不再支持 Turing |

**所以：单人使用就选 llama.cpp；追求高质量量化（4.0–4.5 bpw）的速度上限就选 EXL2；vLLM 没必要碰。**

## 三、22GB 显存能跑哪些模型

| 模型 | 量化 | 权重 | 预期 decode |
|---|---|---|---|
| **Qwen3-30B-A3B**（MoE，3B 激活） | Q4_K_M | ~18.5 GB | **25–40 tok/s** |
| **gpt-oss-20b**（MoE，3.6B 激活） | MXFP4 | ~12 GB | **30–50 tok/s** |
| Qwen3-14B | Q4_K_M | ~9 GB | 35–45 tok/s |
| Gemma 3 12B | Q4_K_M | ~7.5 GB | 40–55 tok/s |
| Mistral Small 3.2 24B | Q4_K_M | ~14.5 GB | 22–30 tok/s |
| Qwen3-32B | **IQ4_XS**（别用 Q4_K_M，会 OOM） | ~17.5 GB | 15–20 tok/s |
| Qwen2.5-Coder-14B 或 32B | Q4_K_M | 9 / 19 GB | 同上 |

<details>
<summary><b>为什么 MoE 是你这张卡的最优解（展开）</b></summary>

22GB 显存能容纳的参数量相当可观，但带宽只有 616 GB/s。MoE 恰好化解了这个矛盾：Qwen3-30B-A3B 权重 18.5GB 能全塞进显存，但每个 token 只读 ~3B 参数（约 2GB），所以 decode 极快。

代价是 **prefill 慢**（长 prompt 要过所有 expert），以及 llama.cpp 在 Turing 上的 expert gather 效率不如 Ampere。因此：
- 短对话、Agent、写作 → 极爽
- 长文档一次性吞下（>16k prompt）→ 反而比同尺寸 dense 更慢

推荐的逻辑就很清晰：**日常对话或干活选 Qwen3-30B-A3B 或 gpt-oss-20b，写代码选 Coder-14B，要更强推理再退到 32B dense 慢速跑。**

</details>

<details>
<summary><b>别想着上双卡 70B</b></summary>

2×22GB = 44GB，理论上能放下 70B Q4（~40GB）。但 llama.cpp 是层切分（流水线），单个 token 必须串行穿过两张卡，带宽不叠加，实际大概 6–10 tok/s，且 MoE 模型分卡更惨。2080 Ti 虽然有 NVLink，但 mod 卡不一定保留接口，收益也有限。**性价比远不如单卡跑 30B-A3B。**

</details>

## 四、关键参数（llama.cpp）

```bash
llama-server -m Qwen3-30B-A3B-Q4_K_M.gguf \
  -ngl 99 \
  -fa on \
  -ctk q8_0 -ctv q8_0 \
  -c 16384 \
  --batch-size 2048 --ubatch-size 512 \
  --no-mmap --jinja \
  --host 0.0.0.0 --port 8080
```

- **`-fa on`**：在 Turing 上可用（llama.cpp 的 MMA FA kernel 最低就要求 sm75），开启后能省 KV 显存并提速。如果某个版本报错，就退回默认。
- **`-ctv q8_0` 依赖 `-fa`**，不要单独开启。
- **`--no-mmap`**：让权重常驻显存，避免首次加载和偶发 PCIe 抖动；显存够用就开启。
- **`--ubatch-size 512`**：这是提升 prefill 速度最省事的一项，2080 Ti 上 512 通常比默认 128 快不少，显存紧张就降到 256。
- 显存不够时，把 `-c` 降到 8192，或换 IQ4_XS。

> 用 `llama-bench` 实测，不要参考别人的截图：同样的卡换了驱动和量化，速度能差 30%。

## 五、这张卡本身的注意事项

<details>
<summary><b>硬件与驱动的注意事项（展开）</b></summary>

1. **背面显存颗粒没散热**——22G mod 卡最常见的故障来源。加铜片或风扇直吹，跑长上下文前摸一下。
2. **供电与 BIOS**：确认 `Above 4G Decoding` 打开；这类卡常有魔改 BIOS，功率墙可能被改过，用 `nvidia-smi -q -d POWER` 看实际限制。
3. **没有官方保修**，别拿它做唯一生产力。
4. **别用 Ollama 的默认参数**跑大模型——它会自作聪明地部分卸载，结果 CPU 拖后腿，直接 `-ngl 99` 全量上卡。
5. **新 llama.cpp 编译**：用官方 CUDA 后端即可，`CMAKE_CUDA_ARCHITECTURES=75`（如果你自己编，别漏了，默认可能只编 80+）。

</details>

## 先说判断

**方向对，但 base 选错了。** nano-vllm 那类 ~1k 行教学实现，你 fork 的实际上是**调度器骨架**，而你需要的东西全在 kernel 层——那部分 nano-vllm 里没有，vLLM 里对 sm75 也恰好是空的。所以真正的问题不是“改 nanovllm”，而是**“自己搭一个调度器 + 去别处偷 sm75 内核”**。

而且要先接受一个现实：**batch=1 decode 上你赢不了多少**。2080 Ti 是 616 GB/s，llama.cpp 已经跑到 roofline 的 75–85%，理论上限就 15–25% 的余量。真正能撬出 1.5–2.5x 的是另外三个地方，下面细说。

---

## 一、你的直觉里对的那一半

先把“llama.cpp 优化太烂”落实到具体层面，这几条是真的：

| llama.cpp 的真实短板 | 严重度 | 能不能自己修 |
|---|---|---|
| **MoE expert gather 是逐个 expert 的 matvec**，没有 grouped GEMM，Turing 上尤其惨 | ⭐⭐⭐⭐ | 能，且收益最大 |
| **Prefill 没有 INT4 fast path**（dequant→FP16→FP16 MMA），Turing INT4 TC 有 4x FP16 吞吐完全闲置 | ⭐⭐⭐⭐ | 能，但要写 kernel |
| **没有 paged KV**，靠统一 cache + `seq_rm` 切分，前缀共享只支持“完全相同前缀”，长会话碎片化 | ⭐⭐⭐ | 能，但要重写整个 KV 管理 |
| **无真正的 chunked prefill + 优先级调度**，`--parallel` 的 continuous batching 很粗糙 | ⭐⭐ | 能，调度的活 |
| **Decode 每步 kernel launch 数偏多**，小模型上 launch 开销占比不低 | ⭐⭐ | CUDA graph 能救，llama.cpp 有但覆盖不全 |
| **投机解码只支持 draft model**，没有 n-gram/lookup 解码 | ⭐⭐⭐ | 能，且极廉价 |

注意第 2 条：**vLLM 在 sm75 上同样没有 INT4 fast path**——Marlin 要 sm80，FlashAttention 要 sm80，vLLM 的 sm75 4bit 只能走 `exllama` GPTQ kernel 或退回 dequant。**这是你唯一能在“引擎层”正面打赢 vLLM 的地方**，而且赢的是 prefill，不是 decode。

## 二、nano-vllm 作为 base 的真实问题

<details>
<summary><b>它缺的不是性能，是所有"无聊"的正确性（展开）</b></summary>

~1k 行意味着它实现了：paged attention、prefix cache、CUDA graph、TP、block manager。听起来齐全，但生产可用还差：

- **调度**：无抢占（preemption/recompute/swap）、无公平性、无优先级、无 chunked prefill 与 decode 混合批
- **KV cache**：无 eviction 策略的调优（LRU 够用但块回收时机粗糙）、无 sliding-window / 混合注意力（Gemma 3、gpt-oss 都要）
- **采样**：无 logits processor 链、无 repetition/presence/frequency、无 grammar/structured output、无 logprobs
- **投机解码**：没有
- **量化**：没有（这是核心问题，见下）
- **服务层**：OpenAI 兼容协议的边角（tools、streaming delta、usage、abort）、请求取消、超时、异常恢复
- **可观测**：无 metrics

你要花的时间 80% 在这些地方，而它们的性能收益 ≈ 0。**"vLLM 太重"的重，指的就是这些，但它们是必要的，不是冗余的。**

</details>

**结论：把 nano-vllm 当“调度器骨架 + 参考实现”读，别当“代码基”继承。** 它的 block manager 和 CUDA graph 封装值得抄，别的都自己写。

## 三、如果你真要动手：三个真正的杠杆

### 杠杆 1：投机解码（最高 ROI，先做这个）

216 GB/s 是问题吗？不是——问题是**每个 token 都要把 18.5GB 权重流一遍**。投机解码是唯一能把这个成本摊薄的手段，而且是纯调度+注意力掩盖的活，不需要新 kernel：

- **n-gram / lookup decoding**：从 prompt 和已生成内容里匹配后缀当 draft，**零额外显存、零额外 matmul**。写代码、RAG、改写类任务上实测 1.5–2.2x，成本大概 200 行。llama.cpp 没有，vLLM 有 `--speculative-config` 的 ngram。
- **draft model**：Qwen3-0.6B 给 14B 当 draft，显存才 0.5GB，接受率 60–70% → 1.8–2.5x。
- **EAGLE-3 / Medusa head**：Turing 上完全跑得动（就是小 matmul + tree attention），但树形 attention 要自己写，值得放到第二阶段。

**在你这个带宽受限场景下，spec decode 的收益比任何 kernel 优化都大。** 先把这块做出来，再谈 INT4。

### 杠杆 2：Turing INT4 GEMM（真能打赢 vLLM 的地方）

sm75 是有 INT4 Tensor Core 的，这是 Turing 被低估的点：

- `mma.sync.aligned.m16n8k64.row.col.s4.s4.s4`（也有 `m8n8k32.s4`），Turing INT4 TC ≈ 430 TOPS，是 FP16 TC 的 4x
- 2080 Ti：FP16 TC ~107 TFLOPS / INT8 ~215 TOPS / INT4 ~430 TOPS
- **别从零写**。直接抄 `ExLlamaV2` 的 `q4_matmul` / `q6_matmul` kernel（它明确支持 sm75，就是为这代卡写的，代码干净、可读、C++ 模板化），或 CUTLASS 2.x 的 `sm75` INT4 GEMM 实例。ExLlamaV2 的整个 kernel 目录基本就是你需要的全部素材。

收益预期：prefill 1.5–2x，decode 在 batch≥4 时开始显现，batch=1 上主要靠省带宽（EXL2 4.0bpw vs GGUF Q4_K_M 4.8bpw，能省 15%）。**单用户日常用，这块是锦上添花；上并发或长 prompt 才值钱。**

### 杠杆 3：MoE grouped GEMM

llama.cpp 的 MoE 是每个 token 的每个 expert 单独一次 matvec，Turing 上 tile 完全填不满。你要做的是：

- 一次 token 分发后按 expert 排序 → **single grouped GEMM**（persistent kernel 或 sorted-batch）
- expert 权重常驻，用 shared memory 做 staging
- 这是 **Qwen3-30B-A3B 在 2080 Ti 上唯一能显著超过 llama.cpp 的地方**，我估计 1.3–1.6x decode、2x 左右 prefill

## 四、sm75 的硬件约束（写 kernel 前必须知道）

| 项目 | sm75 状态 | 影响 |
|---|---|---|
| `cp.async` | ❌（sm80+） | 不能异步预取，只能 `ld.global` + 手动双缓冲，**隐藏延迟难度高一个档** |
| TMA / `wgmma` | ❌ | 别想 Hopper 那套 |
| Shared memory | 96KB 统一 / 单 block 最多 **64KB** | tile 尺寸受限，比 Ampere 的 164KB 紧 |
| `ldmatrix` | ✅ | 好消息，warp 级 load 没问题 |
| INT4 MMA | ✅ `m16n8k64.s4` | Turing 的隐藏福利 |
| BF16 | ❌ | 只能 FP16，注意 accumulate 溢出 |
| L2 persistence / access policy window | ❌（sm80+） | 没法给权重常驻做 L2 保护 |
| Triton | ✅ 支持但调优差 | 建议**关键 kernel 手写 CUDA**，别指望 Triton 在 sm75 上打好 |
