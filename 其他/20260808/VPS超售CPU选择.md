## 结论与建议

### ✅ 并行跑 CI 够用吗？

> **对于 500 人以下的研发团队，完全够用，甚至过剩。** 1000+ 人的企业级团队在高峰期会接近瓶颈。

### 🎯 优化建议

| 方面 | 建议 |
|------|------|
| **CPU 是瓶颈** | 3TB 内存远超 CI 需求。如果纯跑 CI，考虑减配内存（1TB 足够），省下的预算可以加第三颗 CPU 或买更高频的型号 |
| **SMT 策略** | 编译密集型 CI 建议关 SMT 或只分配物理核；IO 密集型 CI (npm install、下载依赖) 开 SMT 收益大 |
| **磁盘 I/O** | ⚠️ **这是真正可能卡脖子的地方！** 126 个容器同时编译会产生巨大 I/O。强烈建议配 **NVMe SSD RAID**（如 8× U.2 NVMe），并用 tmpfs / build cache 加速 |
| **网络** | 126 个容器同时拉镜像/依赖，需要 ≥10Gbps 网卡 + 本地镜像仓库 (Harbor/Nexus) 做缓存代理 |
| **混合利用** | RAM 有 2.5TB 剩余，可以同时跑：Redis 构建缓存、ccache/sccache 服务、本地 pypi/npm mirror，进一步加速 CI |
| **调度器** | 用 Kubernetes + GitLab Runner / GitHub Actions Runner Controller 做 autoscaling，比裸 Docker 更高效管理 126+ 容器 |

### 💰 一句话总结

> **256 核 + 3TB 内存 = 126 个标准 CI 容器，覆盖 500 人团队绰绰有余。CPU 是瓶颈而非内存，磁盘 I/O 才是真正需要关注的隐藏瓶颈。**

# 2× EPYC 9755 + 3TB DDR5 — VPS 超售开 VM 容量评估

## 硬件基线

| 资源 | 总量 | 扣除宿主开销 | 可售资源 |
|------|------|-------------|---------|
| CPU (SMT 线程) | 512 线程 | -8 线程 (宿主/QEMU/KVM) | **504 线程** |
| 内存 | 3072 GB | -32 GB (宿主/hugepage) | **3040 GB** |
| 可用内存 (KSM 后) | — | KSM 合并率 ~20-30% | **~3800-4000 GB 等效** |

> KSM (Kernel Samepage Merging) 对同模板创建的 VM 尤为有效——大量页面内容相同（内核、glibc、基础库），实测合并率 20-35%。

---

## 核心公式

$$VM_{数量} = \min\left(\frac{线程数 \times CPU超售比}{每VM\,vCPU},\; \frac{可用内存}{每VM\,内存}\right)$$

**CPU 几乎总是瓶颈**（除非内存配额极小 + KSM 高效）。

## ⚠️ 真正的瓶颈不在 CPU 和内存

| 隐藏瓶颈 | 影响 | 解决方案 |
|----------|------|---------|
| **🔥 磁盘 I/O** | 500+ VM 同时读写，即使 NVMe 也会出现严重排队 | 8× NVMe SSD RAID-10 + IO throttle (`blkio` cgroup) + zram/zswap |
| **🔥 网络带宽** | 500+ VM 争抢带宽，DDoS 防护压力 | 双 25G/100G 网卡 + OVS + per-VM 流量限速 (`tc`/`ifb`) |
| **🔥 内核调度** | 500+ vCPU 的调度开销显著 | CPU pinning + NUMA 绑定 + `schedstats` 监控 |
| **🔥 内存带宽** | 256 核同时访问内存，带宽争抢 | 12 通道 DDR5-6400 = ~460 GB/s 峰值，500 VM 时每 VM 不到 1 GB/s |
| **🔥 存储容量** | 500+ VM 系统盘 | Thin provisioning + qcow2 + 去重；或 ZFS zvol + compression |
| **🔥 突发负载** | 所有 VM 同时编译/跑分 → 雪崩 | CPU quota cgroup 限制 + 突发信用桶 (burst credits) |

## 分场景冠军

### 🏆 场景一：均衡型 (高性能 + 高密度)
**冠军：EPYC 9005 Zen 5 (如 9755)**

```
优势：
  • 128 核 Zen 5，每核 IPC 领先
  • 12 通道内存带宽 = 容器/VM 争抢最小
  • 单核性能强 → 容器内编译/计算快
  • SEV-SNP 加密虚拟化 → 多租户隔离

劣势：
  • 核心数不及 Sierra Forest (288) 或 Zen 5c (192)
  • 单路价格较高
```

> **适合：** 中高端 VPS 提供商、企业私有云、CI/CD 平台（你的场景）

---

### 🏆 场景二：纯密度极限 (最大 VM 数量)
**冠军：Intel Xeon 6 Sierra Forest (288 E-core)**

```
优势：
  • 288 核 → 同等超售比下 VM 数量最多
  • E-core 面积小 → 性价比高
  • 12 通道内存带宽与 AMD 持平

劣势：
  • E-core 单核 IPC 低 ~30-40%（相比 Zen 5）
  • 无超线程 → 288 核就是 288 线程
  • P/E 混合调度复杂（虽然 SF 是纯 E-core，避免此问题）
  • 首代产品生态待验证
```

> **适合：** 极致低价 VPS、微服务密度优先的场景、Web hosting

---

## 潜在挑战与不足

| 不足 | 详细说明 | 缓解方案 |
|------|---------|---------|
| **Zen 5 标准版只有 128 核** | 纯密度不如 Sierra Forest 288 核 | 选择 Zen 5c 变体 (192 核) |
| **Zen 5c L3 缓存更小** | 每核 L3 仅 ~1-2 MB，cache miss 增多 | 对 I/O 密集型容器影响小；计算密集型需评估 |
| **首代 DDR5-6400 平台** | 内存条价格高于 DDR5-4800/5600 | 可降速运行 DDR5-5600 节省成本 |
| **Sierra Forest 威胁** | 288 核对密度场景冲击大 | AMD 可能在 2025 推出更高核数 Zen 5c 产品应对 |
| **Intel TDX 竞争** | TDX 功能与 SEV-SNP 类似 | 两者功能对等，看生态选择 |
