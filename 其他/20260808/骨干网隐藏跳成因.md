# 骨干网隐藏跳成因

### 🧑‍💻 User

针对运营商骨干网，什么情况下会遇到traceroute看不到隐藏跳的情况？

---

### 🤖 Assistant

在运营商骨干网中，`traceroute` 是网络排障的常用工具，其基本原理是利用 IP 数据包头部中的 `TTL`（Time-To-Live）字段，每次递增 $TTL = 1, 2, 3...$ 发送探测包，并通过接收中间路由器返回的 `ICMP Time Exceeded` 消息来逐跳描绘网络路径。

然而，在实际的运营商骨干网环境中，经常会遇到 `traceroute` 无法显示某些“隐藏跳”的情况。这通常是由以下几个维度的原因造成的：

### 1. MPLS 网络中的 TTL 处理机制
运营商骨干网广泛使用 MPLS（多协议标签交换）技术。MPLS 头部中也有一个独立的 `TTL` 字段，其与底层 IP `TTL` 的交互方式直接决定了 `traceroute` 的表现。

<details>
<summary><b>🔧 核心机制：TTL 传播</b></summary>

- **默认情况（TTL 传播开启）**：当 IP 包进入 MPLS 网络时，入口路由器（PE）会将 IP 包的 `TTL` 值减 1 后复制到 MPLS 头部的 `TTL` 字段中。此时，`traceroute` 能正常显示骨干网内部的 P 路由器。
- **隐藏情况（TTL 传播关闭）**：为了隐藏骨干网内部拓扑结构，或者防止因 TTL 过期引发潜在的攻击，运营商常在 PE 路由器上配置 `no mpls ip propagate-ttl`（Cisco/华为等设备的常见命令）。
  - **效果**：进入 MPLS 网络时，MPLS `TTL` 被固定为 255，而不再继承 IP `TTL`。当数据包在骨干网内部传输时，只有 MPLS `TTL` 在递减，而 IP `TTL` 保持不变。
  - **结果**：骨干网内部的 P 路由器不会因为 IP `TTL` 耗尽而返回 `ICMP Time Exceeded`。对端 PE 路由器弹出标签后，继续处理 IP 包。此时 `traceroute` 会直接从源端跳到远端 PE 路由器，中间的所有核心 P 路由器全部被“隐藏”。
</details>

### 2. ICMP 限速与控制平面策略
骨干网核心路由器每秒要处理海量的数据包。如果对每一个 `TTL=0` 的包都立即生成并发送 `ICMP Time Exceeded` 消息，会极大地消耗路由器的控制平面 CPU 资源。

<details>
<summary><b>⚙️ 控制平面保护机制</b></summary>

- **ICMP 限速**：路由器通常配置了 ICMP 生成速率限制（例如 Cisco 的 `ip icmp rate-limit unreachable`）。当探测包到达速率超过阈值时，路由器会直接丢弃部分 `TTL=0` 的包，而不生成 ICMP 消息。这会导致 `traceroute` 在该跳显示为 `* * *`，看起来像是网络断了或跳数隐藏了。
- **CoPP（控制平面策略）**：运营商会在路由器上严格配置 CoPP，过滤或限制发往路由器自身 CPU 的流量。如果 `traceroute` 探测包的源端口、目的端口或协议类型碰巧命中了 CoPP 的丢弃策略，中间路由器将不会响应。
</details>

### 3. 网络架构与物理层设备（真正的透明跳）
`traceroute` 是一个三层（网络层）工具，它无法感知不参与 IP 路由的设备。

<details>
<summary><b>🌐 透明设备与二层网络</b></summary>

- **光传输设备（DWDM/OTN/SDH）**：运营商骨干网长距离传输依赖光放器（EDFA）、分光器、OTN 电交叉设备等。这些设备工作在物理层（L1），完全不感知 IP/MPLS 头部，自然不会处理 `TTL`，它们在 `traceroute` 中是完全隐形的。
- **二层交换机 / CE 设备**：如果在两台核心路由器之间串联了 L2 交换机，由于交换机基于 MAC 地址转发，不会递减 IP `TTL`，因此也不会出现在 `traceroute` 结果中。
</details>

### 4. ECMP（等价多路径）负载均衡
骨干网为了冗余和高带宽，广泛使用 ECMP。`traceroute` 发送多个探测包（通常每跳发 3 个），由于探测包的源端口或目的端口可能会变化，导致哈希结果不同。

<details>
<summary><b>🔀 路径不一致导致的跳数丢失</b></summary>

- **现象**：假设从 R1 到 R4 有两条路径：`R1 -> R2 -> R4` 和 `R1 -> R3 -> R4`。
- **问题**：如果第一个包（$TTL=1$）走 R2，第二个包（$TTL=2$）走 R3，第三个包（$TTL=3$）走 R2。那么 `traceroute` 的输出可能会将 R2 和 R3 混合显示在同一跳中，或者在某些极端哈希情况下，某一跳的 ICMP 响应全部丢失，导致路径显示不连续，形成“隐藏跳”的错觉。
- **解决思路**：在某些实现中，可以使用固定源/目的端口的 `traceroute`（如 Linux 的 `traceroute -T -p 80` 或 TCP traceroute）来尽量保证路径一致。
</details>

### 5. 安全策略与 ICMP 过滤
出于安全考虑，运营商经常在边缘或骨干网接入点部署 ACL 或防火墙策略。

<details>
<summary><b>🛡️ 安全过滤策略</b></summary>

- **丢弃 ICMP Time Exceeded**：某些运营商会在核心路由器的入接口配置 ACL，直接丢弃所有 `ICMP Time Exceeded` 消息。这样即使路由器生成了该消息，也会在离开接口前被丢弃，导致该跳及后续跳数无法显示（除非后续跳数绕过了该过滤点，但这在骨干网中较少见）。
- **不响应 ICMP Echo**：如果中间节点配置了不响应 `ICMP Echo Request`，使用基于 ICMP 的 `tracert`（如 Windows 默认工具）可能会失败，但基于 UDP 的 `traceroute`（Linux/Mac 默认）可能仍然有效。
</details>

### 6. 隧道封装与 TTL 复制
骨干网中常使用 GRE、IPsec 等隧道技术。

<details>
<summary><b>🚇 隧道封装机制</b></summary>

- 当数据包进入 GRE 隧道时，会被添加一个新的外部 IP 头部。大多数现代路由器默认会将内部 IP 包的 `TTL` 复制到外部 IP 头部。
- 如果隧道内的中间路由器因为外部 `TTL` 耗尽而返回 `ICMP Time Exceeded`，该 ICMP 消息会沿着外部网络返回。但在某些复杂的隧道嵌套场景（如 MPLS over GRE over IPsec）中，由于 TTL 的复制规则或 ICMP 消息被隧道封装，可能导致 `traceroute` 无法正确解析路径中的某一跳。
</details>

### 总结
在运营商骨干网中遇到 `traceroute` 看不到隐藏跳，最常见且最可能的原因是 **MPLS 网络关闭了 TTL 传播 (`no mpls ip propagate-ttl`)** 以及 **路由器的 ICMP 限速策略**。在进行骨干网排障时，如果怀疑有隐藏跳，可以尝试结合 MPLS OAM 工具（如 `ping mpls`）、光层网管系统或联系对端运营商核查跨域路由策略来获取完整的路径信息。

### 🧑‍💻 User

所以很可能是因为中间路由器配置了不响应ICMP或者MPLS标签交换，traceroute看不到这些隐藏的跳吗？

---

### 🤖 Assistant

是的，您的总结非常准确。在运营商骨干网中，遇到 `traceroute` 看不到中间跳数（即所谓的“隐藏跳”），**绝大多数情况都是这两个原因导致的**。

为了让您在实际排障时更有底气，我们可以把这两个原因再稍微细化一下：

### 1. MPLS 标签交换（确切地说是关闭了 TTL 传播）
MPLS 本身并不一定会隐藏跳数，关键在于运营商是否开启了 **TTL 传播**。

- **如果开启了 TTL 传播**：IP 包进入 MPLS 网络时，IP 头部的 $TTL$ 会减 1 并复制到 MPLS 头部。此时，骨干网内部的 P 路由器依然会因为 $TTL$ 耗尽而返回 ICMP，`traceroute` 是能看到这些核心路由器的。
- **如果关闭了 TTL 传播（最常见）**：运营商为了隐藏内部拓扑，或者防止核心路由器处理大量 ICMP 报文，会在入口 PE 路由器上配置 `no mpls ip propagate-ttl`。此时，MPLS 头部的 $TTL$ 被硬编码为 255，而 IP 头部的 $TTL$ 在骨干网内部**冻结不变**。结果就是，中间的 P 路由器根本不知道 IP 包的 $TTL$ 已经耗尽，`traceroute` 就会直接从源端 PE“瞬移”到目的端 PE，中间的所有 P 路由器全部隐形。

### 2. 中间路由器不响应 ICMP（控制平面保护与安全策略）
骨干网核心路由器每秒转发数十亿个数据包，如果对每个 $TTL=0$ 的包都回复 ICMP，CPU 会被瞬间打爆。因此，运营商会在中间路由器上采取“不响应”或“限制响应”的策略：

- **ICMP 限速**：路由器限制了生成 `ICMP Time Exceeded` 消息的速率（例如每秒只生成 10 个）。如果探测包到达速率超过阈值，路由器会直接静默丢弃，`traceroute` 就会显示为 `* * *`。
- **CoPP（控制平面策略）拦截**：路由器会将发往自身 CPU 的数据包（如 $TTL=1$ 的探测包）交由 CoPP 策略处理。如果策略明确丢弃了这类 ICMP 请求，路由器就不会生成任何回复。
- **ACL 过滤**：在核心路由器的入接口或出接口配置了访问控制列表，直接丢弃 `ICMP Time Exceeded` 报文，导致探测端收不到回包。

---

<details>
<summary><b>💡 附加说明：如何区分是哪种原因导致的隐藏跳？</b></summary>

如果您在排障时想知道到底是 MPLS 还是 ICMP 过滤导致了“隐藏跳”，可以通过以下现象判断：

1. **看跳数变化**：
   - 如果 `traceroute` 结果中，上一跳是 $TTL=3$，下一跳直接变成了 $TTL=4$（即只增加了 1，但跨越了很长的物理距离），这通常是 **ICMP 限速或过滤** 导致某一跳没回包，但包确实经过了它。
   - 如果 `traceroute` 结果中，上一跳是 $TTL=3$（比如骨干网入口 PE），下一跳直接变成了 $TTL=4$（比如骨干网出口 PE），但根据物理距离判断中间至少经过了 5 台 P 路由器，那这绝对是 **MPLS 关闭了 TTL 传播** 导致的。

2. **看延迟（Latency）**：
   - 在 MPLS 隐藏跳的场景中，虽然中间跳数不显示，但出口 PE 的延迟会包含中间所有 P 路由器的转发延迟。如果两台 PE 之间延迟高达 30ms，但 `traceroute` 显示它们是相邻的（跳数只差 1），就可以断定中间有 MPLS 隐藏跳。

</details>

总结来说，**MPLS 关闭 TTL 传播** 是运营商刻意为之的拓扑隐藏机制，属于“设计上的隐藏”；而 **不响应 ICMP** 更多是出于设备自我保护或安全策略，属于“工程上的隐藏”。两者在骨干网中都非常普遍。

### 🧑‍💻 User

如果是中间的MPLS LSR不回包到底是traceroute会直接跳过它们还是显示多个*？
换个说法，MPLS网络里标签交换的路由器默认不对TTL过期回ICMP，所以traceroute会跳过它们吗？

---

### 🤖 Assistant

这是一个非常核心且经典的问题！直接回答您的两个问题：

1. 如果是因为 MPLS 相关机制导致的隐藏，`traceroute` 会**直接跳过它们，不会显示多个 `*`**。
2. 您的换种说法稍微有一点偏差：**MPLS LSR（核心 P 路由器）默认是会对 TTL 过期回 ICMP 的**。导致它们被跳过的真正原因，不是它们“拒不回复”，而是因为它们**“根本没收到 TTL 过期的包”**。

这里面的核心机制在于 **TTL 冻结**。我们通过详细拆解数据包在 MPLS 网络中的旅程，就能彻底明白为什么是“跳过”而不是“显示 `*`”。

### 为什么会被“直接跳过”？

当运营商在入口 PE 路由器上配置了 `no mpls ip propagate-ttl`（关闭 TTL 传播）时，会发生以下魔法：

1. **进入骨干网（入口 PE）**：
   假设您的 `traceroute` 探测包到达入口 PE 路由器时，IP 头部的 $TTL = 2$。
   正常情况下，PE 会将其减 1 变为 $TTL = 1$ 并压入 MPLS 标签。但关闭了 TTL 传播后，PE 会**强行将 MPLS 头部的 TTL 设置为 255**，而底层 IP 头部的 $TTL$ 被原封不动地“冻结”在 $2$。

2. **穿越骨干网（中间 LSR / P 路由器）**：
   中间的 P 路由器只看 MPLS 头部。它们看到 MPLS $TTL = 255$，于是逐跳减 1（254, 253...）。
   **关键点来了**：因为底层的 IP $TTL$ 被冻结在 $2$，并没有随着经过 P 路由器而递减。所以，中间的 P 路由器**永远不会遇到 IP TTL=0 的情况**，它们自然不需要生成任何 ICMP Time Exceeded 消息。数据包只是被静默地标签交换转发。

3. **离开骨干网（出口 PE）**：
   数据包到达出口 PE。PE 弹出 MPLS 标签，此时它才发现里面藏着一个 IP 包，且 IP $TTL = 2$。
   出口 PE 像普通路由器一样，将 IP $TTL$ 减 1，变成 $TTL = 1$，然后转发给目的端。
   如果目的端发现 $TTL=1$ 但自己不是最终目的地，它会丢弃该包并返回 `ICMP Time Exceeded`。

**结论**：在 `traceroute` 的视角里，它发出了 $TTL=2$ 的包，直接收到了出口 PE（或目的端）的回复。中间的所有 P 路由器因为 $TTL$ 被冻结，完全没有参与 $TTL$ 递减的游戏，所以 `traceroute` **直接从入口 PE 跳到了出口 PE**，中间不产生任何 `*`，也不产生任何跳数。

---

### 什么时候才会显示多个 `*`？

`*` 在 `traceroute` 中代表**超时无响应**。也就是说，某台路由器**确实收到了 $TTL=1$ 的包，本该回复 ICMP，但它没回**。

在以下情况中，跳数**不会**被跳过，而是会显示 `*`：

1. **开启了 TTL 传播，但开启了 ICMP 限速/过滤**：
   如果运营商没有关闭 TTL 传播，那么 IP $TTL$ 会正常递减。当探测包到达某台核心 P 路由器时，$TTL$ 变成 0。这台 P 路由器**本该**回复 ICMP，但因为它配置了 CoPP（控制平面策略）或 ICMP 限速，它把生成 ICMP 的任务丢弃了。
   此时，`traceroute` 会等待超时，然后在这一跳打印 `* * *`。但后续的包 $TTL$ 更大，能越过这台路由器继续往后走，所以后面的跳数依然能显示出来。

2. **ICMP 回包被 ACL 拦截**：
   中间路由器收到了 $TTL=0$ 的包，老老实实生成了 `ICMP Time Exceeded` 消息往回发。但在回程的路上，这个 ICMP 包被某台防火墙或路由器的 ACL 丢弃了。探测端收不到回包，也会显示 `* * *`。

### 总结对比

为了方便记忆，您可以参考下表：

| 场景 | 中间路由器是否处理 TTL | 现象 | traceroute 表现 |
| :--- | :--- | :--- | :--- |
| **关闭 MPLS TTL 传播** | 否（IP TTL 被冻结，P 路由器只看 MPLS TTL） | $TTL$ 未耗尽，路由器无需回复 | **直接跳过**，无 `*`，跳数不增加 |
| **开启 TTL 传播 + ICMP 限速** | 是（IP TTL 正常递减并耗尽） | $TTL$ 耗尽，但路由器限速不生成 ICMP | **显示 `* * *`**，跳数正常占位 |
| **开启 TTL 传播 + ACL 过滤** | 是（IP TTL 正常递减并耗尽） | $TTL$ 耗尽且生成了 ICMP，但回包被丢 | **显示 `* * *`**，跳数正常占位 |

所以，如果您在 `traceroute` 中看到某两跳之间延迟突然增加几十毫秒（说明跨越了长距离骨干网），但跳数只增加了 1，且没有任何 `*`，那绝对是因为骨干网部署了 **MPLS 关闭 TTL 传播**，把中间节点完美地“隐身”了。
