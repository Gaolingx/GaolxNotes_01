# 软件开发模式概览

### 🧑‍💻 User

除了敏捷开发还有什么开发模式？

---

### 🤖 Assistant

除了敏捷开发（Agile），软件工程领域还有许多其他开发模式（生命周期模型）。它们通常可以分为**传统预测型**（计划驱动、线性/阶段性明确）和**其他适应型/混合型**两大类。下面列举一些常见模式及其核心特点。

---

### 📋 传统预测型开发模式

这类模式强调详尽的早期计划、严格的阶段划分与文档驱动，变更成本较高。

| 模式 | 核心思路 | 适用场景 |
|------|----------|----------|
| **瀑布模型 (Waterfall)** | 按需求→设计→编码→测试→维护的顺序线性推进，前一阶段完全完成后才进入下一阶段。 | 需求稳定、明确、变动极少的大型项目（如航天、政府合同）。 |
| **V模型 (V-Model)** | 瀑布模型的变体，强调测试与开发阶段一一对应（左侧分解需求，右侧集成测试），将验证与确认贯穿全程。 | 对质量和可追溯性要求极高、需求固定的系统（如汽车电子、医疗设备）。 |
| **增量模型 (Incremental)** | 将系统拆分成多个独立的功能增量，每个增量按瀑布方式开发，逐步交付可用的软件。 | 核心需求清晰、需要尽早获得部分功能的项目。 |
| **螺旋模型 (Spiral)** | 反复进行风险分析、原型构建、开发和评审的循环，每个螺旋周期都包含目标设定、风险分析、开发与测试、计划下一轮。 | 高风险、大型复杂系统，需求可能随风险分析逐步清晰。 |
| **原型法 (Prototyping)** | 快速构建一个可运行的原型（界面或功能简化版），通过用户反馈澄清需求，之后再正式开发或丢弃原型。 | 需求模糊、人机交互复杂的项目，常用于演示和确认。 |
| **快速应用开发 (RAD)** | 强调极短的开发周期（30-90天），通过组件复用、用户深度参与和紧密协作快速构建系统。 | 需求可模块化、时间紧迫的中小型系统。 |

---

### ⚙️ 其他现代/衍生模式（常与敏捷并存，但理念独立）

这些模式有的吸收了敏捷思想，有的更偏重流程优化，经常被单独提及。

| 模式 | 核心思路 | 与敏捷的关系 |
|------|----------|--------------|
| **精益软件开发 (Lean)** | 源自丰田生产系统，聚焦消除浪费、增强学习、延迟决策、快速交付、赋能团队、整体优化。 | 敏捷的理念基础之一，但可独立应用于非敏捷环境。 |
| **看板方法 (Kanban)** | 可视化工作流、限制在制品（WIP）、度量交付周期，追求渐进式改进，不强求固定迭代。 | 通常归入敏捷范畴，但也可看作独立的精益方法，比 Scrum 更少“仪式感”。 |
| **DevOps** | 打破开发与运维的墙，通过持续集成、持续交付、自动化流水线和文化变革实现快速且可靠的发布。 | 可与敏捷协同使用，但它自身是一种**工程文化与技术实践体系**，而非开发框架。 |
| **持续交付 (CD)** | 通过自动化流水线保持软件始终处于可部署状态，任何通过测试的变更都可随时一键上线。 | DevOps 的核心实践之一，同样可以配合多种开发模型。 |
| **大爆炸模型 (Big Bang) （极端情况）** | 几乎没有正式流程，所有资源集中投入编码，最后测试，成功与否随机性大。 | 无模式可言，仅用于小型实验或课程项目。 |

---

### 🔍 敏捷家族中其他具体方法（可看作“敏捷开发”的替代实现方式）

如果把“敏捷开发”宽泛理解为一类原则，那么以下具体流派也可以作为不同选择：

- **Scrum**：最流行的敏捷框架，固定时间盒（Sprint），角色明确（PO、SM）。
- **极限编程 (XP)**：强调工程实践（TDD、结对编程、持续集成、重构）。
- **特征驱动开发 (FDD)**：按功能列表规划，短期迭代设计、构建。
- **动态系统开发方法 (DSDM)**：功能固定但时间/资源可调，注重业务需求优先级。
- **水晶方法 (Crystal)**：根据项目规模与关键性定制方法，强调沟通与频繁交付。

---

### ✅ 如何选择？

- 需求不确定、期望快速响应变化 → **敏捷/Scrum/XP**
- 需求完全固定、质量认证严格 → **瀑布 / V模型**
- 高风险、技术不确定性大 → **螺旋模型 / 原型法**
- 想渐进改进现有流程，不颠覆现有角色 → **看板**
- 追求端到端自动化与运维整合 → **DevOps + 持续交付**

这些模式并非完全互斥，实践中经常融合多种思想（例如 “敏捷 + DevOps + 看板” 的混合模式）。
